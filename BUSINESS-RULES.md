is a summary.

## Rule 12 — `Asset.lastSeen` means verified network presence

written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts` (no-regress: it only advances, and stamps `Asset.lastSeenSource` provenance alongside). Valid evidence: live DHCP lease (`seenLeased`), FortiGate device-inventory sighting (the FortiGate's own per-client `last_seen` timestamp — never discovery-run time), connected FortiSwitch/FortiAP, firewall answering discovery, agent heartbeat, answering monitor probe, presence-verification ping, operator-resolved conflict. **Polling is authoritative for monitored assets**: when `Asset.monitored === true`, the monitor probe is the sole authority for presence — `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter` — a powered-on VM / connected ESXi host reported at scrape time — and `arc`) so they can't advance `lastSeen` past what polling established. A successful probe stamps `lastSeen = now, lastSeenSource = "probe"` (written through the `probePatchBuffer` bulk-update in `recordProbeResult`, not a Prisma write); a failed probe writes nothing, so a monitored-but-down device's `lastSeen` freezes at its last successful poll even if a FortiGate still reports it `is_online` in device inventory. Active/operator sources (`probe`, `agent`, `ping`, `conflict-*`) are never deferred. (Repointing a managed FortiSwitch/FortiAP's response-time stream to poll "via parent FortiGate" / the controller rather than direct SNMP is the fix when the device is genuinely up but unpollable directly.) **Device inventory outranks the DHCP lease** (unmonitored assets): when a MAC appears in this cycle's device inventory, the lease path skips its bump so the inventory's real `last_seen`/`is_online` wins — a bound-but-idle lease (device leased an IP then went home) must not stamp `now`. Lease-only assets keep the lease bump. **Fortinet-discovery-owned infra never takes client-sighting presence**: firewall/switch/access_point assets carrying a `fortinetTopology` stamp skip BOTH the dhcp-lease and device-inventory bumps — their presence comes only from their own discovery loop (gated on answered-live / connected / `!offline`) and the probe, so an offline-in-FMG gate sighted as a DHCP client of another gate (lingering lease binding, stale cached `is_online`) can't keep freshening its lastSeen; the fortigate-firewall AssetSource row's lastSeen likewise freezes on offline cached-CMDB pulls. Operator-typed non-Fortinet "firewall"/"switch" assets (no topology stamp) keep the endpoint-style bumps. Directory timestamps (Entra `lastSyncDateTime`, AD `lastLogonTimestamp`) deliberately do NOT write it — they stay on the `AssetSource` rows and surface as "Last Directory Activity" in the slide-over; the Entra duplicate-registration tiebreaker compares those directory timestamps, not `lastSeen`. (vCenter and Azure Arc are the exceptions among discovery integrations: vCenter's `power_state`/`connection_state` and Arc's `properties.status === "Connected"` are real-time truth READ AT SCRAPE TIME — categorically different from the stored historical timestamps directory sources carry — so unmonitored VMs/hosts/Arc machines DO get a `"vcenter"` / `"arc"`-sourced bump; both are in the deferred set, so polling stays authoritative once monitoring is on. For Arc the evidence timestamp is always RUN TIME, never `properties.lastStatusChange`, which records when the status last CHANGED and so is 90 days stale on a machine that has been Connected for 90 days.) Presence evidence also gates status resurrection: a remembered-but-offline inventory/switch/AP entry must not flip a `decommissioned` asset back to `active`. `decommissionStaleAssets` consults directory/agent `AssetSource.lastSeen` as a veto so cloud-only laptops don't age out. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path).

## Rule 13 — SD-WAN monitoring is opt-in, read-only, FortiOS-only

Gated per-integration by `Integration.config.pullSdwan` (default false), on both the FortiManager and standalone FortiGate integrations. When on, the heavy/system-info pass for FortiGate firewalls also calls `collectSdwanFortinet` (`/api/v2/monitor/virtual-wan/health-check` + `/api/v2/cmdb/system/sdwan`). It writes the `AssetPerfSlaSample` **SLA-metrics time-series** (latency/jitter/loss per WAN member — append-only, rolled up + retained), and refreshes the `AssetSdwanRule` **current-state** table (one row per rule, delete-replaced per scrape via `persistSdwanRules` — no history/timeline). Never writes to the device. The asset modal's **SD-WAN** tab appears only for FortiGate firewalls with data. The runtime "selected route" per rule is **inferred** (first candidate member up in priority order) when FortiOS doesn't expose it over REST — clearly labeled in the UI; verify the exact endpoint/field shapes on a real FortiOS 7.x device. Rules configured for zone-based selection (`priority-zone`) carry no interface members — `parseSdwanRules` resolves their candidates from the preferred zones' member interfaces and records the zones in `priorityZones`, so the UI lists each zone's members (grouped) instead of an empty cell.

## Rule 14 — Description sync is opt-in and Polaris-primary

Gated per-integration by `Integration.config.syncDescriptions` (default false), on both the FortiManager and standalone FortiGate integrations (Description Sync tab). **A non-empty Polaris value always wins**: pushed to the device on save and re-asserted by every reconcile, so device-side edits are overwritten (audited with the value they replaced — `asset.description.pushed` `overwroteDeviceValue` detail). **An empty Polaris field adopts** the device value (`asset.description.adopted` / `asset.interface.description.adopted` Events) — clearing the Polaris description is how an operator takes the device's value. No conflict state exists (the earlier newest-edit-wins three-way merge was retired 2026-07; legacy `conflict` sync-state rows resolve on the next reconcile by pushing the Polaris value). `Asset.descriptionSync.value` / `AssetInterfaceOverride.syncedValue` persist the last synced value (bookkeeping for the FMG-mirror device-agrees check + the UI badge, not a merge base). A device-side *clear* never removes a Polaris value (the push re-asserts it). `decideDescriptionSync(polaris, device)` is the pure decision. Surfaces: interface comments (`AssetInterfaceOverride`) ↔ FortiGate `system/interface` description / FortiSwitch port description; `Asset.description` ↔ FortiGate `system/global` alias / FortiSwitch managed-switch description / FortiAP wtp **`location`** (AP Manager's field — wtp `comment` doesn't exist in FMG's copy, so installs strip it; confirmed on a live FMG 7.x). All device I/O rides `reservationPushService`'s Transport (works in FMG proxy AND bypass/direct modes + standalone). Runs at save time (always pushes, best-effort, never blocks the Polaris write) plus a Phase 13.7 discovery reconcile that re-pushes drift / adopts into empty fields and is the retry path — no queue. Clearing a Polaris value is local-only (no device-side delete). Push verifies by read-back; transport errors never mutate sync state. FortiOS field shapes (alias cap, ports child-table PUT) are flagged verify-on-real-device in `descriptionSyncService.ts`; the wtp `location` cap is confirmed at 35 chars. **FMG central management:** each FMG discovery start detects whether the ADOM centrally manages FortiAPs / FortiSwitches (`detectCentralManagement` → stamped on `Integration.config.centralManagement`, rendered on the integration card after the FMG Proxy row); for a centrally-managed class, device-side description pushes are additionally **mirrored into FMG's database** — wtp `location` into the controller FortiGate's device DB (`/pm/config/device/<fgt>/vdom/root/wireless-controller/wtp`, where AP Manager's per-AP rows live), switch descriptions into the ADOM-level `obj/fsp/managed-switch` table — via plain JSON-RPC `update` (never `set`, never an install) so the next install doesn't revert them, and the reconcile batch-heals FMG-side drift for values the device already agrees on. See TOUCHES.md → services/descriptionSyncService.ts.

## Rule 15 — Location codes ride device descriptions; notes are operator-only

FortiSwitch/FortiAP admin descriptions (managed-switch CMDB `description` / wtp `location` with `comment` fallback — `location` is the sync surface and the only field present in FMG's copy under central AP management) are captured on every FMG + standalone FortiGate discovery cycle into `fortinetTopology.deviceDescription` (`buildDeviceDescriptionStamp` in `discoveryEngine.ts`), and `a:`(area)/`b:`(building)/`f:`(floor)/`r:`(room)/`jb:`(junction box) codes are parsed from them server-side by `src/utils/locationCodes.ts` (effective codes: the `Asset.description`'s codes when it carries any — EXCLUSIVELY, no per-key fall-through, so removing a code from the description removes the node from that group even while the device copy lags a sync cycle — else the device description's; `Asset.notes` is deliberately NOT a source, notes never inform the topology map) to drive Device Map grouping hulls, row clustering, and floor views. **Discovery never writes `Asset.notes` on an existing asset** (the former description→notes mirror and its `notesSyncedFrom` provenance were removed 2026-07); the only discovery-authored notes content is the one-time `Auto-discovered from FortiGate …` boilerplate stamped at asset creation. Interplay with rule 14: with `syncDescriptions` ON, codes maintained in the Polaris description push to the device (Polaris-primary); device-only codes show through only while the Polaris description carries no codes at all.

## Rule 16 — Maintenance windows pause everything; status flips are scheduler-managed

While a `MaintenanceSchedule` window is active for a monitored asset, the `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` (restored when the last window closes; a manually-set "maintenance" is parked verbatim so exit can't loop). `status="maintenance"` stops ALL server-driven polling (`MONITOR_CANDIDATE_WHERE` in `monitoringService` — shared by both the cursor pass and the pg-boss publisher — excludes it; presence-verification pings and `decommissionStaleAssets` skip it too; agent pushes and the operator's explicit Poll Now still work), makes the asset count as DOWN for child dependency suppression (`evaluateSuppression` treats it like an active `dependencyTestUntil` overlay — unless the schedule's `suppressChildren` toggle is off, in which case suppression ignores the maintenance status and the asset evaluates by its frozen `monitorStatus`, so dependents keep monitoring/alerting; OR-ed across an asset's open windows, surfaced as the "Mark dependent devices as down" checkbox on the builder + both ad-hoc paths), and silences notifications for the asset AND for every dependency-suppressed asset (`isSuppressedForNotifications` in `notificationEngine`: readings dropped, `pending` state rows reset so a still-bad condition re-earns its debounce post-window, `firing` rows frozen so exit can't double-fire; escalation sends pause). **Discovery/system writers must never write status over a maintenance asset** (Entra/AD sync, FortiSwitch state sync, lease-presence flip, and the `lastSeen`-aging `decommissionStaleAssets` job are guarded; the reconcile self-heals anything missed by re-flipping and absorbing the clobbered value into `maintenanceReturnStatus`). **Deletion-at-source is the one carve-out:** the discovery decommission sweeps (Phase 2a firewalls + its controller cascade onto their managed FortiSwitches/FortiAPs / Phase 2b FortiSwitches+FortiAPs) DO judge maintenance assets and call `releaseAssetsForDecommission` — window closed `endReason="decommissioned"`, parked status cleared, `status="decommissioned"` written in the same transaction (so the reconcile can't re-enter or self-heal-reflip; the `monitored=false` clamp keeps it out of the target set, and the spent ad-hoc schedule self-deletes). Roster/inventory absence is config truth, not reachability (an offline device stays in the FMG roster; a powered-off switch/AP stays CMDB-protected), so a device deleted mid-window must not sit in maintenance and then be restored to `"active"`. An operator status write moving OFF "maintenance" wins: the assets PUT route calls `operatorReleaseAsset` first (windows closed `endReason="operator"`, which suppresses scheduler re-entry for that occurrence). Open `AssetMaintenanceWindow` rows are the restart-safe source of truth; closed rows feed the labeled chart bands. Dashboard surfaces treat maintenance as its own state, never an outage: the NOC feeds (`nocDashboardService`, mirrored by `/summary` monitorAlerts) exclude `status="maintenance"` from every down/warning/stale list — the frozen `monitorStatus` is not live state — and bucket it as `statusCounts.maintenance`; the Status Map dot and Status Summary "Maint" tile paint it purple (matching the assets-page pill). Events: `maintenance.entered` / `maintenance.exited` / `maintenance_schedule.*`.

## Rule 17 — ARP presence evidence for stale reservations; the sweep is opt-in

Every FMG/standalone-FortiGate discovery cycle already reads each gate's ARP table; sync Phase 7.6 stamps `Reservation.lastSeenArp` (and clears `staleNotifiedAt`/`staleSnoozedUntil`, same re-arm semantics as a live lease) whenever the table binds an active dhcp_reservation's IP to its **reserved MAC** on the owning device — minutes-fresh L2 presence that keeps statically-configured / ICMP-silent devices (which never pull a lease) out of the stale list. `effectiveLastSignalMs` in `reservationStaleService` folds it in as a third real signal alongside `lastSeenLeased` and the correlated `Asset.lastSeen`. MAC match is required (a different MAC answering the reserved IP is not presence), matching is scoped per (fortigateDevice, ip) so overlapping RFC1918 subnets behind different gates can't cross-match, and absence of an ARP entry is NEVER negative evidence (reach depends on routing + firewall policy). The **ARP presence sweep** (`Integration.config.arpPresenceSweep`, DHCP Push tab, default off, FMG + standalone parity) additionally primes each gate's ARP cache right before its table read: `arpPrimeService` fires one fire-and-forget UDP datagram per reserved IP — per-gate targets only, paced batches, ~2s settle inside the FortiOS neighbor-cache GC window — so even quiet-but-live devices resolve into the table. Opt-in because the sweep is IDS-visible.

## Rule 18 — Automation precedence is same-trigger, most-specific-wins

Two automations "watch the same thing" iff their `triggerSignature` matches (asset_metric metric + dimensionFilter / asset_state field + dimensionFilter; host/event/change/composite are exempt, signature `null`). Among same-signature automations, the more-specific one (higher `scopeRank` on the ladder all assets 0 < device type 1 < OS 2 < manufacturer 3 < model 4 < tag 5 < region 6 < subnet 7 < hostname 8; only positive rules count — negatives/none/notAll broaden; a `region:` tag outranks a plain tag; lifecycle status + assetId are OFF the ladder) **carves out** the assets it covers from every lower-rank one: `evaluateThresholdRule` drops those readings (no fire), clears any active alert (`notification.superseded`, unlike maintenance which freezes), and resets pending debounce. Same-rank + same-signature ties both fire. Index built once per tick (`buildShadowIndex`), per-asset test reuses the pure `scopeMatchesAsset`. Authoring-time preview (`previewRule`) warns both directions: `carveOut.carvesFrom` (this specific draft removes N devices from lower-rank automation X) + `carveOut.carvedOut`/per-match `excludedBy` (this general draft's devices already covered by more-specific Y).

## Rule 19 — Severity bands escalate one alert by value, each on its own clock

A numeric automation (asset_metric/host_metric) can stack `severityBands` on the base trigger: tier 0 = `rule.severity` at `trigger.threshold` for `trigger.forDurationSec`, each band a higher `{threshold, severity, operator?, forDurationSec?, actions, escalation}`. **Severities must strictly increase** tier-over-tier (`validateSeverityBands`; UI defaults a new tier one rank up + blocks lowering); tiers **share the base sampling** (aggregation / window / dimensionFilter) but may carry their own ordered `operator` and their own **sustained duration** (both fall back to the trigger's). The value is resolved once and compared to each tier; the **most-severe MET tier wins**, so per-tier thresholds need not be monotonic. **"Sustained for" is per tier, not per rule** — "loss > 5% for 30 min = warning, > 25% for 5 min = critical" is one automation, so a shared `conditionMetSince` can't express it: the engine keeps `NotificationRuleState.bandMetSince` (`{[severity]: epochMs}`, each tier's continuously-satisfied run, rewritten only when a tier enters or leaves) and takes the most-severe tier whose OWN run has outlasted its OWN duration (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure + unit-tested). Consequences that follow from that and are deliberate: a higher tier can fire before the base tier has served its time (each tier earns its own severity); a value climbing between bands never restarts the lower tier's run; a tier that drops out and returns restarts only ITS clock, so flapping into critical never sustains while a steady warning still fires. **De-escalation is immediate** (the lower tier's run is already old) and dropping below tier 0 clears every run. `severityForValue` remains the instantaneous tier-0 membership test; the alert is **one row per asset** whose severity climbs and eases in place. `bandNotify` policy governs delivery: `onIncrease` (default on) runs the entered band's actions; `onDecrease` (default off) runs the destination band's actions; `onResolved` (default on, below tier 0) runs the reuse-the-alert-or-dedicated resolved actions then clears. In the hysteresis dead band (auto reset + `clearThreshold`, value below tier 0 but above the clear line) the alert stays active but **eases to the base severity** — it must not park at a higher band the value no longer satisfies. Each band's own time-escalation is swept band-aware (`escalationChainsForSeverity` in notificationTypes — the band's level chain + its actions' per-action chains, with the empty-band fallback to the base actions mirrored; timers restart from `escalationState.bandSince`, stamped on every crossing). Value-bands (severity) and time-escalation (delivery tiers) are independent axes and coexist.

## Rule 20 — Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup

Three operability invariants added by the 2026-08 production-readiness remediation. (a) **Subnet overlap** (rules 1 + 2) is a check-then-insert, so it is only as strong as what serializes the two halves. Every subnet-creating path (`createSubnet`, `allocateNextSubnet`, `bulkAllocate`, the DHCP-discovery create in `discoveryEngine`) now goes through `createSubnetRowChecked` or `lockBlockForSubnetWrites` in `subnetService.ts`, which take a per-block `pg_advisory_xact_lock` BEFORE re-reading siblings; a UNIQUE index on `subnets (blockId, cidr)` is the backstop for the exact-duplicate case. `allocateNextSubnet` retries on a lost race rather than 409-ing, because the caller asked for "any free /N". There is deliberately no exclusion constraint for general overlap — stock PostgreSQL has no GiST-indexable `&&` for `inet`/`cidr`. **The same medicine now covers the `mapRegions` blob** (2026-08-25): every region create / update / delete is a read-modify-write of ONE JSON `Setting` value — load the whole array, change one element, write the whole array back — so two overlapping writers both read the same starting array and the second write silently discarded the first one's edit. That was not theoretical: the Device Map's edit mode saved every changed polygon at once with `Promise.all`, so dragging three regions and clicking Save reliably persisted only one while all three PUTs returned 200 and the toolbar reported "3 regions saved". `withRegionBlobLock` in `mapRegionService` takes a `pg_advisory_xact_lock` (classid `0x504c5255` "PLRU", the next in the PLRS/PLRT sequence) as the first statement of a transaction wrapping the read AND the write; the map now also saves sequentially, so N dirty polygons no longer park N requests on that lock each holding a DB connection. One lock for the whole blob, because the unit being rewritten IS the whole blob — a per-region lock would serialize nothing. Proven by `tests/integration/mapRegionConcurrentWrites.test.ts`, which needs a real database: a mocked Prisma makes the advisory lock a no-op and would pass either way. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret-named string leaves of `Credential.config`, `Integration.config`, `NotificationChannel.config` and `Setting.value` (`utils/secretBox.ts` + `utils/configSecretFields.ts`). The extension is the enforcement seam precisely because several legacy route files still read those models with inline Prisma. **Sealing is per-model; OPENING is all-models**, because Prisma query extensions fire for top-level operations only — a per-model open hook never runs for a relation read like `asset.findUnique({ include: { monitorCredential: true } })`, which is how the monitor hot path loads every credential it polls with, how reservation push loads the FortiGate token, and how description sync loads its integration. So the open pass is its own `$extends` layer (`openNestedSecrets` over `$allModels.$allOperations`) that walks whole results, gated by a zero-allocation `containsSecretField` pre-scan and an `isWalkable` plain-object check so rebuilding a row can't turn its `Date` columns into `{}`. Sealing is a NO-OP without `POLARIS_SECRET_KEY`, and `openValue` never throws — a wrong key degrades to "this credential stopped authenticating", never to an exception on every monitor tick. Raw SQL bypasses the extension; the only raw reader of these columns (`monitorOverrideService`'s `integrations.config #>> '{…,addAsMonitored}'`) touches no secret field. (c) **Backup/restore** lives in `services/backupService.ts`: streamed end to end (never `execSync`/`readFileSync`/`gzipSync`), connection via libpq PG* env vars rather than argv, and the restore wrapped in `timescaledb_pre_restore()` / `timescaledb_post_restore()` in three separate psql sessions with post_restore in a `finally`. A failed pre-update backup ABORTS the update by default (`applyUpdate(password, allowWithoutBackup=false)`) — migrations are irreversible, so a silently-missing backup is the difference between a bad update and an unrecoverable one.

## Rule 21 — SSH host-key verification is opt-in and fails closed

Polaris passed no `hostVerifier` to ssh2 until 2026-08, so EVERY SSH connection accepted whatever host key was presented: agent install (which SFTPs a script and runs it as root), agentless process collection, and the SSH monitor probe alike. `SshConfig.verifyHostKey` enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin` — no pin stores and accepts, a match accepts, a CHANGED key **refuses the connection** and stamps a warning `ssh.host_key.mismatch` with both fingerprints. It is **opt-in, default OFF** (default ON only for newly created credentials), mirroring WinRM's `verifyTls`: turning it on globally would break every install whose hosts were never pinned. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites (`withSshClient` + `monitoringService.probeSsh` — the only two) so they can't drift, and it **fails closed** — an internal error refuses the connection rather than silently skipping verification. Pins are per `(host, port)` in their own table, never on `Credential.config`, because one credential spans a fleet of hosts. Deleting a pin (Integrations → Polaris Agent → Windows SSH Deployment) is the documented recovery for a legitimately rebuilt or re-keyed host and is audited at warning level, since it re-opens first-use trust. **TOFU only detects a key CHANGING** — enabling it against a running fleet pins whatever currently answers, so it is strongest on a greenfield rollout where the pin is taken at deploy time.

## Rule 22 — The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered

An asset known to several discovery sources at once has several competing answers to "where is it?" (an AD OU path, a controller FortiGate, an Azure Arc onboarding, an Intune enrollment), and which one an operator wants to read is a site convention Polaris can't decide. The assets table's **Sources** column (formerly "Server"; the `data-sf-key` stays `_server` so saved presets keep working) renders the operator's `location` when set, else `Asset.learnedLocation`. The priority behind that second half lives in the `assetSourcePriority` Setting (`{order[], integrationPrefix}`, drag-to-reorder on Assets → Settings → Sources, `assetSourcePriorityService`), and it feeds the **projection** — not just rendering — because the column's filter, its sort, "behind FortiGate X" tag/maintenance criteria and the Device Map's per-site narrowing all read `learnedLocation`. The catalogue of contributors is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string (AD `ouPath`, FortiSwitch/FortiAP `controllerFortigate`, fortigate-endpoint device name, vCenter `clusterName`/`hostName`), **label** contributors have nothing location-shaped to say and contribute their own NAME (`arc` → "Azure Arc", `arc-k8s`, `intune`, `entra`) so the column names who knows the device instead of sitting blank. **Azure Arc is deliberately label-mode:** its only location-ish field is the Azure resource group — a billing container whose name ("updatemanager") tells an operator nothing — which stays on the observed blob and the Sources tab. Never contribute the Azure region (it says where the RECORD lives). `polaris-agent` / `manual` / `fortigate-firewall` never contribute; the `fortigate-endpoint` rule stays suppressed when ANY Fortinet infra source exists — fortigate-firewall / fortiswitch / fortiap — whatever the order says (invariant, not preference: a managed device's site label is its own identity or its controller, and the pre-adoption DHCP sighting row outlives the adoption). Propagation is **pull-based** — the projection runs in the discovery process, so `refreshProjectionPriority()` installs the order at boot in every role and at the top of every `runDiscovery`; reordering is **not retroactive**, each integration's assets re-project on its next run. **The default order is closest-to-a-place first**: sighting FortiGate → the label-only cloud sources (arc / intune / entra / arc-k8s) → vCenter cluster → AD's OU path → fortiswitch / fortiap. The gate is the only contributor naming a physical place; an OU path is org structure that reads as a location only because sites tend to name OUs after buildings; fortiswitch/fortiap sit last where rank is inert (those kinds only exist on assets with no competitor). A **source blob may never be built from the projection's own output**, which is the rule this contributor broke twice: `fortigate-endpoint`'s `observed.learnedLocation` used to be copied off `Asset.learnedLocation` at flush time, so it accumulated the render's `<integration>:` prefix one segment per cycle AND, on a domain-joined laptop, laundered AD's OU path into the blob as something the FortiGate had supposedly said (`CENTRALFMG1:OU=Computer Workstation2` in the column, prod 2026-08). The blob now takes the gate name from the discovery pathway that did the sighting.

## Rule 23 — Who owns an IP and how the gate hands it out are two facts, not one

`Reservation.sourceType` answers the first; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers the second. Conflating them is what made a FortiLink-addressed FortiAP unreservable: Phase 3a/3b create a `fortiswitch`/`fortinap` row for **every** managed switch/AP, and the address can come from the gate's own DHCP lease table via the `dhcpByHostname` fallback — so Polaris recorded a dynamic lease as an authoritative reservation (plain "Active" pill, no Reserve action) while the FortiGate's DHCP page reported the same address `Not Reserved`. Phase 5 is the only pass that can see the difference, and before this it had **no branch** for those two source types: the entry fell through to a bare `continue`, dropping the fact every cycle and (silently) breaking the "path-* counters sum to entriesTotal" property of its own summary Event. The Phase 5 infra branch now records the binding via the pure `decideInfraDhcpBinding` (`src/utils/infraDhcpBinding.ts`), writing **only on change** because it runs per DHCP entry per cycle. Three deliberate non-writes there: `sourceType` is never flipped (ownership is unchanged and the row's Phase 5b sweep exclusion + decommission semantics depend on it); `expiresAt` is **never** stamped (a lease carries one, and that would hand these rows to `expireReservations` — a live AP's row would expire on the gate's lease clock, be re-created next discovery, and churn); and `macAddress` is fill-only **from the lease entry**, never from `ap.baseMac`, since only the MAC the gate saw requesting the address is the one a future MAC→IP push could bind. A `"lease"` row is takeover-able by an operator Reserve exactly like a `dhcp_lease` (`isSupersedableByCreate`), and releasing it is a pure DB release — neither unpush branch nor the lease-expiry branch fires for it, so claiming an AP's address never bounces its lease. `"reservation"` and `null` stay authoritative: absence of evidence is not evidence the address is free. Phase 3a/3b's conflict-raise is gated on `reservationBelongsToInfraDevice` (MAC, else hostname, else "Polaris pushed it") — without that, the first operator reservation of an AP's IP would raise a conflict card per AP on the next cycle. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets`, called from the Phase 2a controller cascade, the Phase 2b stale-infra sweep, both asset DELETE routes, the operator decommission branch of `PUT /assets/:id`, and `decommissionStaleAssets` — every call site filtered to `switch`/`access_point`, since the same predicate would otherwise match a Polaris-pushed reservation on an ordinary server): it delegates to `releaseReservation`, so the CMDB unpush + lease expiry + audit Events all come for free, and it is bounded per invocation because that call can perform device I/O and a controller cascade can cover hundreds of APs. **"No longer discovered" is deliberately NOT a release trigger** — an offline AP stays in its controller's roster (business rule 16's config-truth-vs-reachability line), so the release hangs off the existing decommission decision rather than a second staleness rule. `reconcileOrphanedInfraReservations` (6h job) is the backstop for a decommission that happened while the gate was unreachable; its pure `classifyOrphanInfraRow` releases on an explicitly decommissioned device, but for "no device found at all" — which is also what a transient discovery state looks like — releases only rows Polaris never pushed, because a false positive on a pushed row would delete a reserved-address entry on a live gate. **Optionally, Polaris writes the binding itself** (`infraReservationPushService`, a post-sync discovery pass): double-gated on `config.pushReservations` (the transport nucleus, re-checked server-side via `integrationPushEnabled`) AND `config.autoReserveFortinetInfra`, both default off, on the DHCP Push tab of BOTH Fortinet integration types. It turns a managed device's dynamic lease into a real `reserved-address` entry on its own gate — **pinning an address the device already holds, so pool occupancy never changes** (this is not a mechanism for claiming free space; the pool-capacity question is deferred because Polaris stores no DHCP range and has no subnet-utilization alerting). This is the only DHCP write in Polaris that happens on a schedule rather than because an operator acted on one IP, so it is bounded per cycle (`RUN_CEILING`), low-concurrency, MAC-from-the-lease-table-only, read-back-verified, and never re-attempts a row carrying push state — a permanent refusal is recorded as `pushStatus="failed_permanent"` + `pushError`, which both drops the row from the candidate set and surfaces the device's own message in the IP panel, instead of being retried every cycle. The push pointers it stamps are exactly what the lifecycle release's pinned-unpush branch needs, so decommissioning the device removes the entry.

## Rule 24 — Alert on the device's own alarm bit before inventing a threshold for it

Two boolean asset_metrics exist, and which one to reach for is decided by whether Polaris already collects the fact. **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus` — the per-sensor bit the FortiOS REST `sensor-info` and SNMP `fgHwSensorTable` collectors ALREADY write on the normal hardware-sensor cadence, and which the asset System tab already renders as its STATUS column. It needs no operator configuration, works on every transport that fills the column, and shares `hwSensorValue`'s `sensorClass` / `sensorNamePattern` dimensions (same `hwSensorFilterMatches` predicate), so a rule can target one named sensor or a whole class. Prefer it over a threshold on the reading: the device knows its own per-model limits, and for a fan tray or a PSU the health lives in the bit rather than in any comparable number (a FortiGate PSU reports `1` forever and signals failure only through the alarm). **`customStateValue`** (business rule/`AssetStateSample`, state probes) is the general mechanism for status OIDs Polaris does NOT already collect — any vendor, any table — and is deliberately NOT the answer for Fortinet hardware sensors: pointing a probe at `fgHwSensorEntAlarmStatus` re-walks an OID the collector already walks, into a second table, to alert on a value sitting in the first one, and gives two copies of one truth that can disagree. The shared invariant is the NULL rule: `alarmStatusToFlag` (`src/utils/hardwareSensors.ts`) returns `0 | 1 | null` and the engine excludes `alarmStatus: null` **in SQL**, because a source that publishes no alarm bit (the FortiAP-controller path) must not have its absence mapped to 0 — that would assert health nothing ever checked, clearing live alerts and making every such sensor look verified-healthy. An unrecognized non-empty status maps to 1, not null: it's a claim something is off-nominal, and dropping it would go silent on a real fault. **The ENTITY-SENSOR-MIB walk now DOES publish the bit**, from `entPhySensorOperStatus` via `entityOperStatusToAlarm`: `nonoperational(3)` → `"alarm"`, `ok(1)` → `"ok"` (needed so a cleared fault resolves), and — the load-bearing case — **`unavailable(2)` → NULL, never `"alarm"`**, because an empty SFP cage reports unavailable and a port with no transceiver in it is not a fault; mapping it to alarm would fire on every unused port on the switch. Note the bit means something narrower here than on the Fortinet paths: it reports whether the SENSOR is functioning, not whether the reading is inside its limits. For "this optic is degrading but not yet dead", use a severity-band automation on the dBm `hwSensorValue` instead (business rule 19).

## Rule 25 — An alert you can't acknowledge from where you read it isn't really acknowledgeable

`POST /alerts/acknowledge` has existed since the notifications feature shipped, gated `alerts:write`, with **zero frontend call sites**: the asset-details Alerts tab and the mobile Alerts list both rendered alerts read-only, so `escalation.stopOn: "acknowledge"` — offered on every escalation chain the wizard builds — could in practice only ever be stopped by clearing. Acknowledgement now reaches the three places an alert is actually read. **In-app** (the Alerts tab + the mobile list) calls the existing route. **Email and web push** carry a one-click link backed by `NotificationAckToken`, and the rules around that link are what keep it from being a hole: (a) a token is minted **only for a recipient who is a configured Polaris user holding `alerts:write`**, because the token records WHO acknowledged and an address-book contact is an address with no account behind it — contacts and typed addresses get the same mail without a link, never a link that 403s; (b) redemption **re-checks the permission live**, so a role downgrade invalidates links already sitting in mailboxes; (c) the **GET is inert and only the POST redeems** — Outlook Safe Links, Proofpoint and every other mail gateway fetches links before a human sees them, so an acting GET would acknowledge every alert Polaris mails at scan time; (d) the route mounts **above `session()` and `csrfMiddleware`**, not merely CSRF-exempt, because `csrfMiddleware` stamps `req.session.csrfToken` on any request carrying a session and would have every scanner GET mint a `connect-pg-simple` row; (e) the digest is **sha256 with no prefix column**, deliberately unlike the argon2id + prefix-walk pattern `ApiToken` and the agent tokens use — that pattern protects operator-visible secrets of unknown entropy, whereas this is 192 bits Polaris mints, embeds once and consumes, and argon2 at ~50 ms/row would spend seconds of blocked CPU per large alert **on the alert fan-out path**. A composed email (one shared body, several recipients) carries a link only when exactly one To address is user-owned and cc/bcc are empty — otherwise a cc'd contact could acknowledge as the To user. `{ack}` is the one catalogued template token with **no key in `buildTemplateContext`**: its value is per-recipient while the context is built once per fire and snapshotted onto `Notification.templateCtx`, so it is substituted at delivery expansion instead (which works only because unknown tokens survive the render — don't "fix" that). **And the note is per-automation optional or mandatory** (`NotificationRule.requireAckNote`, the wizard's in-app alert card, default off): "someone looked at it" is enough for a noisy interface flap, while a critical outage wants the operator to say what the problem was and what they did. It is enforced in **`acknowledgeNotifications`**, not in the dialog, because that one function backs all four read surfaces and three of them can acknowledge without ever rendering a form — the modal's required field, the emailed page's `required` textarea and the mobile note sheet are each just the local courtesy. Four decisions follow: a **batch is refused whole** (the route takes ONE note for every id, so acknowledging the note-free half under a success toast would leave the alerts that mattered open — the bulk dialog therefore demands a note when ANY selected alert's automation does); the emailed link answers a recoverable **`"note_required"`** and **does not spend the token**, since form validation must not cost a recipient their only way to acknowledge from a mail client; the **web-push action button opens the ack page** on that answer rather than the app, having no text field of its own and needing no session; and a **rule-less alert reads false** (a test fire, or one whose automation was deleted — `ruleId` is SetNull), because there is no policy left to enforce and refusing to let anyone close it out would be worse than a missing note. The flag rides each row of `GET /alerts` and `GET /assets/:id/alerts` as a flat boolean (`withAckPolicy`) so no surface has to fetch the automation to know how to ask.

## Rule 26 — A generated MAC is a placeholder until the network proves otherwise

A DHCP reservation is a MAC→IP binding, so reserving an IP for a device that isn't racked yet needs a MAC before there is a device to supply one; the IP panel's **Generate** button synthesizes one. Before this, that MAC was `02:` + 5 bytes of `Math.random()` from two duplicated client-side copies, marked as synthetic nowhere — so the entry sat on the gate matching nothing, the device arrived, DHCP'd with its real MAC, missed the reservation and took a pool address, and the reservation looked correct on both sides while doing nothing forever. **The prefix is the marker, and the only one.** `reservationMacPlaceholder` (Setting, default `02:0F:5E`, Server Settings → Identification) is what makes a stored MAC recognizable as synthetic — there is deliberately no boolean column on Reservation and no Conflict row, because the prefix is visible on the FortiGate's own reserved-address table, so an operator reading the gate can tell which entries are waiting on a device without consulting Polaris. `normalizePlaceholderPrefix` (`utils/mac.ts`) accepts 1–5 hex octets and **rejects any prefix that isn't locally-administered unicast** — that rejection is load-bearing: pointing this at a real vendor OUI (`00:50:56`) would make that vendor's genuine devices look like placeholders and hand discovery permission to overwrite them, whereas a locally-administered prefix cannot be assigned to a vendor, so no factory MAC can fall inside the placeholder space. (`AA:BB:CC` is legal here for the same reason — 0xAA has the LA bit set.) **Adoption** (`placeholderMacAdoptionService`, discovery Phase 7.7, double-gated on `config.pushReservations` + `config.adoptDiscoveredMac`, both default off, FMG + standalone parity) replaces such a MAC with the real one when the gate reports a device at that reserved IP, and re-pushes the corrected binding. Evidence is the **ARP table** and **device inventory** only, keyed `(fortigateDevice, ip)` like Phase 7.6 so overlapping RFC1918 subnets behind different gates can't cross-match; ARP wins over inventory (a live L2 binding beats a cache whose `is_online` lags), an online inventory row beats an offline one, and two ARP rows disagreeing about one address drop it permanently — a duplicate IP on the wire is not something to burn into DHCP config. DHCP lease entries are deliberately NOT evidence (a device whose MAC doesn't match never gets the reserved address, so it can't appear there) and neither is `Asset.ipAddress` (not device-scoped). Five guards make the unattended overwrite defensible: the stored MAC must be a placeholder, the observed MAC must **not** be (never swap one synthetic value for another — that also makes the legacy `02` prefix safe, since a genuine `02:` device presents that same `02:` MAC in ARP and is skipped rather than churned), it must differ, it must not already be held by another active reservation in the same subnet (FortiOS would refuse it *permanently*, parking the row), and the row must not be at `failed_permanent`. The gate write goes through `updatePushedReservation` — **device first, verified by read-back, Polaris second** — so the two views can't diverge; a `pending` row skips device contact and lets the retry tick carry the new MAC. Bounded **per RUN, not per call** (`AdoptionBudget`, 50): in FMG mode `syncDhcpSubnets` runs once per managed gate, so a per-call ceiling would multiply by gate count. Audited per row (`reservation.mac.adopted` / `reservation.mac.adopt_failed`). **Changing the prefix is not retroactive in either direction** and the settings card confirms before saving. Related fix in the same change: Phase 6's DHCP-entry MAC overwrite (a bare `prisma.reservation.update` with no push) is now **skipped for rows carrying push pointers** — it was silently diverging Polaris from the gate for any pushed row, and left unfixed it would have adopted the placeholder away in Polaris while the gate kept it forever.

## Rule 27 — A logo is picked by theme; a name is text only when the picture doesn't already say it

The shipped Polaris art is theme-paired (`public/img/brand/polaris-{horiz,vert,symbol}-{dark,light}.png`): the dark-theme wordmark is light blue and the light-theme one near-black, and the symbol's wedges are white on one and navy on the other — so painting the wrong variant makes the logo *disappear* rather than merely look off. Horizontal art on the login card, vertical in the sidebar. The two variants of a pair are **normalized to one geometry** (the vendor exports were not — the vertical light star was ~39% larger relative to its wordmark), so a theme flip swaps the file and moves nothing on screen; re-exported art has to be re-normalized, see ARCHITECTURE.md → `public/img/brand/`. **One module decides** — `public/js/brand-logo.js` (`PolarisBrandLogo.resolve/applyTo`), consumed by the desktop login, the mobile login, the sidebar and the Customization preview, because four surfaces each deriving the rule is four chances to disagree; it reads `data-theme` (observed via MutationObserver, so it repaints on the in-app toggle without hooking it) and registers the `prefers-color-scheme` listener that keeps a user who has **never** chosen a theme tracking their OS. With nothing in `localStorage["polaris-theme"]` every bootstrap (`js/theme-init.js`, `app.js`, `mobile/app.js`, `dash-boot.js`) now resolves the OS preference, matching on `light` so a browser stating no preference still lands on dark — the historical default. Nothing is persisted by that path: staying unsaved *is* the "follow my system" state, and the theme toggle is the opt-out. **The Application Name is a caption for a custom logo only.** The Polaris art carries the wordmark, so printing the name under it says it twice — `showName` is false whenever the shipped art is in play, and `appName` may therefore be stored EMPTY (`displayAppName` is the fallback for the surfaces that must print one: page titles, the PWA manifest, the acknowledge page). The operator's `subtitle` is their own line of copy and renders either way. **Placement is per surface** (`logoOnLogin` / `logoOnSidebar`, both default on, Server Settings → Customization → Logo): switching one off returns THAT surface to the Polaris mark without discarding the upload. **The accent** (`logoAccent`) composites the theme's `polaris-symbol-*.png` onto the bottom-right of the operator's logo at ~50% of its longest side (`ACCENT_FRACTION`, clamped to half its shortest so a wide banner isn't swallowed) — rendered **server-side** by `brandLogoService` and served from the public `GET /server-settings/branding/logo-accent.png`, not as a per-surface CSS overlay, so the geometry can't drift between login, sidebar and mobile. It renders per theme (`?theme=`), which both picks the right symbol variant and gives the `<img>` a new URL to re-fetch on a theme flip; otherwise the path is fixed (the upload route reuses one filename), so it answers `no-cache` + a strong ETag over the source mtimes **and the theme**, and 302s to the plain logo whenever there is nothing to accent.

## Rule 28 — The Windows build is the authority; the product name is not

Microsoft never updated the registry key `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProductName` when Windows 11 shipped, so it still reads **"Windows 10 Pro" on every Windows 11 client**. That key is what WMI's `Win32_OperatingSystem.Caption` and `systeminfo` read, which means this is not one broken integration but *every* source at once — AD's `operatingSystem`, Intune/Entra (which collapse it to a bare "Windows" anyway), and gopsutil's `Platform` inside the Polaris Agent. So the projection's priority order cannot fix it: whichever source wins is equally wrong. The **build number** is always right (it comes from `CurrentBuild`, not the frozen display string), so `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the family from it and labels the pair with the release operators actually speak in: `"Windows 10 Pro"` + `"10.0.22631.7219"` → `"Windows 11 Pro"` + `"23H2 (10.0.22631.7219)"`. **Family from a threshold, release from a table** — deliberately different mechanisms: `build >= 22000 ⇒ Windows 11` never goes stale, so a build shipped after this code was written still gets the right family, while the release table does go stale and an unlisted build therefore keeps its RAW `osVersion` rather than being guessed at. **Windows Server is excluded entirely** (any os string containing "server"): its ProductName is already correct, and build 26100 is BOTH Windows 11 24H2 and Windows Server 2025, so the threshold would relabel a 2025 server as a workstation. Applied at **write** time — in `projectAssetFromSources` AND in the `db.ts` Asset hooks (the catch-all for the inline writers) — not at render, because the Assets table's OS/Firmware **filter and sort**, CSV/PDF export, `os`/`osVersion` tag criteria, maintenance criteria and automation scope conditions all read the stored columns: an "os contains Windows 11" rule is only true if the column says so. Two properties keep that safe to run on every write: it is **idempotent** (a re-write of its own output is a no-op, or the label would nest — `"23H2 (23H2 (…))"`), and it **reads no row** (the build comes from whatever `osVersion` the same write stages, so the monitor hot path pays nothing). Normalizing only on the way to the DB would make `projectionDriftService` report permanent os drift, which is why the projection normalizes its own output too. Not retroactive: existing rows correct themselves when their integration next re-projects them (rule 22's pull-based precedent), and there is no backfill job.

## Rule 29 — One outage is one alert: packet loss is what happens while the device is answering

`probeLossPct` is the only metric whose INPUT is failed probes, which made it the only one that could raise a second alert about an outage `monitorStatus == down` already owns. Two gates now bound it, and both are about the same distinction — *lossy* is not *dark*. (a) **Only an ANSWERING device reports loss**: `assetIsAnsweringProbes` (notificationEngine) admits `up` and `warning` and nothing else. `warning` is deliberately IN — it is 1..`failureThreshold`-1 consecutive failures on a device still replying, i.e. the state a lossy-but-alive device lives in (an alternating pass/fail device never reaches `down` at all), so gating on `up` alone would silence the feature's whole purpose. `down` and `recovering` are OUT (`recovering` is the tail of the same outage — asset-down is still live until successes reach the threshold), as are `unknown`/null (nothing measured yet). The filter sits in the `probeLossPct` resolver so the composite-trigger path and the wizard's preview inherit it from one place; `evaluateThresholdRule` separately **clears** a live loss alert on an asset that stopped answering (`clearedBy="system:device-down"`, `notification.superseded` Event with `reason:"device-down"`) rather than freezing it — the carve-out's handoff semantics, because freezing is exactly what used to park a packet-loss alert next to the asset-down alert for the whole outage. No reset actions on that path (the alert isn't recovering; mailing "loss resolved" about a device that just went dark would be worse than silence). Metric-scoped via `ANSWERING_ONLY_METRICS` — every other metric is derived from SUCCESSFUL polls, so a dark device simply stops producing readings. (b) **The ratio starts at the first successful probe inside the window**, not at the window's leading edge (`probeLossQuery.ts`: a partitioned `min("timestamp") FILTER (WHERE "success")`, older samples trimmed) — a device unreachable for part of the window had no probes there to lose. Without it a device recovering from a 55-minute outage reads ~93% loss the moment it answers again and keeps alerting until the outage slides out of the window, i.e. it alerts *because* it came back, for a full window (an hour, on a 60-minute one); with it the first clean probe reads 0% and the alert clears. The cost is that a leading failure run isn't counted even when it was a blip rather than an outage — accepted, since the alternative is an arbitrary blip-vs-outage threshold and the blip re-enters the ratio on the next tick anyway (the anchor only discards samples OLDER than the first success). Both gates apply to the NOC Packet Loss widget too, through the one shared query — with one display-only divergence: the widget passes **`includeFullyDown`**, so an asset with NO successful probe in the window reads **100%** instead of being dropped by the anchor (before this it VANISHED from the widget, which reads as "no loss" — the opposite of the truth). The engine must never pass it: `assetIsAnsweringProbes` already keeps `down`/`recovering` assets out of its id list, and a 100% reading reaching a `probeLossPct` automation would fire exactly the second alert this rule exists to prevent. **And it starts no earlier than the end of the last outage** (2026-08-21): the first-success anchor only helps while the outage is still running at the window's leading edge — once the device has been back long enough for a healthy sample to precede the outage, the window's first success sits BEFORE it, the anchor goes inert, and every failed probe of the outage is back in the denominator. Same false alert, same full window: a 5-minute outage inside a 60-minute History reads ~8% loss for an hour *because* the device recovered, and the device-down supersede in (a) covers only the outage itself, not the window after it. So `Asset.recoveryStartedAt` — stamped by `recordProbeResult` on the success that ends an outage, i.e. the probe that takes `monitorStatus` out of `down`/`unknown` — is a second anchor, and the measurement starts at `GREATEST(first success, recoveryStartedAt)` (Postgres's `GREATEST` ignores NULLs, so a device that hasn't recovered inside the window behaves exactly as before; the pure JS mirror both the alert-email loss chart and the writer's predicate share is `utils/probeLossAnchor.ts`). **Only an outage-ending recovery stamps it — a `warning`->`up` recovery deliberately does not**, and that asymmetry is what keeps flapping measurable: a lossy device passes through `warning` constantly, so stamping there would restart the window every few probes and report ~0% forever. The stamp is never cleared (it ages out of the window on its own and the next recovery overwrites it) and never backfilled. (c) **The window is HISTORY; sustain is its own optional knob.** A ratio needs a denominator, so `windowSec` isn't a smoothing choice layered on a reading — it IS the reading, which is why the wizard labels it **History (minutes)** (mandatory, default 15, range 5..1440 = the schema's 24h ceiling) and hides the aggregation control (the engine ignores it). Since 2026-08-20 a SECOND field, **Sustained for (minutes)** (`#tf-sustain-min` → `forDurationSec`, optional, 0 = fire on first crossing), puts the hold axis back as its own control — "loss over a 60-minute History, sustained over the threshold for 10 minutes" is now expressible — and severity tiers keep their own hold clocks like any other numeric metric (they still share the base's History window per rule 19; the engine's generic debounce + `bandMetSince` machinery needed no change). The sustain field is rendered on every device/host trigger but hidden unless a ratio condition is present, so nothing else can pick a value up from it. The metric class is declared server-side as `WINDOWED_RATIO_METRICS` and published on `/automations/schema` as `windowedRatioMetrics`, so the builder doesn't hardcode it. Before the History rename the one field was "Sustained for" and a `latest` ratio leaf routed those minutes to `forDurationSec`: an automation reading "loss over 60 minutes" actually measured over the engine's 15-minute floor and then held for 60 — the two knobs meant one axis and neither said so. A stored legacy rule reads its `forDurationSec` minutes back as the History the operator meant (and shows sustain 0 — `triggerSustainMinutes` takes the hold ONLY from a rule that also stores a window, or one save would double the minutes into both axes), and re-saves as a window. The engine correspondingly uses `windowSec` EXACTLY for this metric (`probeLossWindowSec` in notificationTypes — 5 min floor, 15 min default when absent — SHARED with the alert-email loss chart) rather than `max(windowSec, DEFAULT_LOOKBACK)`, which every other metric needs to be sure a `latest` reading finds a sample. Granularity follows probe count, not the window: at a 60s interval a 5-minute History is ~5 probes, so loss can only read in 20% steps — the field's hint says so, since that is PRTG's 5-pings-per-scan coarseness arrived at from the other direction. (d) **The ICMP loss sampler is what buys resolution back** (business rule 30): during `warning`/`recovering` a 10s ping adds rows to the same window, so a 15-minute History divides ~90 samples rather than ~15. Its rows count toward the ratio and nothing else. Note what that means for the reading: the sampler runs BECAUSE a poll failed, so its samples are not a uniform rate — a lossy device's loss climbs on real ICMP failures, while a one-off transport hiccup followed by clean pings reads LOWER than the poll-only ratio would (1/22 rather than 1/15). That cost turned out NOT to be accepted — the bias is why the sampler is **currently disabled** (rule 30's `LOSS_SAMPLER_ENABLED` kill switch, 2026-08-20), so today the ratio divides the response-time poll's own samples at the configured cadence and reads in the coarse steps the wizard's History hint describes; a uniform N-pings-per-scan sampler remains the unbiased alternative if the resolution is ever wanted back.

## Rule 30 — Confirmation is the configured cadence's job; ICMP only fills in the loss ratio

`monitorStatus` reaches `down` after `failureThreshold` consecutive misses (default 3) of the operator's configured transport at the operator's configured `intervalSeconds`, so time-to-down is `failureThreshold × intervalSeconds` — 3 minutes at a 60s cadence, **15 at 300s** — and the figure the monitor-settings card reports is the figure you get. `resolveProbeIntervalSec` (monitoringService, pure + unit-tested) therefore applies exactly ONE clamp: **dependency suppression** (parent dark ⇒ 2× interval, never poll harder into an upstream outage; a `disabled` stream has nothing to slow). **This replaced the fast-confirm re-probe** (2026-08-17 → 2026-08-19), which re-probed a mid-confirmation asset at `fastConfirmIntervalSec` so confirmation cost ~35s regardless of cadence. It was removed because it made the counters a function of a second, tighter cadence that operators could not see in the number they had configured, and because the resolution it bought during a run is worth more as *loss data* than as a faster verdict. `fastConfirmIntervalSec` stays as a **dormant** column (migration `20260817000000`; dropping it would cost an irreversible migration for no gain) read by nothing, and is no longer surfaced on the three monitor-settings cards. What replaced it is the **ICMP packet-loss sampler** (`src/utils/lossSampler.ts` + `runLossSampleFor`, its own `lossSample` cadence / pg-boss queue / worker pool, `POLARIS_MONITOR_LOSS_SAMPLE_WORKERS` default 24) — **currently DISABLED via the `LOSS_SAMPLER_ENABLED` kill switch in `lossSampler.ts`** (2026-08-20: the sampler's failure-period oversampling made alert readings diverge visibly from the wall-clock chart average — see rule 29d's bias note — so packet loss reads from the response-time poll alone until the feature is revisited; the switch defaults `lossSamplerAppliesTo` off, so both due-set builders and the worker's pickup re-check go quiet through the one predicate, and everything downstream stays wired for a one-line re-enable): a single ping at **10s with a 5s timeout** while an asset sits in **`warning` or `recovering`**, writing `AssetMonitorSample` rows with `probeKind="icmp"` and a NULL `responseTimeMs`, anchored by `Asset.lastLossSampleAt` (stamped on every attempt, so a ping-blocked host is not re-queued each tick). It **never calls `recordProbeResult`** — it cannot move `consecutiveFailures` / `consecutiveSuccesses` or `monitorStatus` — because ICMP does not authenticate the device it reaches: a second transport voting on `down` would make the state mean whichever of the two answered last, an ICMP-blocked host would false-`down` on its first transient miss, and a device whose SNMP agent had died would never confirm down at all. **`down` is excluded from the window for the same reason**: there every response-time poll is failing, so a ping reply is uncorroborated and a host that has taken over the address would drag a dead device's loss down from 100% to something reading like congestion — in `warning`/`recovering` the real transport is still succeeding intermittently, which is what makes the reply trustworthy. Dependency-suppressed assets are skipped (the suppression clamp's reasoning), and so are `agent` / `disabled` streams. **`probeKind` splits the readers:** the ONLY all-kinds readers are `probeLossQuery` (both modes) and `alertChartService`'s loss chart — that is the point of the sampler — while every response-time reader filters to primary (`probeKind IS NULL OR 'primary'`; NULL is the pre-feature value and means primary). That list is the engine's `responseTimeMs`/`uptimeSec` metrics, the alert-email RTT chart, `sampleHistoryService`'s detail tier + `readLastMonitorSuccessAt` (an ICMP reply is not a success of the monitored service), the NOC response-time ranking, the Device Map's traffic light (a fixed-COUNT window, which mixed rows would silently shrink from ~10 minutes to ~100 seconds mid-incident), **and every rollup** — folding incident-only rows into 400-day aggregates would make historical loss non-comparable across time, so the sampler's resolution lives and dies with the detail retention window. The three monitor-settings cards keep the DERIVED **"Declare Down after (seconds)"** entry (`_polarisMonDownAfterCalc`, shared by render and the live sync, unit-tested), now computed as `interval × (threshold − 1) + probe timeout` and writing `failureThreshold` — operators think in "down after 30 seconds", and storing that as a second setting would just be a number that could disagree with the product of the two that already exist. In cursor mode the sampler's due-set is capped per pass (`LOSS_SAMPLES_MAX_PER_PASS`, 200, logged on truncation) because `runMonitorPass` awaits the whole pass under the light tick's guard and a site-wide outage must never delay the probes that decide whether those assets are down; pg-boss mode has its own pool and a 15s job expiry instead. Both due-set paths call the one resolver and mirror the sampler's due-check (`computeDueWork` + the pg-boss publisher in `jobs/monitorAssets.ts`); their due-sets are contractually identical, so a second copy of this arithmetic is exactly how they would drift.

## Rule 31 — The login page is the way back in, so restricting it is opt-in and must refuse to lock you out

"Skip login page" redirects unauthenticated visitors on PROTECTED pages straight to SSO, but `/login.html` is deliberately NOT in `protectedPages`: it is the recovery path when the IdP is down, and local + LDAP accounts reach it by typing the URL. That leaves the password surface reachable from anywhere, which some installs don't want. `loginAccessConfig` (`{enabled, ipScope, allowedCidrs}`, Server Settings → Web Server → Local Login Access, **default off**) restricts it by source IP, resolving through the same `utils/ipScope.ts` the Dash wallboard gates on. Six decisions carry it. (a) **Both halves or neither**: the gate covers `/login.html` AND `POST /auth/login` + `/auth/login/totp`, because the form is a plain POST to a JSON API — gating only the page is cosmetic, the endpoint gate is the control. (b) **The two refusals differ deliberately**: the page is DROPPED (socket destroyed, no response — the dashServer stealth posture, so a scanner can't confirm a local login path exists), the API answers the SAME generic 401 a wrong password gets, since "you're on the wrong network" is a fact worth learning. Every blocked POST writes a warning `auth.login.blocked_source` Event, bounded by the existing 10-per-15-min login limiter mounted above it. (c) **SSO is never gated** — SAML, OIDC and App Proxy must keep working from anywhere, and that is exactly what makes restricting the password path survivable. (d) **LDAP is gated, because it shares `POST /auth/login`** — an install whose remote users bind against LDAP should leave this off or scope it to include them; the "Skip login page" checkbox now says so. (e) **It fails OPEN** (`isLoginSourceAllowed` swallows a settings read error): a DB blip must not become the lockout the feature prevents, and no attacker can induce one. The PUT's anti-lockout guard is the mirror of the rising-edge SSO check on `skipLoginPage` — it refuses a scope excluding the admin's own `req.ip` and names the address it saw, and it restricts new LOGINS rather than live sessions, so a too-narrow save is still undoable from the open session. (f) **It is only as true as `req.ip`** — behind two proxies with a one-hop `TRUST_PROXY`, `req.ip` is the INNER proxy's RFC1918 address, so an "rfc1918" scope would admit the entire internet while reading as enforced. That is why the GET returns `callerIp` and the card prints it: the failure is invisible without it.

<a id="rule-32"></a>

## Rule 32 — A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives

Unchecking "reset when the trigger is no longer true" used to leave only *timed* and *manually only* on a single-condition automation: the custom-condition builder was composite-only (`validateRuleV2` refused a `reset.condition` on any other trigger), so the two things an operator actually wants — a different recovery value, or recovery measured on something else — had no home. The mode is now offered on every trigger with a continuous condition (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event`/`change` fire on an instant and are still refused, client and server), and unchecking the box lands on it **pre-seeded with the trigger inverted** — same comparator flip `resetSentence` has always rendered (`invertedLeaf`; a 0/1 flag flips its VALUE, not its comparator), extended to trees by `invertedTree` (**De Morgan** — group operators flip alongside each leaf, which is what keeps the result expressible in an and/or-only vocabulary). Severity bands are ignored: every tier recovers at tier 0, so the base condition is the only one there is anything to invert. Four decisions carry it. (a) **The tree is the SOLE recovery authority while firing** — the trigger falling away does not clear the alert and the trigger re-meeting does not cancel the reset's sustain timer (`recoveredSince` belongs to the tree). That contract already existed for composites; `evaluateThresholdRule` now honors it too, in a dedicated pass after the readings loop rather than inside it, because the tree's leaves need not be the trigger's metric at all — an alert whose trigger metric stopped reporting must still be able to clear, where the auto path deliberately freezes. That pass **re-reads the firing rows from the DB** rather than trusting the pre-loop `states` snapshot the carve-out / device-down / vanished sweeps have since invalidated, so a row cleared as superseded this tick can't then be "recovered", and a row that only just fired can't recover in the tick it fired. Suppressed assets stay frozen. (b) **Resolution is DIMENSION-FIRST with a per-asset fallback** (`resolveResetTruths`): a per-mount or per-interface alert whose reset leaf sits on that same dimension space clears independently of its siblings, while a leaf on a device-wide metric (CPU, memory, monitor status) reports nothing at `assetId|port2`, falls through to the ANY-dimension fold composites use, and therefore clears every alert on the device together. Both halves are wanted — "clear port2 when port2 recovers AND the box's CPU is under 70" evaluates each half where that half lives — so the wizard says which one the operator is building instead of picking for them. (c) **Kind coherence is enforced on single triggers too**, not just composites: a device trigger with a `host_metric` reset leaf (or the reverse) resolves against assets that can never report it, so the tree reads permanently false and the alert could only ever be cleared by hand. (d) **Reset leaves inherit the trigger's measurement window** — the reset step has no window control and must not grow one (rule 29c), so an aggregated reset condition is measured over the same period as the trigger; when the trigger reads `latest` there is no period to average over and the save is refused with a message that says so, rather than the trigger step's message pointing at a field that isn't there.

## Rule 33 — A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login

ICMP proves a NIC answers and SNMP/SSH prove a management plane answers. Neither proves the thing the device exists to do still works: a web server that has lost its backend still completes the handshake and still returns 200, with an error page in the body. The **HTTP check** is one GET against the device's own address, up/down decided by the status code and optionally by a string the response body must contain (`utils/httpCheck.ts` decides, `probeHttp` in monitoringService owns the socket). It shipped as a POLLING METHOD and was **retired as one in 2026-08**; it is now a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType = "http"`). The move is about where a check DEFINITION belongs: as a polling method it had to ride an `http`-typed Credential, which made the thing that answers "how do I log in to this vendor" also carry "which path, expecting what" — so a second path meant a second copy of the same password, and rotating the password meant editing every path. Keyed by manufacturer + optional `modelPattern` instead, it varies on the axis a check actually varies on: every Axis camera answers the same VAPIX path, and a blank model pattern means every device of that manufacturer. Eight decisions carry it. (a) **The body match is the load-bearing half**: a 200 whose body doesn't match FAILS, with the missing content named. There WAS a `failOnMismatch` toggle letting a mismatch pass anyway — it made sense while this drove `monitorStatus` and reachability-only semantics were a reasonable ask, but a widget only RECORDS an outcome and an automation decides what "down" means, so a mismatch stored as a PASS would make `expectBody` decorative (nothing downstream could tell the two apart). It is stripped on save; a laxer rule is expressed by leaving `expectBody` empty and judging on the status code. (b) **Status is judged before content**: a 401 is a broken credential, not missing content, and blaming the body sends the operator to the wrong field. (c) **Redirects are never followed** — a 302 to a login page is the single most common way an HTTP health check reports "up" about a device serving nothing; an operator who wants the 3xx sets `expectStatus` to it. (d) **The body is capped** at 64 KB and the request torn down at the cap, which bounds both a device streaming a log file at the check path and the text an operator-authored `regex` runs against — that pattern is not analyzed for backtracking (nothing static can be); `contains` is the default for the same reason, and a truncated miss SAYS it was truncated. The regex is COMPILED at save by `validateHttpCheckDefinition`, the SAME function the Test Connection flow uses, so a check cannot pass a live test and then be rejected when it is saved. (e) **The credential is authentication and nothing else**, with **no "none" mode**: an unauthenticated check is a widget with no credential attached, which is the same outcome without an empty row that still reads as configuration. `credentialId` is `SetNull` — deleting a credential must not silently delete the check that used it. (f) **The auth scheme is STATED, not guessed.** `authMode` (`bearer` | `basic` | `digest`) is explicit because Basic and Digest carry the same username/password pair, so nothing stored could distinguish them — and the obvious inference (try Basic, fall back on a 401) would send the password in cleartext to any device that answered a Digest challenge, which is precisely the exposure Digest exists to prevent. **Digest is a handshake, not a header** (`utils/digestAuth.ts`, RFC 7616): the response hash is keyed on a server-issued nonce, so `probeHttp` fires bare, reads the 401 challenge and re-fires exactly ONCE — never a loop, because a server rejecting a correctly-computed response will reject it again and retrying past that turns a wrong password into a request amplifier aimed at the device; the second request inherits what REMAINS of the probe timeout. The nonce is deliberately NOT cached: that would cut the steady state to one request but requires a strictly-increasing `nc`, trading a cheap doubling of a cheap request for a replay-shaped failure that only appears under concurrency. It matters for exactly the devices this exists for — Axis OS answers VAPIX with Digest and 11+ disables Basic by default; cameras, PDUs and older BMCs are the same story. (g) **It no longer moves `monitorStatus`.** Each scrape writes a 0/1 to **`AssetStateSample`** (alertable through the existing `customStateValue` metric with no engine change) plus the round-trip time to `AssetCustomWidgetSample` as a gauge, so a slow-but-passing endpoint is visible before it starts failing. The 0/1 is written PASS OR FAIL — the opposite of the state-PROBE rule, which drops an unreadable row because 0 there is a positive claim of health about hardware that may not exist; here a failed request IS the reading, and dropping it would make an outage indistinguishable from a device nobody checked. The gauge is written only on success (a failed request has no meaningful duration). Up/down for such a device therefore comes from whatever transport its responseTime stream uses — usually ICMP. The check also runs INDEPENDENTLY of the SNMP widget gate: an HTTP check must not depend on whether the device also answers SNMP, and a failed SNMP session no longer aborts the pass. `Asset.httpCheckPath` still overrides just the path, for the single device whose endpoint sits elsewhere. (h) **`netGuard` is deliberately NOT applied** — every other outbound-HTTP path in Polaris (automation `api_call` actions, webhooks) SSRF-checks its target because the URL is config pointed at arbitrary hosts, whereas this target is the monitored asset's own private address, the same one the SNMP / SSH / WinRM probes already dial, so a guard rejecting RFC1918 would reject the entire feature. It is also happy to dial a NAME rather than an IP (`dnsName || hostname` when there is no `ipAddress`): a TLS check against a name is the check an operator means, since the cert and any vhost routing are keyed on it. **Tailoring a check is a first-class flow**, because the expectation is a string that has to be picked OUT of the device's response: `POST /credentials/test` accepts a full check definition alongside the credential and returns `httpDiagnostics` — request line as dialed, status, content-type, byte count, cap flag, match verdict, the auth schemes the device asked for, and a 4 KB body excerpt — so the loop is point it at a device, read the body, paste a distinctive string into Expected content, re-test, then save the settled values onto the widget. The response BODY is deliberately kept out of the `credential.tested` audit Event (arbitrary device output would ride every pg_dump and syslog forward), and no response header beyond `content-type` is returned, since a full dump would put a live `Set-Cookie` into the modal.

## Rule 34 — An active scan finds things; a separate grant adds them

Every other discovery pathway in Polaris asks something that already knows the device (a controller, a directory, a hypervisor, a tenant). A **Discovery** (`NetworkScan`) instead sweeps addresses the operator names, which makes it the only Polaris feature that touches hosts it has no prior relationship with — so the posture matters more than the mechanism. Six decisions carry it. (a) **Scanning and adopting are separate grants.** Authoring and running ride the `networkScan` key; `POST /network-scans/:id/adopt` chains `assets:write` on top (the `PUT /application-map/discovery` precedent). A role may therefore be allowed to find out what is on a range without being allowed to put it in inventory, and the wizard renders that state rather than discovering it at the POST — Export and Save work, **Create assets** is absent with a reason. A `read`-level caller gets a read-only walkthrough, since a scan run by one operator is legitimately handed to another to adopt. (b) **It is opt-in and IDS-visible, and says so.** There is no scheduler and no shipped default range: a scan happens because an operator pressed a button. `arpPrimeService`'s file header already warns that an unannounced sweep of every reserved IP is what IDS dashboards flag, and this is more aggressive than that sweep. The wizard does NOT say so — an operator-removed banner (2026-08-25): an operator who reaches a screen headed "which addresses should Polaris sweep" already knows they are scanning, so the warning read as noise on every visit while the posture it describes is enforced by the mechanism (no scheduler, no shipped default range, a separate grant) rather than by being read. Pacing, batching, a hard target cap and swallowed per-target errors all follow that service. (c) **Some addresses are excluded regardless of what the operator typed** — loopback, link-local (including the `169.254.169.254` cloud-metadata address), multicast and unspecified: the `netGuard` blocklist minus its RFC1918 allowance, since RFC1918 *is* the point here. They are filtered out of the expansion and COUNTED in `droppedTargetCount` alongside over-the-cap truncation, because silent removal reads as "the range is clean". (d) **New addresses only.** A responder whose address an Asset already carries is excluded server-side and reported as a count, so "nothing new" is distinguishable from "nothing there". The corollary is deliberate and worth stating so it doesn't read as an oversight: **a re-run enriches nothing** — it is a way to find what has appeared, not a sync. (e) **No `network-scan` sourceKind.** Adopted assets are created exactly like the manual `POST /assets` path (fields inline, `ipSource="manual"`, the `db.ts` extension minting the `manual` AssetSource row), because `projectAssetFromSources` has ZERO rules for a kind outside its union: such a row would contribute nothing to the projection while `projectionDriftService` compared projection against the stored row, i.e. a drift-log generator. Adding rules instead would put a one-time scan blob in competition with a later agent for hostname priority, which is the wrong outcome. Scan provenance goes where discovery already puts it — the one-time `Asset.notes` boilerplate plus an audit Event. (f) **SNMP goes through the gate, always.** `withSnmpGate(host, port, …)` is not optional here: many switch and AP SNMP agents are single-threaded, and a scan that skips it contends with the monitor loop's probes on the very hosts Polaris already polls. Identification reuses the one exported probe surface (`probeCredentialAgainstHost`) and the exported `snmpWalkRaw` rather than reaching into the module-private per-transport probes.
