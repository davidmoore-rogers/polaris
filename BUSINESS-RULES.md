# Polaris — Business Rules & Constraints

Full narrative for business rules **12–37**. Each rule records a decision *and the
incident or constraint that forced it* — the reasoning is the point, so nothing here
is a summary.

This file is **not** auto-loaded into Claude Code sessions. [CLAUDE.md](CLAUDE.md#business-rules--constraints)
carries all 37 rules; rules 1–11 live there in full (they are one-line invariants),
and rules 12–37 appear there as the invariant plus a pointer into this file.

**Rule numbers are a stable citation key.** Commits, code comments and the other
reference docs cite them as "business rule 23". Never renumber a rule — retire one in
place if it stops being true, and give a new rule the next free number.

## Rule 12 — `Asset.lastSeen` means verified network presence

written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts` (no-regress: it only advances, and stamps `Asset.lastSeenSource` provenance alongside). Valid evidence: live DHCP lease (`seenLeased`), FortiGate device-inventory sighting (the FortiGate's own per-client `last_seen` timestamp — never discovery-run time), connected FortiSwitch/FortiAP, firewall answering discovery, agent heartbeat, answering monitor probe, presence-verification ping, operator-resolved conflict. **Polling is authoritative for monitored assets**: when `Asset.monitored === true`, the monitor probe is the sole authority for presence — `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter` — a powered-on VM / connected ESXi host reported at scrape time — and `arc`) so they can't advance `lastSeen` past what polling established. A successful probe stamps `lastSeen = now, lastSeenSource = "probe"` (written through the `probePatchBuffer` bulk-update in `recordProbeResult`, not a Prisma write); a failed probe writes nothing, so a monitored-but-down device's `lastSeen` freezes at its last successful poll even if a FortiGate still reports it `is_online` in device inventory. Active/operator sources (`probe`, `agent`, `ping`, `conflict-*`) are never deferred. (Repointing a managed FortiSwitch/FortiAP's response-time stream to poll "via parent FortiGate" / the controller rather than direct SNMP is the fix when the device is genuinely up but unpollable directly.) **Device inventory outranks the DHCP lease** (unmonitored assets): when a MAC appears in this cycle's device inventory, the lease path skips its bump so the inventory's real `last_seen`/`is_online` wins — a bound-but-idle lease (device leased an IP then went home) must not stamp `now`. Lease-only assets keep the lease bump. **Fortinet-discovery-owned infra never takes client-sighting presence**: firewall/switch/access_point assets carrying a `fortinetTopology` stamp skip BOTH the dhcp-lease and device-inventory bumps — their presence comes only from their own discovery loop (gated on answered-live / connected / `!offline`) and the probe, so an offline-in-FMG gate sighted as a DHCP client of another gate (lingering lease binding, stale cached `is_online`) can't keep freshening its lastSeen; the fortigate-firewall AssetSource row's lastSeen likewise freezes on offline cached-CMDB pulls. Operator-typed non-Fortinet "firewall"/"switch" assets (no topology stamp) keep the endpoint-style bumps. Directory timestamps (Entra `lastSyncDateTime`, AD `lastLogonTimestamp`) deliberately do NOT write it — they stay on the `AssetSource` rows and surface as "Last Directory Activity" in the slide-over; the Entra duplicate-registration tiebreaker compares those directory timestamps, not `lastSeen`. (vCenter and Azure Arc are the exceptions among discovery integrations: vCenter's `power_state`/`connection_state` and Arc's `properties.status === "Connected"` are real-time truth READ AT SCRAPE TIME — categorically different from the stored historical timestamps directory sources carry — so unmonitored VMs/hosts/Arc machines DO get a `"vcenter"` / `"arc"`-sourced bump; both are in the deferred set, so polling stays authoritative once monitoring is on. For Arc the evidence timestamp is always RUN TIME, never `properties.lastStatusChange`, which records when the status last CHANGED and so is 90 days stale on a machine that has been Connected for 90 days.) Presence evidence also gates status resurrection: a remembered-but-offline inventory/switch/AP entry must not flip a `decommissioned` asset back to `active`. `decommissionStaleAssets` consults directory/agent `AssetSource.lastSeen` as a veto so cloud-only laptops don't age out. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path).

## Rule 13 — SD-WAN monitoring is opt-in, read-only, FortiOS-only

Gated per-integration by `Integration.config.pullSdwan` (default false), on both the FortiManager and standalone FortiGate integrations. When on, the heavy/system-info pass for FortiGate firewalls also calls `collectSdwanFortinet` (`/api/v2/monitor/virtual-wan/health-check` + `/api/v2/cmdb/system/sdwan`). It writes the `AssetPerfSlaSample` **SLA-metrics time-series** (latency/jitter/loss per WAN member — append-only, rolled up + retained), and refreshes the `AssetSdwanRule` **current-state** table (one row per rule, delete-replaced per scrape via `persistSdwanRules` — no history/timeline). Never writes to the device. The asset modal's **SD-WAN** tab appears only for FortiGate firewalls with data. The runtime "selected route" per rule is **inferred** (first candidate member up in priority order) when FortiOS doesn't expose it over REST — clearly labeled in the UI; verify the exact endpoint/field shapes on a real FortiOS 7.x device. Rules configured for zone-based selection (`priority-zone`) carry no interface members — `parseSdwanRules` resolves their candidates from the preferred zones' member interfaces and records the zones in `priorityZones`, so the UI lists each zone's members (grouped) instead of an empty cell.

## Rule 14 — Description sync is opt-in and Polaris-primary

Gated per-integration by `Integration.config.syncDescriptions` (default false), on both the FortiManager and standalone FortiGate integrations (Description Sync tab). **A non-empty Polaris value always wins**: pushed to the device on save and re-asserted by every reconcile, so device-side edits are overwritten (audited with the value they replaced — `asset.description.pushed` `overwroteDeviceValue` detail). **An empty Polaris field adopts** the device value (`asset.description.adopted` / `asset.interface.description.adopted` Events) — clearing the Polaris description is how an operator takes the device's value. No conflict state exists (the earlier newest-edit-wins three-way merge was retired 2026-07; legacy `conflict` sync-state rows resolve on the next reconcile by pushing the Polaris value). `Asset.descriptionSync.value` / `AssetInterfaceOverride.syncedValue` persist the last synced value (bookkeeping for the FMG-mirror device-agrees check + the UI badge, not a merge base). A device-side *clear* never removes a Polaris value (the push re-asserts it). `decideDescriptionSync(polaris, device)` is the pure decision. Surfaces: interface comments (`AssetInterfaceOverride`) ↔ FortiGate `system/interface` description / FortiSwitch port description; `Asset.description` ↔ FortiGate `system/global` alias / FortiSwitch managed-switch description / FortiAP wtp **`location`** (AP Manager's field — wtp `comment` doesn't exist in FMG's copy, so installs strip it; confirmed on a live FMG 7.x). All device I/O rides `reservationPushService`'s Transport (works in FMG proxy AND bypass/direct modes + standalone). Runs at save time (always pushes, best-effort, never blocks the Polaris write) plus a Phase 13.7 discovery reconcile that re-pushes drift / adopts into empty fields and is the retry path — no queue. Clearing a Polaris value is local-only (no device-side delete). Push verifies by read-back; transport errors never mutate sync state. FortiOS field shapes (alias cap, ports child-table PUT) are flagged verify-on-real-device in `descriptionSyncService.ts`; the wtp `location` cap is confirmed at 35 chars. **FMG central management:** each FMG discovery start detects whether the ADOM centrally manages FortiAPs / FortiSwitches (`detectCentralManagement` → stamped on `Integration.config.centralManagement`, rendered on the integration card after the FMG Proxy row); for a centrally-managed class, device-side description pushes are additionally **mirrored into FMG's database** — wtp `location` into the controller FortiGate's device DB (`/pm/config/device/<fgt>/vdom/root/wireless-controller/wtp`, where AP Manager's per-AP rows live), switch descriptions into the ADOM-level `obj/fsp/managed-switch` table — via plain JSON-RPC `update` (never `set`, never an install) so the next install doesn't revert them, and the reconcile batch-heals FMG-side drift for values the device already agrees on. See TOUCHES.md → services/descriptionSyncService.ts.

## Rule 15 — Location codes ride device descriptions; notes are operator-only

FortiSwitch/FortiAP admin descriptions (managed-switch CMDB `description` / wtp `location` with `comment` fallback — `location` is the sync surface and the only field present in FMG's copy under central AP management) are captured on every FMG + standalone FortiGate discovery cycle into `fortinetTopology.deviceDescription` (`buildDeviceDescriptionStamp` in `discoveryEngine.ts`), and `a:`(area)/`b:`(building)/`f:`(floor)/`r:`(room)/`jb:`(junction box) codes are parsed from them server-side by `src/utils/locationCodes.ts` (effective codes: the `Asset.description`'s codes when it carries any — EXCLUSIVELY, no per-key fall-through, so removing a code from the description removes the node from that group even while the device copy lags a sync cycle — else the device description's; `Asset.notes` is deliberately NOT a source, notes never inform the topology map) to drive Device Map grouping hulls, row clustering, and floor views. **Discovery never writes `Asset.notes` on an existing asset** (the former description→notes mirror and its `notesSyncedFrom` provenance were removed 2026-07); the only discovery-authored notes content is the one-time `Auto-discovered from FortiGate …` boilerplate stamped at asset creation. Interplay with rule 14: with `syncDescriptions` ON, codes maintained in the Polaris description push to the device (Polaris-primary); device-only codes show through only while the Polaris description carries no codes at all.

## Rule 16 — Maintenance windows pause everything; status flips are scheduler-managed

> The notification half of this rule is now one clause of a wider gate — see **[rule 37](#rule-37)**: `assetCanTrigger` tests `monitored` AND this rule's suppression, and every trigger path (the event/change tail included) applies it. Read both before changing either; the suppression semantics below are unchanged.

While a `MaintenanceSchedule` window is active for a monitored asset, the `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` (restored when the last window closes; a manually-set "maintenance" is parked verbatim so exit can't loop). **Parking can only ever hold `active` now**, and that is a consequence nobody costed at the time: business rule 10's unmonitorable set grew to cover `storage` and `quarantined` in 2026-08, `decommissioned` and `disabled` were always in it, and `maintenance` is the window itself — so targeting's `∩ monitored` leaves exactly one status a maintained asset can arrive in. Two integration fixtures here entered from `storage` and `quarantined` to prove parking round-trips a non-trivial value; the widening clamped both to `monitored=false` at create time, they stopped being targets, and this file went red on main for three pushes. The product answer that settles it: a window on a shelved or quarantined device would be a no-op, because a quarantined device already fails every probe by design and a shelved one is not polled at all — there is nothing for a window to silence. `tests/integration/maintenanceSchedules.test.ts` pins both halves (parking from `active`; an unmonitorable status is never entered). `status="maintenance"` stops ALL server-driven polling (`MONITOR_CANDIDATE_WHERE` in `monitoringService` — shared by both the cursor pass and the pg-boss publisher — excludes it; presence-verification pings and `decommissionStaleAssets` skip it too; agent pushes and the operator's explicit Poll Now still work), makes the asset count as DOWN for child dependency suppression (`evaluateSuppression` treats it like an active `dependencyTestUntil` overlay — unless the schedule's `suppressChildren` toggle is off, in which case suppression ignores the maintenance status and the asset evaluates by its frozen `monitorStatus`, so dependents keep monitoring/alerting; OR-ed across an asset's open windows, surfaced as the "Mark dependent devices as down" checkbox on the builder + both ad-hoc paths), and silences notifications for the asset AND for every dependency-suppressed asset (`isSuppressedForNotifications` in `notificationEngine`: readings dropped, `pending` state rows reset so a still-bad condition re-earns its debounce post-window, `firing` rows retired by the suppression sweep below; escalation sends pause). **Discovery/system writers must never write status over a maintenance asset** (Entra/AD sync, FortiSwitch state sync, lease-presence flip, and the `lastSeen`-aging `decommissionStaleAssets` job are guarded; the reconcile self-heals anything missed by re-flipping and absorbing the clobbered value into `maintenanceReturnStatus`). **Deletion-at-source is the one carve-out:** the discovery decommission sweeps (Phase 2a firewalls + its controller cascade onto their managed FortiSwitches/FortiAPs / Phase 2b FortiSwitches+FortiAPs) DO judge maintenance assets and call `releaseAssetsForDecommission` — window closed `endReason="decommissioned"`, parked status cleared, `status="decommissioned"` written in the same transaction (so the reconcile can't re-enter or self-heal-reflip; the `monitored=false` clamp keeps it out of the target set, and the spent ad-hoc schedule self-deletes). Roster/inventory absence is config truth, not reachability (an offline device stays in the FMG roster; a powered-off switch/AP stays CMDB-protected), so a device deleted mid-window must not sit in maintenance and then be restored to `"active"`. An operator status write moving OFF "maintenance" wins: the assets PUT route calls `operatorReleaseAsset` first (windows closed `endReason="operator"`, which suppresses scheduler re-entry for that occurrence). Open `AssetMaintenanceWindow` rows are the restart-safe source of truth; closed rows feed the labeled chart bands. Dashboard surfaces treat maintenance as its own state, never an outage: the NOC feeds (`nocDashboardService`, mirrored by `/summary` monitorAlerts) exclude `status="maintenance"` from every down/warning/stale list — the frozen `monitorStatus` is not live state — and bucket it as `statusCounts.maintenance`; the Status Map dot and Status Summary "Maint" tile paint it purple (matching the assets-page pill). Events: `maintenance.entered` / `maintenance.exited` / `maintenance_schedule.*`.

**A window opening on top of a live alert now ENDS it (2026-08-28).** Suppression used to freeze `firing` rows so that exiting maintenance couldn't double-fire an alert that was already active. What that produced in practice was announced downtime with a red row sitting beside it for the whole window and *nothing able to end it*: the readings that would have recovered the alert are precisely what maintenance stops collecting, so a frozen alert could only outlive the window it was announced for, and an operator looking at the board during a planned change saw exactly the noise the window exists to remove. `clearSuppressedAlerts` (in `notificationService`, the lifecycle side, not the engine) soft-clears every ACTIVE alert whose asset is suppressed — `clearedBy="system:maintenance"` or `"system:dependency-suppressed"` (maintenance wins when an asset is both: it is the downtime the operator announced), one `notification.suppressed` Event each — and releases the `NotificationRuleState` row that owned it, since a `firing` key pointing at a dead notification can never fire again. Three decisions carry it. **It is a handoff, not a recovery** — the same contract as the precedence carve-out (rule 18) and the packet-loss/device-down clear (rule 29): NO reset actions run, because nothing recovered and mailing "resolved" about a device nobody is polling would be a lie; the Event is the audit trail. **The condition re-earns its debounce**: a device still bad when the window closes fires a NEW alert rather than resurrecting the old one, which is the honest reading — the old alert's evidence is a window old, and the pending rows were already being reset on exactly that reasoning. **And it sweeps `Notification` rows, not state rows**, which is why it does not live in the engine's per-rule loops: event and change alerts are created by the event tail's `createMany` with no `NotificationRuleState` at all, so a state-machine-side clear would have missed the automations most likely to have fired on the way into a window (`agent.disconnected`, a firmware change, a discovery failure). Two callers: the `maintenanceScheduler`'s own entering edge, so an ad-hoc "enter maintenance now" clears the board while the operator is still looking at it, and the 60s `evaluateNotificationRules` tick ahead of the rules — the safety net, and the only thing that catches **dependency** suppression, whose flag is owned by the dependency reconciler and has no edge of its own here. Both calls are best-effort: a failed sweep must never cost the fleet a tick of evaluation or leave a status flip half-applied.

## Rule 17 — ARP presence evidence for stale reservations; the sweep is opt-in

Every FMG/standalone-FortiGate discovery cycle already reads each gate's ARP table; sync Phase 7.6 stamps `Reservation.lastSeenArp` (and clears `staleNotifiedAt`/`staleSnoozedUntil`, same re-arm semantics as a live lease) whenever the table binds an active dhcp_reservation's IP to its **reserved MAC** on the owning device — minutes-fresh L2 presence that keeps statically-configured / ICMP-silent devices (which never pull a lease) out of the stale list. `effectiveLastSignalMs` in `reservationStaleService` folds it in as a third real signal alongside `lastSeenLeased` and the correlated `Asset.lastSeen`. MAC match is required (a different MAC answering the reserved IP is not presence), matching is scoped per (fortigateDevice, ip) so overlapping RFC1918 subnets behind different gates can't cross-match, and absence of an ARP entry is NEVER negative evidence (reach depends on routing + firewall policy). The **ARP presence sweep** (`Integration.config.arpPresenceSweep`, DHCP Push tab, default off, FMG + standalone parity) additionally primes each gate's ARP cache right before its table read: `arpPrimeService` fires one fire-and-forget UDP datagram per reserved IP — per-gate targets only, paced batches, ~2s settle inside the FortiOS neighbor-cache GC window — so even quiet-but-live devices resolve into the table. Opt-in because the sweep is IDS-visible.

## Rule 18 — Automation precedence is same-trigger, most-specific-wins

Two automations "watch the same thing" iff their `triggerSignature` matches (asset_metric metric + dimensionFilter / asset_state field + dimensionFilter; host/event/change/composite are exempt, signature `null`). **`monitorStatus` is keyed differently and deliberately** (2026-08-25): by the compared **operator+value** and NOT by the dimensionFilter, because it is a single per-asset column with no reading dimensions — the only filter it can carry is a DEVICE filter, which narrows the asset set rather than the reading. So every `== down` automation lands in ONE group whatever its device filter (they must be able to carve each other out), while `== down` and `== warning` are correctly different things to watch. Two consequences: coverage is now tested as scope AND device filter (`peerCoversAsset` / `carveOutPeerCovers`, so a `hostname matches "core-"` peer only shadows the core switches), and this same group is what decides **whose missed-poll count governs each asset** — business rule 36's down-detection authority rides rule 18's ladder rather than inventing a second precedence system. Note a `monitorStatus == warning` rule no longer shadows a `== down` rule (they were one group before). Among same-signature automations, the more-specific one (higher `scopeRank` on the ladder all assets 0 < device type 1 < OS 2 < manufacturer 3 < model 4 < tag 5 < region 6 < subnet 7 < hostname 8; only positive rules count — negatives/none/notAll broaden; a `region:` tag outranks a plain tag; lifecycle status, assetId + **`interfaceName`** are OFF the ladder — an interface is a component of a device, not a statement of WHICH devices an automation is about, so "switches with a fortilink port" ties with "switches" rather than carving it up) **carves out** the assets it covers from every lower-rank one: `evaluateThresholdRule` drops those readings (no fire), clears any active alert (`notification.superseded`; maintenance clears its alerts too since 2026-08-28, under its own reason — rule 16), and resets pending debounce. Same-rank + same-signature ties both fire. Index built once per tick (`buildShadowIndex`), per-asset test reuses the pure `scopeMatchesAsset`. **A peer's scope may read facts the evaluated rule's scope never asked for**, and coverage is tested against the SAME asset rows the rule loaded: `interfaceName` is resolved out-of-band (`scopeInterfaceIndex`, since joining the interface inventory on a 60s tick is the 2000-asset anti-pattern), so the tick decorates those rows for every peer in the signature group before testing coverage. Leaving that out does not fail loudly — an unresolved leaf reads as "this device has no interfaces", which quietly makes an interface-filtered peer cover nothing (positive operator) or everything (negative one), i.e. a duplicate alert or a silenced one. Authoring-time preview (`previewRule`) warns both directions: `carveOut.carvesFrom` (this specific draft removes N devices from lower-rank automation X) + `carveOut.carvedOut`/per-match `excludedBy` (this general draft's devices already covered by more-specific Y).

## Rule 19 — Severity bands escalate one alert by value, each on its own clock

A numeric automation (asset_metric/host_metric) can stack `severityBands` on the base trigger: tier 0 = `rule.severity` at `trigger.threshold` for `trigger.forDurationSec`, each band a higher `{threshold, severity, operator?, forDurationSec?, actions, escalation}`. **Severities must strictly increase** tier-over-tier (`validateSeverityBands`; UI defaults a new tier one rank up + blocks lowering); tiers **share the base sampling** (aggregation / window / dimensionFilter) but may carry their own ordered `operator` and their own **sustained duration** (both fall back to the trigger's). The value is resolved once and compared to each tier; the **most-severe MET tier wins**, so per-tier thresholds need not be monotonic. **"Sustained for" is per tier, not per rule** — "loss > 5% for 30 min = warning, > 25% for 5 min = critical" is one automation, so a shared `conditionMetSince` can't express it: the engine keeps `NotificationRuleState.bandMetSince` (`{[severity]: epochMs}`, each tier's continuously-satisfied run, rewritten only when a tier enters or leaves) and takes the most-severe tier whose OWN run has outlasted its OWN duration (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure + unit-tested). Consequences that follow from that and are deliberate: a higher tier can fire before the base tier has served its time (each tier earns its own severity); a value climbing between bands never restarts the lower tier's run; a tier that drops out and returns restarts only ITS clock, so flapping into critical never sustains while a steady warning still fires. **De-escalation is immediate** (the lower tier's run is already old) and dropping below tier 0 clears every run. `severityForValue` remains the instantaneous tier-0 membership test; the alert is **one row per asset** whose severity climbs and eases in place. `bandNotify` policy governs delivery: `onIncrease` (default on) runs the entered band's actions; `onDecrease` (default off) runs the destination band's actions; `onResolved` (default on, below tier 0) runs the reuse-the-alert-or-dedicated resolved actions then clears. In the hysteresis dead band (auto reset + `clearThreshold`, value below tier 0 but above the clear line) the alert stays active but **eases to the base severity** — it must not park at a higher band the value no longer satisfies. Each band's own time-escalation is swept band-aware (`escalationChainsForSeverity` in notificationTypes — the band's level chain + its actions' per-action chains, with the empty-band fallback to the base actions mirrored; timers restart from `escalationState.bandSince`, stamped on every crossing). Value-bands (severity) and time-escalation (delivery tiers) are independent axes and coexist. **The BUILDER offers one hold, not one per tier (2026-08-28).** Everything above is the ENGINE's contract and is unchanged — `bandMetSince` is still per tier, a band's own `forDurationSec` is still honoured, and an API-authored ladder can still give each tier its own clock. What changed is what the wizard writes: it renders a single "Sustained for" on the trigger and every tier inherits it, because four holds were four clocks doing one job and the base tier's field (moved inside the base severity group so it would read as that tier's) made the shared hold look like a property of the lowest severity. A rule loaded with per-tier holds LOSES them on the next save from the wizard — deliberately, since the alternative is a rule behaving in a way nothing on screen states. An install that needs "warning for 30 min, critical for 5" writes it through the API. **Where that one hold SITS took two more passes (2026-08-31).** Moved out of the base severity group it came to rest between the first tier and the second and read as the first tier's own — the same misreading in a new place, a number directly above a block being read as belonging to it. It now lives back INSIDE the base severity block, below that block's conditions, and every added tier renders the same field again as a **disabled mirror** (`syncBandDurationMirrors`) carrying the trigger field's value and its label — "History (polls)" on a windowed ratio, "Measured over (polls)" on an aggregate, repainted live as the operator types and as a cadence answer lands. Each tier stating the count it will wait out is what makes "applies to every severity level" visible rather than asserted, and it is what lets the base tier hold the editable copy without that copy reading as the lowest severity's. A mirror hides itself when the trigger states no hold, or has no hold field at all (an all-down-detection tree), where an empty disabled box in each tier would read as a field each tier was meant to fill in. Two consequences follow from the hold now folding away with its block: `data-hold-off` marks a field the TRIGGER switched off so unfolding a severity block can't re-offer it (that is how a CPU automation once rendered a second "Sustained for" captioned about packet loss), and the mirrors read that attribute rather than the field's display, or folding the first tier would blank the number out of every tier below it. That same change recounted every hold and window in the builder in POLLS rather than minutes (see rule 30 for why a reading is the unit that decides anything), and the follow-up (2026-08-29) made the ENGINE count them, because a count the engine measured in seconds was still a wall-clock hold wearing a different label.

**What a hold means now.** A trigger states `forPolls` and a reset states `reset.sustainPolls`; where either is set it is the authority and the engine counts consecutive qualifying READINGS. `forDurationSec` / `sustainSec` remain written as the wall-clock mirror — they are what the sentences and the alert email read, and what sizes the sample window the engine has to fetch to SEE N readings (`lookbackMsFor`, twice the mirror, capped at 6 hours). Nothing is migrated: a rule that states only seconds keeps the old behaviour exactly, until it is re-saved from the builder (which shows a count and therefore stores one).

Sources split two ways, because they have to:

- A **series source** — every sample table, plus the Polaris host's own 30-second metrics — hands the engine its recent readings newest-first (`Reading.series`), and the run is the leading count of qualifying ones (`leadingRun`). Stateless, so it is exact whatever the engine's tick spacing is, and a device that stopped reporting has no readings to count rather than one stale sample re-counted every tick.
- A **current-state source** — the Asset columns (`monitorStatus`, `status`, `consecutiveFailures`, `dependencySuppressed`, `quarantined`), the delete-replaced SD-WAN rule table, the windowed-ratio metrics recomputed per tick, and a composite tree's own outcome — has no series at all, so the run lives on `NotificationRuleState.metRun` / `clearRun` and advances only when that stream's poll anchor moved (`advanceRun`; `lastMonitorAt` for the probe-backed fields, `lastSystemInfoAt` for SD-WAN, the newest leaf reading for a tree). Without that gate the 60-second engine tick would count five "polls" against a device polled every five minutes.

Three consequences worth stating. A run is **consecutive**: one reading back under the line zeroes it, however long it was — this is not the probe loop's leaky bucket (rule 30), which is counting misses outstanding rather than a condition holding. The runs are **zeroed whenever a row returns to `clear`**, or a stale `metRun` would let the next qualifying reading fire immediately and skip the hold. And a **band that states its own `forDurationSec` stays on the wall clock** (`resolveTierLadder` gives it no `forPolls`): per-tier counts would need a per-tier run map on the state row, for a shape the builder cannot produce — every tier that INHERITS the trigger's hold inherits its unit too.

The four failures this replaced, all of them the same bug wearing different clothes: a device that stopped reporting satisfied a hold on ONE reading (the 15-minute "find the latest sample" lookback re-presented it at every tick); a slow-cadence device fired on fewer readings than asked whenever a poll was late; a fast-cadence device could not fire faster than the 60-second tick however short its hold; and "must stay cleared for" had all three problems on the way back out.

<a id="rule-20"></a>

## Rule 20 — Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup

Three operability invariants added by the 2026-08 production-readiness remediation. (a) **Subnet overlap** (rules 1 + 2) is a check-then-insert, so it is only as strong as what serializes the two halves. Every subnet-creating path (`createSubnet`, `allocateNextSubnet`, `bulkAllocate`, the DHCP-discovery create in `discoveryEngine`) now goes through `createSubnetRowChecked` or `lockBlockForSubnetWrites` in `subnetService.ts`, which take a per-block `pg_advisory_xact_lock` BEFORE re-reading siblings; a UNIQUE index on `subnets (blockId, cidr)` is the backstop for the exact-duplicate case. `allocateNextSubnet` retries on a lost race rather than 409-ing, because the caller asked for "any free /N". There is deliberately no exclusion constraint for general overlap — stock PostgreSQL has no GiST-indexable `&&` for `inet`/`cidr`. **The same medicine now covers the `mapRegions` blob** (2026-08-25): every region create / update / delete is a read-modify-write of ONE JSON `Setting` value — load the whole array, change one element, write the whole array back — so two overlapping writers both read the same starting array and the second write silently discarded the first one's edit. That was not theoretical: the Device Map's edit mode saved every changed polygon at once with `Promise.all`, so dragging three regions and clicking Save reliably persisted only one while all three PUTs returned 200 and the toolbar reported "3 regions saved". `withRegionBlobLock` in `mapRegionService` takes a `pg_advisory_xact_lock` (classid `0x504c5255` "PLRU", the next in the PLRS/PLRT sequence) as the first statement of a transaction wrapping the read AND the write; the map now also saves sequentially, so N dirty polygons no longer park N requests on that lock each holding a DB connection. One lock for the whole blob, because the unit being rewritten IS the whole blob — a per-region lock would serialize nothing. Proven by `tests/integration/mapRegionConcurrentWrites.test.ts`, which needs a real database: a mocked Prisma makes the advisory lock a no-op and would pass either way. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret-named string leaves of `Credential.config`, `Integration.config`, `NotificationChannel.config` and `Setting.value` (`utils/secretBox.ts` + `utils/configSecretFields.ts`). The extension is the enforcement seam precisely because several legacy route files still read those models with inline Prisma. **Sealing is per-model; OPENING is all-models**, because Prisma query extensions fire for top-level operations only — a per-model open hook never runs for a relation read like `asset.findUnique({ include: { monitorCredential: true } })`, which is how the monitor hot path loads every credential it polls with, how reservation push loads the FortiGate token, and how description sync loads its integration. So the open pass is its own `$extends` layer (`openNestedSecrets` over `$allModels.$allOperations`) that walks whole results, gated by a zero-allocation `containsSecretField` pre-scan and an `isWalkable` plain-object check so rebuilding a row can't turn its `Date` columns into `{}`. Sealing is a NO-OP without `POLARIS_SECRET_KEY`, and `openValue` never throws — a wrong key degrades to "this credential stopped authenticating", never to an exception on every monitor tick. Raw SQL bypasses the extension; the only raw reader of these columns (`monitorOverrideService`'s `integrations.config #>> '{…,addAsMonitored}'`) touches no secret field. (c) **Backup/restore** lives in `services/backupService.ts`: streamed end to end (never `execSync`/`readFileSync`/`gzipSync`), connection via libpq PG* env vars rather than argv, and the restore wrapped in `timescaledb_pre_restore()` / `timescaledb_post_restore()` in three separate psql sessions with post_restore in a `finally`. A failed pre-update backup ABORTS the update by default (`applyUpdate(password, allowWithoutBackup=false)`) — migrations are irreversible, so a silently-missing backup is the difference between a bad update and an unrecoverable one.

## Rule 21 — SSH host-key verification is opt-in and fails closed

Polaris passed no `hostVerifier` to ssh2 until 2026-08, so EVERY SSH connection accepted whatever host key was presented: agent install (which SFTPs a script and runs it as root), agentless process collection, and the SSH monitor probe alike. `SshConfig.verifyHostKey` enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin` — no pin stores and accepts, a match accepts, a CHANGED key **refuses the connection** and stamps a warning `ssh.host_key.mismatch` with both fingerprints. It is **opt-in, default OFF** (default ON only for newly created credentials), mirroring WinRM's `verifyTls`: turning it on globally would break every install whose hosts were never pinned. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites (`withSshClient` + `monitoringService.probeSsh` — the only two) so they can't drift, and it **fails closed** — an internal error refuses the connection rather than silently skipping verification. Pins are per `(host, port)` in their own table, never on `Credential.config`, because one credential spans a fleet of hosts. Deleting a pin (Integrations → Polaris Agent → Windows SSH Deployment) is the documented recovery for a legitimately rebuilt or re-keyed host and is audited at warning level, since it re-opens first-use trust. **TOFU only detects a key CHANGING** — enabling it against a running fleet pins whatever currently answers, so it is strongest on a greenfield rollout where the pin is taken at deploy time.

## Rule 22 — The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered

An asset known to several discovery sources at once has several competing answers to "where is it?" (an AD OU path, a controller FortiGate, an Azure Arc onboarding, an Intune enrollment), and which one an operator wants to read is a site convention Polaris can't decide. The assets table's **Sources** column (formerly "Server"; the `data-sf-key` stays `_server` so saved presets keep working) renders the operator's `location` when set, else `Asset.learnedLocation`. The priority behind that second half lives in the `assetSourcePriority` Setting (`{order[], integrationPrefix}`, drag-to-reorder on Assets → Settings → Sources, `assetSourcePriorityService`), and it feeds the **projection** — not just rendering — because the column's filter, its sort, "behind FortiGate X" tag/maintenance criteria and the Device Map's per-site narrowing all read `learnedLocation`. The catalogue of contributors is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string (AD `ouPath`, FortiSwitch/FortiAP `controllerFortigate`, fortigate-endpoint device name, vCenter `clusterName`/`hostName`), **label** contributors have nothing location-shaped to say and contribute their own NAME (`arc` → "Azure Arc", `arc-k8s`, `intune`, `entra`) so the column names who knows the device instead of sitting blank. **Azure Arc is deliberately label-mode:** its only location-ish field is the Azure resource group — a billing container whose name ("updatemanager") tells an operator nothing — which stays on the observed blob and the Sources tab. Never contribute the Azure region (it says where the RECORD lives). `polaris-agent` / `manual` / `fortigate-firewall` never contribute; the `fortigate-endpoint` rule stays suppressed when ANY Fortinet infra source exists — fortigate-firewall / fortiswitch / fortiap — whatever the order says (invariant, not preference: a managed device's site label is its own identity or its controller, and the pre-adoption DHCP sighting row outlives the adoption). Propagation is **pull-based** — the projection runs in the discovery process, so `refreshProjectionPriority()` installs the order at boot in every role and at the top of every `runDiscovery`; reordering is **not retroactive**, each integration's assets re-project on its next run. **The default order is closest-to-a-place first**: sighting FortiGate → the label-only cloud sources (arc / intune / entra / arc-k8s) → vCenter cluster → AD's OU path → fortiswitch / fortiap. The gate is the only contributor naming a physical place; an OU path is org structure that reads as a location only because sites tend to name OUs after buildings; fortiswitch/fortiap sit last where rank is inert (those kinds only exist on assets with no competitor). A **source blob may never be built from the projection's own output**, which is the rule this contributor broke twice: `fortigate-endpoint`'s `observed.learnedLocation` used to be copied off `Asset.learnedLocation` at flush time, so it accumulated the render's `<integration>:` prefix one segment per cycle AND, on a domain-joined laptop, laundered AD's OU path into the blob as something the FortiGate had supposedly said (`CENTRALFMG1:OU=Computer Workstation2` in the column, prod 2026-08). The blob now takes the gate name from the discovery pathway that did the sighting.

## Rule 23 — Who owns an IP and how the gate hands it out are two facts, not one

`Reservation.sourceType` answers the first; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers the second. Conflating them is what made a FortiLink-addressed FortiAP unreservable: Phase 3a/3b create a `fortiswitch`/`fortinap` row for **every** managed switch/AP, and the address can come from the gate's own DHCP lease table via the `dhcpByHostname` fallback — so Polaris recorded a dynamic lease as an authoritative reservation (plain "Active" pill, no Reserve action) while the FortiGate's DHCP page reported the same address `Not Reserved`. Phase 5 is the only pass that can see the difference, and before this it had **no branch** for those two source types: the entry fell through to a bare `continue`, dropping the fact every cycle and (silently) breaking the "path-* counters sum to entriesTotal" property of its own summary Event. The Phase 5 infra branch now records the binding via the pure `decideInfraDhcpBinding` (`src/utils/infraDhcpBinding.ts`), writing **only on change** because it runs per DHCP entry per cycle. Three deliberate non-writes there: `sourceType` is never flipped (ownership is unchanged and the row's Phase 5b sweep exclusion + decommission semantics depend on it); `expiresAt` is **never** stamped (a lease carries one, and that would hand these rows to `expireReservations` — a live AP's row would expire on the gate's lease clock, be re-created next discovery, and churn); and `macAddress` is fill-only **from the lease entry**, never from `ap.baseMac`, since only the MAC the gate saw requesting the address is the one a future MAC→IP push could bind. A `"lease"` row is takeover-able by an operator Reserve exactly like a `dhcp_lease` (`isSupersedableByCreate`), and releasing it is a pure DB release — neither unpush branch nor the lease-expiry branch fires for it, so claiming an AP's address never bounces its lease. `"reservation"` and `null` stay authoritative: absence of evidence is not evidence the address is free. Phase 3a/3b's conflict-raise is gated on `reservationBelongsToInfraDevice` (MAC, else hostname, else "Polaris pushed it") — without that, the first operator reservation of an AP's IP would raise a conflict card per AP on the next cycle. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets`, called from the Phase 2a controller cascade, the Phase 2b stale-infra sweep, both asset DELETE routes, the operator decommission branch of `PUT /assets/:id`, and `decommissionStaleAssets` — every call site filtered to `switch`/`access_point`, since the same predicate would otherwise match a Polaris-pushed reservation on an ordinary server): it delegates to `releaseReservation`, so the CMDB unpush + lease expiry + audit Events all come for free, and it is bounded per invocation because that call can perform device I/O and a controller cascade can cover hundreds of APs. **"No longer discovered" is deliberately NOT a release trigger** — an offline AP stays in its controller's roster (business rule 16's config-truth-vs-reachability line), so the release hangs off the existing decommission decision rather than a second staleness rule. `reconcileOrphanedInfraReservations` (6h job) is the backstop for a decommission that happened while the gate was unreachable; its pure `classifyOrphanInfraRow` releases on an explicitly decommissioned device, but for "no device found at all" — which is also what a transient discovery state looks like — releases only rows Polaris never pushed, because a false positive on a pushed row would delete a reserved-address entry on a live gate. **Optionally, Polaris writes the binding itself** (`infraReservationPushService`, a post-sync discovery pass): double-gated on `config.pushReservations` (the transport nucleus, re-checked server-side via `integrationPushEnabled`) AND `config.autoReserveFortinetInfra`, both default off, on the DHCP Push tab of BOTH Fortinet integration types. It turns a managed device's dynamic lease into a real `reserved-address` entry on its own gate — **pinning an address the device already holds, so pool occupancy never changes** (this is not a mechanism for claiming free space; the pool-capacity question is deferred because Polaris stores no DHCP range and has no subnet-utilization alerting). This is the only DHCP write in Polaris that happens on a schedule rather than because an operator acted on one IP, so it is bounded per cycle (`RUN_CEILING`), low-concurrency, MAC-from-the-lease-table-only, read-back-verified, and never re-attempts a row carrying push state — a permanent refusal is recorded as `pushStatus="failed_permanent"` + `pushError`, which both drops the row from the candidate set and surfaces the device's own message in the IP panel, instead of being retried every cycle. The push pointers it stamps are exactly what the lifecycle release's pinned-unpush branch needs, so decommissioning the device removes the entry.

## Rule 24 — Alert on the device's own alarm bit before inventing a threshold for it

Two boolean asset_metrics exist, and which one to reach for is decided by whether Polaris already collects the fact. **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus` — the per-sensor bit the FortiOS REST `sensor-info` and SNMP `fgHwSensorTable` collectors ALREADY write on the normal hardware-sensor cadence, and which the asset System tab already renders as its STATUS column. It needs no operator configuration, works on every transport that fills the column, and shares `hwSensorValue`'s `sensorClass` / `sensorNamePattern` dimensions (same `hwSensorFilterMatches` predicate), so a rule can target one named sensor or a whole class. Prefer it over a threshold on the reading: the device knows its own per-model limits, and for a fan tray or a PSU the health lives in the bit rather than in any comparable number (a FortiGate PSU reports `1` forever and signals failure only through the alarm). **`customStateValue`** (business rule/`AssetStateSample`, state probes) is the general mechanism for status OIDs Polaris does NOT already collect — any vendor, any table — and is deliberately NOT the answer for Fortinet hardware sensors: pointing a probe at `fgHwSensorEntAlarmStatus` re-walks an OID the collector already walks, into a second table, to alert on a value sitting in the first one, and gives two copies of one truth that can disagree. The shared invariant is the NULL rule: `alarmStatusToFlag` (`src/utils/hardwareSensors.ts`) returns `0 | 1 | null` and the engine excludes `alarmStatus: null` **in SQL**, because a source that publishes no alarm bit (the FortiAP-controller path) must not have its absence mapped to 0 — that would assert health nothing ever checked, clearing live alerts and making every such sensor look verified-healthy. An unrecognized non-empty status maps to 1, not null: it's a claim something is off-nominal, and dropping it would go silent on a real fault. **The ENTITY-SENSOR-MIB walk now DOES publish the bit**, from `entPhySensorOperStatus` via `entityOperStatusToAlarm`: `nonoperational(3)` → `"alarm"`, `ok(1)` → `"ok"` (needed so a cleared fault resolves), and — the load-bearing case — **`unavailable(2)` → NULL, never `"alarm"`**, because an empty SFP cage reports unavailable and a port with no transceiver in it is not a fault; mapping it to alarm would fire on every unused port on the switch. Note the bit means something narrower here than on the Fortinet paths: it reports whether the SENSOR is functioning, not whether the reading is inside its limits. For "this optic is degrading but not yet dead", use a severity-band automation on the dBm `hwSensorValue` instead (business rule 19). **The same invariant now holds one layer down, at the varbind decoder.** `snmpVbToNumber` (`services/monitoringService.ts`) used to fall through to `Number(v)` for anything it didn't recognize, and `Number(null)` is a perfectly finite **0** — so every OID a device does not publish decoded as a confident zero rather than as "no reading". `snmpGetScalar` returns exactly that `null` for an error varbind (noSuchObject / noSuchInstance / endOfMibView), which made the failure indistinguishable from a healthy device reporting zero, and worse than merely wrong: because `0` is not `null`, the HOST-RESOURCES-MIB fallback in `collectTelemetrySnmp` (guarded on `cpuPct == null`) never ran to correct it. A FortiSwitch whose empty `Asset.model` had misrouted it onto the FortiGate OIDs therefore charted a flat 0.0% CPU and 0.0% memory forever, with no error anywhere (prod 2026-08-31, FSR-112D-POE; the misroute itself is fixed by `fortinetClassHint`). Absence and empty now decode to `null`; a genuine zero is still believed, since the distinction being drawn is "said zero" vs "said nothing". The visible consequence is that a series which used to sit convincingly at zero now shows a GAP — which is the honest reading, and looks like data loss precisely because the old behavior was silent.

## Rule 25 — An alert you can't acknowledge from where you read it isn't really acknowledgeable — and who acknowledged it is a session, not a link

`POST /alerts/acknowledge` has existed since the notifications feature shipped, gated `alerts:write`, with **zero frontend call sites**: the asset-details Alerts tab and the mobile Alerts list both rendered alerts read-only, so `escalation.stopOn: "acknowledge"` — offered on every escalation chain the wizard builds — could in practice only ever be stopped by clearing. Acknowledgement now reaches the three places an alert is actually read. **In-app** (the Alerts tab + the mobile list) calls the existing route. **Email and web push** carry a link to the alert's own acknowledge page.

That link was a single-use token for one release, and the reason it is not any more is worth stating first, because the token version was not obviously wrong. `NotificationAckToken` was a 192-bit secret minted per (recipient, channel) at delivery fan-out and redeemed at a PUBLIC `/ack/:token` route mounted above `session()` and `csrfMiddleware`. It bought one genuinely good thing: acknowledging from a phone's mail client in a single tap, with no password. Everything else it bought was cost. **The token had to name a person**, because the row it writes records WHO acknowledged — so a composed email, which renders ONE body, could not carry a link that worked for more than one reader. The first shape of that compromise withheld the button unless exactly one To address was user-owned with cc/bcc empty, which withheld it from essentially every real automation. The second shape kept the body and split the MESSAGE: `planComposedEmails` fanned the To line out into one delivery row per recipient, each with its own token. That worked, and it multiplied the send — one SMTP message per person, one chart-rasterization pass per person until a per-drain memo was added to stop it, and a To line that no longer showed the reader who else was on the alert. It also meant address-book contacts and typed addresses got a deliberately button-less copy of the same mail, because there was no account to file the acknowledgement under. And the whole apparatus had to be defended: the GET kept inert against mail-gateway prefetch, the route mounted above the session middleware so a Safe Links scan could not mint a `connect-pg-simple` row, a live permission re-check at redemption so a role downgrade invalidated links already sitting in mailboxes, a 30-day TTL, an hourly prune, and a sha256 digest chosen over the house argon2id pattern specifically because argon2 on the alert fan-out path would spend seconds of blocked CPU per large alert.

**Polaris already has a way to know who someone is.** The link is now `/alert-ack.html?id=<notificationId>` — it names the ALERT and carries no credential of any kind. `alert-ack.html` is listed in `protectedPages`, so an unauthenticated reader is bounced to the login page and lands back on the alert signed in; a reader who already has a session never sees a login form at all. Identity is that session, and `alerts:write` is enforced by the same `POST /alerts/acknowledge` route the in-app surfaces use. The trade is explicit: an emailed acknowledgement now costs a login when you do not already have one, and in exchange the entire token apparatus — table, TTL, prune job, unauthenticated route, permission re-check, per-recipient fan-out — is gone, along with the last unauthenticated state-changing surface in Polaris.

Six decisions carry it. (a) **The email is ONE message again.** `expandDeliveries` resolves `{ack}` once per alert (`fillComposedAckUrl`) and writes a single delivery row whose `target` is the joined To list; Cc/Bcc are just Cc/Bcc. The chart memo (`RenderMemo`) stays — it is no longer load-bearing for email, but one alert still drains as several rows when a rule has more than one notify action, or a web-push target with a row per enrolled device. (b) **Every recipient Polaris cannot identify gets the button; one it can is asked first.** A contact or a typed address gets the same working link; whether they can act is decided at the page, and the honest answer to "can this person acknowledge" is a login prompt rather than a missing control. This is the one place the new design is weaker on its face — someone forwarded the mail can now see that an acknowledge page exists — and it costs nothing, because they still cannot get past the login. That reasoning stops where Polaris already knows the answer (2026-08-28). An address belonging to an account whose role holds `alerts` below `write` gets the same alert with the button taken out: the page can only refuse them, and a button that exists to be refused is noise in an inbox that already carries a lot of alert mail. The cost is a bounded, partial return of the fan-out the token design forced — `ackCapabilityByAddress` maps address → the role's level and pure `splitAckVariants` splits To/Cc/Bcc into an ack copy and a no-ack copy, so a send is TWO messages at most however many people are on it, and a message with no read-only recipient still writes the single row it always did. Two shape rules keep both copies deliverable: a variant that loses its whole To line promotes its Cc into To rather than dying on the empty-To guard, and a variant left holding only Bcc goes out one message per address so the blind list stays blind. **Unknown means capable, in both directions** — an address with no account keeps the button, and where two accounts share one address (`User.email` is neither unique nor required) whichever may act decides, because withholding from someone who may acknowledge is the worse error. The button-less body is the SAME substitution an install with no `POLARIS_PUBLIC_URL` already produced (`fillComposedAckUrl(body, null)`), so the pruning was already written and already tested; the one gap it exposed was an operator template with a bare `<a href="{ack}">` instead of the shipped template's cell-wrapped button, which is why `pruneDeadLinks` grew a bare-anchor fallback. Push is simpler, because a subscription always has an account behind it: the payload carries no `ackUrl` at all and `sw.js` renders no Acknowledge action. And what this withholds from is a genuinely read-only role, not merely someone an admin never got round to promoting — migration `20260828030000_alerts_ack_write_capable_roles` raised `alerts` to `write` on every role already holding write or fullwrite on any other function key, which is the whole "everyone except read-only" policy expressed once, in the matrix, where the in-app Ack button reads it too. (c) **Loading is a GET and acknowledging is a POST.** Outlook Safe Links, Proofpoint and every other mail gateway fetch each link before a human sees it. That was the sharpest edge of the token design and it survives here for free: the prefetch carries no session, and even with one the page acts only when someone presses the button. (d) **The page gate is `alerts:read`, not `write`.** Someone whose role can see alerts but not acknowledge them reaches the page and is told so; bouncing them to "/" would leave them on a dashboard with no explanation of where their link went. (e) **A web-push Acknowledge action OPENS the page** instead of acting from the tray. One tap became two, and in exchange the note gets typed (a tray button has no text field, which the token design had to special-case with a recoverable `"note_required"` answer) and the acknowledger is a real session. It shares the tray with at most one other button: `Notification.maxActions` is 2 on every browser that renders actions, and the overflow is dropped from the END, so `sw.js` lists candidates in priority order and slices — Acknowledge, then **Open device**, then **Ignore**. Acknowledge leads because it is the only one that changes state and stops an escalation. Open device is second because it goes somewhere the body tap does not: the tap follows the server-chosen deep link to the alerts LIST, right for triaging several alerts at once and two taps away from the one box this alert is about. Ignore is last, and rides only a `requireInteraction` alert, because it is the one candidate whose job the platform already does — a Windows toast carries its own close button, and a non-sticky notification clears itself on the OS banner timer. Ignore sends nothing at all: a tray button carries no session, so it cannot mean the alert was handled, and the alert goes on repeating and escalating exactly as if the push had never been read. (f) **`GET /alerts/:id` answers 404, not 403**, when the caller's region scope excludes the alert — which alerts exist outside your regions is not something a route should confirm.

The return trip is a **cookie**, not a `?next=` query parameter. `utils/loginRedirect.ts` drops a 10-minute `polaris_next` when `app.ts` bounces an unauthenticated request off any protected page, and every login path consumes it. There are five ways into Polaris (local, the TOTP second step, SAML, OIDC, Entra App Proxy) and three of them hand the browser back on a URL Polaris does not control; worse, the SSO callbacks call `req.session.regenerate()`, so a session-stashed target does not survive the very step it would have to survive. The cookie is deliberately not HttpOnly, because `login.js` reads it after a local login — safe by construction, since `safeNextPath` reduces whatever comes back to a same-origin PATH and refuses `/login.html` itself, so the worst a forged value achieves is landing an operator on another page of their own Polaris.

**And the note is per-automation optional or mandatory** (`NotificationRule.requireAckNote`, the wizard's in-app alert card, default off): "someone looked at it" is enough for a noisy interface flap, while a critical outage wants the operator to say what the problem was and what they did. It is enforced in **`acknowledgeNotifications`**, not in the dialog, because that one function backs every read surface — the modal's required field, the ack page's `required` textarea and the mobile note sheet are each just the local courtesy. Three decisions follow: a **batch is refused whole** (the route takes ONE note for every id, so acknowledging the note-free half under a success toast would leave the alerts that mattered open — the bulk dialog therefore demands a note when ANY selected alert's automation does); the ack page treats the resulting **400 as form validation**, re-rendering with the reason rather than becoming a dead end; and a **rule-less alert reads false** (a test fire, or one whose automation was deleted — `ruleId` is SetNull), because there is no policy left to enforce and refusing to let anyone close it out would be worse than a missing note. The flag rides each row of `GET /alerts`, `GET /alerts/:id` and `GET /assets/:id/alerts` as a flat boolean (`withAckPolicy`) so no surface has to fetch the automation to know how to ask. And **the note has to be readable somewhere**, or requiring it is theatre: it rode both list payloads for free but was rendered by nothing until 2026-08, so the answer to "what was the problem and what did you do" was stored on the row and shown to no one. The asset-details Alerts tab's **Acknowledge** column is that reader — note first, acknowledger and time under it, and "No note" rather than an em dash when someone acknowledged in silence, since a blank there reads as an alert nobody has touched. The acknowledge page shows it back too, once there is one. The dashboard widget and the mobile list still show only who; they need no backend change to follow.

<a id="rule-26"></a>

## Rule 26 — A generated MAC is a placeholder until the network proves otherwise

A DHCP reservation is a MAC→IP binding, so reserving an IP for a device that isn't racked yet needs a MAC before there is a device to supply one; the IP panel's **Generate** button synthesizes one. Before this, that MAC was `02:` + 5 bytes of `Math.random()` from two duplicated client-side copies, marked as synthetic nowhere — so the entry sat on the gate matching nothing, the device arrived, DHCP'd with its real MAC, missed the reservation and took a pool address, and the reservation looked correct on both sides while doing nothing forever. **The prefix is the marker, and the only one.** `reservationMacPlaceholder` (Setting, default `02:0F:5E`, Server Settings → Identification) is what makes a stored MAC recognizable as synthetic — there is deliberately no boolean column on Reservation and no Conflict row, because the prefix is visible on the FortiGate's own reserved-address table, so an operator reading the gate can tell which entries are waiting on a device without consulting Polaris. `normalizePlaceholderPrefix` (`utils/mac.ts`) accepts 1–5 hex octets and **rejects any prefix that isn't locally-administered unicast** — that rejection is load-bearing: pointing this at a real vendor OUI (`00:50:56`) would make that vendor's genuine devices look like placeholders and hand discovery permission to overwrite them, whereas a locally-administered prefix cannot be assigned to a vendor, so no factory MAC can fall inside the placeholder space. (`AA:BB:CC` is legal here for the same reason — 0xAA has the LA bit set.) **Adoption** (`placeholderMacAdoptionService`, discovery Phase 7.7, double-gated on `config.pushReservations` + `config.adoptDiscoveredMac`, both default off, FMG + standalone parity) replaces such a MAC with the real one when the gate reports a device at that reserved IP, and re-pushes the corrected binding. Evidence is the **ARP table** and **device inventory** only, keyed `(fortigateDevice, ip)` like Phase 7.6 so overlapping RFC1918 subnets behind different gates can't cross-match; ARP wins over inventory (a live L2 binding beats a cache whose `is_online` lags), an online inventory row beats an offline one, and two ARP rows disagreeing about one address drop it permanently — a duplicate IP on the wire is not something to burn into DHCP config. DHCP lease entries are deliberately NOT evidence (a device whose MAC doesn't match never gets the reserved address, so it can't appear there) and neither is `Asset.ipAddress` (not device-scoped). Five guards make the unattended overwrite defensible: the stored MAC must be a placeholder, the observed MAC must **not** be (never swap one synthetic value for another — that also makes the legacy `02` prefix safe, since a genuine `02:` device presents that same `02:` MAC in ARP and is skipped rather than churned), it must differ, it must not already be held by another active reservation in the same subnet (FortiOS would refuse it *permanently*, parking the row), and the row must not be at `failed_permanent`. The gate write goes through `updatePushedReservation` — **device first, verified by read-back, Polaris second** — so the two views can't diverge; a `pending` row skips device contact and lets the retry tick carry the new MAC. Bounded **per RUN, not per call** (`AdoptionBudget`, 50): in FMG mode `syncDhcpSubnets` runs once per managed gate, so a per-call ceiling would multiply by gate count. Audited per row (`reservation.mac.adopted` / `reservation.mac.adopt_failed`). **Changing the prefix is not retroactive in either direction** and the settings card confirms before saving. Related fix in the same change: Phase 6's DHCP-entry MAC overwrite (a bare `prisma.reservation.update` with no push) is now **skipped for rows carrying push pointers** — it was silently diverging Polaris from the gate for any pushed row, and left unfixed it would have adopted the placeholder away in Polaris while the gate kept it forever.

## Rule 27 — A logo is picked by theme; a name is text only when the picture doesn't already say it

The shipped Polaris art is theme-paired (`public/img/brand/polaris-{horiz,vert,symbol}-{dark,light}.png`): the dark-theme wordmark is light blue and the light-theme one near-black, and the symbol's wedges are white on one and navy on the other — so painting the wrong variant makes the logo *disappear* rather than merely look off. Horizontal art on the login card, vertical in the sidebar. The two variants of a pair are **normalized to one geometry** (the vendor exports were not — the vertical light star was ~39% larger relative to its wordmark), so a theme flip swaps the file and moves nothing on screen; re-exported art has to be re-normalized, see ARCHITECTURE.md → `public/img/brand/`. **One module decides** — `public/js/brand-logo.js` (`PolarisBrandLogo.resolve/applyTo`), consumed by the desktop login, the mobile login, the sidebar and the Customization preview, because four surfaces each deriving the rule is four chances to disagree; it picks by theme **FAMILY, not by theme id** — since the three-theme cutover there are `morning`, `noon` and `nightfall` but still only two sets of art, so `morning` and `noon` both take the light files with no third asset and an id comparison would silently miss every daylight theme but the one it names. `PolarisBrandLogo.currentTheme()` answers that family (deferring to `app.js`'s `isLightTheme` where it exists — brand-logo.js loads *before* app.js and also runs on the login page, the mobile SPA and the dash wallboard, which never load it at all), and it repaints on the `themechange` event `_setTheme` fires **and** on a `data-theme` MutationObserver, so a theme set by any other means (the pre-CSS boot, the OS listener, another tab) is covered too. A morning → noon flip changes no family and forces no re-fetch. It also registers the `prefers-color-scheme` listener that keeps a user who has **never** chosen a theme tracking their OS. With nothing in `localStorage["polaris-theme"]` every bootstrap (`js/theme-init.js`, `app.js`, `mobile/app.js`, `dash-boot.js`) resolves the OS preference, landing on `morning` for a light preference and `nightfall` otherwise — and each of them now VALIDATES a saved value against its known list first, because the retired `dark`/`light` ids name no token block and trusting one would render the whole install unstyled. Nothing is persisted by that path: staying unsaved *is* the "follow my system" state, and the theme picker is the opt-out. **The Application Name is a caption for a custom logo only.** The Polaris art carries the wordmark, so printing the name under it says it twice — `showName` is false whenever the shipped art is in play, and `appName` may therefore be stored EMPTY (`displayAppName` is the fallback for the surfaces that must print one: page titles, the PWA manifest, the acknowledge page). The operator's `subtitle` is their own line of copy and renders either way. **Placement is per surface** (`logoOnLogin` / `logoOnSidebar`, both default on, Server Settings → Customization → Logo): switching one off returns THAT surface to the Polaris mark without discarding the upload. **The accent** (`logoAccent`) composites the theme's `polaris-symbol-*.png` onto the bottom-right of the operator's logo at ~50% of its longest side (`ACCENT_FRACTION`, clamped to half its shortest so a wide banner isn't swallowed) — rendered **server-side** by `brandLogoService` and served from the public `GET /server-settings/branding/logo-accent.png`, not as a per-surface CSS overlay, so the geometry can't drift between login, sidebar and mobile. It renders per theme (`?theme=`), which both picks the right symbol variant and gives the `<img>` a new URL to re-fetch on a theme flip; otherwise the path is fixed (the upload route reuses one filename), so it answers `no-cache` + a strong ETag over the source mtimes **and the theme**, and 302s to the plain logo whenever there is nothing to accent.

## Rule 28 — The Windows build is the authority; the product name is not

Microsoft never updated the registry key `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProductName` when Windows 11 shipped, so it still reads **"Windows 10 Pro" on every Windows 11 client**. That key is what WMI's `Win32_OperatingSystem.Caption` and `systeminfo` read, which means this is not one broken integration but *every* source at once — AD's `operatingSystem`, Intune/Entra (which collapse it to a bare "Windows" anyway), and gopsutil's `Platform` inside the Polaris Agent. So the projection's priority order cannot fix it: whichever source wins is equally wrong. The **build number** is always right (it comes from `CurrentBuild`, not the frozen display string), so `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the family from it and labels the pair with the release operators actually speak in: `"Windows 10 Pro"` + `"10.0.22631.7219"` → `"Windows 11 Pro"` + `"23H2 (10.0.22631.7219)"`. **Family from a threshold, release from a table** — deliberately different mechanisms: `build >= 22000 ⇒ Windows 11` never goes stale, so a build shipped after this code was written still gets the right family, while the release table does go stale and an unlisted build therefore keeps its RAW `osVersion` rather than being guessed at. **Windows Server is excluded entirely** (any os string containing "server"): its ProductName is already correct, and build 26100 is BOTH Windows 11 24H2 and Windows Server 2025, so the threshold would relabel a 2025 server as a workstation. Applied at **write** time — in `projectAssetFromSources` AND in the `db.ts` Asset hooks (the catch-all for the inline writers) — not at render, because the Assets table's OS/Firmware **filter and sort**, CSV/PDF export, `os`/`osVersion` tag criteria, maintenance criteria and automation scope conditions all read the stored columns: an "os contains Windows 11" rule is only true if the column says so. Two properties keep that safe to run on every write: it is **idempotent** (a re-write of its own output is a no-op, or the label would nest — `"23H2 (23H2 (…))"`), and it **reads no row** (the build comes from whatever `osVersion` the same write stages, so the monitor hot path pays nothing). Normalizing only on the way to the DB would make `projectionDriftService` report permanent os drift, which is why the projection normalizes its own output too. Not retroactive: existing rows correct themselves when their integration next re-projects them (rule 22's pull-based precedent), and there is no backfill job.

## Rule 29 — One outage is one alert: packet loss is what happens while the device is answering

`probeLossPct` is the only metric whose INPUT is failed probes, which made it the only one that could raise a second alert about an outage `monitorStatus == down` already owns. Two gates now bound it, and both are about the same distinction — *lossy* is not *dark*. (a) **Only an ANSWERING device reports loss**: `assetIsAnsweringProbes` (notificationEngine) admits `up` and `warning` and nothing else — `passive` included in the exclusion (business rule 36): a dark passive device sits at 100% loss indefinitely and there is no asset-down alert to supersede the loss alert, that alert being precisely what is missing, so admitting it would park a permanently-firing, never-clearing alert on every device an operator just told Polaris to stop judging. `warning` is deliberately IN — it is 1..`failureThreshold`-1 consecutive failures on a device still replying, i.e. the state a lossy-but-alive device lives in (an alternating pass/fail device never reaches `down` at all), so gating on `up` alone would silence the feature's whole purpose. `down` and `recovering` are OUT (`recovering` is the tail of the same outage — asset-down is still live until successes reach the threshold), as are `unknown`/null (nothing measured yet). The filter sits in the `probeLossPct` resolver so the composite-trigger path and the wizard's preview inherit it from one place; `evaluateThresholdRule` separately **clears** a live loss alert on an asset that stopped answering (`clearedBy="system:device-down"`, `notification.superseded` Event with `reason:"device-down"`) rather than freezing it — the carve-out's handoff semantics, because freezing is exactly what used to park a packet-loss alert next to the asset-down alert for the whole outage. No reset actions on that path (the alert isn't recovering; mailing "loss resolved" about a device that just went dark would be worse than silence). Metric-scoped via `ANSWERING_ONLY_METRICS` — every other metric is derived from SUCCESSFUL polls, so a dark device simply stops producing readings. (b) **The ratio starts at the first successful probe inside the window**, not at the window's leading edge (`probeLossQuery.ts`: a partitioned `min("timestamp") FILTER (WHERE "success")`, older samples trimmed) — a device unreachable for part of the window had no probes there to lose. Without it a device recovering from a 55-minute outage reads ~93% loss the moment it answers again and keeps alerting until the outage slides out of the window, i.e. it alerts *because* it came back, for a full window (an hour, on a 60-minute one); with it the first clean probe reads 0% and the alert clears. The cost is that a leading failure run isn't counted even when it was a blip rather than an outage — accepted, since the alternative is an arbitrary blip-vs-outage threshold and the blip re-enters the ratio on the next tick anyway (the anchor only discards samples OLDER than the first success). Both gates apply to the NOC Packet Loss widget too, through the one shared query — with one display-only divergence: the widget passes **`includeFullyDown`**, so an asset with NO successful probe in the window reads **100%** instead of being dropped by the anchor (before this it VANISHED from the widget, which reads as "no loss" — the opposite of the truth). The engine must never pass it: `assetIsAnsweringProbes` already keeps `down`/`recovering` assets out of its id list, and a 100% reading reaching a `probeLossPct` automation would fire exactly the second alert this rule exists to prevent. **And it starts no earlier than the end of the last outage** (2026-08-21): the first-success anchor only helps while the outage is still running at the window's leading edge — once the device has been back long enough for a healthy sample to precede the outage, the window's first success sits BEFORE it, the anchor goes inert, and every failed probe of the outage is back in the denominator. Same false alert, same full window: a 5-minute outage inside a 60-minute History reads ~8% loss for an hour *because* the device recovered, and the device-down supersede in (a) covers only the outage itself, not the window after it. So `Asset.recoveryStartedAt` — stamped by `recordProbeResult` on the success that ends an outage, i.e. the probe that takes `monitorStatus` out of `down`/`unknown` — is a second anchor, and the measurement starts at `GREATEST(first success, recoveryStartedAt)` (Postgres's `GREATEST` ignores NULLs, so a device that hasn't recovered inside the window behaves exactly as before; the pure JS mirror both the alert-email loss chart and the writer's predicate share is `utils/probeLossAnchor.ts`). **Only an outage-ending recovery stamps it — a `warning`->`up` recovery deliberately does not**, and that asymmetry is what keeps flapping measurable: a lossy device passes through `warning` constantly, so stamping there would restart the window every few probes and report ~0% forever. The stamp is never cleared (it ages out of the window on its own and the next recovery overwrites it) and never backfilled. **Both anchors bound the READING, not the picture** (2026-08-28): the alert email's loss chart applies them to its caption and plots the whole window regardless. Anchoring the line too — the behaviour until then — mailed a packet-loss graph that began at the moment the device came back, so the outage that caused the page was missing from the chart sent to explain it, and an axis labelled `-60 min` carried four. What made trimming look right was the fear of a wall of loss under a caption reading 0 %; the answer to that is to say where the number starts, not to delete the evidence, so `probeLossSeriesFrom` returns `measuredFromMs` whenever the anchor excludes plotted samples and `sparklineSvg` draws it as a dashed `measured` rule (with the same clause on the text summary, for a reader whose client blocks images). The engine's own reading is untouched — `probeLossQuery` still trims, and it is still the number the caption prints. (c) **The window is HISTORY; sustain is its own optional knob.** A ratio needs a denominator, so `windowSec` isn't a smoothing choice layered on a reading — it IS the reading, which is why the wizard labels it **History (minutes)** (mandatory, default 15, range 5..1440 = the schema's 24h ceiling) and hides the aggregation control (the engine ignores it). Since 2026-08-20 a SECOND field, **Sustained for (minutes)** (`#tf-sustain-min` → `forDurationSec`, optional, 0 = fire on first crossing), puts the hold axis back as its own control — "loss over a 60-minute History, sustained over the threshold for 10 minutes" is now expressible — and severity tiers keep their own hold clocks like any other numeric metric (they still share the base's History window per rule 19; the engine's generic debounce + `bandMetSince` machinery needed no change). The sustain field is rendered on every device/host trigger but hidden unless a ratio condition is present, so nothing else can pick a value up from it. The metric class is declared server-side as `WINDOWED_RATIO_METRICS` and published on `/automations/schema` as `windowedRatioMetrics`, so the builder doesn't hardcode it. Before the History rename the one field was "Sustained for" and a `latest` ratio leaf routed those minutes to `forDurationSec`: an automation reading "loss over 60 minutes" actually measured over the engine's 15-minute floor and then held for 60 — the two knobs meant one axis and neither said so. A stored legacy rule reads its `forDurationSec` minutes back as the History the operator meant (and shows sustain 0 — `triggerSustainMinutes` takes the hold ONLY from a rule that also stores a window, or one save would double the minutes into both axes), and re-saves as a window. The engine correspondingly uses `windowSec` EXACTLY for this metric (`probeLossWindowSec` in notificationTypes — 5 min floor, 15 min default when absent — SHARED with the alert-email loss chart) rather than `max(windowSec, DEFAULT_LOOKBACK)`, which every other metric needs to be sure a `latest` reading finds a sample. Granularity follows probe count, not the window: at a 60s interval a 5-minute History is ~5 probes, so loss can only read in 20% steps — the field's hint says so, since that is PRTG's 5-pings-per-scan coarseness arrived at from the other direction. (d) **The ICMP loss sampler is what buys resolution back** (business rule 30): during `warning`/`recovering` a 10s ping adds rows to the same window, so a 15-minute History divides ~90 samples rather than ~15. Its rows count toward the ratio and nothing else. Note what that means for the reading: the sampler runs BECAUSE a poll failed, so its samples are not a uniform rate — a lossy device's loss climbs on real ICMP failures, while a one-off transport hiccup followed by clean pings reads LOWER than the poll-only ratio would (1/22 rather than 1/15). That cost turned out NOT to be accepted — the bias is why the sampler is **currently disabled** (rule 30's `LOSS_SAMPLER_ENABLED` kill switch, 2026-08-20), so today the ratio divides the response-time poll's own samples at the configured cadence and reads in the coarse steps the wizard's History hint describes; a uniform N-pings-per-scan sampler remains the unbiased alternative if the resolution is ever wanted back.

## Rule 30 — Confirmation is the configured cadence's job; ICMP only fills in the loss ratio

`monitorStatus` reaches `down` when N missed polls are OUTSTANDING against the operator's configured transport at the operator's configured `intervalSeconds`. For a device that simply stops answering that is still N misses in a row, so time-to-down is unchanged at `N × intervalSeconds`; what changed is the intermittent device, and the bucket that made that work is the paragraph below. **N is the covering automation's `missedPolls` (default 3), not a Monitor Settings value** — see business rule 36; `failureThreshold` on the settings tiers is dormant. What this rule is about is the CADENCE half, which is unchanged: it still comes from the monitor-settings hierarchy — 3 minutes at a 60s cadence, **15 at 300s** — and the figure the monitor-settings card reports is the figure you get. `resolveProbeIntervalSec` (monitoringService, pure + unit-tested) therefore applies exactly ONE clamp: **dependency suppression** (parent dark ⇒ 2× interval, never poll harder into an upstream outage; a `disabled` stream has nothing to slow). **This replaced the fast-confirm re-probe** (2026-08-17 → 2026-08-19), which re-probed a mid-confirmation asset at `fastConfirmIntervalSec` so confirmation cost ~35s regardless of cadence. It was removed because it made the counters a function of a second, tighter cadence that operators could not see in the number they had configured, and because the resolution it bought during a run is worth more as *loss data* than as a faster verdict. `fastConfirmIntervalSec` stays as a **dormant** column (migration `20260817000000`; dropping it would cost an irreversible migration for no gain) read by nothing, and is no longer surfaced on the three monitor-settings cards. What replaced it is the **ICMP loss sweep** (`src/utils/lossSweep.ts` deciding who and how often, `src/utils/burstPing.ts` doing the measuring, `runLossSweepFor` running it, on the existing `lossSample` cadence / pg-boss queue / worker pool and `POLARIS_MONITOR_LOSS_SAMPLE_WORKERS` — those names deliberately kept, since renaming them would orphan a persisted queue and an operator-set env var for nothing). It went through one failed shape first, and that history is the rule. **v1 (2026-08-19) was a per-asset SAMPLER** — a single ping every 10s while an asset sat in `warning` or `recovering` — and it was **disabled the next day**: sampling only while probes were already failing oversamples failure, so the alert's reading diverged visibly from the wall-clock average its own chart drew (rule 29d). There is no way to correct that bias after the fact; the only fix is to stop creating it. **v2 (2026-09-01) is a UNIFORM BATCHED SWEEP** and ships enabled: every eligible asset, every cycle, a burst of 5 echoes, whatever state it is in. Uniform spacing is what makes the ratio mean what an operator thinks it means, and it is affordable only because the pinger is batched — one `fping` process per 500 targets, bounded by burst period rather than host count, so a 2000-asset fleet costs 4 process spawns where v1's shape would have cost 2000. (fping is optional, not required: RHEL ships it only via EPEL and Windows Server has no build, so a bounded per-host fan-out keeps loss CORRECT where it is absent, just slower — `resolveSweepIntervalSec` floors the cadence at what the installed pinger can actually finish, because publishing sweeps faster than they drain grows the queue without bound.) Rows carry `probeKind="icmp"`, a NULL `responseTimeMs`, and the new `packetsSent` / `packetsReceived` pair that lets ONE row describe a burst — which is what makes loss a ratio of PACKETS rather than of poll outcomes, and so what finally separates it from down detection. Anchored by `Asset.lastLossSampleAt`, stamped in one `updateMany` for every asset actually attempted. It **never calls `recordProbeResult`** — it cannot move `consecutiveFailures` / `consecutiveSuccesses` or `monitorStatus` — because ICMP does not authenticate the device it reaches: a second transport voting on `down` would make the state mean whichever of the two answered last, an ICMP-blocked host would false-`down` on its first transient miss, and a device whose SNMP agent had died would never confirm down at all. **`down` assets are now IN the sweep**, reversing v1: that exclusion was a corroboration argument (an uncorroborated ping reply from a host that had taken over the address would drag a dead device's loss down from 100% to something reading like congestion) and it was load-bearing only while loss shared a stream with down detection. It no longer does, and the engine's own answering gate already stops a down device raising a loss alert (rule 29a), so excluding them would only punch a hole in the series at the moment an operator wants to read it. **Dependency-suppressed assets are in it too**, reversing v1's COST argument — five extra packets inside a sweep that was already running, where the old shape would have put every asset behind a dead gate into its own 10s ping loop; their failures are still marked explained via `AssetMonitorSample.dependencyDown` (rule 38b), which is a rendering question rather than a sampling one. The only exclusions left are not `monitored` (covering rule 10's four unmonitorable statuses), `maintenance` (rule 16's one status that keeps `monitored` true while polling stops), and `responseTimePolling === "disabled"` — rule 30 already reads that as the operator saying do not reach out to this device, and it has to extend to ICMP or the setting means less than it says. Note `agent` is NOT excluded any more: "I use the agent for status" must not silently mean "do not measure this network's packet loss". **`probeKind` splits the readers:** the ONLY all-kinds readers are `probeLossQuery` (both modes) and `alertChartService`'s loss chart — that is the point of the sampler — while every response-time reader filters to primary (`probeKind IS NULL OR 'primary'`; NULL is the pre-feature value and means primary). That list is the engine's `responseTimeMs`/`uptimeSec` metrics, the alert-email RTT chart, `sampleHistoryService`'s detail tier + `readLastMonitorSuccessAt` (an ICMP reply is not a success of the monitored service), the NOC response-time ranking, the Device Map's traffic light (a fixed-COUNT window, which mixed rows would silently shrink from ~10 minutes to ~100 seconds mid-incident), **and every rollup** — folding incident-only rows into 400-day aggregates would make historical loss non-comparable across time, so the sampler's resolution lives and dies with the detail retention window. The three monitor-settings cards keep the DERIVED **"Declare Down after (seconds)"** entry (`_polarisMonDownAfterCalc`, shared by render and the live sync, unit-tested), now computed as `interval × (threshold − 1) + probe timeout` and writing `failureThreshold` — operators think in "down after 30 seconds", and storing that as a second setting would just be a number that could disagree with the product of the two that already exist. In cursor mode the sampler's due-set is capped per pass (`LOSS_SAMPLES_MAX_PER_PASS`, 200, logged on truncation) because `runMonitorPass` awaits the whole pass under the light tick's guard and a site-wide outage must never delay the probes that decide whether those assets are down; pg-boss mode has its own pool and a 15s job expiry instead. Both due-set paths call the one resolver and mirror the sampler's due-check (`computeDueWork` + the pg-boss publisher in `jobs/monitorAssets.ts`); their due-sets are contractually identical, so a second copy of this arithmetic is exactly how they would drift.

**The counter is a leaky bucket, not a run length (2026-08).** A missed poll adds one to `Asset.consecutiveFailures`; an ANSWERED poll takes one back, floored at zero. It stopped being a literal consecutive count because a run length forgets an outage the instant one packet answers, and that cuts both ways. A device losing two polls out of every three never reached a verdict in either direction — every single answer reset the run to zero, so the count sawtoothed between 1 and 2 forever and the chronically lossy device stayed invisible to down detection while looking healthy on the pill. And a device already at `threshold - 1` was handed a completely clean slate by one lucky poll, so an outage that had been one probe from being declared started over from nothing. The bucket keeps the debt: three misses then an answer is still two outstanding, and the next miss lands on three rather than on one. **The LEVEL decides the verdict and the outcome of the current probe only breaks the tie below the threshold** — `cf >= threshold` is `down` whatever this probe did, `cf > 0` is `warning` on a miss and `recovering` on an answer, `cf == 0` is `up`. Letting a success win outright would mean a device dark for an hour (cf=60) reads `recovering` on one answered packet out of sixty, and since a down automation tests `monitorStatus == down`, that one packet would clear the alert. Four consequences. **Recovery is now symmetric and free**: draining 3 → 2 → 1 → 0 takes exactly `threshold` answers, the same number of confirmations `consecutiveSuccesses` used to count, so the machine no longer consults it (the column is still written — it is a true fact and it is charted — it simply decides nothing). **`recovering` no longer means “was down”**: it means answering with misses still outstanding, which is reachable straight out of `warning`, so a device that missed twice and then answered is visibly climbing back instead of sitting in amber. **`consecutiveFailures` is no longer a run length**, so the automatable field was relabelled “Missed polls outstanding” — the KEY is unchanged because stored automations reference it, but a rule reading `>= 5` now fires on five outstanding, which a flapping device can reach without ever missing five in a row. And **“Declare Down after” is a floor, not a promise**: `interval × (threshold − 1) + probe timeout` is exact for a device that simply stops answering, and is the fastest possible verdict for one that answers intermittently, which is the honest way round. Mirrored client-side by `PolarisMonitorStates.replay` in `public/js/monitor-states.js` — the ONE browser copy, read by the Last-30-min strip, the desktop response-time chart and the phone's, each of which used to decide it privately — and server-side by `probeOutageService.replayProbeStates` for the alert-email charts; pinned in both directions by `tests/unit/monitorStatusStateMachine.test.ts`, whose parity block reads `monitoringService.ts` itself — the stub in that file is a hand-copy, and it silently pinned the old machine through this very rewrite until the guard was added.

**The bucket gained a CEILING, and an answered probe became unconditionally `recovering` (2026-09-01).** Both halves of the paragraph above were right about what they were solving and wrong about what they left unbounded, and the two defects met on the response-time chart.

The first is the debt. Nothing capped the climb, so `consecutiveFailures` tracked the LENGTH of the outage rather than the operator's definition of one. A FortiGate dark overnight at a 60 s cadence came back at `cf` around 480, and since a success only ever takes one back, it owed 480 answered probes — eight hours — before it could read `up`. Its down alert holds through `down`/`recovering`/`warning` (`DOWN_ALERT_HOLDING_STATES`), so the alert kept repeating hourly and escalating to the L2 recipients for the whole of the following morning, about a device that was answering every poll. The paragraph above defends the unbounded climb explicitly — "a device dark for an hour (cf=60) reads `recovering` on one answered packet out of sixty" — and that concern is real; the mistake was paying for it with an unbounded debt when the alert layer already handles it. `recovering` is a HOLDING state, so one lucky packet clears nothing either way.

So `nextFailureBucket` locks the level at `bucketCapFor(threshold, recoveryPolls)` — the larger of the missed-poll count and the covering automation's reset count — the moment a miss carries it to the threshold. Recovery costs exactly that cap, however long the outage ran: a four-minute outage and a four-day one are the same climb, and the climb is the number the operator wrote down. A miss anywhere in it re-locks the bucket at the cap, so a flapping device still cannot walk itself out of an outage. `MAX_MISSED_POLL_BUCKET` (100) is the absolute ceiling and the passive device's cap, matching the `missedPolls` maximum so no covered asset is ever capped by the constant rather than by its own rule.

The second is the colour. The verdict rule read "the LEVEL decides" without qualification, so a probe that ANSWERED while the bucket sat at or above the threshold was `down`. Defensible for a verdict — the asset genuinely is down until the debt drains — but the response-time chart has no way to paint an `ok` point in the down colour (`_chartPointColor` offers an `ok` point exactly two answers: the series colour or the recovering blue), so those probes fell through to the plain series GREEN. A long outage drew red, then GREEN, then blue, then green, and read as though the device had recovered, broken, and recovered again. The Last-30-min strip directly above it colours straight off the same replay and drew them RED, so two surfaces stacked on the same screen described the same probes in opposite terms — precisely what that shared vocabulary exists to prevent.

With the bucket capped, an answered probe during an outage is unambiguously the device climbing back, so `monitorStatusFor` returns `recovering` for ANY answered probe with `cf > 0`. The level still decides what a MISS means. Nothing downstream loosens: the alert ends at `up`, which is when the drain has served the reset count.

Two clean-ups fall out. `consecutiveSuccesses` now decides nothing at all — the bucket's own level is the whole of the verdict AND of the recovery arithmetic — so `owesRecoveryConfirmation` and the `Asset.awaitingRecoveryConfirm` bit it read are retired (rule 36). And the machine moved OUT of the inline block in `recordProbeResult` into two exported pure functions in `utils/monitorStatus.ts`, which is what let `tests/unit/monitorStatusStateMachine.test.ts` stop hand-copying it — that copy had already silently pinned a retired machine once, through the very rewrite that introduced the bucket.

Existing rows self-heal: `nextFailureBucket` clamps with `min(cap, cf)` before it moves the level in either direction, so an over-cap row converges on its own automation's number at its next probe of either outcome. `jobs/clampFailureBucket.ts` sweeps them at boot anyway, for the readers that reach the column before that probe lands — the strip's tooltip, `runsHeavyCadences`, and `consecutiveFailures` as an automatable `asset_state` field.

**A probe may also decline to be a reading (2026-08).** `ProbeResult.skipped` is neither a hit nor a miss: no `AssetMonitorSample`, no counter movement, no state transition — only `lastMonitorAt`, so the cadence keeps its spacing instead of re-firing on every tick. It exists because of the vCenter polling method, where the thing that answers for a device is not the device. `readVcenterAsset` splits two outcomes that look identical from the outside: vCenter ANSWERED and this VM was not in the answer (deleted at source — a real finding, so the probe fails and names it), versus Polaris could not ASK at all (vCenter down, credential rejected, integration disabled). Counting the second as a miss would declare an entire virtual fleet down at the same instant on a hypervisor-manager hiccup, and a fleet-wide simultaneous outage alert is the one alert nobody can act on. The distinction is the same one rule 38 draws for a dependency-explained miss — Polaris knows why it has no reading — except there is nothing to chart here, because nothing was measured.

**The second skip: `responseTimePolling === "disabled"` (2026-08-28).** For a while the vCenter case above was the only one, on the reasoning that every other transport talks to the device itself, where failing to reach it IS the measurement. That reasoning is sound and it does not cover `disabled`, which is not a transport at all — it is the operator saying *don't poll this*. Nothing was measured, so it is a skip by the same definition.

It had been a *failure*, and the mechanism is worth recording because it is a gap in an otherwise uniform pattern rather than a wrong decision. Every stream's queue publisher checks its resolved method before enqueueing — `lldp` and `storage` and `processes` all do, inline. The response-time probe's push did not. So `disabled` was queued like any other value, reached `probeAsset`, matched no dispatch branch, and fell through to `Unknown polling method "disabled"` — a failed `ProbeResult`. `recordProbeResult` guards `skipped` and `agent` and had no reason to guard a third thing, so it wrote a failed `AssetMonitorSample` and advanced `consecutiveFailures`. An operator switching Response Time off therefore watched the device march to `down` over the next N polls, with the alert naming an outage that was not happening. The one place that already had it right was `utils/lossSampler.ts`, which excludes `null`, `"disabled"` and `"agent"` explicitly.

The fix is a shared pure predicate, `responseTimeProbeShouldQueue` in `utils/pollingCompatibility.ts`, called by BOTH publishers — `computeDueWork` and the pg-boss publisher in `jobs/monitorAssets.ts`, which are a required lockstep pair and are exactly the kind of duplicated condition that drifts. `probeAsset` additionally returns a `skipped` result for `disabled`, which is not redundant: it covers operator-triggered `/probe-now`, and it covers a `disabled` stored in a JSON tier (`manualMonitorSettings`, an `Integration.config` per-class block) that no publisher-side gate can be sure it has seen. **`"agent"` deliberately still queues** — `probeAsset` returns a synthetic success so the probe counter keeps incrementing under `transport="agent"`, and `recordProbeResult` early-returns before any DB write; dropping it from the queue would silently change that metric.

<a id="rule-31"></a>

## Rule 31 — The login page is the way back in, so restricting it is opt-in and must refuse to lock you out

"Skip login page" redirects unauthenticated visitors on PROTECTED pages straight to SSO, but `/login.html` is deliberately NOT in `protectedPages`: it is the recovery path when the IdP is down, and local + LDAP accounts reach it by typing the URL. That leaves the password surface reachable from anywhere, which some installs don't want. `loginAccessConfig` (`{enabled, ipScope, allowedCidrs}`, Server Settings → Web Server → Local Login Access, **default off**) restricts it by source IP, resolving through the same `utils/ipScope.ts` the Dash wallboard gates on. Six decisions carry it. (a) **Both halves or neither**: the gate covers `/login.html` AND `POST /auth/login` + `/auth/login/totp`, because the form is a plain POST to a JSON API — gating only the page is cosmetic, the endpoint gate is the control. (b) **The two refusals differ deliberately**: the page is DROPPED (socket destroyed, no response — the dashServer stealth posture, so a scanner can't confirm a local login path exists), the API answers the SAME generic 401 a wrong password gets, since "you're on the wrong network" is a fact worth learning. Every blocked POST writes a warning `auth.login.blocked_source` Event, bounded by the existing 10-per-15-min login limiter mounted above it. (c) **SSO is never gated** — SAML, OIDC and App Proxy must keep working from anywhere, and that is exactly what makes restricting the password path survivable. (d) **LDAP is gated, because it shares `POST /auth/login`** — an install whose remote users bind against LDAP should leave this off or scope it to include them; the "Skip login page" checkbox now says so. (e) **It fails OPEN** (`isLoginSourceAllowed` swallows a settings read error): a DB blip must not become the lockout the feature prevents, and no attacker can induce one. The PUT's anti-lockout guard is the mirror of the rising-edge SSO check on `skipLoginPage` — it refuses a scope excluding the admin's own `req.ip` and names the address it saw, and it restricts new LOGINS rather than live sessions, so a too-narrow save is still undoable from the open session. (f) **It is only as true as `req.ip`** — behind two proxies with a one-hop `TRUST_PROXY`, `req.ip` is the INNER proxy's RFC1918 address, so an "rfc1918" scope would admit the entire internet while reading as enforced. That is why the GET returns `callerIp` and the card prints it: the failure is invisible without it.

<a id="rule-32"></a>

## Rule 32 — A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives

Unchecking "reset when the trigger is no longer true" used to leave only *timed* and *manually only* on a single-condition automation: the custom-condition builder was composite-only (`validateRuleV2` refused a `reset.condition` on any other trigger), so the two things an operator actually wants — a different recovery value, or recovery measured on something else — had no home. The mode is now offered on every trigger with a continuous condition (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event`/`change` fire on an instant and are still refused, client and server), and unchecking the box lands on it **pre-seeded with the trigger inverted** — same comparator flip `resetSentence` has always rendered (`invertedLeaf`; a 0/1 flag flips its VALUE, not its comparator), extended to trees by `invertedTree` (**De Morgan** — group operators flip alongside each leaf, which is what keeps the result expressible in an and/or-only vocabulary). Severity bands are ignored: every tier recovers at tier 0, so the base condition is the only one there is anything to invert. Four decisions carry it. (a) **The tree is the SOLE recovery authority while firing** — the trigger falling away does not clear the alert and the trigger re-meeting does not cancel the reset's sustain timer (`recoveredSince` belongs to the tree). That contract already existed for composites; `evaluateThresholdRule` now honors it too, in a dedicated pass after the readings loop rather than inside it, because the tree's leaves need not be the trigger's metric at all — an alert whose trigger metric stopped reporting must still be able to clear, where the auto path deliberately freezes. That pass **re-reads the firing rows from the DB** rather than trusting the pre-loop `states` snapshot the carve-out / device-down / vanished sweeps have since invalidated, so a row cleared as superseded this tick can't then be "recovered", and a row that only just fired can't recover in the tick it fired. Suppressed assets stay frozen. (b) **Resolution is DIMENSION-FIRST with a per-asset fallback** (`resolveResetTruths`): a per-mount or per-interface alert whose reset leaf sits on that same dimension space clears independently of its siblings, while a leaf on a device-wide metric (CPU, memory, monitor status) reports nothing at `assetId|port2`, falls through to the ANY-dimension fold composites use, and therefore clears every alert on the device together. Both halves are wanted — "clear port2 when port2 recovers AND the box's CPU is under 70" evaluates each half where that half lives — so the wizard says which one the operator is building instead of picking for them. (c) **Kind coherence is enforced on single triggers too**, not just composites: a device trigger with a `host_metric` reset leaf (or the reverse) resolves against assets that can never report it, so the tree reads permanently false and the alert could only ever be cleared by hand. (d) **Reset leaves inherit the trigger's measurement window** — the reset step has no window control and must not grow one (rule 29c), so an aggregated reset condition is measured over the same period as the trigger; when the trigger reads `latest` there is no period to average over and the save is refused with a message that says so, rather than the trigger step's message pointing at a field that isn't there.

**(e) The two triggers a condition is refused on get the counterpart EVENT instead (2026-08).** "They reset on a timer or by hand" was the honest answer only for as long as the alternative was a condition tree, and it produced automations that lie: the seeded "Agent disconnected" rule cleared itself after four hours whether or not the agent ever came back, so the Alerts tab said the fleet was healthy on the strength of a clock. An event automation has no reading to recover — but it usually has a recovery EVENT, because Polaris writes both halves of the pair itself (`agent.disconnected` / `agent.connected`, `integration.discover.error` / `.completed`, `agent.upgrade_failed` / `.upgrade_succeeded`). `reset.mode = "event"` is that pair, and `TRIGGER_TYPES_WITH_RESET_EVENT` is deliberately the exact COMPLEMENT of `TRIGGER_TYPES_WITH_RESET_CONDITIONS`: a continuous trigger already recovers on its own reading, and letting an unrelated Event clear a live threshold alert would hide a device still over the line. Four decisions carry it. **Same-subject is not configurable** — the clear is keyed on the identity the notification already stores (`assetId` when the event names an asset, else the resource label), because one agent reconnecting says nothing about another's, and offering a toggle would only offer a way to get it wrong. **An event that both fires and clears a rule only fires it**: a glob wide enough to match its own recovery (`agent.*` on both sides) would otherwise clear the alert it just raised, every tick, forever, so a rule that matched an event as a trigger drops that event's reset hit. **Resets apply after the batch's own fires land** — within one 1000-event batch a disconnect and its reconnect can both arrive, and the disconnect genuinely happened, so it is raised, delivered, then cleared rather than swallowed. And **the recovery pattern is prefilled, not guessed**: `RESET_EVENT_SUGGESTIONS` maps trigger pattern → counterpart and is published in the builder catalog, so the wizard fills the field from the server's own list rather than the browser inventing a verb — a new event automation whose action has a known counterpart starts on this mode instead of on a timer. Existing installs are carried forward by the seed job's V4 one-shot, which repoints ONLY rules whose pattern has a known counterpart, that are still on a timer, and that the operator has never edited (`updatedAt === createdAt`) — an edited timer is a decision, and changing when someone's tuned alert clears is worse than leaving it on a clock.

**And `cooldownSec` is not a reset at all — which is why it is gone.** It sat on the reset step from the beginning, where it read as part of how an alert clears; it decides how often a NEW alert may be raised and does nothing to one that is already up. Moving it to the Actions step's in-app-alert card, beside the other two properties of the alert RECORD (`requireAckNote`, `repeat`), fixed where it read but not whether it earned its place: sitting inches from "Repeat this notification", it invited operators to reach for it to answer a question repeat answers better, and its own help text had to spend three clauses saying what it does NOT limit (reminders, escalation, an alert already up). It was retired from the builder in 2026-08.

The DATA went with the control, and that pairing is the rule. The engine still enforces the column, so removing only the field would have left rules holding a suppression nothing on screen states and nothing in the UI can edit — an automation silent for twenty minutes with no surface anywhere in Polaris able to explain why, which is worse than either keeping the control or dropping the behaviour. `jobs/clearNotificationCooldowns.ts` nulls it fleet-wide behind a one-shot marker, and writes its audit Event FIRST: the Event names every affected rule and its old value in seconds, because the UPDATE is what makes those numbers unrecoverable and an operator who wants the suppression back has nowhere else left to read it. One Event for the sweep rather than one per rule, so fifty cooled-down automations can't push a day of unrelated history off the 7-day retention window.

What survives is the column and the two engine checks, **dormant** — the `failureThreshold` precedent from business rule 36. An API caller may still set a cooldown deliberately; the wizard simply never reads one back and writes null on every save, so it cannot outlive the next edit in the builder. The list row's enable/disable toggle, which PUTs the whole record, still carries a stored value through unchanged — that toggle must not be a way to silently discard configuration its operator never opened.

<a id="rule-33"></a>

## Rule 33 — A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login

ICMP proves a NIC answers and SNMP/SSH prove a management plane answers. Neither proves the thing the device exists to do still works: a web server that has lost its backend still completes the handshake and still returns 200, with an error page in the body. The **HTTP check** is one GET against the device's own address, up/down decided by the status code and optionally by a string the response body must contain (`utils/httpCheck.ts` decides, `probeHttp` in monitoringService owns the socket). It shipped as a POLLING METHOD and was **retired as one in 2026-08**; it is now a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType = "http"`). The move is about where a check DEFINITION belongs: as a polling method it had to ride an `http`-typed Credential, which made the thing that answers "how do I log in to this vendor" also carry "which path, expecting what" — so a second path meant a second copy of the same password, and rotating the password meant editing every path. Keyed by manufacturer + optional `modelPattern` instead, it varies on the axis a check actually varies on: every Axis camera answers the same VAPIX path, and a blank model pattern means every device of that manufacturer. Eight decisions carry it. (a) **The body match is the load-bearing half**: a 200 whose body doesn't match FAILS, with the missing content named. There WAS a `failOnMismatch` toggle letting a mismatch pass anyway — it made sense while this drove `monitorStatus` and reachability-only semantics were a reasonable ask, but a widget only RECORDS an outcome and an automation decides what "down" means, so a mismatch stored as a PASS would make `expectBody` decorative (nothing downstream could tell the two apart). It is stripped on save; a laxer rule is expressed by leaving `expectBody` empty and judging on the status code. (b) **Status is judged before content**: a 401 is a broken credential, not missing content, and blaming the body sends the operator to the wrong field. (c) **Redirects are never followed** — a 302 to a login page is the single most common way an HTTP health check reports "up" about a device serving nothing; an operator who wants the 3xx sets `expectStatus` to it. (d) **The body is capped** at 64 KB and the request torn down at the cap, which bounds both a device streaming a log file at the check path and the text an operator-authored `regex` runs against — that pattern is not analyzed for backtracking (nothing static can be); `contains` is the default for the same reason, and a truncated miss SAYS it was truncated. The regex is COMPILED at save by `validateHttpCheckDefinition`, the SAME function the Test Connection flow uses, so a check cannot pass a live test and then be rejected when it is saved. (e) **The credential is authentication and nothing else**, with **no "none" mode**: an unauthenticated check is a widget with no credential attached, which is the same outcome without an empty row that still reads as configuration. `credentialId` is `SetNull` — deleting a credential must not silently delete the check that used it. (f) **The auth scheme is STATED, not guessed.** `authMode` (`bearer` | `basic` | `digest`) is explicit because Basic and Digest carry the same username/password pair, so nothing stored could distinguish them — and the obvious inference (try Basic, fall back on a 401) would send the password in cleartext to any device that answered a Digest challenge, which is precisely the exposure Digest exists to prevent. **Digest is a handshake, not a header** (`utils/digestAuth.ts`, RFC 7616): the response hash is keyed on a server-issued nonce, so `probeHttp` fires bare, reads the 401 challenge and re-fires exactly ONCE — never a loop, because a server rejecting a correctly-computed response will reject it again and retrying past that turns a wrong password into a request amplifier aimed at the device; the second request inherits what REMAINS of the probe timeout. The nonce is deliberately NOT cached: that would cut the steady state to one request but requires a strictly-increasing `nc`, trading a cheap doubling of a cheap request for a replay-shaped failure that only appears under concurrency. It matters for exactly the devices this exists for — Axis OS answers VAPIX with Digest and 11+ disables Basic by default; cameras, PDUs and older BMCs are the same story. (g) **It no longer moves `monitorStatus`.** Each scrape writes a 0/1 to **`AssetStateSample`** (alertable through the existing `customStateValue` metric with no engine change) plus the round-trip time to `AssetCustomWidgetSample` as a gauge, so a slow-but-passing endpoint is visible before it starts failing. The 0/1 is written PASS OR FAIL — the opposite of the state-PROBE rule, which drops an unreadable row because 0 there is a positive claim of health about hardware that may not exist; here a failed request IS the reading, and dropping it would make an outage indistinguishable from a device nobody checked. The gauge is written only on success (a failed request has no meaningful duration). Up/down for such a device therefore comes from whatever transport its responseTime stream uses — usually ICMP. The check also runs INDEPENDENTLY of the SNMP widget gate: an HTTP check must not depend on whether the device also answers SNMP, and a failed SNMP session no longer aborts the pass. `Asset.httpCheckPath` still overrides just the path, for the single device whose endpoint sits elsewhere. (h) **`netGuard` is deliberately NOT applied** — every other outbound-HTTP path in Polaris (automation `api_call` actions, webhooks) SSRF-checks its target because the URL is config pointed at arbitrary hosts, whereas this target is the monitored asset's own private address, the same one the SNMP / SSH / WinRM probes already dial, so a guard rejecting RFC1918 would reject the entire feature. It is also happy to dial a NAME rather than an IP (`dnsName || hostname` when there is no `ipAddress`): a TLS check against a name is the check an operator means, since the cert and any vhost routing are keyed on it. **Tailoring a check is a first-class flow**, because the expectation is a string that has to be picked OUT of the device's response: `POST /credentials/test` accepts a full check definition alongside the credential and returns `httpDiagnostics` — request line as dialed, status, content-type, byte count, cap flag, match verdict, the auth schemes the device asked for, and a 4 KB body excerpt — so the loop is point it at a device, read the body, paste a distinctive string into Expected content, re-test, then save the settled values onto the widget. The response BODY is deliberately kept out of the `credential.tested` audit Event (arbitrary device output would ride every pg_dump and syslog forward), and no response header beyond `content-type` is returned, since a full dump would put a live `Set-Cookie` into the modal.

<a id="rule-34"></a>

## Rule 34 — An active scan finds things; a separate grant adds them

Every other discovery pathway in Polaris asks something that already knows the device (a controller, a directory, a hypervisor, a tenant). A **Discovery** (`NetworkScan`) instead sweeps addresses the operator names, which makes it the only Polaris feature that touches hosts it has no prior relationship with — so the posture matters more than the mechanism. Six decisions carry it. (a) **Scanning and adopting are separate grants.** Authoring and running ride the `networkScan` key; `POST /network-scans/:id/adopt` chains `assets:write` on top (the `PUT /application-map/discovery` precedent). A role may therefore be allowed to find out what is on a range without being allowed to put it in inventory, and the wizard renders that state rather than discovering it at the POST — Export and Save work, **Create assets** is absent with a reason. A `read`-level caller gets a read-only walkthrough, since a scan run by one operator is legitimately handed to another to adopt. (b) **It is opt-in and IDS-visible, and says so.** There is no scheduler and no shipped default range: a scan happens because an operator pressed a button. `arpPrimeService`'s file header already warns that an unannounced sweep of every reserved IP is what IDS dashboards flag, and this is more aggressive than that sweep. The wizard does NOT say so — an operator-removed banner (2026-08-25): an operator who reaches a screen headed "which addresses should Polaris sweep" already knows they are scanning, so the warning read as noise on every visit while the posture it describes is enforced by the mechanism (no scheduler, no shipped default range, a separate grant) rather than by being read. Pacing, batching, a hard target cap and swallowed per-target errors all follow that service. (c) **Some addresses are excluded regardless of what the operator typed** — loopback, link-local (including the `169.254.169.254` cloud-metadata address), multicast and unspecified: the `netGuard` blocklist minus its RFC1918 allowance, since RFC1918 *is* the point here. They are filtered out of the expansion and COUNTED in `droppedTargetCount` alongside over-the-cap truncation, because silent removal reads as "the range is clean". (d) **New addresses only.** A responder whose address an Asset already carries is excluded server-side and reported as a count, so "nothing new" is distinguishable from "nothing there". The corollary is deliberate and worth stating so it doesn't read as an oversight: **a re-run enriches nothing** — it is a way to find what has appeared, not a sync. (e) **No `network-scan` sourceKind.** Adopted assets are created exactly like the manual `POST /assets` path (fields inline, `ipSource="manual"`, the `db.ts` extension minting the `manual` AssetSource row), because `projectAssetFromSources` has ZERO rules for a kind outside its union: such a row would contribute nothing to the projection while `projectionDriftService` compared projection against the stored row, i.e. a drift-log generator. Adding rules instead would put a one-time scan blob in competition with a later agent for hostname priority, which is the wrong outcome. Scan provenance goes where discovery already puts it — the one-time `Asset.notes` boilerplate plus an audit Event. (f) **SNMP goes through the gate, always.** `withSnmpGate(host, port, …)` is not optional here: many switch and AP SNMP agents are single-threaded, and a scan that skips it contends with the monitor loop's probes on the very hosts Polaris already polls. Identification reuses the one exported probe surface (`probeCredentialAgainstHost`) and the exported `snmpWalkRaw` rather than reaching into the module-private per-transport probes.

<a id="rule-35"></a>

## Rule 35 — The GAL is a mirror, not a source of truth — and Polaris only ever deletes what it wrote

Polaris could already SEARCH the organization's Global Address List live: one typeahead query fanned out to Microsoft Graph and LDAP, merged, and **persisted nothing**, so only an address an operator actually picked became a stored `Contact`. That design was deliberate and this rule reverses it, which is worth stating plainly rather than quietly overwriting: the header of `directorySearchService.ts` argued that a bulk sync lands the entire employee roster — names, addresses, titles, departments, phone numbers — in Postgres with its own retention, backup and audit-exposure surface, to make a typeahead marginally faster. What changed is the ask. Alert recipients and device ownership are chosen from the address book, and curating that book by hand for a company of this size is not something anyone will keep up with; a directory that is already the system of record for who works here should be able to fill it. So the roster is now stored, and the whole rule is about what it costs and what bounds that cost.

**What lands where.** Every non-excluded GAL entry becomes a `Contact` row carrying primary SMTP address, display name, job title, department and phone, plus a per-source `observed` blob in `DirectoryContactSource` holding the same fields and the AD distinguished name or Entra object id. All of it rides every `pg_dump` the install produces, including the off-host backup copies. None of it may reach `Event.details` or the logs — those are readable by anyone holding events access and are shipped off-host by the syslog (CEF) and SFTP archivers, so the sync's own Events carry COUNTS ONLY. The one deliberate exception is `contact.adopted`, which names the address exactly as `contact.created` already does: a single act by a person is audited by name, bulk machine activity is anonymous. Do not "fix" that asymmetry. Granting Graph tenant-wide directory scopes, and accepting the retention posture, are decisions for a human before the toggle is switched on.

**(a) Provenance decides deletion.** This is the `TagAutoAssignment` / `RegionTagAssignment` pattern, with one adaptation forced by `Contact.email` being UNIQUE: a synced row and a hand-added row for the same address cannot coexist, so provenance governs the DELETE half only, and the CREATE half is handled by never writing over a claimed address. A person present in both AD and Entra owns ONE contact with TWO provenance rows, and the contact dies only when the last one goes. Because `email` is unique, a synced row also physically BLOCKS an operator from creating that person by hand — which is why creating or editing over a synced address ADOPTS the row (origin → `manual`, `createdBy` stamped, provenance deleted in the same transaction) rather than failing. Adoption is what preserves this rule's own guarantee: an adopted row has no provenance, so the reconcile will never remove it. Deleting a synced row is refused outright with a 409 naming the exclusion filter and the adopt path, because a delete would succeed and then be silently undone by the next run — leaving the operator believing the address was gone. Reaching the adopt path already requires `fullwrite` with no extra code, since synced rows carry `createdBy = null` and `assertOwnership` refuses a null `createdBy` at write level.

**(b) A Polaris account or a curated contact wins.** SSO-provisioned users (SAML, OIDC, LDAP) have addresses that are also in the GAL, so without this the sync would mint a duplicate entry for every colleague who can already log in. The claimed-address set is recomputed each run — `Contact where origin = 'manual'` unioned with every `User.email`, compared case-insensitively because `User.email` is nullable, non-unique and not normalized — so an account created AFTER the first sync retires the synced row on the next run rather than coexisting with it forever.

**(c) An empty read is ambiguous, so it never wipes.** The same lesson as `persistMacTable` and `persistInterfaces`: a source that answered but returned nothing is indistinguishable from a source that has nothing, and the two want opposite handling. A revoked Graph grant, an expired secret or an unreachable DC would otherwise present as "everyone left the company" and empty the address book in one pass. So a run that scanned zero entries, or whose delete set exceeds the guard, skips the deletion half entirely, records it in the summary, and raises the Event to warning.

**(d) Visibility is gated on `automationManagement`, not `contacts`.** Every built-in role holds `contacts` at read or better, so gating synced rows on that key would gate nothing: any account could enumerate and export the entire company directory. `automationManagement` is seeded `fullwrite` for admin and assetsadmin and `none` for readonly, networkadmin and user, so it does real work. The live GAL fan-out takes the SAME gate, because it serves the same people from the same directory a query at a time — gating the stored copy alone would be a gate in name only. Both FILTER rather than 403, the posture `/search` and `/dashboard/noc-summary` already use; and a gated caller who asks for ONLY the synced rows gets an EMPTY page, never the manual rows, because answering a question nobody asked reads as a broken filter rather than as a boundary.

**(e) Counts, never names.** See "what lands where" above: the run Event reports scanned / created / updated / deleted / excluded and the dominant exclusion reason, and names nobody. Per-row Events are not written at all — twenty thousand of them would flood the 7-day retention table AND put the roster into `Event.details`, which is precisely the exposure this rule spends its other four invariants bounding.

<a id="rule-36"></a>

## Rule 36 — The automation decides what "down" means; a device no automation covers is never judged

Down used to be a Monitor Settings value: `recordProbeResult` compared `consecutiveFailures` against a `failureThreshold` resolved through the (integration, assetType) tier hierarchy. That put the number that decides an outage in a settings card scoped by integration and asset type, while the thing operators think of as "my down alert" — the automation, with its device filter — could not touch it, and there was no way to say "core switches are down after 2 missed polls and page the NOC; workstations after 10 and stay in-app". Now a `monitorStatus == down` automation carries a **`missedPolls`** count and that count IS the definition of down for every device it covers (`downDetectionService.resolveDownThreshold`, called once per probe). **Precedence is business rule 18's existing ladder, not a second system**: all down automations share ONE `triggerSignature`, so the same most-specific-wins rule decides both whose count governs a device and which automation alerts on it — which is what makes overlapping device filters (the central use case) explainable, and what lets the wizard's existing carve-out warnings describe down-detection coverage with no new concept. On a same-rank TIE the **smaller count wins** (the more-sensitive definition — matching `getMetricSeverityTiers`' existing convention, and the safe direction: both tied automations still fire, so the smaller means neither fires later than its own config promised), then older `createdAt`, then lower `id` for a stable diagnostic identity. **A device covered by NO down automation reads `passive`** — the sixth `monitorStatus` value. It is still polled, still sampled, still charted; Polaris simply renders no verdict about a device nobody asked it to judge. Four things follow, and each is a place the naive reading breaks something: the counters **keep advancing** while passive (so a surface can tell "passive and answering" from "passive and dark" without a new column, and an asset that later gains coverage converges on its very next probe instead of restarting its run at zero); the heavy cadences run for a passive asset **whose last probe succeeded** (`runsHeavyCadences` — a bare `=== "up"` gate would stop telemetry/interfaces/storage for every passive device and every chart would silently go flat with nothing erroring); entering or leaving passive is a **CONFIGURATION edge** (`isConfigStatusEdge`) that writes no `monitor.status_changed` Event and fires no dependency propagation, because one rule save can move thousands of assets across that line at once and the rule-CRUD audit trail already records the cause; and anything testing `!== "up"` as a proxy for "unreachable" must exempt it — the DHCP-push deferral in `reservationService` would otherwise defer a passive FortiGate's pushes **forever**. **Deleting every down automation blinds the fleet, and the thing that would alert about that is what was deleted** — hence a one-shot `monitor.down_detection_absent` warning Event on the transition into a zero-rule fleet, a `passive` bucket in the NOC rollup (never folded into `unknown`, which renders as "never probed"), and the `polaris_down_detection_assets{coverage}` gauge. `failureThreshold` stays on the settings tiers as a **dormant** column read only by the V3 seed that mirrors each install's pre-cutover thresholds forward (the `fastConfirmIntervalSec` precedent — dropping it would cost an irreversible migration for no gain); the cadence and probe timeout still come from that hierarchy, which is what business rule 30 is about.

### The way back up (2026-08-29)

The cutover above gave the automation the way DOWN and left the way back to fall out of the leaky bucket: `missedPolls` doubled as the recovery threshold, so three misses cost three answers. That is a reasonable default and it is not what the wizard's own reset step appears to promise. The reset asks "must stay cleared for N **polls**" — the operator who writes "down after 3 missed, reset after 5 received" is describing a device coming back, watches the Assets pill go green on the third answer, and reasonably reads the difference as a bug. The asset's intermittency strip is where this surfaced: it replays the state machine cell by cell, so it went green at three while the alert it was raised by sat firing for another five minutes.

So the reset sustain now reaches the state machine as well as the alert row. `DownWinner.recoverySustainSec` rides the same down-detection snapshot as the threshold — the SAME automation must answer both directions, or the two could resolve onto different rules — and `recoveryPollsFor` resolves it to polls. Since 2026-08-29 the reset can state that count OUTRIGHT (`reset.sustainPolls`, alongside `recoverySustainPolls` on the snapshot — see rule 19), and a stated count is used as-is: no cadence, no division, no asset read. A rule authored before counts were stored still carries seconds only, and those are converted back at the asset's own `intervalSeconds` at probe time rather than trusting the frozen arithmetic the wizard did at authoring time — which is what keeps "5 polls" meaning five polls after someone changes the interval. That division ROUNDS rather than ceils, so a cadence that does not divide evenly hands the operator their own number back instead of quietly adding one.

Four decisions bound it.

**The drain is a floor, never a ceiling.** A reset asking for fewer answers than the bucket owes cannot make recovery faster — business rule 30's bucket still wants one answer per miss — so `recoveryPollsFor` takes `max(threshold, polls)`. An automation with no auto reset, or one that resets immediately, gets exactly the pre-change behavior, which is every automation authored before this existed. **Superseded in part on 2026-09-01**: the clause that used to close this paragraph — "and a deep outage that already out-drained the count is untouched" — was true and was the defect. The bucket now LOCKS at `max(threshold, recoveryPolls)` on the verdict miss, so the drain no longer out-runs the reset on exactly the long outages the count mattered most for. `max(threshold, polls)` survives unchanged as the cap itself.

**It needed one bit of memory, and the counters could not fake it — until the cap removed the question (RETIRED 2026-09-01; what follows is why the column exists and why it is now dormant).** At `consecutiveFailures == 0` a success run of N is ambiguous: either a bucket that drained from N, or a healthy device that has simply answered N times. The confirmation hold must apply to the first and never to the second. Inferring it from `consecutiveSuccesses >= threshold` paints two amber cells into every ordinary blip on a healthy device; inferring it from the previous status loses the memory the moment a mid-run miss parks the asset in `warning`, letting a flapping device out of its run on one answer. Hence `Asset.awaitingRecoveryConfirm` (migration `20260829000000_recovery_confirmation`): armed on the transition into `down`, cleared on the transition into `up`, carried through everything in between — including across the probe-patch buffer's merge, where the preserve-on-absent rule has to be `??`/COALESCE rather than truthiness, because `false` is a real value that must land. It defaults false, which is right for existing rows: an asset mid-outage at upgrade time recovers on the drain the way it always did, and its next `down` arms it.

**The engine must not charge the wait twice.** `monitorStatus == down` stops being met the instant the asset reads `recovering`, so plain `!meets` would clear the alert on the FIRST answered packet and then the engine's own `sustainSec` would add five more minutes on top of the five polls the machine just served. `downRecoveryConsumesSustain` settles both halves: `engineSustainSec` returns 0 for such a rule, and `recoveredMeets` holds the alert through `down`, `recovering` AND `warning` (`DOWN_ALERT_HOLDING_STATES`) so it ends when the device actually reads `up`. Warning is in that set deliberately — a device that answered once and then missed again is further from recovered than one that is climbing, and letting it clear the alert would reward flapping.

**Only an `auto` reset counts.** `manual` and `timed` say nothing about how many probes must answer, and a `condition` tree is already the sole recovery authority while an alert fires (business rule 32a) — a poll count layered underneath would be a second clock that disagrees with it. `downRecoverySustainSec` returns null for all four.

Two consequences worth stating. `recovering` can now occur at `cf == 0`, a state unreachable before, so `runsHeavyCadences` admits it: the asset is answering every probe and is amber only because its automation asked for more confirmations, which is not a thing that should decide how fresh its charts are. And the asset strip's client-side replay tracks the same fact by OBSERVING a down within the window rather than by the stored bit it cannot see — a bar whose first cells predate the outage would otherwise have to guess.

### The cap serves the count, so the memory is gone (2026-09-01)

The design above holds the asset in `recovering` at `cf == 0` until a success run reaches the reset count, and needs `Asset.awaitingRecoveryConfirm` to know which devices owe one. Business rule 30's bucket ceiling makes the whole arrangement unnecessary: the level now LOCKS at `max(missedPolls, recoveryPolls)` on the verdict miss, so a device that went down is already carrying exactly the debt the operator asked for, and the ORDINARY drain serves it. Five answers to `up` on a "reset after 5 received" automation, from a bucket that jumped to 5 — no hold at zero, no stored bit, and the ambiguity that bit resolved (at `cf == 0`, is this a drained bucket or a healthy device's success run?) cannot arise, because the debt itself carries the answer.

It also fixes what the floor left broken. Under the old shape a deep outage out-drained the reset — seven misses cost seven answers and a 5-poll reset added nothing on top — so the number the operator wrote down stopped applying at exactly the outages that mattered most. Now it always applies, and a four-minute outage and a four-day one cost the same climb.

`owesRecoveryConfirmation` is deleted from `utils/monitorStatus.ts` and `recordProbeResult` no longer writes the column. `Asset.awaitingRecoveryConfirm` survives **dormant** — the `cooldownSec` and `failureThreshold` precedent, dropping it costing an irreversible migration for no gain — and `jobs/clampFailureBucket.ts` zeroes it once fleet-wide so a stale `true` can never be mistaken for live state by a later reader. `consecutiveSuccesses` is left maintained and charted but now decides nothing anywhere. The probe-patch buffer keeps its optional `awaitingRecoveryConfirm` plumbing, written by nobody.

One thing this does NOT change: the engine still must not charge the wait twice. `downRecoveryConsumesSustain` and `DOWN_ALERT_HOLDING_STATES` are untouched, and they are also what keeps rule 30's answered-probe-is-always-`recovering` change from clearing a down alert early — `recovering` is a holding state, so the alert still ends only at `up`.

### The automation also decides what colour Down is (2026-09-01)

Every surface painted `down` red. Red was never a property of the state, though — it is what `critical` looks like, and `critical` is simply the default severity of every down automation Polaris seeds. An operator who rates outages on a device class `warning` has said something about how those outages should read, and the product overrode it everywhere at once.

So `DownWinner.severity` rides the same down-detection snapshot as the threshold and the reset count — the SAME automation answers all three, for the same reason the two counts already share it — and reaches the browser on the `downDetection` block of the effective-settings and monitor-history payloads as a severity NAME rather than a colour, because the palette belongs to whichever client is drawing. Four surfaces read it: the Last-30-min strip, the desktop response-time chart, the phone's, and the chart rasterized into the alert email.

The palette is duplicated by necessity — `downSeverityHex` in `utils/severityStyle.ts` for the email, `DOWN_SEV_COLOR` in `public/js/chart-severity.js` for the browser, nothing crossing that boundary — and `tests/unit/downSeverityColor.test.ts` pins the two to each other, because one outage drawn two different colours depending on where you read it is the failure this whole vocabulary exists to prevent.

Three decisions bound it. It is deliberately **not** the alert-wide `severityHex`: that colours a whole alert — an email's severity bar, a Teams card — where nothing competes with it, while these land on a chart already spending amber on a below-threshold miss (`#ffc107`), blue on a recovering probe (`#0288d1`) and grey on a dependency-explained one (`#9aa0a6`), so each value is pulled deliberately deeper than the neighbour it sits beside. **`critical` keeps `#d32f2f`**, the red every surface already used, so a default install is pixel-identical, and an absent or unrecognized severity — passive devices and unresolved automations both — falls back to it rather than understating a verdict Polaris is still asserting. And the **Status pill does not move**: its text already names the state, so the colour there is redundant, and recolouring it would make the Down and Missed badges the same colour in a list column where an operator reads them as a set.

The `warning` case is the honest limit. Its down colour (`#f9a825`) and the below-threshold miss amber are two shades of one yellow — the price of honouring the operator's rating on a chart that already spends amber on the climb toward that same verdict. They stay separable by the tooltip, which names the state and the running count, and by the pill above the chart. Deepening it far enough to be unmistakable would stop being the yellow the operator asked for.

## Rule 37 — An automation only fires about a device Polaris is actually polling

Two facts had drifted apart: whether an automation *covers* a device (its scope matched) and whether Polaris *watches* that device (`monitored = true`). A scope is a device filter, so it deliberately selects on inventory attributes and says nothing about polling — and for the metric triggers that was harmless, because an unmonitored device produces no samples and therefore no readings. It was not harmless for the two trigger families that read something other than a sample.

**The incident shape.** `monitorStatus` is a stored column, and turning monitoring off does not clear it — `clampMonitoredState` resets the counters and leaves the last verdict standing, deliberately, so the assets table can show where a device was when polling stopped. The `asset_state` resolver reads that column straight off the scope row. So a device that was down when an operator shelved it kept its `monitorStatus = "down"`, kept matching a `monitorStatus == down` automation forever, and kept an alert firing about a device nobody had polled since. Nothing cleared it either: the vanished-state sweep only clears rows whose asset left the SCOPE, and the asset had not left the scope — it had left the fleet. The event and change tail had the mirror-image version: it fires on new `Event` rows and never looked at `monitored` at all, so a firmware change or a discovery failure on a decommissioned host raised an alert exactly as loudly as one on a production firewall.

**The decision is one gate, not a per-trigger-type judgement.** `assetCanTrigger(asset)` — `monitored` **and** not suppressed — is applied by every path: the threshold loop, the composite loop, the metric and state previews, and the event/change tail. It folds in business rule 16's maintenance/dependency suppression rather than sitting beside it, because the question an operator asks is singular ("will this alert on that box right now?") and answering it from two places is how the two halves drifted in the first place. The four lifecycle statuses that cannot carry monitoring at all — decommissioned / disabled / storage / quarantined — reach this gate through business rule 10 rather than being retested here; that is the whole point of clamping `monitored` at the DB layer instead of teaching every consumer the status list.

**Event and change triggers were the deliberate exception, and reversing that is the substance of this rule.** The prior reasoning was that those triggers fire on audit events rather than readings, so nothing about them requires a live poller — a discovery failure or an asset edit is real whether or not anyone is watching the device. That is true and still beside the point: an operator who turns monitoring off has said "stop telling me about this box", and honouring that for five trigger types and not two makes the setting mean nothing they can predict. The cost is accepted openly: an audit-worthy change to an unmonitored asset now produces an `Event` row (visible on the Events page, shipped by the syslog and SFTP archivers) and no alert.

**Two carve-outs inside the tail, both about not swallowing a real signal.** A **null** asset detail fires — the row is GONE, and the case that matters is `asset.deleted`, where refusing to alert because the asset can no longer be found would silence exactly the event worth hearing. **System-scoped** events (capacity, backups, updates, lockouts — the 12 seeded event automations are mostly these) carry no `assetId`, never reach the gate, and are unaffected.

**The monitored half is SQL, not a filter after the fact.** `scopeWhere(scope, monitoredOnly)` pushes `monitored: true` into the WHERE on every evaluation load, so the engine's per-tick read shrinks to the fleet it can actually judge instead of loading shelved inventory to discard it — which matters at 2000 assets on a 60-second tick. It is pushed in **after** the dimension count, so the gate can never make an otherwise-empty scope (`{}` = match nothing) look like it selected something. And because un-monitoring now takes a device out of the scope load, the existing vanished-state sweep **clears** its live alerts as `notification.out_of_scope` — the fix for the frozen alert falls out of the gate rather than needing its own sweep.

**The raw resolver survives, because three other surfaces ask a different question.** `loadScopeAssets` without the flag still exists for: the Step-2 device-list preview, which reports the unmonitored remainder as a separate count rather than hiding it (an operator has to be able to see that their filter covers 40 devices of which 12 will never alert); the dimension-value picker and mass pinning, which are about what devices *have*, not what they fire; and `Contact.assetCondition`, where ownership is an address-book fact — a contact still owns a device nobody polls, and the editor says so in as many words. Any new consumer has to answer which of those two questions it is asking before picking a form.

<a id="rule-38"></a>
## Rule 38 — A device behind a dark parent is not accused, and it is not released on one packet

Dependency suppression already answered "don't alert about a switch whose gate is down." Two things it did not answer turned out to matter as much: **when** the suppression ends, and what the charts say about the hours it covered.

**Releasing on `recovering` un-did the whole point.** The evaluator's parent test was `monitorStatus !== "down"`, which makes `recovering` a healthy parent. But `recovering` is the state a device enters on its FIRST successful probe after an outage and stays in until it has passed the covering automation's success threshold — one answered packet, and a failure drops it straight back to `down`. So a gate that answered once released every switch and AP behind it, all of which were still failing their own probes, all of which immediately started their own down runs, and the single upstream outage re-alerted device by device as exactly the storm suppression exists to prevent. Worse on a flapping gate, which could do it repeatedly.

The fix is **hysteresis, and only on the two states where it means something.** Entering suppression is unchanged — a parent has to be confirmed `down`, because `warning`/`recovering` flapping must never drag a healthy subtree into Dep. Down. Leaving it additionally counts `recovering` as down, decided by the child's own persisted `dependencySuppressed` (`SuppressionAssetState.currentlySuppressed` selects the side of the asymmetry). Every other state stays "ok" in both directions on purpose: `unknown` (never probed), `passive` (rule 36 — no automation renders a verdict on it) and `warning` are not claims that the parent is unreachable, and gating release on them would strand a subtree in Dep. Down with nothing that could ever clear it. Note the release cascades one layer per pass rather than all at once, which is correct: a gate coming back does not mean the switch under it has, and the AP under THAT switch stays suppressed until its own parent is genuinely up.

**The charts were calling an explained gap an outage.** A suppressed asset is still probed — at half cadence, because it may answer over a redundant path or out-of-band management — and those probes fail. Every failure was written indistinguishable from a real one, so a device sat behind a dead gate for six hours and its charts drew the red dive that means *this device stopped answering and we don't know why*, in the one case where Polaris knew exactly why.

So the probe row carries the reason: `AssetMonitorSample.dependencyDown`, set by `recordProbeResult` from the asset row's own `dependencySuppressed` (never re-derived on the probe path — the reconciler owns that flag, and deciding it twice would give two answers), rolled up as `dependencyFailureCount`. `probeOutageService` classifies each window as an `OutageKind`, and every chart surface — desktop, phone, compare, alert email — draws `dependency` in grey.

Four decisions inside that:

- **Same shape, different colour.** The line still dives to the baseline, because nothing was measured; only the accusation is dropped. It is deliberately not a band — bands mean "the gap is explained *and* expected", which is maintenance-window vocabulary (rule 16, UI-GUIDE section 15). A dependency outage is explained but nobody scheduled it.
- **A run splits at a change of kind.** Misses that were unexplained when they happened are not retroactively excused by the parent going down later, and a tail that keeps failing after the parent recovers goes back to red — that tail is a real outage, and it is the most important thing on the chart.
- **A rollup bucket must qualify WHOLE.** Grey only when `dependencyFailureCount >= failureCount`; a bucket mixing explained and unexplained misses stays red, because part of that hour is still unaccounted for. A NULL count — a bucket rolled up before the column existed — reads as zero, i.e. red, which is the safe direction.
- **The reason is stored, not reconstructed.** No table keeps a history of when each asset was suppressed, and inferring it after the fact from parent status history would be a second, disagreeing answer to a question the probe path could simply record.

The grey is duplicated in four places by design (`_CHART_DEP_COLOR` in `public/js/assets.js`, read by `assets-compare.js`; `DEP_COLOR` in `public/js/mobile/charts.js`; `DEP_COLOR` in `src/utils/sparklineSvg.ts`), the same way the failure red already is. Change one, change all of them, or one outage renders two ways.

<a id="rule-39"></a>
## Rule 39 — How a person wants to be reached is theirs, not the automation's — but an automation that only offers one way still reaches them

Polaris could always send an alert by email and by web push. What it could not do was ask the person on the other end which they wanted. Two things followed from that, and both of them were bad.

**Enrollment was a per-browser switch pretending to be a preference.** "Enable push" lived in the account menu and on the Automations page, and it enrolled *that browser*. So an operator who turned push on at their desk did not have push on their phone, had no way to find that out except by not being paged, and had to remember to do it again on every device — including after a reinstall, a new laptop, or clearing site data. "I turned push on" and "my phone buzzes" were different facts, and only one of them was visible.

So the switch is gone. What the operator answers now is **how they want to be alerted** — Email (the default), Push, or both — and the answer lives on `User.notificationPreference`, not in the browser. Every client reads it at boot and reconciles *its own* subscription to it: choosing Push on the laptop enrolls the phone the next time it is opened, and switching back to Email un-enrolls every device the same way. Enrollment stopped being a decision and became the consequence of one.

The one thing that boot-time reconcile will not do is **prompt**. `Notification.requestPermission()` needs live user activation on Safari and a page load has none, so a browser that has never been asked stays un-enrolled until the operator picks the preference *there* — which is why the choice is a menu item and a bottom sheet rather than a dialog with a Save button several awaits away from the click, and why the row says which of those two states this device is in. Where permission is already granted the subscribe is silent, which covers every browser that has ever enrolled.

The preference is **saved even when the browser refuses the prompt**. It is an account-wide answer and the operator's other devices may honour it, so the toast reports what happened *here* rather than the save quietly not happening. The one exception is **iOS outside standalone**, where choosing push saves nothing and routes to the install steps instead: Apple grants Web Push only to a home-screen app, so a preference this phone cannot honour, chosen on this phone, is a promise Polaris would be breaking on the spot. For the same reason the chooser disables the push options **only when the SERVER has no Web Push channel** — an unsupported or permission-denied browser may not withhold a choice that belongs to the account.

**An action can now be plural, which is what makes the preference expressible at all.** A notify action carries `channelIds` — several channels, one recipient list — because "page the on-call by email and by push" was two actions with two copies of the same recipients, and a preference could not be stated across them. `channelId` survives as the primary and the lossless single-channel mirror every legacy reader still names a channel through; `assertActionRefs` refuses a payload where the two disagree rather than repairing it, because picking one of two answers is how an alert quietly goes to the wrong destination. `actionsToTargets` expands one action to one `DeliveryTarget` per channel, so nothing below that line knows an action can be plural.

**And then the gate, which is the whole rule.** A notify action may opt into `respectUserPreference`: deliver to each recipient only through the channel their own preference accepts. But it is consulted **only when the action group actually offers both methods** — otherwise the preference would *delete* the alert instead of routing it. An email-only automation whose recipient prefers push would reach nobody, silently, and nothing anywhere reports a recipient who was filtered out.

The group is the `actions[]` list being executed — the rule's own actions, one severity band's, the reset list, or a single escalation tier's — which is exactly the unit the wizard grays the checkbox on. A **multi-channel action counts on its own**: one action carrying an SMTP channel and a Web Push channel offers both methods by itself, and that is the shape the checkbox was really added for. The test lives in `automationActionService.actionsCarryBothMethods` (server) and `hostOffersBothMethods` (wizard) — same question, same answer, so the checkbox is never enabled on a group the server would ignore it for. `expandDeliveries` defaults `enforceUserPreference` to false, so a caller that never opts in behaves exactly as it did before the feature even if a stored target carries the flag.

Four smaller decisions carry it:

- **Only accounts are filtered.** A typed address and an address-book contact have no Polaris account and therefore no preference; withholding their copy on a preference they never expressed would be inventing one for them. Same posture as the acknowledge-capability split in rule 25: unknown means deliver.
- **A preference routes an alert; it never deletes one.** `preferenceWithholds` keeps a recipient on the channel they did NOT pick whenever the one they did pick cannot reach them — a push-preferring account with no enrolled device still gets the email, an email-preferring account whose `User.email` is null still gets the push, and an account neither can reach is kept on both rather than dropped from both. Without it the two halves cancel: the filter removes them from one channel and the other has nowhere to send, so they are simply absent from the alert and nothing anywhere reports an omitted recipient. The device count is one `groupBy`, read only when a filter is actually about to drop someone and memoized per notification.
- **A push that dies for good is re-routed to email at SEND time.** The drain is the only place the second signal arrives: a push service answering 404/410 means that subscription is dead, so `enqueuePushFallbacks` queues an email instead. Three guards keep it from mailing people who were reached perfectly well — it is per RECIPIENT rather than per row (`pushStillInPlay`: an account with three enrolled browsers has three delivery rows and two may have succeeded, and `pending` means a retry may still land it), it uses the ACTION'S OWN email channel (stamped into the push row's `meta.fallback` at expansion time, so no alert is re-routed through an SMTP config nobody picked for it, and a push-only action still has nowhere to go), and it never sends twice (`alreadyEmailedOnChannel`, a SUBSTRING test because a composed send is one row whose target is the whole joined To list). The body is cloned from a sibling email row on the same channel so a custom composition carries over. Its real value is bounded and worth stating: because a 410 also PRUNES the subscription, every later alert takes the fire-time path above instead — so this rescues exactly one alert per dead endpoint.
- **Reachability is the only thing Polaris can honestly check.** A subscription EXISTS or it does not. Whether the phone is on, online, or looked at is not knowable: a 201 from a push service means it accepted the message for later delivery, not that it arrived. A genuinely dead endpoint surfaces later still, at SEND time, when it answers 404/410 and `deliverNotifications` prunes it — too late to re-route that alert. So the fallback is deliberately pre-send and subscription-shaped; anything promising “fall back when the phone didn’t buzz” would be a lie.
- **An unrecognized preference means email, never nobody.** `normalizeNotificationPreference` degrades anything it does not know to `"email"`, the method everyone has. A plain TEXT column holding a value this build has not heard of must not un-address an alert.
- **The broadcast toggles stayed push-only.** "Send to All Users" / "All User Regions" live in the builder's push block and read as *tell every device*. On a mixed action they now apply to the push half alone (gated on `transport === "web_push"` in `expandDeliveries`), because letting them widen the email half would mail the whole roster off a control that never said so. Save-time validation loosened in step: broadcast is refused only when an action carries **no** push channel at all, since the toggles are renderable the moment one is selected.
- **The preference is audited.** `user.notification_preference.changed` is written on every change, because "I never got paged" has to be answerable from the Events tab.
