## Summary

**0 critical · 1 high · 7 medium · 5 low/informational.** No critical or
remotely-unauthenticated-RCE-class issues found. The dominant theme is **outbound
TLS verification** — Polaris is conservative on *inbound* security (auth, sessions,
CSRF, CSP, uploads all solid) but disables or defaults-off TLS verification on
several *outbound* paths to operator-configured devices, which exposes integration
**credentials** and discovered data to network MITM. The highest-value item (H1) is
WinRM Basic-auth credential exposure.

## Findings

### H1 — WinRM Basic-auth credentials over unverified TLS *(High)*

`utils/winrm.ts:257` and the inline WinRM probe at `monitoringService.ts:2761` both
set `rejectUnauthorized: false` **unconditionally** (not operator-toggleable) while
sending `Authorization: Basic base64(user:pass)` to an operator-configured Windows
host over HTTPS. A network attacker positioned between Polaris and the target (ARP
spoof, rogue switch, DNS hijack) can present any certificate, terminate the TLS
session, and recover the **Windows DHCP / monitoring credentials** in cleartext
(Basic auth is trivially base64-decoded).

- **Impact:** disclosure of domain/service credentials used for WinRM DHCP discovery
  and Windows monitoring; lateral movement.
- **Why it exists:** comment says "operator self-signed certs are common in lab."
  Legitimate need, wrong default — verification should be on by default with an
  explicit per-integration opt-out, and even when opted out, a CA-pin option should
  exist for the credential-bearing path.
- **Remediation:** thread a `verifyTls` flag (default **true**) through the WinRM
  transport, mirroring `monitoringService.ts:2858`'s FortiGate pattern
  (`rejectUnauthorized: !!verifyTls`). When the operator opts out, surface a visible
  warning. Apply to both the probe and the DHCP-discovery WinRM path.

### M1 — TLS verification defaults to off for FMG / FortiGate / AD *(Medium)*

The integration config schemas default the verify flag to insecure:
`integrations.ts:426` (`FortiManagerConfigSchema.verifySsl` → `false`),
`:484` (`FortiGateConfigSchema.verifySsl` → `false`),
`:546` (`WindowsServerConfigSchema`/AD `verifyTls` → `false`). A fresh integration
created without touching the toggle talks to the device with **no certificate
verification**.

- **Impact:** MITM of FortiOS REST sessions (carries the API key), LDAP binds
  (carries bind credentials on non-LDAPS or unverified LDAPS), discovered topology.
- **Remediation:** flip the schema defaults to `true`. Provide a migration story for
  existing rows that rely on `false` (do **not** silently start failing their
  discovery — leave stored `false` values intact; only the *default for new rows*
  changes). Add a UI warning when an operator sets verify-off. **FMG ↔ standalone
  FortiGate parity:** apply identically to both.

### M2 — Process-global TLS-verification toggle *(Medium)*

`fortimanagerService.ts:524` and `fortigateService.ts:121` disable verification by
mutating the **process-wide** `process.env.NODE_TLS_REJECT_UNAUTHORIZED = "0"` for
the duration of a call (restored in `finally`). Node reads this env var globally, so
**any other outbound TLS connection** that overlaps that window — a concurrent call
to a different FortiGate, Entra Graph, LDAPS, syslog-TLS — also skips verification,
even if *that* integration has verify-on.

- **Impact:** verify-on integrations silently lose verification during overlapping
  FMG/FGT calls; the blast radius of M1's opt-out is the whole process, not one call.
- **Mitigating factor:** in the reference deployment, FMG discovery parallelism is forced to 1
  and runs in the discovery-role process, narrowing overlap — but the discovery
  process also issues Entra/AD HTTPS, which can overlap.
- **Remediation:** stop using the global env var. Pass an `https.Agent` with
  `rejectUnauthorized` set per-request (FortiOS REST is plain `fetch`/`https`, so a
  per-call `Agent`/`dispatcher` works), scoped to that one connection.

### M3 — DoH/DoT resolver TLS verification disabled *(Medium)*

`dnsService.ts:196` (DNS-over-HTTPS) and `:354` (DNS-over-TLS) hard-code
`rejectUnauthorized: false` against an **operator-supplied resolver URL/host**. DNS
results drive PTR hostname learning and `dns_resolved` auto-reservations.

- **Impact:** a MITM can forge DNS answers → poisoned hostnames / spurious
  reservations; lower direct severity than H1 (no credentials on this path) but it
  feeds data that operators trust.
- **Remediation:** verify by default. Public resolvers (Cloudflare/Google/Quad9 — the
  documented use case) all present valid certs, so verification costs nothing there;
  expose an opt-out only for operators running an internal resolver with a private CA
  (preferably via a CA path, not blanket disable).

### M4 — No SSRF / host guard on operator-supplied integration host *(Medium)*

Every integration `host` is `z.string().optional().default("")` — no format check and
no guard against `127.0.0.1`, `::1`, `169.254.169.254` (cloud metadata),
`localhost`, or other private/loopback targets. Polaris will issue authenticated
outbound requests (and, for FMG proxy, relay arbitrary FortiOS API calls) to whatever
host is entered.

- **Impact:** authenticated SSRF — a user with `integrations:write` can point Polaris
  at internal services (the DB on `localhost:5432`, cloud metadata, other intranet
  hosts) and use it as a request relay / port-scanner.
- **Mitigating factor:** `integrations:write` is a privileged role; this is
  defense-in-depth, not an anonymous-SSRF hole. Still relevant for least-privilege
  custom roles.
- **Remediation:** add a shared `src/utils/netGuard.ts` validator that rejects
  loopback / link-local / multicast / cloud-metadata ranges (and resolves the
  hostname to check the resolved IP, not just the literal), reused by every
  integration config validator. Allow normal RFC1918 device ranges (these are
  legitimate targets). Make it an explicit allow-with-warning if a private/metadata
  target is genuinely needed.

### M5 — Backup password has no strength validation *(Medium)*

`serverSettings.ts:240` (backup) and `:311` (restore) read
`req.body?.password || null` with no Zod schema. An empty or 1-char string is
accepted as the passphrase for `scryptSync` → AES-256-GCM. A weak passphrase makes
the encrypted backup brute-forceable, defeating the point of encryption.

- **Remediation:** add a Zod schema with a minimum length (≥12) and a basic strength
  floor for the *backup* path; on *restore*, only require non-empty (you must accept
  whatever encrypted an existing file). Pure-function-testable.

### M6 — SAML `validateInResponseTo: never` *(Medium)*

`azureAuthService.ts:123` disables binding of the SAML Response to the `InResponseTo`
ID of the AuthnRequest Polaris issued. This weakens replay protection on the SAML
assertion.

- **Compensating controls present:** signed assertions (`wantAssertionsSigned: true`),
  a server-generated RelayState that is cross-checked on callback, and SAML's own
  assertion validity window.
- **Assessment:** common node-saml configuration (full `InResponseTo` validation
  requires a server-side request-ID cache, which adds state in the split-role layout).
  **Recommend** evaluating whether to enable it with a shared cache; if it stays off,
  the rationale and the compensating controls should be documented and the assertion
  `NotOnOrAfter` window kept tight. **Not auto-remediated** — needs an
  infra/architecture decision (request-ID store) and an admin's SSO sign-off.

### L1 — CSP `scriptSrcAttr: 'unsafe-inline'` *(Low)*

`app.ts:322` permits inline `on*` handlers (the bigger `<script>`-tag hole is closed —
`scriptSrc: 'self'`). Many pages still render `onclick="..."` via `innerHTML`.

- **Mitigating factor:** the SPA defines and broadly uses an `escapeHtml()` helper
  (`public/js/app.js`, `map.js`, and all `public/js/mobile/*`), so user-supplied
  fields (hostname, assetTag, SNMP sysLocation, etc.) are escaped at the sinks
  reviewed. Risk is contained but not zero.
- **Remediation:** track migration of inline handlers to `addEventListener`
  delegation so `scriptSrcAttr` can drop to `'none'`. Larger follow-up, not blocking.

### L2 — Process-local lockout / MFA-pending stores *(Low)*

`utils/loginLockout.ts` (per-username 5-fail / 15-min lockout) and the MFA-pending
token store are in-process Maps. If the **web** role ever scales beyond one replica,
an attacker can distribute login attempts across replicas to dilute the per-username
lockout (the per-IP `express-rate-limit` is also per-process).

- **Assessment:** auth runs only on the `web` role; prod's `POLARIS_MONITOR_REPLICAS`
  scales monitors, not web. **Document the single-web-replica assumption**; if web
  scales out, move these to a shared store (Postgres/Redis).

### L3 — API-token verification cost / no guess rate-limit *(Low)*

`apiTokenService.ts` verifies bearer tokens by prefix-filtering then argon2-verifying
each candidate — O(live tokens) argon2 ops per request, and no per-IP rate limit on
repeated failed token guesses. Small token counts make this a non-issue today; note
for scale and consider a failed-auth limiter on token routes.

### L4 — DB restore has no decompressed-size cap *(Low)*

`serverSettings.ts:347` streams gunzip → psql with "no decompressed-size cap"
(comment is explicit). An admin-equivalent caller could upload a zip-bomb. Admin-gated
and the operator is already trusted to restore arbitrary SQL, so impact is limited to
self-inflicted DoS; note for completeness.

### L5 — `pg_dump`/`psql` connection-URL interpolation *(Informational — reviewed, safe)*

`serverSettings.ts:251` interpolates the connection URL into an `execSync` string
(double-quoted) and `:348` passes it as a `spawn` argument array (no shell). Reviewed
for shell injection: the `spawn` path is shell-free; the `execSync` path is
double-quoted and the URL comes from `getDirectDatabaseUrl()` / `DATABASE_URL` (an
operator-set env var, not request input). **No injection** found. Recorded so the next
reviewer doesn't re-flag it.

## Verified strengths (no action needed)

These were checked and are sound — recorded so future reviews can confirm they
haven't regressed:

- **Password & token hashing:** argon2id for user passwords and *all* API/agent
  tokens; constant-time dummy verify on unknown-username login (`auth.ts`).
- **Sessions:** `httpOnly`, `secure: "auto"`, `sameSite: "lax"`, 8-hour maxAge,
  session **regenerated** on successful login; `SESSION_SECRET` **hard-fails** boot in
  production (`app.ts:294-304,366-385`).
- **CSRF:** synchronizer-token; safe-method bypass; `/api/v1/agents/*` exemption is
  **correct** (bearer-auth, no session); stale-Secure-cookie recovery path.
- **CSP:** inline `<script>` disallowed; `objectSrc`/`frameSrc` `'none'`;
  `baseUri 'self'`; HSTS 1y + includeSubDomains + preload.
- **Agent fleet:** bearer bound to `assetId` **server-side** (client-supplied assetId
  ignored); one-shot enrollment token (10-min TTL, argon2id-hashed); dual-pin leaf-cert
  pinning with `MinVersion: TLS1.2` in the Go agent; agent.conf written `0600`.
- **Uploads:** SVG sanitized (script/handler/external-ref rejection) **and rasterized
  to PNG** on upload; magic-byte MIME validation; size caps (MIB 1 MB, icon 256 KB).
- **SQL:** all `$queryRaw*` sites parameterized via tagged templates / typed params;
  no user-supplied table names; TimescaleDB `$queryRawUnsafe` sites use
  server-computed constants.
- **Privileged nginx wrapper** (`deploy/scripts/polaris-nginx-apply.sh`): hardcoded
  staging paths, symlink + regular-file checks, `flock` serialization, `nginx -t`
  validate-before-swap with `.bak` rollback, numeric-port regex on `verify-listening`.
- **Backup crypto:** AES-256-GCM with random 32-byte salt + 16-byte IV + auth tag;
  versioned `POLARIS\0` magic.
- **RBAC:** 25-key permission matrix; last-admin-equivalent invariant on role-change
  and delete; ownership dimension on subnets/reservations; role-snapshot cache with
  version-bump invalidation.
