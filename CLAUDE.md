# Polaris — Claude Code Project

## Project Overview

**Polaris** is an IP management tool that allows users to reserve and manage IP address space (IPv4 and IPv6) for use across other infrastructure projects. Named after the North Star — a fixed reference point operators can navigate by when wiring up everything else. It provides a central registry for subnets, individual IPs, and reservations — preventing conflicts and giving teams visibility into IP utilization.

> **Naming:** the project was previously called Shelob and has been fully rebranded — every on-host identifier (install path, system user, Postgres DB/user, systemd unit, NSSM service name, firewall rule label), browser-side identifier (CSRF cookie, localStorage keys), and source-level constant (argon2 timing dummy, encrypted-backup magic) now uses `polaris` / `Polaris` / `POLARIS`. Encrypted backups are versioned by the 8-byte magic header `POLARIS\0`; the previous `SHELOB1\0` format is no longer recognized. Existing installs migrate via dump-and-reinstall (plain `pg_dump` carries cleanly into a polaris-named DB).

Version policy: `<major>.<minor>` lives in `package.json` and is the single source of truth — pre-release line is the 0.x series, bump the minor (e.g. `0.9.0` → `0.10.0`) when cutting a named release. The patch is the git commit count, computed at runtime by `src/utils/version.ts`: it reads `POLARIS_BUILD_COMMIT_COUNT` (baked into the Docker image at build time) when set, otherwise falls back to `git rev-list --count HEAD` for RHEL prod / dev where the .git tree is present. Never edit the patch in package.json — it stays `<major>.<minor>.0` there. Version is shown in the sidebar and embedded in backup filenames.

### Entities (definition + load-bearing invariant; full notes in ARCHITECTURE.md)

- **IpBlock** — top-level CIDR namespace; has many Subnets.
- **Subnet** — CIDR carved from a block; has many Reservations; tracks discovery origin. `tags` carries operator tags **plus inherited `region:<name>` tags** (a subnet served by a FortiGate inside a map region inherits it, matched through `controllerIdentityKeys`) — provenance-bounded by `RegionTagAssignment`, so a reconcile strips only what it applied and hand-added region tags survive.
- **Reservation** — single IP (or full-subnet) entry; `sourceType` distinguishes manual from discovered. Carries FortiGate push state (`pushStatus`, `pushQueuedAt`, etc.), stale-detection state, and `dhcpBinding` (`null` | `"lease"` | `"reservation"` — how the gate hands the address out, deliberately orthogonal to `sourceType`'s "who owns it"; see business rule 23). **A `vip` or `interface_ip` row is READ-ONLY** — a FortiGate virtual IP and a statically-configured router/firewall interface address are owned by the DEVICE's own config, not by anything Polaris granted, so Polaris reports them and offers no Reserve / Release / Edit. Creating over one was already refused (neither sourceType is in `isSupersedableByCreate`, so the collision check 409s); `assertNotDeviceOwned` in `api/routes/reservations.ts` closes the PUT and DELETE, at the ROUTE layer rather than in the service because discovery's own reconcile still has to refresh and retire these rows. Both render with the purple `.ip-dot-device-config` dot in the IP panel ("VIP" / "Interface").
- **Integration** — FMG / FortiGate / Entra ID / AD / Windows Server / vCenter / Azure Arc config + discovery state.
- **Asset** — device inventory. Owns six-state monitor machine (`monitorStatus` — the fifth/sixth being `unknown` and `passive`; see business rule 36), polling-method per stream, FortiGate sightings, dependency layer/suppression, quarantine state, and the `managementAccess` summary (read-only `allowaccess` read during FMG/FortiGate discovery → asset slide-over Open HTTPS / Open SSH buttons, the same verbs in the Assets list row menu, + FortiAP SNMP-disabled warning; see `fortinetManagementAccessService`). **A `server` gets Open RDP / Open SSH off its TYPE instead** — nothing reads a Windows or Linux host's management surface, so there is no `allowaccess` to consult and never will be; the verbs are offered through the same `_assetMgmtAccess` gate with the same "unknown is not denied" optimism the unreadable-FortiSwitch path takes. Deliberately not extended to `workstation` (two dead verbs on every endpoint row) and HTTPS is deliberately not offered on a server (its :443 is the application, not a management UI).
- **AssetSource** — per-discovery-source view of an asset (entra / intune / ad / arc / fortigate-firewall / fortiswitch / fortiap / fortigate-endpoint / vcenter-vm / vcenter-host / manual / polaris-agent). Discovery-owned Asset fields are projected from these rows.
- **AssetDependencyParent** — parent→child edges of the dependency DAG; drives `Asset.dependencySuppressed`. `source` ∈ `computed` (Fortinet infra recompute) / `override` (operator pins, always win) / `vcenter` (VM→host) / `endpoint` (fleet-wide, at most ONE parent, resolved most-specific-first). **One parent, never a union** — all-down semantics model REDUNDANT parents, but a switch and the gate above it are in SERIES. Consumers resolving the effective set must test `source !== "override"`, **not** `source === "computed"`.
- **AssetMonitorSample / AssetTelemetrySample / AssetInterfaceSample / AssetHardwareSensorSample / AssetStorageSample / AssetIpsecTunnelSample / AssetPerfSlaSample** — the seven append-only sample tables, each with `*Hourly` + `*Daily` rollup companions populated by `runSampleRollup` (14 rollup tables). **They carry `assetId` but NO foreign key to Asset** — they are TimescaleDB hypertables, and a cascade DELETE matching a compressed chunk decompresses it into un-truncatable bloat (prod 2026-06-08). **Never re-add the relation, and never row-DELETE/UPDATE sample rows that could sit in a compressed chunk.** `AssetInterfaceSample` is **pinned-only** (one row per operator-pinned interface); current interface state lives in `AssetInterface`.
- **AssetSdwanRule** — current-state SD-WAN service rules (one row per `(asset, ruleName)`), delete-replaced per scrape by `persistSdwanRules`. FortiOS only, gated by `config.pullSdwan`. Not a hypertable, not a retention entity — no history.
- **AssetProcess** — current-state process inventory (one row per `(asset, name)` program, aggregated across PIDs), delete-replaced per scrape by `persistAssetProcesses`. Operator pins live on `Asset.monitoredProcesses` (telemetry + logs) and `Asset.mappedProcesses` (Application Map).
- **AssetService** — current-state service inventory (one row per `(asset, unit)` systemd unit / Windows service), delete-replaced by `persistAssetServices`. The **unit-centric sibling** of `AssetProcess`: a service running as a shared runtime is visible as itself, and exited oneshot units still appear. Agent-only. Read-only — service control was removed in the Satellite-posture change.
- **VcenterDatastore** — current-state vCenter datastore inventory (one row per `(integration, datastore MoRef)`), delete-replaced per discovery run by `syncVcenterDevices`. `Asset.virtualization` is the per-asset counterpart (role-discriminated vm/host blob, single writer).
- **AssetInterface** — **current-state** interface inventory (one row per `(asset, ifName)`, plain table with a real FK), delete-replaced per FULL system-info scrape by `persistInterfaces`. Exists because every all-interface consumer wants current state, not history. It also backs the device-filter condition tree's **`interfaceName`** ("Device interface") field — "switches that have a fortilink port" — which is the FIRST condition field reading a relation (`AssetApVap.ssid` — "Broadcast SSID" — is the second), so a fleet-scale filter resolves it in SQL via `scopeRelationIndex` rather than joining it onto a per-tick asset read, and deliberately reads the FULL inventory rather than the pinned subset every interface TRIGGER is limited to (a trigger needs a metric, this asks what the device has). **Single-writer cadence is load-bearing**: only the full pass and the agent push may write it — never `recordFastFilteredResult`, which sees only pinned interfaces. Both callers **skip an empty list rather than wiping**, because empty is ambiguous. One carve-out: a **FortiLink trunk interface** (named for its peer's serial) leaves the ifTable while the link is down, so a dropped row whose name resolves to a still-active peer switch whose own inventory reciprocates is **preserved and marked down** rather than deleted — deleting it made a downed trunk vanish from the System tab, the pin picker and the alert dimension at the moment its down alert fired (`resolvePreservedTrunkNames`). Switch-port VLANs come from SNMP first, the controller CMDB second. It is also the **identity of record for interface names**: the SNMP collectors name a port `ifName` with an `ifDescr` fallback, and on a FortiSwitch `ifDescr` is the operator's port DESCRIPTION — so a tick whose `ifName` walk failed renamed `port9` to `MORGAN-221E-1`, the AP plugged into it, and that name became an identity in the inventory, the pin list, the sample table and the alert dimension (prod 2026-08-25). Every writer therefore reconciles collected names through `loadInterfaceIdentity` + `utils/interfaceIdentity.ts` first: a real `ifName` wins, a label two ports claim resolves to nothing, an unknown name passes through, and `repairInterfacePins` rewrites a pin that names a description onto the port.
- **AssetInterfaceOverride** — operator-typed Interface Comments override. Polaris-local by default; description-synced to the device when the integration's `syncDescriptions` is on, carrying per-row sync state. See business rule 14.
- **AssetMacTableEntry** — the switch's layer-2 forwarding database (CAM table), from Q-BRIDGE-MIB with a BRIDGE-MIB fallback. Current-state, delete-replaced per scrape by `persistMacTable`. **The MAC is not always in the INDEX** — `resolveFdbIdentity` reads the address COLUMN first, because a FortiSwitch indexes the table by row number. A table that answered but decoded to zero rows returns `undefined` (preserve), never `[]` (wipe). Feeds MAC-derived topology inference; **display-only — it writes no LLDP neighbour and no dependency edge.**
- **AssetArpEntry** — the FortiGate's layer-3 neighbour cache, one row per `(IP, MAC, interface)` binding — the L3 sibling of `AssetMacTableEntry`. **Accumulate + age**, not delete-replace, which is what makes its two writers (the monitor system-info pass and discovery Phase 7.5b) safe. `ifName` is `""`, never NULL — it is part of the business key and Postgres treats NULLs as distinct. `matchedAssetId` is MAC-only. History is an interval, not a timeline.
- **AssetTrunkMember** — FortiSwitch trunk → local physical port, from the `fsTrunkMember` SNMP scalar (`1.3.6.1.4.1.12356.106.3.1.0`). The trunk name is the **peer serial left-truncated to 15 characters** on a trunk the switch auto-created, so matching is a SUFFIX test (`matchTrunkPeer`), never a reconstruction; an ambiguous tail resolves to NULL rather than a guess. **A trunk name is a parent/member edge always and a peer identity only sometimes** — the same scalar carries the operator's hand-configured LAGs, named for whatever is plugged into them (`Storage Node 2`, `_FlInK1_ICL0_`) — so a tail that isn't serial-SHAPED (alphanumeric, ≥10 chars) never reaches the peer lookup at all. Delete-replaced per scrape; covers the FortiLink links LLDP does not republish. **It is also the only source of the trunk/member relationship on a directly-polled switch**, so the same scrape overlays it onto the interface list (`ifParent` + `ifType="aggregate"`, `trunkMemberMap` → `overlayFortiswitchTrunkMembers`) — the ifTable publishes no aggregation of its own, and the controller-CMDB overlay that used to be the only writer of that edge reaches only switches with a resolvable controller.
- **AssetPhysicalEntity** — field-replaceable hardware inventory from ENTITY-MIB (transceivers, PSUs, fan trays with serial + model for an RMA). Current-state, delete-replaced per scrape, plain table with a real FK. `firstSeen` survives a re-scrape and resets on a serial change, i.e. on a swap. `ifName` is on the model but **deliberately never populated** — correlating by index is right often enough to look correct and silently wrong the rest of the time.
- **AssetLldpNeighbor / AssetWirelessStation** — current-state tables refreshed per scrape. **`localIfName` is a JOIN KEY, not a caption** — the System tab's Neighbor column, the alert email's LLDP block and auto-monitor's By-LLDP rule all look interfaces up by it, so `persistLldpNeighbors` canonicalizes it through the `AssetInterface` identity: LLDP-MIB hands over whatever `lldpLocPortId` / `lldpLocPortDesc` say, which on a FortiSwitch is the port DESCRIPTION (rows arrived keyed `MORGAN-221E-1` and `Tim Smith` instead of port9 and port12, duplicating one neighbour under two names and teaching By-LLDP to pin a port that doesn't exist). A stored row whose label resolves to a different port is a duplicate by construction, so it is deleted immediately rather than waiting out the 48h stickiness window.
- **AssetApRadio / AssetApVap** — a FortiAP's radios and the SSIDs each one broadcasts: the two levels ABOVE `AssetWirelessStation`, so the Stations tab renders as radio → SSID → station. Current-state, delete-replaced per scrape, plain tables with real FKs. **Two writers carrying COMPLEMENTARY columns** — the controller's `wifi/managed_ap` `radio[]` array (source `fortios`, written by discovery, which is what reaches the many APs with SNMP disabled) and the AP's own `fapRadioTable` + `fapVapTable` (source `snmp`, walked on the SNMP system-info pass; the only source for the CONFIGURED and MAXIMUM tx power, the radio mode and the country) — so the write **merges per column**: a null from a source that doesn't collect a column never erases the other's value, at the cost that a column can't be cleared back to null by a scrape (which is why nothing fluctuating is stored here). Radio IDENTITY is not merged — a `radioIndex` absent from a scrape is deleted along with its VAPs, which hang off `(assetId, radioIndex)` with no FK of their own. A VAP's identity is `vapName`, never the SSID (several VAPs commonly share one) and never the BSSID (absent on some sources) — but the two sources disagree on the NAME (FortiOS publishes the VAP object's, the MIB only the SSID), so a write matches on **BSSID first** and treats the name as an attribute of the matched row, or each source would insert its own row and delete the other's every pass; `bssid` is instead the join key down to `AssetWirelessStation.bssid`. `ssid` additionally backs the device filter's **"Broadcast SSID"** condition field — the SECOND relation-backed field, resolved through the same `scopeRelationIndex` prefetch as `interfaceName` and offered from the same monitored-only picker. Tx power is stored as each source states it and never normalized: `txPowerPct` is the controller's PERCENTAGE of the radio's ceiling, while `txPowerConfig` / `txPowerOper` / `txPowerMax` are the MIB's bare integers — that module carries **no `UNITS` clause**, so they are rendered without one rather than labelled dBm on a guess, and converting between the two would need a per-model ceiling Polaris doesn't have. The MIB publishes no MINIMUM; what it has is the CONFIGURED value, and the gap between it and the operating value is what DARRP did.
- **AssetProcessConnection** — **accumulate + age** socket facts (listening ports / outbound / inbound peers) for MAPPED processes and units. Plain table with a real FK; rows upsert on the business key behind a churn gate and age out on the `appMapConnections` retention window. `unit` is attribute-only and **backfill-only on conflict**. Unmapping deletes matching rows immediately.
- **ApplicationMapLayout** — shared Application Map drag layout (TopologyLayout pattern, one global `view="global"` row, no per-site FK). Written via `PUT /application-map/layout` (`applicationMap=write`); embedded as `savedLayout` on `GET /application-map`; localStorage is the per-browser reader fallback. Single writer: `applicationMapService`.
- **AssetMclagPeer** — current-state MCLAG ICL peers (one row per local `mclag-icl-port`), delete-replaced per scrape by `persistMclagPeers`. `peerSn` is the canonical pairing key and resolves to `matchedAssetId`.
- **AssetCustomWidgetSample** — time-series for `ManufacturerCustomWidget` probes. Standalone detail-only TimescaleDB hypertable (no rollups; `timescaleService.STANDALONE_SAMPLE_TABLES`), composite PK `(id, timestamp)`, pruned by `pruneSystemInfoSamples` on the system-info umbrella window.
- **AssetStateSample** — the **0/1 sibling** of `AssetCustomWidgetSample`: one row per (asset, state probe, table row) per scrape. Polarity is **operator-declared** via the probe's `stateMap`, never inferred — vendors disagree, so a bare `value >= 1` is wrong about as often as it's right. Two invariants: **`value` is 0 or 1 and never null** (an absent or incomparable row is DROPPED, because 0 is a positive claim of health that would clear a live alert), and **`rowKey`** is the stable dimension identity while `rowLabel` is what operators read. Deliberately no rollups — averaging a boolean gives a duty cycle, not a state.
- **AssetMacAddress / AssetAssociatedIp / AssetIpHistory / AssetFortigateSighting** — side tables behind Asset.
- **ApiToken** — bearer tokens for external callers (e.g. SIEM quarantine, NOC kiosk); each token is bound to a Role and acts with that role's permission matrix.
- **SshHostKey** — trust-on-first-use pins for SSH **server** host keys, one row per dialed `(host, port)` — no Asset FK, since a host is often onboarded before it exists as an Asset. A changed key **refuses** the connection. Gated per credential by `SshConfig.verifyHostKey`. See business rule 21.
- **Credential** — named SNMP / WinRM / SSH / REST API / HTTP credentials for monitoring probes. The `http` type carries **authentication only** (`authMode` ∈ bearer/basic/digest) and deliberately has no "none" mode — see business rule 33. Secret fields inside `config` are **encrypted at rest** by the Prisma extension in `src/db.ts` (business rule 20b) and masked on read at the API layer.
- **MibFile** — admin-uploaded SNMP MIBs used by `oidRegistry` + `vendorTelemetryProfiles`.
- **ManufacturerProfile** / **ManufacturerProfileMetric** / **ManufacturerProfileMetricOverride** / **ManufacturerCustomWidget** — operator-editable per-manufacturer telemetry profile + custom widget definitions. `widgetType` ∈ `gauge | line | table | state | http`; `state` is a state probe (see `AssetStateSample`) and `http` is an HTTP check (business rule 33). Every widget type is gated by `modelPattern` — blank means every asset of that manufacturer.
- **ManufacturerAlias** — vendor-name canonicalization map.
- **DeviceIcon** — operator-uploaded topology icon blobs (scope + key), served to the Device Map / topology renderer.
- **AssetTypeDef** — operator-extensible asset-type registry (replaces the prior `AssetType` enum).
- **User** / **Role** — dynamic-role RBAC; `User.roleId` → `Role`; permissions matrix on Role over 32 function keys.
> **The builder offers only MONITORED devices' values — and since 2026-08 so does matching.** Every inventory-derived list behind a device filter — `listScopeOptions`' manufacturers + models + `interfaceNames` (the values behind the **Device interface** condition field, one `assetInterface.groupBy` capped at 500 names), the `tag` catalogue (`listAssetTags`), and the trigger step's interface (already pin-scoped) and storage-mount dimensions — reads `monitored: true` devices only: a value that only unmonitored inventory reports is a choice that can't produce an alert AT ALL, and offering it is how an operator builds a filter, sees it match nothing, and stops trusting the picker. The **previews** follow suit and report the two halves separately (`unmonitoredCount` on `POST /automations/preview`, `matchCount` + `unmonitoredCount` on `POST /contacts/preview`) rather than hiding the remainder. **Matching now agrees**: `scopeWhere(scope, monitoredOnly)` pushes `monitored: true` into the WHERE on every EVALUATION load — threshold, composite, and the metric/state previews — and the event/change tail applies the same `assetCanTrigger` gate per row, so an unmonitored device triggers nothing. Event and change triggers were the deliberate exception until 2026-08 and no longer are (see business rule 37). The raw, unfiltered resolver survives for the surfaces asking a different question: the device-list preview (which REPORTS the remainder), the dimension-value picker, mass pinning, and `Contact.assetCondition` — a contact still OWNS a device nobody polls, ownership being an address-book fact rather than an alerting one. The storage-mount picker is the one place where offered ⊂ can-fire: unpinned mounts do get samples (`cadence:"slow"`, 24h, never rolled up) and the engine has no pin gate for storage, so a stored rule on one still evaluates — the picker steers to mounts that actually keep history. The IPAM subnet list is not inventory and stays unfiltered.

- **NotificationRule** — operator-defined alert definition — user-facing name: an **Automation**; a fired instance is an **Alert**. Carries a discriminated `trigger` (`asset_metric` | `asset_state` | `host_metric` | `event` | `change` | `composite`), an asset `scope` (nested AND/OR condition tree), unified `actions` (`notify` | `api_call` | `script` | `event`), `reset` (manual/auto/timed/condition/event — the last being the counterpart audit Event that says it recovered, for the two triggers that fire on an instant), optional `severityBands`, `escalation`, `repeat`, `resetActions` and `emailComposition`. **Rule-shape v2 supersedes the legacy `targets`/`clearBehavior` columns, which CRUD keeps rewritten as a lossless mirror** — every reader normalizes through `normalizeRuleToV2`, and input accepts both shapes. `allRuleActionRefs` is the canonical walk over all **eight** action locations. Evaluated by `notificationEngine`; CRUD gated `automationManagement` (script actions additionally require `automationScripts=fullwrite`). Vocabulary + builder catalog live in `src/services/notificationTypes.ts`.
- **Notification** — a triggered alert instance. Carries snapshotted `regionTags` + `assetHostname` so it renders after the asset is deleted, plus `templateCtx` (the fire-time token context escalation emails render from) and `escalationState`. Soft-clear preserves history. View gated `alerts:read`, acknowledge `alerts:write`, clear `alerts:fullwrite`.
- **NotificationRuleState** — per-(rule, asset, dimension) firing state machine (`clear`→`pending`→`firing`) for sustained-duration, debounce and auto-clear. **Writes only on transition**, so the engine hot path scales with *changes*, not fleet size. `assetId=""` for host/global rules. **Nothing may strand a firing row the engine can no longer see** — the vanished-state sweep clears rows whose asset left scope or whose dimension stopped reporting. **Every interface trigger reads only PINNED interfaces** (`interfaceIsPinned`), and the IPsec pair gates the same way (`tunnelIsPinned`).
- **Contact** — an address-book entry: a named email address alerts can route to, whether or not the recipient holds a Polaris account. `origin` (`manual` | `entra` | `ad`) says WHO owns the row — a directory-synced row is the sync's until an operator adopts it, and the backend names line up with `AddressBookEntry.source` so the picker's badges need no translation. `kind`, `jobTitle`, `department` and `phone` carry directory identity (employee PII at rest — see business rule 35). Synced rows are visible only to `automationManagement:read`, not to the `contacts` key every built-in role holds. `email` is unique, trimmed and lower-cased. Device ownership is stated once on the contact via `assetCondition` (the same condition tree automations use, over the wider `DEVICE_FILTER_FIELD_OPS` vocabulary) unioned with explicit `assetIds`. "All devices" is reachable only through an explicit `assetAllDevices` flag, so a half-built empty tree can never hand a contact the whole fleet. Fire-time lookup evaluates against the ONE triggering asset — never a fleet scan.
- **MaintenanceSchedule** — operator-defined maintenance window definition. Targets = union(criteria matches, explicit `assetIds`) ∩ `monitored=true`; `schedule` is recurrence JSON in **server-local wall-clock**, evaluated per tick so DST is automatic. Reconciled by `maintenanceScheduler` (30s) and inline on every CRUD write. Ad-hoc one-shots self-delete once spent. See business rule 16.
- **AssetMaintenanceWindow** — one realized maintenance window per (asset, schedule). **Open rows (endedAt NULL) are the restart-safe source of truth** for "in maintenance"; closed rows power the chart bands (`scheduleName` snapshotted so labels survive schedule deletion). Plain table with a real FK.
- **NotificationChannel** — operator-configured outbound delivery integration (Automations → Delivery tab). `type` ∈ `smtp | oauth_m365 | pushbullet | slack | teams | web_push` selects transport + `config` shape; secrets masked on read, preserved on write. `web_push` is a singleton (one server VAPID keypair).
- **NotificationDelivery** — one outbound delivery per (notification, channel, concrete recipient), carrying `transport`, `target`, `meta` and retry state. Destination secrets stay on the channel and are read at send time. Expanded at fire time by `notificationRecipientService`, drained (≤3 retries) by `deliverNotifications`. Cascades with the Notification.
- **Alert email** — leads with **what fired, in the builder's own words, with the reading in it** (`{trigger.summary}`), then the chart that explains that trigger, a device facts table, last-hour CPU/memory/response-time charts, and Acknowledge + Open device buttons. The default body is a shared TEMPLATE (`src/utils/alertEmailTemplate.ts`), not server-side string building, and the wizard prefills new Notify actions with the same strings so what Polaris sends is what an operator can edit. Charts are built at DELIVERY time by `alertChartService` and degrade to a text line when samples or the rasterizer are unavailable. **A gap in those three charts is drawn exactly as the in-app charts draw it** (UI-GUIDE section 15): the line DIVES to the baseline in red across the outage and climbs back out, each transition fading between the series color and red. Excluding failed probes keeps the values honest but leaves the polyline interpolating a healthy-looking segment through the exact minutes nothing answered, so the dive is what says an outage happened. It was a red BAND until 2026-08-27, which is band vocabulary — reserved for maintenance windows, i.e. a gap that IS explained — and therefore backwards. **A miss the upstream explains dives GREY, not red**: a failed probe taken while the asset was dependency-suppressed is stamped `AssetMonitorSample.dependencyDown`, and `probeOutageService` hands every reader an `OutageKind` per window — same dive (nothing was measured either way), no accusation, because Polaris knows exactly why that probe missed. A window splits at a change of kind, so misses that were unexplained when they happened are never retroactively excused. The email surface may still diverge on size, flat-hex palette, absence of hover and run-collapsing; never on the shape of an outage, nor on which colour it is. The one band left is `alarmSpans` on the sensor chart, a different claim about a reading that is still arriving. `failSpansFrom` delegates to `probeOutageService.foldProbeOutages` so email and in-app cannot disagree about an outage's bounds. Rendered bodies are **pruned** so an under-populated device never mails blank cells — note `pruneEmptyRows` **may never match across a nested `<table>` or a second `<tr>`**, which once closed the 600px card early and mailed a visibly broken box. An alert about Polaris itself says so.
- **PushSubscription** — a browser/PWA Web Push subscription owned by a User. Carries **`surface`** (`desktop` | `mobile`) recorded at subscribe time — the only moment it is knowable, since on Android the installed PWA and the browser share one subscription — which selects the push deep link. A 410/404 prunes the row; endpoint rotation retires the old row scoped to the caller's own `userId`.
- **AutomationScript** — operator-authored script registry for Automation `script` actions. **RCE-equivalent surface**: CRUD and attaching script actions are gated by `automationScripts`, seeded fullwrite only for admin-equivalent roles; creation and body changes stamp warning Events with old/new sha256.
- **AutomationScriptRun** — one execution of a registry script. Server runs are claimed by the `runAutomationScripts` job and executed via `automationScriptRunner` (0600 temp file + execFile, SIGKILL on timeout) — **never inline in the engine or drain**. Two hardening properties: the interpreter resolves to a known absolute path, and the child environment is `process.env` **stripped of secret-shaped keys** (stdout is stored on the row and rendered in the UI, so a one-line `env` used to copy `DATABASE_URL` into a displayed column). Agent runs ride the AgentCommand queue.
- **HostMetricsSample** — Polaris host CPU / memory / load time-series sampled every 30s by `hostMetricsCollector` (web/all role only); `host_metric` rules read the latest row. Plain prunable table (7-day retention).
- **AgentCommand** — the agent command queue. The only queued action is agent-side script runs (`run_script`, sha256 VERIFIED by the agent before executing). The agent polls, executes in the `scriptexec` sandbox, reports back — it **never self-acts and refuses unknown actions**. Process/service start/stop/restart control was removed in the Satellite-posture change.
- **GroupMapping** — IdP group → role + tags map for OIDC / LDAP / SAML SSO login (`provider` + `groupKey`; nullable `roleId` for tags-only mappings).
- **ManagedAgent** — Polaris Agent install record per Asset (os/arch, version, install credential, cert-pin set for dual-pin rotation, curated `installScriptId`). `privilegeTier` (Linux-only) selects the systemd unit: `unprivileged` (hardened) or `ptrace` (that unit plus `CAP_SYS_PTRACE` **and** `CAP_DAC_READ_SEARCH` — **both are required**; SYS_PTRACE alone collects zero rows). Unit text is written only at install/reinstall, so pre-fix ptrace agents need a reinstall; the agent reports its actual CapEff on heartbeat so the UI shows the VERIFIED state. Full root was retired with service control.
- **UserDashboard** — per-user dashboard layout (widget set + positions).
- **UserTableTabs** — per-user list-page tabs (the Assets page tab strip), one row per `(user, scope)`, each tab carrying its own filter+sort state. A tab opened from a preset keeps only a REFERENCE for its label — editing it never writes back, since the preset may be someone else's. A tab may additionally pin one preset as its **base filter** (`defaultFilterId` + `defaultFilterName` + `defaultState`), the view it RESETS to — which is what makes filtering *inside* a saved filter survivable, and which swaps the page-controls row's "Clear Filters" for **"Reset Filter"** while it is set. `defaultState` is a SNAPSHOT and is the single truth for "this tab has a base" (a label with no snapshot is normalized away), so a preset deleted by its owner can never cost a tab its way back; the client re-syncs the snapshot from the live preset every time it lists them, which is how an edit to the preset reaches the tabs based on it. A tab also owns its **favorites** (`favoriteIds`, capped at `MAX_TAB_FAVORITES` = 500) — the starred rows that float to the top of THAT view. They live here rather than in localStorage (where the blocks / subnets / widget-library stars still live) because a favorite is part of a view, and a view follows the operator across browsers; `public/js/favorites.js` grew a **provider seam** (`registerFavoritesProvider`) so the Assets page's existing star / query call sites resolve to the active tab with no page-side change. `favoriteIds: null` means "predates per-tab favorites" and is the one moment the client may seed the tab from the legacy per-user localStorage set — normalizing it to `[]` would let a second browser re-seed tabs the operator had since curated. Strictly per-caller, no Event audit, cascades with the user. Absent row = the default single tab.
- **SavedTableFilter** — a named, optionally SHARED snapshot of one list page's filter + sort state. `scope` names the table and maps to the RBAC key that already gates that page — no new permission key. `state` is re-validated on every write because a public preset is replayed into other operators' browsers. `ownerId` is SetNull, so a shared preset outlives its author.
- **TopologyLayout** — SHARED Device Map topology node positions, one row per (siteId, view). Written full-replace by operator drags (gated `deviceMap=write`, last-write-wins); server layout wins over the per-browser localStorage fallback. Cascades with the site Asset.
- **Event** — audit log, 7-day rolling retention. Four per-asset **change events** (`asset.firmware.changed` / `asset.switch_port.changed` / `asset.wireless_ap.changed` / `asset.gateway_firewall.changed`) are written edge-triggered and **unconditionally**, never behind the `change.*` subscription gate. Row builders are pure and centralized in `eventLogService`; discovery emits them from an end-of-run baseline, because coarse-then-corrected phases ping-pong within a single run.
- **Conflict** — discovery-vs-existing conflicts (reservation + asset variants; the asset variant also covers the ip-override flavor — `proposedAssetFields.collisionReason="ip-override"`, raised when discovery disagrees with an operator IP pin).
- **DiscoveryRun** — per-integration discovery-run state; one row per integration. `scopeDeviceName` marks a single-FortiGate scoped re-discovery, whose finalize runs per-controller decommission only, never the roster-based sweeps.
- **NetworkScan / NetworkScanRun** — a saved, re-runnable **active scan** of operator-supplied IP ranges (operator-facing name: a **Discovery**), and one row per execution. Reached from the Assets page's `+ Add Asset(s)` menu, not Integrations: the path for equipment that answers SNMP or a REST API but belongs to no controller and no directory. Deliberately **not** a `DiscoveryRun` row (that table is one-per-integration and a queued row there would trip the backup-restore guard and show up as an integration that isn't one) and deliberately **no `network-scan` AssetSource kind** — adoption creates assets like the manual `POST /assets` path. **Adoption is new-addresses-only**, so a re-run enriches nothing. Gated by the `networkScan` key with `assets:write` chained for adoption. See business rule 34.
- **Setting** — key-value config store (`manualMonitorSettings`, `sampleRetention`, `mapRegions`, `branding`, `backupSchedule`, `assetSourcePriority`, `reservationMacPlaceholder`, `loginAccessConfig`, `dashConfig`, `agentEventLog`, etc.). Secret-bearing rows are encrypted at rest (business rule 20b). `assetSourcePriority` orders learned-location precedence (business rule 22); `reservationMacPlaceholder` is the synthetic-MAC OUI (business rule 26).
- **MonitorClassOverride** — tier-2 of the monitor settings hierarchy; manual-scope only post-Phase-2.
- **Tag** / **GeocodeCache** — registry tables. `Tag` carries an optional **auto-assignment device filter**; when set, `tagAssignmentService` keeps the tag synced onto matching assets (managed sync — adds AND removes on drift). The shape is `assetCondition` — the SAME nested AND/OR condition tree the automations device filter and `Contact.assetCondition` store, edited in the same shared `PolarisConditionBuilder` and evaluated by the same `evaluateScopeCondition` — which superseded the flat `criteria` blob it shipped with (still READ, one shape live per row, folded forward by `criteriaToCondition` + the `migrateTagFilterShape` one-shot; an `integration` rule is the one thing the tree can't express, so a blob carrying it stays on the legacy predicate). Two asymmetries with `Contact`: an **empty tree is NO filter, never "all devices"** (a tag has no All-devices control, so an empty tree could only come from a half-built form and honoring it would tag the whole fleet on save), and a **decommissioned asset is skipped unless the filter mentions status**. The **"Map Regions" category is locked to the Device Map** — the registry refuses creating a tag in it or moving one in, and a tag in it may not carry a filter, since `RegionTagAssignment` already manages those names and a second managed-sync engine on the same string would undo the first every cycle. **TagAutoAssignment** is the per-(tag,asset) provenance table that lets managed sync strip auto-applied copies without touching a hand-applied copy of the same tag. **RegionTagAssignment** is the same pattern for `region:` tags, keyed by region id so a rename doesn't disturb it. **DirectoryContactSource** is that pattern again for the address book: one row per (integration, directory object) the GAL sync created, so a reconcile deletes only what it wrote and a hand-added row (which never has one) survives forever. A person in BOTH directories owns ONE Contact with TWO provenance rows, and the Contact dies only when its last one goes; the Contact is PROJECTED from the set rather than last-writer-wins, so two directories that disagree can't ping-pong it. **No FK on `integrationId`, deliberately** — a cascade would strip the provenance and strand the rows it justified.

See business rule 33.) **`rest_api` is gated on being able to make a FortiOS call at all**: a FortiManager on the PROXY transport with no `fortigateApiToken` cannot, because every FortiOS collector builds its config through `buildFortinetConfig()`, which has no `useProxy` branch — it dials the asset's own IP and needs that token. `defaultPollingForSource` therefore returns `disabled` for cpuMemory / temperature / interfaces there (response time stays `icmp`, unchanged deliberately), and the resolver's validity gate skips a *stored* `rest_api` the same way it skips any method the source can't use, so the layer below stays — non-destructively, since the stored value returns the moment a token is supplied. The one exception is a managed FortiSwitch / FortiAP's response time, which rides the parent gate's controller table via `fetchViaFortinetTransport` (the one monitoring path honouring `useProxy`) and works on FMG's own credential; the shared predicate is `fortiosRestUsable(stream, assetType)`. Note the condition is NOT "proxy mode" — proxy WITH a token is a valid setup and keeps the normal REST defaults. The **`fortimanager`** polling method (2026-08-28) asks FortiManager's own device database instead of the device: **response-time only** (`FORTIMANAGER_STREAMS`) on the **`fortimanager` source only**, reading `conn_status` / `ha_slave[].status` out of one NATIVE `/dvmdb/adom/<adom>/device` call that is outside the `/sys/proxy/json` concurrency-1 lane and covers the whole fleet — so ~187 gates cost one round trip, and a gate Polaris has no route to is still reachable. Keyed by **serial, never the FMG device name**; **FMG unreachable ⇒ `ProbeResult.skipped`**, never a miss (one manager outage must not down a fleet — the vCenter rule). It is lagged, second-hand, and carries **no uptime** (so no reboot detection), and FMG stores no metrics of any kind, which is why it is one stream rather than a transport. **Not a source default** — response time stays ICMP. The **`vcenter`** polling method covers FOUR streams (`VCENTER_STREAMS` in `pollingCompatibility.ts`, enforced by `isMethodValidForStream`): `responseTime`, `cpuMemory`, `interfaces` and `storage` — everything the vCenter server publishes about a VM or an ESXi host. It is the **source default for all four on both roles** (it was cpuMemory-only until 2026-08, with response time on ICMP), which is what lets a vCenter fleet be monitored with no credential in the guest, no SNMP enabled on ESXi and no reachable guest IP. Two warm caches in `monitoringService` (30s TTL + promise-singleton, one SOAP round trip per integration per tick each) back it: `fetchVcenterQuickStatsCached` for VMs (CPU/RAM, power state, uptime, `guest.disk`, `guest.net`) and `fetchVcenterHostSnapshotCached` for ESXi hosts (CPU/RAM, connection state, uptime, pNICs + VMkernel ports + virtual switches, paired with the datastore inventory in ONE session — the SAME fetch discovery's Phase 2 uses, whose two halves report failure separately so a host-property gap can't cost discovery its datastore detail). **A host's interfaces arrive nested**: `buildVcenterSystemInfo` writes each vSwitch (standard, or the host's end of a DVS) as an `ifType:"aggregate"` row and stamps `ifParent` on its uplink pNICs and on the vmks riding its port groups — the FortiSwitch-trunk shape, so the System tab nests it unchanged — and each vmk picks up its port group's `vlanId` through the same name-to-name join. A vSwitch's `operStatus` is derived (up while any uplink is up, **null with no uplinks at all**, since an internal-only vSwitch is not an outage) and carries no `speedBps`, vCenter publishing no aggregate rate. Teaming policy, port counts and the port-group VLAN table are inventory and render on the host's General-tab Virtualization section instead; a DVS's own configuration is a per-vCenter object and is deliberately not read. `readVcenterAsset` resolves the reading through the asset's `vcenter-vm` **or** `vcenter-host` AssetSource — not `discoveredByIntegration` — which is also why the method is allowed on the directory source kinds (a vCenter sync merges into AD/Entra-discovered VMs); the per-asset PUT validation requires that row. **Absent ≠ unreachable**: vCenter answering without this asset in it is a real finding and fails the probe, while Polaris being unable to ASK skips it (`ProbeResult.skipped` — no sample, no counter, cadence anchor only), so a vCenter outage can never declare an entire virtual fleet down at once. Temperature and LLDP stay unavailable on the method; the dedicated storage-only cadence (`runStorageFor`) stays SNMP-only because vCenter storage already rides the system-info pass.

## Authentication & RBAC

Sessions are PostgreSQL-backed (`connect-pg-simple`), 8-hour max age, HttpOnly/Secure/SameSite=Lax cookies.

**Dynamic-role model (post-cutover).** RBAC is enforced via `requirePermission(functionKey, level)` from [src/api/middleware/permissions.ts](src/api/middleware/permissions.ts). Each route declares the function key it gates + the required access level; the resolver consults the caller's `Role.permissions` matrix denormalized into `req.session.roleSnapshot` at login. The matrix is `{ [functionKey]: "none" | "read" | "write" | "fullwrite" }` over a 32-key catalogue. The five built-in roles (`admin` / `readonly` / `networkadmin` / `assetsadmin` / `user`) are seeded by `prisma/migrations/20260524000000_roles_table_cutover` so existing accounts keep their pre-cutover access exactly. Admin creates custom roles from the Roles section under Users → Manage Roles.

| Built-in role | Locked? | Pre-cutover behavior preserved |
|---|---|---|
| `admin` | Protected — cannot be edited or deleted; hidden from the editable list | every function = `fullwrite` |
| `readonly` | Protected | every function readable by non-admins = `read`, admin-only functions = `none` |
| `networkadmin` | Editable, cannot delete | IP space / integrations / map-regions / discovery-conflicts write; read elsewhere |
| `assetsadmin` | Editable, cannot delete | assets / quarantine / monitor-settings write + own-subnet/own-reservation write |
| `user` | Editable, cannot delete | own-subnet / own-reservation write; read elsewhere |

**Ownership model for networks, reservations and contacts.** `subnets`, `reservations` and `contacts` carry an ownership dimension: `write` lets the caller edit only rows where `createdBy` matches their username; `fullwrite` bypasses the ownership filter. Built-in `user` and `assetsadmin` are seeded with `write`, `networkadmin` and `admin` with `fullwrite`. Route handlers branch on `req.permissionLevel` (set by `requireOwnership(functionKey)`). **A `dhcp_lease` is not a reservation:** it's observed device presence, so reserving an IP that currently shows a lease is a plain *create* (gated on the caller's `reservations:write`), NOT a release of someone's row — `reservationService.createReservation` supersedes the observed lease server-side via `releaseSupersededDhcpLeaseAt`, which **delegates to `releaseReservation`** (so on push-enabled subnets the FortiGate lease is expired via `releaseDhcpLease`, on read-only subnets it's a pure DB release — identical to the old client `release+create` flow, minus the route ownership gate). This parallels how `createReservation` already supersedes `dns_resolved` via `releaseDnsResolvedAt`. The create's collision check excludes `dhcp_lease`, `dns_resolved`, **and lease-backed `fortiswitch`/`fortinap` rows** (`Reservation.dhcpBinding === "lease"` — see business rule 23); `manual`/`dhcp_reservation`/`vip`/`interface_ip` and infra rows that aren't lease-backed are authoritative and still 409. The takeover set has one definition, `isSupersedableByCreate` in `reservationService.ts`, shared by the 409 check and the supersede-release. Because the take-over is a create, the IP-panel "Reserve" button (desktop `_openLeaseReserveModal` + mobile reserve sheet) no longer issues a separate ownership-gated DELETE. (The `owner` column is display metadata with no role in the ownership gate — on discovered rows it carries the matched asset's `assignedTo`; on manual creates/updates it auto-stamps to the caller's username when not explicitly typed. Gating rides `createdBy` only.)
**Function-key catalogue (32 keys).** Single source of truth in `src/api/middleware/permissions.ts:FUNCTION_KEYS`. (Newest — **`networkScan`**, migration `20260825040000_network_scan`: the active-scan **Discovery** feature — create / edit / run a saved sweep of operator-supplied IP ranges and adopt what answers. Its OWN key rather than part of `assetsProbe` (probe-now / SNMP walk on ONE existing asset), because an unannounced sweep is IDS-visible and is exactly the capability an admin may want to withhold from someone who may still edit inventory. `read` = browse saved Discoveries + watch a run; `write` = create / edit / delete / run / import. Seeded admin=fullwrite, readonly=read, networkadmin/assetsadmin=write, **user=none** (that role exists for IP-space self-service). ADOPTING is chained: `POST /network-scans/:id/adopt` requires this key's `write` AND `assets:write`, the `PUT /application-map/discovery` precedent — so "may scan" and "may create assets" stay separable. Before that — **`contacts`**, migration `20260810000000_contacts`: the address book, and the third key to carry the **ownership dimension** (`hasOwnershipDimension`) alongside `subnets` / `reservations` — `read` browses, `write` adds and edits/deletes only rows the caller created, `fullwrite` manages anyone's. Seeded admin=fullwrite, readonly=read, networkadmin/assetsadmin/user=write. Before that — the **Automations cutover**, migration `20260721000000_automations_rbac_rename`: `notifications` → **`alerts`** and `notificationManagement` → **`automationManagement`** (levels carried over verbatim), plus new **`automationScripts`** — automation script-registry CRUD + attaching script actions; **RCE-equivalent** (server scripts run as the polaris service user, agent scripts as the agent's user — unprivileged on Linux, LocalSystem on Windows), seeded `fullwrite` only for admin-equivalent roles (users+roles=fullwrite), else `none`. Runtime compat: `LEGACY_KEY_ALIASES` + `permissionOf()` in `permissions.ts` resolve the old key names from pre-deploy session snapshots and `normalizePermissions` folds them on write — never remove that without a session-invalidation plan. Prior additions: `applicationMap` (`20260721000000_application_map` — Application Map page/graph read + shared-layout write, mirrors deviceMap: admin=fullwrite, other built-ins=read), `maintenanceManagement` (`20260715000000`), the notification keys (`20260628000000`), `processControl` (`20260627000000` — now vestigial: process/service control was removed in the Satellite-posture change, so the key remains in the catalogue for matrix compat but gates nothing); removed: vestigial `reservationPush` (`20260703000000`).) Exposed at `GET /api/v1/roles/functions` so the frontend matrix UI renders without hardcoding the list. Adding a new key requires a migration to seed it on every existing Role + a corresponding guard at the route layer; removing one requires a migration to strip it (`normalizePermissions` also drops unknown keys on the next role write).

**Session role snapshot + cache invalidation.** `req.session` carries `roleId` + a denormalized `roleSnapshot` stamped at login. Every `requirePermission` call hits a module-level `Map<roleId, updatedAt>` cache first (O(1)); a Role write bumps the map via `bumpRoleVersion(roleId, updatedAt)` and the next request from any session holding the stale snapshot triggers ONE Prisma fetch + `req.session.save()` to refresh. Changing a user's `roleId` takes effect on next login; changing a role's permissions takes effect on the next request for every session that holds the role.

**Region tags + other tags (storage-only consumer pending).** `Role`, `User`, and `GroupMapping` each carry two operator-typed tag dimensions: `regionTags: String[]` and `otherTags: String[]` (free-form). Empty = unrestricted. Effective scope for a session is `union(role, user, group-derived)` per dimension. Returned by `GET /api/v1/auth/me` as `{ regionTags: { user, role, group, effective }, otherTags: {...} }`. Group-derived tags are re-resolved live from `User.ssoGroups` on each `/auth/me` (never persisted onto the user's own columns, so operator-set tags survive a re-login). Normalization is shared in `src/utils/tagNormalize.ts`. **Assign Tags edits both dimensions through the ONE tag picker**: a map region already IS a registry tag (`region:<name>` in the locked Map Regions category), so the separate Region Scope control listed the same names twice in the same dialog. The prefix carries the split instead — the picker seeds each region tag under its registry name and `_splitUserTagScope` routes anything so prefixed back to `regionTags`, bare, which is what keeps region-ONLY consumers (`resolveUsersByRegions`, level-scoped routing, Device Map "My regions") reaching the same people. The role slide-over and Group Mappings still carry the two pickers separately. The **Users list draws BOTH dimensions** under the username (`userTagPillsHtml`, regions in their map colour then tags in their registry colour) — it drew regions alone while Region Scope was its own control, which after the merge read as “my tags did not save”. The browser picker behind the second dimension (Users → a username → **Assign Tags**, the role slide-over, and Group Mappings) offers the `Tag` registry as selectable pills and creates a registry row — in an operator-chosen **category** — for a typed name that isn't in it when the caller holds `serverSettingsSystem:fullwrite` — but the stored values stay bare free-form strings with **no FK to that registry**, so deleting a tag there strips nothing from any principal's scope. **A region RENAME carries these columns with it and a region DELETE never strips them** (`regionScopeService.renameRegionInPrincipalScopes` / `principalsScopedToRegion`, called from the `/map/regions` PUT and DELETE): the columns hold bare region names with no FK to any registry, so a rename that left them behind revoked every scoped operator's region in silence — tag present, matching no region, every name-resolving consumer (Device Map "My regions", the dashboard region filter, `recipientDeviceRegion`, level-scoped routing) quietly reaching nothing. A delete has no new name to move an assignment to, so the assignment survives and a warning Event names who now holds a dangling one. The rename bumps `notificationRecipientService.bumpRecipientIndex()`. The downstream consumer (list filters, map scoping) still lands in a separate change.

**SSO/LDAP login + IdP group mapping.** Beyond local accounts and Azure SAML, Polaris supports **OIDC** (Authorization-Code + PKCE via `openid-client`; `oidcAuthService.ts`), **LDAP/AD bind** login (`ldapAuthService.ts` over the shared `ldapClient.ts`; LDAP routes through the existing `POST /auth/login` form), and **Entra Application Proxy header-based SSO** (`entraProxyAuthService.ts`; for installs published externally through Entra App Proxy — see below). `authProvider` is now `"local" | "azure" | "oidc" | "ldap" | "entra-proxy"`. At SSO/LDAP login the user's IdP groups are matched against `GroupMapping` rows (`groupMappingService.resolveGroupsToAccess`, scoped by provider — `GROUP_MAPPING_PROVIDERS = oidc/ldap/saml/entra-proxy`) to assign a role + tags: **highest-privilege role wins** (`rankRole` in `permissions.ts`), tags from all matched groups union. No match → keep an existing user's role (new user → `readonly` + `needsRoleReview`). Group-mapping CRUD is gated on `users=fullwrite` (no new function key) and exposed at `/api/v1/group-mappings`; managed in the UI under Users → Group Mappings. **Security caveat:** a mapping to an admin-equivalent role makes IdP group membership a path to Polaris admin (outside the `lastAdminEquivalent` guard) — `groupMappingService` stamps a warning Event when one is created/updated. OIDC requires `POLARIS_PUBLIC_URL` (derives the redirect URI); Azure-AD's `groups` claim emits group object-IDs (GUIDs), so map those IDs unless the IdP is configured to emit names.

**Entra App Proxy header SSO (`entra-proxy`).** For installs published through Microsoft Entra Application Proxy with Entra ID pre-authentication + header-based SSO: App Proxy authenticates the user in the cloud and forwards their claims (UPN, object-ID GUID, group object-ID GUIDs) as operator-named **plain HTTP headers** (configured in the App Proxy SSO blade). Polaris reads them at `GET /auth/entra-proxy/login`, matches on `User.azureOid` (shared with SAML — a user who signs in both ways converges to one account), provisions via `ssoProvisioning`, and stamps a session. **The headers are UNSIGNED — the entire security model is source-IP trust:** Polaris honors the identity headers ONLY from operator-allowlisted App Proxy connector IPs (checked against `req.ip`; empty allowlist = header login disabled, fail closed), and a strip middleware (`api/middleware/entraProxyHeaders.ts`) removes them from every untrusted request as defense in depth. Users arriving from a trusted source are silently auto-logged-in (no login page) via the app.ts protected-page branch; a fallback button shows on the login page only when the request is trusted + carries headers. Config + trusted-IP allowlist + header-name mapping live on Users → Authentication → App Proxy (Setting key `entraProxy`, no secrets). The **Test** button reports the request's source IP as Polaris sees it — the value to put in the allowlist. Note: Entra silently omits the groups header past ~150 groups unless the App Proxy app uses "groups assigned to the application".

**Role-bound bearer tokens.** Each `ApiToken` is bound to a Role at mint time (migration `20260706000000_api_tokens_role_cutover` — replaced the prior fixed scope strings `assets:read` / `dashboard:read` / `assets:quarantine`; legacy tokens were mapped onto seeded `api-*` roles with matching matrices). Token callers pass the same `requirePermission` gates as sessions: the token's role matrix is resolved through an in-process cache invalidated by `bumpRoleVersion`, so a token reaches exactly what its role grants — including filter-don't-403 surfaces like `/search` and `/dashboard/noc-summary`. `requireSessionOrTokenPermission` is retired. `integrationIds` on the token is required when the bound role grants `assetsQuarantine` ≥ write (per-integration quarantine scoping is unchanged). Binding a token to an admin-equivalent role logs an `api_token.admin_equivalent` warning Event (same posture as group mappings). A role bound to any token refuses deletion (friendly 409). **CSRF exemption:** requests carrying `Authorization: Bearer` skip the CSRF token check in `csrf.ts` — cross-site attackers can't attach custom headers, and this is what lets token writes (quarantine push, role-granted mutations) through; authentication is still fully enforced downstream. Write routes reachable by tokens attribute Events via `requestActor(req)` (`api:<token name>`) from `auth.ts`.

**Last-admin invariant.** `roleService.countAdminEquivalentUsers` + `roleService.isAdminEquivalentRole` (in `src/services/roleService.ts`) back the guard that refuses any operation that would leave Polaris with zero users holding `users=fullwrite` AND `roles=fullwrite`. Enforced in `src/api/routes/users.ts` on `PUT /users/:id/role` and `DELETE /users/:id`.

Rate limiting: 10 login attempts / 15 min per IP (limiter in `src/app.ts`). Additional per-surface limiters live in `src/api/middleware/rateLimits.ts`: TOTP confirm/disable (10 / 15 min, mirrors login), OIDC login kick-off (30 / 15 min), Entra App Proxy header login (60 / 5 min — deliberately generous: all App Proxy users share the connector IP, and there's no guessable-credential surface), IdP-driven SSO callbacks + the public `/entra-proxy/config` probe (300 / 5 min — a callback carries a signature-validated assertion rather than a guessable credential, so the limiter bounds flood volume, not guessing; per-IP, and one NAT egress address can carry a whole site's shift-start logins), admin maintenance/backup/logo/login-access routes (120 / 5 min), SIEM quarantine verify (300 / 5 min), agent bearer router (1200 / 5 min — per-IP, far above any healthy agent's cadence), agent binary downloads (60 / 5 min). The first-run setup server has its own limiters (whole server 600 / 5 min; DB-touching wizard routes 30 / 15 min) built from the same `makeRateLimiter` factory. Azure SAML SSO is optional; users are auto-provisioned on first login with the `readonly` role.

**FMG auth note:** FortiManager 7.4.7+ / 7.6.2+ removed `access_token` query string support. The service uses the Bearer `Authorization` header exclusively. The standalone FortiGate integration (`fortigateService.ts`) uses the same Bearer pattern. **Never call `/sys/logout`** — Polaris authenticates with a predefined REST API Admin api-key, which per Fortinet's FMG API Best Practices Guide is permanent and shares one session per user; logout/login endpoints are for session-based auth only. A prior hourly `/sys/logout` (commit 3e70476) tore that shared session out from under the split-role monitor/discovery processes and caused RPC `-11` "no valid session" churn — removed. The transport layer (`rpcInner`) retries transient faults only (5xx/network, ≤2 retries, exponential backoff, serialized in the FmgWorker lane) and fails fast on permanent ones (401/403/404/405, `-11`).

**Stale-Secure-cookie gotcha (HTTPS → HTTP downgrade):** A `Set-Cookie` from a non-secure origin is silently rejected by Firefox/Chrome if a same-name `Secure`-flagged cookie already exists, and the rejection extends to `Max-Age=0` deletions. The middleware in `csrf.ts` detects the case (HTTP request, no `polaris_csrf` cookie sent at all) and returns a specific error message instructing the operator to clear cookies for the site. The frontend in `public/js/api.js` does a parallel pre-check before mutating requests. Operator-clears-cookies path is the only reliable recovery on Firefox/Chrome.

## Discovery Workflows

Seven integration types feed discovery: **FortiManager** (multi-FortiGate via FMG; proxy or direct realtime per `useProxy`), **standalone FortiGate** (single device via REST), **Entra ID / Intune** (Microsoft Graph), **on-prem Active Directory** (LDAP/LDAPS), **Windows Server** (WinRM DHCP), **VMware vCenter** (vSphere Automation REST session auth + two narrow SOAP property-collector calls against `/sdk` for what REST can't provide: batched VM quickStats and datastore backing/host-mount info — `vcenterService.ts`), and **Azure Arc** (Arc-enabled servers via Azure Resource Manager — `azureArcService.ts`; the Connected Machine agent runs in the guest, so hostname/OS/serial come from the host itself rather than a directory record. Two opt-in enrichments — `enableVmInstances` (Arc-enabled VMware/SCVMM placement, which also supplies the `instanceUuid` that dedupes against a vCenter integration) and `enableSqlServer` — add one Resource Graph query each and create NO assets; both fold into the owning machine's `observed` blob). All produce assets and (for FMG/FortiGate) subnets / reservations / VIPs. Discovery is triggered manually or by `discoveryScheduler.ts` on each integration's `pollInterval`.

**vCenter** discovers VMs (`assetType="server"` — the dedicated `virtual_machine` type was retired 2026-07; VM identity lives in `Asset.virtualization` + the vcenter-vm AssetSource row), ESXi hosts (`"hypervisor"`), and datastores (current-state `VcenterDatastore` table, delete-replaced per run, with NAA-prefix array-vendor identification — `vendorFromNaa`). VM match cascade: `vcenter-vm` AssetSource by externalId (instanceUuid, `${integrationId}:${moref}` fallback) → vNIC MAC (positive-identity takeover of directory/Fortinet-discovered assets) → hostname collision → Conflict → create. Hosts sync first so each VM's `Asset.virtualization` blob can link `hostAssetId`. VM→host placement feeds `AssetDependencyParent` rows with `source="vcenter"`, vMotion-safe: a VM on a clustered host gets one edge per cluster-member host, so all-down suppression fires only when the entire cluster is dark. Merged assets keep their directory assetType (flip only from `"other"`) and their `discoveredByIntegrationId`; the vcenter-vm source row is how the monitor collectors find the vCenter integration. **Guest filesystems are not a discovery fact** — discovery stopped pulling `/guest/local-filesystem` per VM in 2026-08 (one REST call per VM per run) because the `vcenter` storage stream samples them every system-info pass instead, so they belong in the System tab's Storage table with history, pinning and alerting rather than as a static table on the General tab. Because VMs share the `server` type with directory machines, the VM-class behaviors (dependencyLayer=2 stamp, vmMonitor monitored-sweep) gate on ownership — `discoveredByIntegrationId` — not on the type, so vCenter never fights a directory integration over a MAC-matched server it merely enriches. The vCenter classes reuse the workstation/server-style per-class config blocks as `vmMonitor` (full: agent deploy + interface/storage auto-monitor) and `hostMonitor` (addAsMonitored + streams only); the internal auto-monitor/deploy klass name stays `virtual_machine` even though the assets it selects are servers (queries always pair it with `discoveredByIntegrationId`).

A VM or ESXi host that leaves the vCenter inventory is **decommissioned only if nothing else claims it**: the last pass of `syncVcenterDevices` deletes the stale `vcenter-vm` / `vcenter-host` source rows, and an asset thereby left with NO `AssetSource` row at all is flipped to `decommissioned` (`asset.vcenter.decommissioned`, maintenance window force-closed first). Any surviving source — a directory record, an `arc` row, a reporting agent, the `manual` row of an operator-created asset — leaves the asset untouched. Absence only counts when the read was whole: `vcenterSweepBlockedReason` skips the pass (deletes included) on an incomplete inventory (a per-host VM list failed — those are logged rather than failing the run) or an empty one, and `partitionStaleVcenterSources` retains VMs still present in the raw pre-filter listing so changing `vmInclude`/`vmExclude` decommissions nothing.

The **AD / Entra / Azure Arc** Monitoring-tab Workstations/Servers subtabs additionally support, per class: **agent auto-deploy** (opt-in, default off — pushes the Polaris Agent to newly-discovered, agent-less devices over SSH/WinRM during discovery, bounded + paced + idempotent; `agentAutoDeployService.ts`) and **interface + storage auto-monitor** (`autoMonitorInterfacesService` reused for the `workstation`/`server` classes + new `autoMonitorStorageService` pinning `Asset.monitoredStorage`). Both run as post-sync passes in `runDiscovery`. Storage auto-monitor is AD/Entra-only (not on the Fortinet classes). Since these devices only report interfaces/mounts via the agent, auto-monitor pins land the cycle after the agent first reports — self-healing. A third post-sync pass, **network-presence verification** (`presenceVerificationService.ts`; integration-level `config.verifyPresence` toggle on the Monitoring tab, default ON), establishes `Asset.lastSeen` for directory-sourced assets — cheapest signal first: already-fresh lastSeen → agent heartbeat → answering monitor probe → single-ICMP fallback against the DNS name. A failed ping writes nothing.

Assets converge via the multi-source model: every discovery pathway upserts `AssetSource` rows keyed on `(sourceKind, externalId)`, then `projectAssetFromSources()` derives the projected Asset row (hostname, serialNumber, manufacturer, model, os, osVersion, learnedLocation, ipAddress, lat/long, snmpLocation, learnedAddress) by priority — `polaris-agent` (host-truth) > `vcenter-vm`/`vcenter-host` (definitive over every other discovery source; guest data relayed by VMware Tools) > `arc`-FQDN > AD-FQDN > Intune > Entra > `arc`-short > FortiGate sources. For the non-hostname fields Azure Arc ranks higher still — directly below `polaris-agent` for `os` / `osVersion` / `serialNumber` / `manufacturer` / `model`, since the Connected Machine agent reads the RUNNING OS and live SMBIOS in-guest on every check-in, whereas AD's `operatingSystem` lags until the computer object re-registers and VMware Tools reports the CONFIGURED guest-OS identifier. Inline writers still update `Asset.macAddress` / `assetType` / operator-owned fields. Three operator pins freeze projected fields against discovery: `coordSource="manual"` (lat/long, checked at the discovery write sites), `Asset.hostnameOverride` (hostname; set by editing Hostname in the asset edit form, cleared by blanking it — enforced centrally by the Prisma extension in `src/db.ts`, which re-asserts the pin over any write staging `hostname` without touching `hostnameOverride`; pinned assets are excluded from the duplicate-hostname ghost merge and from projection-drift logging), and `Asset.ipOverride` (IP; same edit-form set/blank-to-clear pattern and the same central `src/db.ts` guard, but discovery gets a vote — a discovery write staging the SAME IP as the pin releases it in that write (self-disabling, audited `asset.ip_override.released`), while a DIFFERENT staged IP is re-asserted back to the pin and raises one pending ip-override Conflict per asset via `ipOverrideService` — accept adopts the discovered IP + releases the pin, reject keeps it and suppresses re-raise for that same IP; pinned assets skip ipAddress projection-drift logging).

**Address-book directory (GAL) access** comes in two separate, independently opt-in forms on the same two integrations — **search** reads it live, **sync** stores it. Search is a separate, opt-in read (`config.enableDirectorySearch`, default off): `directorySearchService` fans a typeahead query to Graph (`/users`, mail-enabled `/groups`, org `/contacts`) and an LDAP user/group/contact search, merging and deduping by address. It is the ONLY people-facing query in either integration — discovery is otherwise devices-only (Entra `/devices` + `/deviceManagement/managedDevices`; AD hard-filtered to `objectClass=computer`) — and it **persists nothing**: results live for one request, and only an address an operator picks becomes a rule recipient or a saved `Contact`. Off by default because it needs directory-read permissions device discovery never required, so without the grant every keystroke would 403. Failures degrade per-integration rather than erroring the typeahead, and query strings are never written to Events. **Sync** (`config.enableDirectorySync`, also default off, and a deliberately SEPARATE toggle — same grants, different decision, because one reads and one stores) materializes the roster as `Contact` rows: `directorySyncService.runDirectorySync` runs as the FOURTH post-sync pass of the owning integration's discovery run (last, so a directory outage can't affect the asset passes; never its own scheduler job), reading in bulk via each service's `listDirectoryPeople` — Graph paged with `$select`+`$filter`+`$top` and deliberately NO `$search`, LDAP via the paged-results control with an `objectGUID` identity. It is provenance-bounded (`DirectoryContactSource`), a Polaris `User` or manual `Contact` on an address always wins, an empty or catastrophically-shrunken read never deletes, a steady-state run issues ZERO writes, and the run Event carries COUNTS ONLY. Switching the toggle off — or disabling or deleting the integration — purges what it created (`purgeDirectoryContacts`). Both controls live on the integration's **Directory** tab. See business rule 35.

Hybrid-join detection links AD and Entra/Intune via on-prem SID (`ad.observed.objectSid` ↔ `entra.observed.onPremisesSecurityIdentifier`). Re-discovery key precedence: AssetSource `(sourceKind, externalId)` → SID match → Ethernet MAC match (Entra only) → hostname collision (raises a Conflict).

## Business Rules & Constraints

> Rules **1–11** are one-line invariants and live here in full. Rules **12–38** each record a decision *and the incident that forced it* — the invariant is here, the narrative is in **[BUSINESS-RULES.md](BUSINESS-RULES.md)**. Read the full rule before changing behavior it governs.
>
> **Rule numbers are a stable citation key** (commits, code comments and the other docs cite "business rule 23"). Never renumber; retire a rule in place and give a new one the next free number.

1. **No overlapping subnets** within the same block. Use `cidrContains()` / `cidrOverlaps()` from `src/utils/cidr.ts` before any subnet creation — and take the per-block advisory lock while you do it: create through `createSubnetRowChecked()` (single row) or `lockBlockForSubnetWrites(tx, blockId)` (batch) in `subnetService.ts`, never a bare `prisma.subnet.create`. A bare create re-opens the race described in rule 20a. Backed by a UNIQUE index on `(blockId, cidr)`.
2. **Subnet must be contained within its parent block** — enforced at service layer.
3. **No duplicate IP reservations** — one `active` reservation per IP per subnet (`@@unique([subnetId, ipAddress, status])`).
4. **Block/subnet deletion protection** — HTTP 409 if any `active` reservations exist.
5. **CIDR normalization** — Host bits zeroed on write (e.g., `10.1.1.5/24` → `10.1.1.0/24`).
6. **sourceType tracking** — All discovered reservations carry a `sourceType`; manual entries default to `manual`.
7. **Conflict detection** — Discovery values differing from an existing manual reservation create a `Conflict` record rather than overwriting.
8. **Event archival** — Events older than 7 days are pruned; syslog (CEF) and SFTP/SCP archival are configurable.
9. **Asset `acquiredAt` ≤ `lastSeen`** — Enforced on every write via `clampAcquiredToLastSeen` in `src/utils/assetInvariants.ts`. If a write would leave `acquiredAt` later than `lastSeen`, `acquiredAt` is clamped down to match. Existing rows are repaired by the `clampAssetAcquiredAt` startup job.
10. **Four statuses cannot be monitored: decommissioned / disabled / storage / quarantined** — `UNMONITORABLE_STATUSES` + `statusAllowsMonitoring` in `src/utils/assetInvariants.ts` is the list; enforcement is centralized in the Prisma extension in `src/db.ts` so every write path benefits, in **both directions**: `clampMonitoredForStatus` forces `monitored=false` + resets `consecutiveFailures` when a create/update/updateMany/upsert stages one of those statuses, and `enforceMonitorableStatus` catches the write that stages `monitored: true` with NO status by reading the row first (the shape of the operator toggle, the discovery monitored-sweep and bulk-monitor — without it every unmonitorable state was one `monitored: true` away from being polled again). `updateMany` narrows its WHERE instead of rewriting rows it can't resolve. **`maintenance` is deliberately NOT on the list** — a window pauses polling via `MONITOR_CANDIDATE_WHERE` while `monitored` keeps the operator's intent so it survives the window (business rule 16). `storage` and `quarantined` joined the list in 2026-08 with the automations-only-fire-on-monitored-assets cutover: a quarantined device is isolated at the FortiGate, so every probe fails BY DESIGN and a security action was producing an outage alert storm about the isolation working. Because quarantine is reversible, it **parks** the flag in `Asset.monitoredBeforeQuarantine` (mirroring `statusBeforeQuarantine`) and the release write restores status + `monitored` together — otherwise releasing a quarantine handed the device back to the network with nobody watching it. Otherwise still one-way: flipping status back to `active` does not auto-resume monitoring, re-enabling is operator-driven. The two operator-facing write paths (`PUT /assets/:id`, `POST /assets/bulk-monitor`) **refuse with a reason** rather than leaning on the silent clamp — a form that saves and comes back unticked reads as a bug. Existing rows are reconciled once by migration `20260827000000_monitorable_status_clamp` and swept every boot by `jobs/clampMonitoredForStatus.ts`.
11. **DNS-resolved reservations** — Any Asset with a primary `ipAddress` falling inside a known (non-deprecated) Subnet that has no existing active reservation gets an auto-created Reservation with `sourceType="dns_resolved"`, `createdBy="system:dns-resolved"`, carrying the asset's hostname (`hostname || dnsName`) and `macAddress` when available. Eligible asset statuses: `active`, `maintenance`, `storage`, `quarantined`. IPv4 only. Never pushes to FortiGates. Never raises Conflict rows — defers silently to authoritative source types. See `src/services/dnsResolvedReservationService.ts`.
12. **`Asset.lastSeen` means verified network presence** — written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts`, which no-regresses and stamps `lastSeenSource` provenance. **Polling is authoritative for monitored assets**: when `monitored === true`, `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter`, `arc`) so they can't advance presence past what polling established; a failed probe writes nothing. Device inventory outranks the DHCP lease for unmonitored assets, and Fortinet-discovery-owned infra never takes client-sighting presence at all. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path). → [BUSINESS-RULES.md#rule-12](BUSINESS-RULES.md#rule-12)
13. **SD-WAN monitoring is opt-in, read-only, FortiOS-only** — gated per-integration by `Integration.config.pullSdwan` (default false; FMG + standalone parity). Writes the `AssetPerfSlaSample` SLA time-series and delete-replaces the `AssetSdwanRule` current-state table. **Never writes to the device.** The runtime selected route is *inferred* when FortiOS won't expose it over REST, and is labeled as such in the UI. → [BUSINESS-RULES.md#rule-13](BUSINESS-RULES.md#rule-13)
14. **Description sync is opt-in and Polaris-primary** — gated per-integration by `Integration.config.syncDescriptions` (default false). **A non-empty Polaris value always wins** (pushed on save, re-asserted by every reconcile, device-side edits overwritten); **an empty Polaris field adopts** the device value. No conflict state exists. `decideDescriptionSync(polaris, device)` is the pure decision; all device I/O rides `reservationPushService`'s Transport. Under FMG central management, pushes are additionally mirrored into FMG's database via JSON-RPC `update` (never `set`). → [BUSINESS-RULES.md#rule-14](BUSINESS-RULES.md#rule-14)
15. **Location codes ride device descriptions; notes are operator-only** — `a:`/`b:`/`f:`/`r:`/`jb:` codes are parsed server-side by `src/utils/locationCodes.ts` from device descriptions captured into `fortinetTopology.deviceDescription`. `Asset.description`'s codes win **exclusively** when it carries any (no per-key fall-through); `Asset.notes` is deliberately NOT a source. **Discovery never writes `Asset.notes` on an existing asset.** → [BUSINESS-RULES.md#rule-15](BUSINESS-RULES.md#rule-15)
16. **Maintenance windows pause everything; status flips are scheduler-managed** — `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` — which since rule 10's widening can only ever hold `active`, every other status being unmonitorable and therefore untargetable. It stops ALL server-driven polling, counts the asset as DOWN for child dependency suppression (unless the schedule's `suppressChildren` is off), and silences notifications for it and every dependency-suppressed child. **Discovery/system writers must never write status over a maintenance asset**; deletion-at-source (the discovery decommission sweeps) is the one carve-out. Open `AssetMaintenanceWindow` rows are the restart-safe source of truth, and dashboards treat maintenance as its own state, never an outage. → [BUSINESS-RULES.md#rule-16](BUSINESS-RULES.md#rule-16)
17. **ARP presence evidence for stale reservations; the sweep is opt-in** — discovery Phase 7.6 stamps `Reservation.lastSeenArp` whenever a gate's ARP table binds an active reservation's IP to its **reserved MAC**, keeping statically-configured / ICMP-silent devices out of the stale list. MAC match is required, matching is scoped per (fortigateDevice, ip), and **absence of an ARP entry is never negative evidence**. The cache-priming ARP presence sweep (`Integration.config.arpPresenceSweep`) is default off because it is IDS-visible. → [BUSINESS-RULES.md#rule-17](BUSINESS-RULES.md#rule-17)
18. **Automation precedence is same-trigger, most-specific-wins** — two automations watch the same thing iff their `triggerSignature` matches (host/event/change/composite are exempt). **`monitorStatus` is keyed by operator+value, NOT by dimensionFilter** — it is a single per-asset column, so every `== down` automation lands in ONE group whatever its device filter (they must be able to carve each other out), coverage is tested as scope AND device filter (`peerCoversAsset` / `carveOutPeerCovers`), and this same group decides whose missed-poll count governs each asset (business rule 36 rides this ladder rather than inventing a second precedence system). Among those, the higher `scopeRank` (all assets < device type < OS < manufacturer < model < tag < region < subnet < hostname) **carves out** the assets it covers from every lower-rank one: readings dropped, any active alert cleared as `notification.superseded`, pending debounce reset. Same-rank ties both fire. `buildShadowIndex` / `isAssetShadowed` in the engine; `previewRule` warns in both authoring directions. → [BUSINESS-RULES.md#rule-18](BUSINESS-RULES.md#rule-18)
19. **Severity bands escalate one alert by value, each on its own clock** — tiers stack on the base trigger; **severities must strictly increase** (thresholds need not be monotonic — most-severe MET tier wins). Tiers share the base sampling but may override the comparison operator and the hold time, and **"sustained for" is per tier**, tracked in `NotificationRuleState.bandMetSince` (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure). One alert per asset climbs and eases severity in place; de-escalation is immediate, and the hysteresis dead band eases to the base severity. `bandNotify` governs delivery on each transition. → [BUSINESS-RULES.md#rule-19](BUSINESS-RULES.md#rule-19)
20. **Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup** — three operability invariants. (a) **Overlap checks are check-then-insert**, so every subnet-creating path must go through `createSubnetRowChecked()` or `lockBlockForSubnetWrites()` in `subnetService.ts` (per-block `pg_advisory_xact_lock`), never a bare `prisma.subnet.create`; the same medicine covers the `mapRegions` JSON blob via `withRegionBlobLock` in `mapRegionService`. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret leaves of `Credential`/`Integration`/`NotificationChannel`/`Setting` config — sealing is per-model, **opening is all-models** (relation reads never fire per-model hooks). Raw SQL bypasses the extension. (c) **Backup/restore** is streamed end to end, wraps restore in `timescaledb_pre_restore()`/`post_restore()`, and a failed pre-update backup ABORTS the update by default. → [BUSINESS-RULES.md#rule-20](BUSINESS-RULES.md#rule-20)

21. **SSH host-key verification is opt-in and fails closed** — `SshConfig.verifyHostKey` (default OFF; ON for newly created credentials) enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin`: no pin stores and accepts, a match accepts, a **changed key refuses the connection** and stamps `ssh.host_key.mismatch`. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites and **fails closed** — an internal error refuses rather than silently skipping. Pins are per `(host, port)` in their own table, never on `Credential.config`. → [BUSINESS-RULES.md#rule-21](BUSINESS-RULES.md#rule-21)

22. **The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered** — priority lives in the `assetSourcePriority` Setting and feeds the **projection**, not just rendering (the column's filter, sort, "behind FortiGate X" criteria and Device Map narrowing all read `learnedLocation`). The contributor catalogue is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string, **label** contributors contribute their own name. Propagation is pull-based and **not retroactive**. Invariant: **a source blob may never be built from the projection's own output** — that laundered an AD OU path into a FortiGate-sourced field and accumulated a prefix per cycle. → [BUSINESS-RULES.md#rule-22](BUSINESS-RULES.md#rule-22)

23. **Who owns an IP and how the gate hands it out are two facts, not one** — `Reservation.sourceType` answers ownership; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers how the gate serves it. Phase 5 records the binding via the pure `decideInfraDhcpBinding`, writing only on change, and deliberately **never flips `sourceType`, never stamps `expiresAt`**, and fills `macAddress` only from the lease entry. A `"lease"` row is operator-takeover-able exactly like a `dhcp_lease` (`isSupersedableByCreate`); `"reservation"` and `null` stay authoritative. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets` on decommission — never on "no longer discovered"), with a 6h reconcile as backstop. Polaris writing the binding itself is double-gated (`pushReservations` + `autoReserveFortinetInfra`, both default off). → [BUSINESS-RULES.md#rule-23](BUSINESS-RULES.md#rule-23)

24. **Alert on the device's own alarm bit before inventing a threshold for it** — **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus`, the per-sensor bit the collectors already write; prefer it over a threshold on the reading, since the device knows its own per-model limits. **`customStateValue`** (state probes) is the mechanism for status OIDs Polaris does NOT already collect, and is deliberately not the answer for Fortinet hardware sensors. Shared invariant: `alarmStatusToFlag` returns `0 | 1 | null` and the engine **excludes null in SQL** — a source publishing no alarm bit must never have its absence mapped to 0. An unrecognized non-empty status maps to 1; ENTITY-SENSOR-MIB's `unavailable(2)` maps to NULL, never alarm (an empty SFP cage is not a fault). → [BUSINESS-RULES.md#rule-24](BUSINESS-RULES.md#rule-24)

25. **An alert you can't acknowledge from where you read it isn't really acknowledgeable — and who acknowledged it is a session, not a link** — acknowledgement reaches all three read surfaces (in-app, email, web push). Email and push carry the SAME URL, `/alert-ack.html?id=<notificationId>`, naming the alert and nothing else: the page behind it is an ordinary logged-in Polaris page, so an unauthenticated reader signs in first (returning to the alert via the short-lived `polaris_next` cookie, `utils/loginRedirect.ts` — a cookie rather than `?next=` because three of the five login paths bounce through an IdP and `regenerate()` the session), and identity comes from that session. Five consequences. **The email is one message again** — a shared body carries a link that works for whoever reads it, so `expandDeliveries` substitutes `{ack}` ONCE per alert and stopped fanning the To line out one message per recipient; the only thing that still splits a send is capability, and that is TWO copies at most (`splitAckVariants`), never one per person. **Every recipient Polaris can't vouch for gets the button** — an address-book contact or a typed address has no account behind it, so permission is decided at the page rather than by withholding a control, and `alerts:write` is enforced by the acknowledge route with the page merely reporting the refusal (which is why the PAGE gate is `alerts:read`: bouncing a read-only reader to "/" tells them nothing about where their link went). **A recipient it CAN vouch for is asked first**: an account whose role holds `alerts` below `write` is mailed the same alert with the button pruned out — `ackCapabilityByAddress` → pure `splitAckVariants` splits a composed body's To/Cc/Bcc into an ack copy and a no-ack copy (`fillComposedAckUrl(body, null)`, the same blanking an install with no `POLARIS_PUBLIC_URL` already gets), the plain per-address path stamps `meta.noAck`, and web push omits `ackUrl` so `sw.js` renders no tray action. Unknown means capable in both directions: an address with no account keeps the button, and where two accounts share one address whichever may act decides. The policy behind the withholding is a ROLE policy — migration `20260828030000_alerts_ack_write_capable_roles` raised `alerts` to `write` on every role already holding write anywhere else, so what's left is a genuinely read-only role. **Loading is a GET and acknowledging is a POST**, so a mail gateway prefetching every link — Outlook Safe Links, Proofpoint — cannot acknowledge anything, and no unauthenticated state-changing surface remains. **A push Acknowledge action OPENS the page** rather than acting from the tray: that is where the note is typed, and the session is what records the acknowledger. And **`GET /alerts/:id` answers 404, not 403**, for an alert outside the caller's region scope. `requireAckNote` is still enforced in `acknowledgeNotifications`, not in any dialog, so every surface obeys it; a batch is refused whole. Retired with the single-use token: `NotificationAckToken`, `utils/ackToken.ts`, the public `/ack/:token` route, and the per-recipient `planComposedEmails` fan-out. → [BUSINESS-RULES.md#rule-25](BUSINESS-RULES.md#rule-25)

26. **A generated MAC is a placeholder until the network proves otherwise** — the `reservationMacPlaceholder` prefix (Setting, default `02:0F:5E`) is **the only marker** that a stored MAC is synthetic; there is deliberately no boolean column, because the prefix is visible on the gate's own reserved-address table. `normalizePlaceholderPrefix` (`utils/mac.ts`) **rejects any prefix that isn't locally-administered unicast**, so no factory MAC can fall inside the placeholder space. Adoption (`placeholderMacAdoptionService`, Phase 7.7, double-gated on `pushReservations` + `adoptDiscoveredMac`, both default off) swaps in the real MAC on **ARP-table and device-inventory evidence only**, behind five guards, device-first and read-back-verified. Changing the prefix is not retroactive in either direction. → [BUSINESS-RULES.md#rule-26](BUSINESS-RULES.md#rule-26)

27. **A logo is picked by theme; a name is text only when the picture doesn't already say it** — the shipped art is theme-paired, so painting the wrong variant makes the logo *disappear* rather than look off; the variant is chosen by theme **FAMILY, never by id** (three themes, two sets of art), and **`public/js/brand-logo.js` is the single decider** for all four surfaces (desktop login, mobile login, sidebar, Customization preview). The two variants of a pair are normalized to one geometry, so a theme flip moves nothing. The **Application Name is a caption for a custom logo only** — `showName` is false whenever the shipped wordmark is in play, so `appName` may be stored empty. Placement is per surface (`logoOnLogin` / `logoOnSidebar`); the accent composite renders **server-side** so geometry can't drift. → [BUSINESS-RULES.md#rule-27](BUSINESS-RULES.md#rule-27)

28. **The Windows build is the authority; the product name is not** — `ProductName` still reads "Windows 10 Pro" on every Windows 11 client, so AD, Intune/Entra and the agent are all equally wrong and no projection priority can fix it. `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the **family from the build via a threshold** (`>= 22000 ⇒ Windows 11`, never goes stale) and the **release from a table** (an unlisted build keeps its raw `osVersion` rather than being guessed at). **Windows Server is excluded entirely** — build 26100 is both Windows 11 24H2 and Server 2025. Applied at **write** time (projection + the `db.ts` Asset hooks) because filters, sorts, exports and scope conditions read the stored columns; it is idempotent and reads no row. Not retroactive. → [BUSINESS-RULES.md#rule-28](BUSINESS-RULES.md#rule-28)

29. **One outage is one alert: packet loss is what happens while the device is answering** — `probeLossPct` is the only metric whose input is *failed* probes, so two gates keep it from raising a second alert about an outage `monitorStatus == down` already owns. (a) **Only an answering device reports loss**: the resolver admits `up` and `warning` only (`assetIsAnsweringProbes`; `passive` is excluded — a dark passive device sits at 100% loss with no asset-down alert to supersede it, business rule 36), and an asset that stops answering has its live loss alert **cleared** (`notification.superseded`, reason `device-down`) rather than frozen. (b) **The ratio is anchored** at `GREATEST(first success in window, Asset.recoveryStartedAt)`, so a recovering device can't alert *because* it came back; only an outage-ending recovery stamps that column. The anchor bounds the READING, not the picture: the alert email's loss chart plots the WHOLE window and marks where the caption's number starts (`measuredFromMs` → `sparklineSvg`'s `measuredFrom`), because a graph that begins when the device came back omits the outage it was sent to explain. (c) **`windowSec` IS the reading** — it's History, not smoothing — with `forDurationSec` as its own optional sustain knob (`WINDOWED_RATIO_METRICS`, `probeLossWindowSec`). The NOC widget alone passes `includeFullyDown`; the engine never may. → [BUSINESS-RULES.md#rule-29](BUSINESS-RULES.md#rule-29)

30. **Confirmation is the configured cadence's job; ICMP only fills in the loss ratio** — `monitorStatus` reaches `down` when N missed polls are OUTSTANDING against the operator's configured transport at their configured `intervalSeconds`. **The counter is a LEAKY BUCKET, not a run length**: a miss adds one to `consecutiveFailures`, an answered poll takes one back (floored at 0), and the LEVEL decides the verdict — `cf >= N` is `down` whatever this probe did, `cf > 0` is `warning` on a miss and `recovering` on an answer, `cf == 0` is `up`. So time-to-down is `N × intervalSeconds` for a device that stops answering and longer for one that flaps, draining takes exactly N answers (which is what makes recovery symmetric and retires `consecutiveSuccesses` from the machine), and one lucky packet can never lift a deep outage out of `down`. **N is the covering automation's `missedPolls` (default 3), not a Monitor Settings value** — see business rule 36; `failureThreshold` on the settings tiers is dormant. The CADENCE half is unchanged: it still comes from the monitor-settings hierarchy, and the figure the monitor-settings card reports is the figure you get. `resolveProbeIntervalSec` applies **exactly one clamp**: dependency suppression (parent dark ⇒ 2× interval). **A probe can also decline to be a reading**: `ProbeResult.skipped` writes no sample and moves neither counter — it bumps `lastMonitorAt` alone, so the cadence keeps its spacing. Two sources: the vCenter probe when vCenter itself is unreachable, and **`responseTimePolling === "disabled"`**, which is the operator saying don't poll. The second was a *failure* until 2026-08-28: every other stream's publisher checked its resolved method before queueing and the probe's did not, so `disabled` reached `probeAsset`'s dispatch, fell past every branch to the unknown-method error, and was recorded as a missed poll — switching Response Time off drove the asset to `down`. Both publishers (`computeDueWork` + `jobs/monitorAssets`, the lockstep pair) now gate on the shared `responseTimeProbeShouldQueue`, and `probeAsset` returns `skipped` as the backstop for `/probe-now` and for a `disabled` sitting in a JSON tier no publisher gate can see. A skip is not a miss, so N consecutive misses still means N times the transport actually answered nothing about a device it could reach. The ICMP packet-loss sampler **never calls `recordProbeResult`** (ICMP does not authenticate the device it reaches) and is **currently DISABLED** via `LOSS_SAMPLER_ENABLED`. `probeKind` splits the readers: only `probeLossQuery` and the alert-email loss chart read all kinds — every response-time reader, and every rollup, filters to primary. → [BUSINESS-RULES.md#rule-30](BUSINESS-RULES.md#rule-30)

31. **The login page is the way back in, so restricting it is opt-in and must refuse to lock you out** — `loginAccessConfig` (default **off**) restricts local login by source IP via `utils/ipScope.ts`. It gates **both halves or neither** — `/login.html` AND `POST /auth/login` + `/auth/login/totp` — because the form is a plain POST to a JSON API. The page is **dropped** (socket destroyed, stealth posture); the API answers the **same generic 401** a wrong password gets, and writes `auth.login.blocked_source`. **SSO is never gated** (that's what makes this survivable); **LDAP is**, sharing the login route. It **fails open** on a settings read error, and the PUT refuses a scope excluding the caller's own `req.ip`. Only as true as `req.ip` — the GET returns `callerIp` for exactly that reason. → [BUSINESS-RULES.md#rule-31](BUSINESS-RULES.md#rule-31)

32. **A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives** — the custom-condition mode is offered on every trigger with a continuous condition (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event`/`change` are refused), pre-seeded with the trigger inverted (`invertedLeaf`, and `invertedTree` applying De Morgan so the result stays and/or-only). Four decisions carry it: (a) while firing, **the tree is the sole recovery authority** — evaluated in its own post-loop pass that re-reads firing rows from the DB; (b) resolution is **dimension-first with a per-asset fallback**, so a per-port alert clears independently while a device-wide leaf clears them together; (c) **kind coherence is enforced** on single triggers too; (d) reset leaves **inherit the trigger's measurement window** and have no window control of their own; (e) the two triggers a CONDITION is refused on get the **counterpart Event** instead (`TRIGGER_TYPES_WITH_RESET_EVENT`, the complement set) — `agent.disconnected` clears on `agent.connected`, scoped to the SAME subject the alert is about and prefilled from the server-published `RESET_EVENT_SUGGESTIONS` map, so an event automation is no longer stuck clearing itself on a timer whether or not anything recovered. And **`cooldownSec` is not a reset at all** — it decides how often a NEW alert may fire, so it lives on the Actions step with the alert record it governs, not on the reset step where it read as part of how an alert clears. → [BUSINESS-RULES.md#rule-32](BUSINESS-RULES.md#rule-32)

33. **A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login** — the HTTP check is a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType="http"`), not a polling method (retired 2026-08): a check varies by vendor AND model while a login varies by vendor, so sharing one row meant duplicating passwords. Decisions: the **body match is load-bearing** (a 200 whose body doesn't match FAILS; no lax toggle); **status is judged before content**; **redirects are never followed**; the body is **capped at 64 KB**; the credential is **authentication only, with no "none" mode**; **`authMode` is stated, not guessed** (Digest is a handshake — fire bare, read the challenge, re-fire **exactly once**); it writes `AssetStateSample` 0/1 **pass or fail** plus a success-only RTT gauge and **never moves `monitorStatus`**; and **`netGuard` deliberately does not apply**, the target being the monitored asset's own private address. → [BUSINESS-RULES.md#rule-33](BUSINESS-RULES.md#rule-33)

34. **An active scan finds things; a separate grant adds them** — a **Discovery** (`NetworkScan`) sweeps addresses the operator names, making it the only Polaris feature that touches hosts it has no prior relationship with, so the posture matters more than the mechanism. Six decisions carry it: **scanning and adopting are separate grants** (`networkScan` authors and runs, `assets:write` chains on adopt, and the wizard RENDERS the missing grant rather than discovering it at the POST); it is **opt-in and IDS-visible**, with no scheduler and no shipped default range; **credential order is the try order** and the first method that answers wins; **adoption is new-addresses-only**, so a re-run enriches nothing and "nothing new" stays distinguishable from "nothing there"; it is deliberately **neither an 8th integration type nor a `DiscoveryRun` row**; and there is deliberately **no `network-scan` AssetSource kind**. → [BUSINESS-RULES.md#rule-34](BUSINESS-RULES.md#rule-34)

35. **The GAL is a mirror, not a source of truth — and Polaris only ever deletes what it wrote** — directory sync is opt-in per integration (`config.enableDirectorySync`, default off, deliberately separate from `enableDirectorySearch`, which still persists nothing) and runs as a post-sync pass of the owning integration's discovery run, never as its own scheduler job. Five invariants bound it: (a) **provenance decides deletion** — `DirectoryContactSource` records every (integration, directory object) the sync created, and a `Contact` dies only when its LAST provenance row goes; a hand-added row has none and is never touched, which is also why adoption drops provenance; (b) **a Polaris `User` or a manual `Contact` on an address wins** — the sync never creates over either, and an account created later retires the synced row on the next run; (c) **an empty or catastrophically-shrunken read never wipes** — zero entries, or a delete set over the guard, skips the deletion half and warns, because a revoked grant must not empty the address book; (d) **synced entries are gated on `automationManagement`, not `contacts:read`** — and so is the live GAL fan-out, since gating one and not the other leaves the roster reachable a query at a time; (e) **no directory PII reaches `Event.details` or the logs** — the run Event carries counts only, because Events are readable by anyone with events access and are shipped off-host by the syslog and SFTP archivers. → [BUSINESS-RULES.md#rule-35](BUSINESS-RULES.md#rule-35)

36. **The automation decides what "down" means; a device no automation covers is never judged** — a `monitorStatus == down` automation carries a **`missedPolls`** count, and that count IS the definition of down for every device it covers (`downDetectionService.resolveDownThreshold`, called once per probe); precedence is rule 18's existing ladder — same-rank ties resolve to the **smaller count**, then older `createdAt`, then lower `id`. **A device covered by NO down automation reads `passive`**, the sixth `monitorStatus` value: still polled, still sampled, still charted — Polaris just renders no verdict. The counters keep advancing while passive; heavy cadences run for a passive asset whose last probe succeeded (`runsHeavyCadences`); entering/leaving passive is a **configuration edge** (`isConfigStatusEdge` — no `monitor.status_changed` Event, no dependency propagation); anything testing `!== "up"` as a proxy for "unreachable" must exempt it. A zero-rule fleet stamps a one-shot `monitor.down_detection_absent` warning Event. `failureThreshold` stays on the settings tiers as a dormant column read only by the V3 seed. → [BUSINESS-RULES.md#rule-36](BUSINESS-RULES.md#rule-36)

37. **An automation only fires about a device Polaris is actually polling** — ONE gate, `assetCanTrigger` in `notificationEngine`, applied by EVERY trigger path: the asset must be `monitored` **and** not suppressed (maintenance window / dependency-suppressed — business rule 16, which this rule now subsumes rather than sitting beside). The monitored half is pushed into SQL for the threshold, composite and metric/state-preview loads (`scopeWhere(scope, monitoredOnly)`) and checked per row in the event/change tail off the `assetDetail` row. **Event and change triggers were the deliberate exception and no longer are**: firing about a device nobody polls made "an automation covers it" and "Polaris watches it" two different answers. The four statuses that cannot carry monitoring at all fold in through business rule 10 rather than being retested here. Three consequences: un-monitoring a device **clears** its live alerts through `clearVanishedStates` (`notification.out_of_scope`) the way leaving the scope does — which is the bug that forced the rule, since `monitorStatus` is NOT cleared when monitoring stops and a `monitorStatus == down` automation kept firing forever about a shelved device; a **null `assetDetail` still fires** (the asset row is GONE — an `asset.deleted` event must not be swallowed), as do system-scoped events, which carry no assetId; and the raw unfiltered scope resolver stays for the surfaces asking a different question — the device-list preview REPORTS the unmonitored remainder, and the dimension picker, mass pinning and `Contact.assetCondition` are not about firing. → [BUSINESS-RULES.md#rule-37](BUSINESS-RULES.md#rule-3

38. **A device behind a dark parent is not accused, and it is not released on one packet** — two halves of dependency suppression that had been left implicit. (a) **Release is asymmetric.** Entering suppression still needs every effective parent confirmed `down` (`warning`/`recovering` flapping must never drag a healthy subtree in), but LEAVING it counts `recovering` as down too — a parent mid-recovery has answered ONE packet and is still short of the covering automation's success threshold, so releasing there un-suppresses a subtree whose own probes are all still failing and the outage re-alerts device by device as plain Down. The child's persisted `dependencySuppressed` selects the side (`SuppressionAssetState.currentlySuppressed`); `unknown`, `passive` and `warning` stay ok in both directions, or a subtree could strand in Dep. Down with nothing able to clear it. Release cascades one layer per pass, which is correct — a gate coming back does not mean the switch under it has. (b) **A miss the upstream explains is GREY, not red.** A suppressed asset is still probed (half cadence — it may answer over a redundant path), and every failure used to be indistinguishable from a real one. `recordProbeResult` now stamps `AssetMonitorSample.dependencyDown` from the asset row's own flag (never re-derived — the reconciler owns it), the rollups carry `dependencyFailureCount`, and `probeOutageService` hands every chart an `OutageKind`. Same dive, no accusation; deliberately NOT a band (that vocabulary is maintenance's, rule 16). A run **splits at a change of kind**, a rollup bucket must qualify WHOLE (`dependencyFailureCount >= failureCount`; NULL reads as red), and the grey is duplicated in four places by design like the red already is. → [BUSINESS-RULES.md#rule-38](BUSINESS-RULES.md#rule-38)7)

**List-page conventions.** A list table is TableSF (per-column sort + inline filters) + `setupColumnLayout` (resizable/hideable columns) + a frozen header with the body scrolling inside `.table-wrapper-sticky` + `renderPageControls` (centered pagination, right-aligned "Show N"). Sort, filters, column widths/visibility and page size persist per user under a `PolarisPrefs` key and are **restored before the first render**, so the initial paint carries the operator's setup instead of flashing defaults. Row verbs are a **context menu on the row's name** (`showRowMenu` in `app.js`), not an Actions column. Column widths are decided in `table-sf.js`, never in CSS — under `table-layout: fixed` the `<col>` beats a stylesheet rule and the pin loop overwrites `widths[]` anyway; a page opts a utility column out of the 34px `FIXED_COL_W` track with an inline `style="width:…"` on its `th`. The **auto-fill (last resizable) column is floored** at `max(AUTOFILL_MIN_W, its declared width)`: starved below its label's min-content it wraps one letter per line and stretches the whole `thead`, so overflow goes to the wrapper's horizontal scroll instead — that floor is applied AFTER the crushed-table saved-width fallback, or that fallback becomes dead code. Selection state rides `tr.selected` alongside the checkbox (`syncSelectedRows`).

**Modal conventions.** `openModal` reuses ONE shared `#modal-overlay`. A surface that must stack *over* an open modal (the address-book picker at z-index 1300, its editor at 1320) therefore **builds its own overlay** — calling `openModal` would destroy the form DOM underneath. A standalone overlay still has to restore focus, trap Tab, and call `_ensureLockButton` itself, because that injector's MutationObserver only watches the shared overlay. Reveal through `revealOverlay` (or the same rAF-plus-`setTimeout` pair): **rAF does not fire in a hidden tab**, so a dialog opened in the background would be built and never shown. Panel-lock state lives on `window.__polarisPanelLock` and `initPanelLock({user})` is idempotent + late-safe — app.js can be evaluated twice, and a fresh file-scope object would reset the lock while the injected buttons kept claiming the old state. Wizard stepper CSS is shared in `styles.css`.

**Integration modals are one shape, not seven.** Build every "connect us to another system" dialog with `openIntegrationModal({product, action, tabs, requires, onWire, onTest, onSave})`: title `"<Action> <Product> Integration"`, General tab first then Monitoring then feature tabs, footer `Test Connection · Cancel · Create/Save Changes`, field ids unique ACROSS tabs so one pass collects the whole form. Test is gated on `requires` and the toast NAMES the missing fields; **saving is never blocked on a passing test**. The tab set and the required-field list are declared ONCE per type (`_integrationTabs` / `_INTEGRATION_REQUIRED_FIELDS` in `integrations.js`) and both the Add and Edit flows walk them — they used to be two hand-maintained arrays, so a tab added to one silently missed the other. Secrets are dropped from `requires` on the Edit flow, where a stored one renders blank.

**Charts** are hand-rolled SVG. They render labeled translucent maintenance bands over window gaps (`_maintenanceBandLayer`), dive to the baseline in red across a failed poll and in **grey** across one the upstream explains (`_CHART_DEP_COLOR`; the same value lives in `public/js/mobile/charts.js` and `src/utils/sparklineSvg.ts` — change one, change all three), and may shade the line by automation severity — the ladder comes from `GET /assets/:id/metric-thresholds` (server-side, off the engine's own `resolveTierLadder`) so shading can never disagree with what actually fires.

## Deployment & Updates

The production instance is updated via the **in-app update mechanism** in **Server Settings → Maintenance**. When pushing changes, the user applies the update through that UI rather than manually redeploying. Keep this in mind when giving deployment advice — do not suggest `git pull` or manual restart steps unless asked.

The Application Updates card carries an **update train** selector (`update.train` Setting, default `nightly`): **nightly** tracks the update-branch tip (every commit — the historical behavior), **release** tracks only the highest published release tag (`git tag --sort=-v:refname "v[0-9]*"`, applied via detached-HEAD checkout). The release train stays dormant (reports up-to-date) until the first release is tagged. Logic lives in `checkForUpdates`/`applyUpdate` in [src/services/updateService.ts](src/services/updateService.ts); persisted + surfaced through `GET|PUT /server-settings/updates/settings`.

Every production install runs the split-role systemd layout (`polaris.target` + `polaris-web` + `polaris-monitor@N` + `polaris-discovery` + `polaris-dash` + `polaris-migrate`). The legacy single-process `polaris.service` was removed in Phase 3 — fresh installs land split-role + nginx-fronted out of the box via `deploy/setup-*.sh`, and `restartService()` in [src/services/updateService.ts](src/services/updateService.ts) only handles the split-role + Windows-NSSM paths. Local dev (`npm run dev` with `POLARIS_ROLE` unset = `all`) is still the "everything in one process" runtime behavior — that lives in `src/utils/role.ts`, not in deploy artifacts.

Before kicking `polaris.target`, the transient unit `restartService()` spawns also syncs every shipped `deploy/polaris-*.service` + `polaris.target` into `/etc/systemd/system/` (cmp-only, no-op when unchanged) and runs `systemctl daemon-reload`. The same transient unit ALSO syncs `deploy/nginx/polaris.conf` into `/etc/nginx/conf.d/polaris.conf`, validates with `nginx -t`, and reloads nginx — before the polaris.target restart so any new location blocks are live by the time Polaris comes back up. So unit-file AND nginx-config changes shipped in a Polaris update take effect on the next in-app update with zero operator intervention. **Operator unit customization must live in `<unit>.d/*.conf` drop-ins** — direct edits to the main unit file in `/etc/systemd/system/` (or to `/etc/nginx/conf.d/polaris.conf` itself) get clobbered by the sync (a `journalctl -t polaris-updater` line records each sync).

### Reverse-proxy (nginx) front-end

nginx terminates TLS for every install. `POLARIS_PROXY_CERT_PATH=/etc/polaris-nginx/cert.pem` + `POLARIS_PUBLIC_URL=https://polaris.example.com` are required in `/opt/polaris/.env` (boot fails fast otherwise). Polaris listens HTTP-only on `127.0.0.1:${PORT:-3000}` (web role); `TRUST_PROXY` defaults to `"1"` (first-hop trust) so `req.ip`/`req.secure` honor nginx's `X-Forwarded-*` headers, and Server Settings → Certificates renders the in-app nginx GUI (six operator-settable directives + cert rotation via the dual-pin stage→swap→retire workflow). CA records (`category="ca"`) remain operator-editable because outbound TLS to integrations (LDAP, SMTP) still uses them.

**In-app nginx GUI.** Server Settings → Certificates exposes six directives operators actually need to change day-to-day: HTTPS listen port, HTTP/3 toggle, TLS protocols, HSTS (toggle + max-age + includeSubDomains + preload), Prometheus IP allow-list, plus cert+key rotation. `server_name` is derived from `POLARIS_PUBLIC_URL` and is not user-settable. The GUI persists settings to a `proxyConfig` Setting row and applies via a narrow privileged path: `polaris` user → `sudo /usr/local/sbin/polaris-nginx-apply <subcommand>` → wrapper holds `flock /run/polaris-nginx-apply.lock`, takes the staged file from `/run/polaris-nginx-stage/`, runs `nginx -t`, atomic-renames, reloads nginx. The wrapper is the entire privileged surface — sudoers doesn't restrict args, all validation lives in the shell script ([deploy/scripts/polaris-nginx-apply.sh](deploy/scripts/polaris-nginx-apply.sh)). Setup scripts (setup-rhel/setup-ubuntu and the migrate-to-nginx path) install the wrapper + sudoers + tmpfiles entry + add the polaris user to the nginx group so the existing fingerprint pane reads the `0640 root:nginx` cert file directly. Existing installs picking this up via in-app update get the same wiring through [src/services/updateService.ts](src/services/updateService.ts)'s helper-sync block on every restart. **Adopt-managed-mode gate**: `proxyConfig.managedMode` starts at `false` on every install; the GUI shows a yellow drift banner (with up to five specific drift markers from the parser in [src/services/nginxConfigParser.ts](src/services/nginxConfigParser.ts)) and disables the controls until the operator clicks "Adopt managed mode." This prevents silent clobbering of hand-edits beyond the six controls. In-app updates render `/etc/nginx/conf.d/polaris.conf` from the [polaris.conf.template](deploy/nginx/polaris.conf.template) only when `managedMode=true`; they also check sha256 against `lastAppliedHash` and refuse-to-clobber on drift.

**Cert rotation via the GUI** orchestrates the existing dual-pin endpoints (see the Dual-pin paragraph below): upload cert+key → `/cert/preflight` libcrypto-validates the pair + returns metadata → `POST /agents/cert-pins/bulk-add` stages the new pin on every active agent → `POST /server-settings/proxy/cert/rotate` does the sudo file-swap + nginx reload → `POST /agents/cert-pins/bulk-remove` retires the old canonical fingerprint. The same Maintenance card workflow stays available for operators who prefer it.

The Polaris Agent's leaf-cert pinning: `getServerCertFingerprint()` in [src/services/certInfo.ts](src/services/certInfo.ts) reads `POLARIS_PROXY_CERT_PATH` and computes the same SHA-256 nginx serves. The fingerprint stamps `agent.conf` at install time; the Go agent's `pinned.VerifyPeerCertificate` validates against it on every connection.

**Dual-pin cert rotation** (rotation without fleet-wide agent re-install): each `ManagedAgent` row carries `serverCertFingerprint` (canonical pin) plus `additionalServerCertFingerprints String[]` (staged pins). Enroll cross-check accepts ANY pin in the union; `/agents/config` ships the union to the agent on every poll; the Go agent's `pinned.VerifyPeerCertificate` matches the presented cert against the SET. Operator-driven rotation lives on Server Settings → Maintenance → Polaris Agent → "Cert pin rotation": **stage** a new pin → server pushes to every agent + WS refresh-config → agent saves agent.conf + exits via `os.Exit(0)` so systemd cycles it with the new pin set → rotate the server cert (nginx reload) → wait for every agent to heartbeat post-rotation → **retire** the old pin. The agent.conf format gained a `cert_fingerprints = pin1,pin2,...` line; the legacy `cert_fingerprint = <canonical>` line stays for pre-dual-pin binary downgrade safety. Routes: `GET /server-settings/agents/cert-pins/summary`, `POST /server-settings/agents/cert-pins/bulk-add`, `POST /server-settings/agents/cert-pins/bulk-remove`. Bulk-remove of a pin that would leave any agent with zero pins is skipped for that agent (returns `lastPinSkipped: N`). See cross-cutting/polaris-agent → "Cert pin rotation" in [TOUCHES.md](TOUCHES.md) for the full lockstep checklist.

For pre-nginx installs, cutover is operator-driven via `deploy/migrate-to-nginx.sh --public-url https://polaris.example.com --prometheus-ip 10.0.0.42`. The script: ensures nginx ≥ 1.25 (HTTP/3 stable; falls back to nginx.org mainline repo), extracts the active server cert+key from `Setting.certificates`, stages + validates the nginx config (with HTTP/2 + HTTP/3 listeners both on 443), writes `/etc/polaris-nginx/{cert,key}.pem` with `0640 root:nginx` + SELinux `httpd_sys_content_t`, appends env vars to `.env` (with backup), installs the polaris-web systemd drop-in, opens TCP+UDP/443 in firewalld, restarts polaris.target, smoke-tests Alt-Svc + UDP listener + bearer-gated `/metrics-monitor-1`. Idempotent; transactional (rollback at any gate). See [docs/INSTALL.md](docs/INSTALL.md) for the operator-facing walkthrough.

Fresh installs are documented in `docs/INSTALL.md` with three platform sections (RHEL/Rocky/AlmaLinux 9, Ubuntu/Debian, Windows Server). The disk-sizing table at the top of that file is the single source of truth for DB-volume / app-volume / `/var/log` minimums and recommendations — keep it in sync whenever the runtime workload (sample-table cadences, retention defaults, update-staging cost) changes meaningfully. The setup wizard's preflight check uses `RECOMMENDED_DB_FREE_GB = 50` as the threshold for the warning banner; bump that constant in `src/setup/setupRoutes.ts` if the recommended minimum changes and update the docs table to match.

### Disk-space monitoring (post-install)

Three layers catch a filling DB volume before it crashes Postgres:

1. **Boot-time diagnostic** — `runStartupDiskCheck` in `src/utils/startupDiskCheck.ts` statfs's the app/state/backups dirs plus conventional PostgreSQL data directory candidates per platform. Emits an info/warn/error log line per volume. Non-fatal — never blocks boot.
2. **Periodic capacityWatch job** — every 10 minutes, builds a capacity snapshot and calls `recordCapacityTransition` to write a `capacity.severity_changed` Event when severity flips (ok ↔ watch ↔ amber ↔ red). Events flow out through eventArchiveService → syslog/SFTP archival, so the alert reaches on-call independent of whether the UI is reachable.
3. **Maintenance tab volume bars** — Server Settings → Maintenance → Database card renders one bar per distinct filesystem (deduped by stat.dev) with severity-colored fill and the Polaris-named role(s) each volume serves. Severity tiering: **watch** at 20–30% free (Event-only), **amber** at 10–20%, **red** below 10% (drives the non-dismissible sidebar banner).

### First-run setup lock

The setup wizard is unauthenticated by design (the operator needs to reach it from a browser to provision the host). To stop a network attacker from re-running the wizard against an already-configured host whose `.env` got deleted/corrupted, finalize writes a `.setup-complete` marker at the project root. On every boot:

- `DATABASE_URL` set → app boots normally; marker is back-filled if missing (covers existing installs).
- `DATABASE_URL` missing AND no marker → wizard runs (fresh install).
- `DATABASE_URL` missing AND marker present → process logs a recovery message and exits 1; the wizard never starts.

To intentionally re-provision from scratch, an admin with shell access deletes both `.env` and `.setup-complete`.

## Key Coding Conventions

- All IP math lives in `src/utils/cidr.ts`. **Never** do string manipulation on IPs elsewhere.
- **Resolving a FortiSwitch/FortiAP's parent goes through `src/utils/fortinetParentKey.ts`. Never match `fortinetTopology.controllerFortigate` against `Asset.hostname`.** That field holds FortiManager's *device name*; a firewall's hostname is projected from the gate's own configured hostname, and the two differ on any install where an operator named the FMG device differently — in which case every child resolves to *no parent*, silently, because "no parent" is a legitimate state. That single mismatch broke dependency suppression (a gate in a maintenance window left its switches reading "Down" instead of "Dep. Down"), Device Map site membership, map-region membership + subnet propagation, and FortiLink interface auto-monitor. The util resolves `controllerSerial` → the gate's own `fortinetTopology.deviceName` → hostname → the name-as-serial. Note the *second* class of consumer that must keep using the device name: anything addressing an FMG/FortiOS API (parent-FortiGate polling, decommission sweeps, description-sync transports, the Sources column). See `TOUCHES.md → cross-cutting/fortinet-parent-key-resolution`.
- Services (`src/services/`) contain **all business logic**. Route handlers are thin — validate input, call a service, return a response.
- All Zod schemas live co-located with their route file (top of file).
- Database calls go through service functions only — never raw Prisma in route handlers. **Interim state (2026-06):** several legacy route files still carry inline Prisma (heaviest in `agents.ts`, `assets.ts`, `integrations.ts`, `serverSettings.ts`, `users.ts`). New endpoints MUST use services; when you touch a legacy route, extract opportunistically. Until a handler is extracted, any audit-worthy mutation it makes must still write an `Event` inline (these files already import `logEvent`) — auditability is the part that can't wait for the refactor.
- All errors thrown by services must be instances of `AppError` (`src/utils/errors.ts`) with an `httpStatus` property.
- Use `async/await` throughout; avoid `.then()` chains.
- Write a unit test for every public function in `src/utils/` and `src/services/`. `vitest.config.ts` excludes `**/.claude/**`: those are full scratch checkouts of this repo (one per in-flight branch) and Vitest's default include would otherwise collect every worktree's tests into `npm test` — silently inflating the suite ~3× and failing loudly once a worktree diverges enough to reach a real DB. If the file count jumps between runs, suspect that first.
- All audit-worthy actions (creates, updates, deletes, discovery events) must write an `Event` record.
- **Ask before committing.** After completing each logical change, do not commit automatically — ask the user whether to commit. Each logical change still gets its own commit (don't batch unrelated work), but the user decides when.
- **Before any commit, review CLAUDE.md, `ARCHITECTURE.md`, `BUSINESS-RULES.md`, `TOUCHES.md`, and `UI-CANON.md` for updates.** When the user approves a commit, re-read all five — CLAUDE.md (always-loaded conventions/rules/overview; a business rule's *invariant* lives here), ARCHITECTURE.md (full file map / domain model / API catalog / discovery / jobs / frontend / observability — most likely to need updates), the relevant `BUSINESS-RULES.md` rule (the narrative behind rules 12–38 — when a change alters what a rule constrains, the invariant in CLAUDE.md AND the narrative here both get updated, in the same commit), the relevant `TOUCHES.md` entries (per-service writers/readers/invariants/checklists or cross-cutting writer/reader lists), AND the relevant `UI-CANON.md` entries plus TOUCHES.md's Canonical backend patterns (canonical implementations whose file paths, function names, conventions, or checklists may have shifted; new patterns that have crystallized into a clear canonical and should be added). Anything the change moved, broke, or invalidated gets refreshed in the same commit. The indexes only stay trustworthy if they're reviewed every commit. A pre-commit hook + CI job (`npm run check:docs`, `scripts/check-docs.mjs`) enforce the *structural* half automatically — every Prisma model / service / job / route must be named in ARCHITECTURE.md, no `file:line` refs in the indexes, no dead doc-referenced paths — but they cannot judge whether prose is still accurate, which is what this review is for.
- **Ask before pushing.** Never push without the user's explicit go-ahead.
- **Before any push, audit deployment surfaces.** When the user approves a push, re-read `README.md`, `docs/INSTALL.md`, the installation scripts under `scripts/`, and the Dockerfile / compose files for anything the change invalidated. Stage doc/script fixes as additional commits before pushing.
- **Version is automatic.** The patch is computed by `src/utils/version.ts` (Docker: baked-in `POLARIS_BUILD_COMMIT_COUNT`, otherwise `git rev-list --count HEAD`). Do not touch `package.json` version for patch increments — it stays `<major>.<minor>.0`. Bump the minor (e.g. `0.9.0` → `0.10.0`) only when cutting a named release.
- **FortiManager ↔ standalone FortiGate parity.** Treat the FortiManager and standalone FortiGate integrations as paired surfaces. Whenever you add or change a FortiManager-side feature — new tab, config field, toggle, push pathway, monitoring stream, filter, etc. — evaluate whether the same change applies to the standalone FortiGate path and, if so, ship both in the same change. The two integrations talk to the same FortiOS device fleet via different transports (FMG proxy/direct vs. direct REST), so most user-visible features make sense on both. Only skip parity when the feature is structurally FMG-only (multi-FortiGate device filter, ADOM scoping, FMG-proxy concurrency tuning). UI: the Add/Edit modal tab layouts (`General` / `Filters` / `Monitoring` / `DHCP Push` / `Quarantine Push` / `Description Sync` / `SD-WAN` / `Geographic Location`) should look identical between the two types — diverge only on the tab content where the integrations genuinely differ. Backend: prefer `buildTransportForIntegration()`-style helpers that dispatch on integration type so push/quarantine/lease-release pathways stay generic instead of hardcoding `type === "fortimanager"` checks.
- **Scale-check every change at 100 and 2000 monitored assets.** Before shipping any code that touches background jobs, discovery phases, monitor passes, or per-asset DB queries, explicitly reason through its behaviour at both ends of the fleet-size range. At 100 assets, correctness matters most; at 2000, sequential-await-per-row loops, large IN clauses, repeated findMany calls inside ticking jobs, and DB connection churn become the dominant failure modes. The specific anti-patterns to flag: `for...of rows { await prisma...update() }` (should be `$transaction([...])` or batched `Promise.all`), `for...of items { await someDbCall() }` in a reconciler or job tick (parallelize with `Promise.all` when order doesn't matter), and queries that load all monitored assets without a tight `select` (every extra column at 2000 assets adds memory and serialization cost on the hot 5s/30s ticking loops).

## Observability

`GET /health` (gated by `HEALTH_TOKEN`) and `GET /metrics` (Prometheus, gated by `METRICS_TOKEN`). Tokens are auto-generated by the first-run setup wizard; clearing either surfaces a watch-severity capacity reason. Metrics use the `polaris_` prefix and cover monitor pass duration, per-cadence work duration sliced by asset type + transport, probe RTT, queue depth (cursor + pg-boss), FMG worker dual-lane saturation, DB pool, capacity severity + dead-tuple ratios + steady-state size, discovery duration + per-phase histograms, sample-write + rollup duration, HTTP request latency, per-job duration, per-tick integration-tester outcome (`polaris_integration_test_total{integration_type, outcome}` — `outcome ∈ {success, failure, skipped}`, where `skipped` is the in-discovery branch that preserves prior `lastTestAt`/`lastTestOk`), down-detection index build time + coverage (`polaris_down_detection_build_seconds`, `polaris_down_detection_assets{coverage="covered"|"passive"}` — a climbing `passive` is the signal that devices have stopped being judged, and `polaris_down_detection_unavailable_total` counts the degraded all-passive path), and process crashes (`polaris_process_crash_total{role, kind}` — stamped by the last-resort `unhandledRejection`/`uncaughtException` handlers in `src/utils/crashHandlers.ts` just before `process.exit`; the counter dies with the process, so the signal is `increase()` over a window, not the instantaneous value).

**Multi-process scrape.** prom-client registries are per-process. In the split-role layout (`polaris-web` + `polaris-monitor@N` + `polaris-discovery`), the web process exposes `/metrics` on the main HTTPS listener, but every metric stamped from inside a monitor worker (`runProbeFor`, `runTelemetryFor`, `recordWorkOutcome`, sample-write timers) or discovery consumer (`recordDiscovery`, `observeDiscoveryPhase`, FMG proxy-lane gauges) lives in that worker's local registry. Each non-HTTP role boots a standalone `/metrics` listener via [src/utils/metricsServer.ts](src/utils/metricsServer.ts) when `POLARIS_METRICS_PORT` is set — systemd units default to 910N per monitor replica and 9110 for discovery. Prometheus must scrape **all** role endpoints; dashboard queries aggregate across instances (`sum` for per-process partitions like db_pool / sample buffers / workers, `max` for fleet-wide gauges that one process broadcasts and the others export as 0 — the metric is registered in every process's local registry by virtue of `src/metrics.ts` being imported everywhere) so panels populate as soon as the scrape job is complete. Single-process (`POLARIS_ROLE` unset / `=all`) is unaffected — one registry, one endpoint.

> Full metric catalogue with label sets and operational signal: [ARCHITECTURE.md → Observability](ARCHITECTURE.md#observability).

## Common Claude Code Tasks

- **Add a field to an entity** — Update `prisma/schema.prisma`, generate migration, update Zod schema in the route file, update the service type.
- **Add a new integration type** — New service in `src/services/`, register in `integrations.ts` route (config schema + test/proxy branches), add the sync dispatch in `src/services/discovery/discoveryEngine.ts`. The scheduler is type-agnostic and needs no change; `TOUCHES.md → cross-cutting/integration-type-onboarding` is the authoritative ~30-callsite checklist.
- **Add a new asset field** — Schema + migration, update `assets.ts` Zod schema, update `assets.js` frontend table/form.
- **Add a new role permission** — Add the function key to `FUNCTION_KEYS` in `src/api/middleware/permissions.ts`, migration to seed it on existing Roles, apply the guard at the route layer.
- **Add bulk reservation import via CSV** — Route `POST /api/v1/reservations/import`, service function handles row validation and upsert.
- **Write integration tests** — Vitest + Supertest against a test database (Docker Compose).
- **Add a new environment variable** — Add to `.env.example` with a comment, document in the CLAUDE.md "Environment Variables" block, update `docs/INSTALL.md` if operator-set, and seed a default in `deploy/setup-*.{sh,ps1}` if the install scripts write `.env`. See `TOUCHES.md → cross-cutting/deployment`.
- **Add, rename, or remove a `polaris_*` metric** — Update `src/metrics.ts` (define + helper), the Observability section of this file, the writers list in `TOUCHES.md → cross-cutting/observability-metrics`, AND add/edit/remove the corresponding panel in `docs/grafana/polaris-monitoring-dashboard.json` (with the bullet in `docs/grafana/README.md`). Prometheus picks up new series automatically — Grafana does not.
- **Add a new Polaris Agent sample stream** — Add a Zod variant to `SamplesBodySchema` in `src/api/routes/agents.ts`, map to the enqueue helper, mirror in the Go agent collector under `agent/internal/collectors/`, and bump `agent/VERSION`. See `TOUCHES.md → cross-cutting/polaris-agent`.
- **Bump a runtime dependency or Go pin** — Update `Dockerfile`, every `deploy/setup-*.{sh,ps1}`, and `docs/INSTALL.md` per-platform notes; for Go, bump `agent/go.mod` in lockstep. See `TOUCHES.md → cross-cutting/deployment`.

## Out of Scope

- DNS record management
- DHCP server full-configuration push (scope creation, server policies, lease-time settings — individual reservation push and DHCP lease release ARE supported via the FMG/FortiGate DHCP Push toggle)
- Network device provisioning
- Cloud provider VPC/subnet creation (AWS, GCP, Azure)
- Acting as an identity provider (Polaris authenticates against local accounts, Azure SAML, OIDC, LDAP/AD, or Entra App Proxy header SSO — it does not issue identities for other systems)
