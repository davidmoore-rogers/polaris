# Polaris — Claude Code Project

## Project Overview

**Polaris** is an IP management tool that allows users to reserve and manage IP address space (IPv4 and IPv6) for use across other infrastructure projects. Named after the North Star — a fixed reference point operators can navigate by when wiring up everything else. It provides a central registry for subnets, individual IPs, and reservations — preventing conflicts and giving teams visibility into IP utilization.

> **Naming:** the project was previously called Shelob and has been fully rebranded — every on-host identifier (install path, system user, Postgres DB/user, systemd unit, NSSM service name, firewall rule label), browser-side identifier (CSRF cookie, localStorage keys), and source-level constant (argon2 timing dummy, encrypted-backup magic) now uses `polaris` / `Polaris` / `POLARIS`. Encrypted backups are versioned by the 8-byte magic header `POLARIS\0`; the previous `SHELOB1\0` format is no longer recognized. Existing installs migrate via dump-and-reinstall (plain `pg_dump` carries cleanly into a polaris-named DB).

Version policy: `<major>.<minor>` lives in `package.json` and is the single source of truth — pre-release line is the 0.x series, bump the minor (e.g. `0.9.0` → `0.10.0`) when cutting a named release. The patch is the git commit count, computed at runtime by `src/utils/version.ts`: it reads `POLARIS_BUILD_COMMIT_COUNT` (baked into the Docker image at build time) when set, otherwise falls back to `git rev-list --count HEAD` for RHEL prod / dev where the .git tree is present. Never edit the patch in package.json — it stays `<major>.<minor>.0` there. Version is shown in the sidebar and embedded in backup filenames.

### Entities (one-line summary; see schema + ARCHITECTURE.md for fields)

- **IpBlock** — top-level CIDR namespace; has many Subnets.
- **Subnet** — CIDR carved from a block; has many Reservations; tracks discovery origin.
- **Reservation** — single IP (or full-subnet) entry; `sourceType` distinguishes manual from discovered. Carries FortiGate push state (`pushStatus`, `pushQueuedAt`, etc.), stale-detection state, and `dhcpBinding` (`null` | `"lease"` | `"reservation"` — how the gate hands the address out, deliberately orthogonal to `sourceType`'s "who owns it"; see business rule 23).
- **Integration** — FMG / FortiGate / Entra ID / AD / Windows Server / vCenter / Azure Arc config + discovery state.
- **Asset** — device inventory. Owns five-state monitor machine (`monitorStatus`), polling-method per stream, FortiGate sightings, dependency layer/suppression, quarantine state, and the `managementAccess` summary (read-only `allowaccess` read during FMG/FortiGate discovery → asset slide-over Open HTTPS / Open SSH buttons + FortiAP SNMP-disabled warning; see `fortinetManagementAccessService`).
- **AssetSource** — per-discovery-source view of an asset (entra / intune / ad / arc / fortigate-firewall / fortiswitch / fortiap / fortigate-endpoint / vcenter-vm / vcenter-host / manual / polaris-agent). Discovery-owned Asset fields are projected from these rows.
- **AssetDependencyParent** — parent→child edges of the dependency DAG; drives `Asset.dependencySuppressed`. `source="computed"` rows are the Fortinet infra recompute's (delete-replaced per Fortinet discovery); `source="override"` rows are operator pins (always win); `source="vcenter"` rows are VM→ESXi-host edges written by `syncVcenterDevices` (delete-replaced per vCenter run, scoped to its own source value — the Fortinet recompute never touches them; any non-override source feeds the all-down suppression evaluation).
- **AssetMonitorSample / AssetTelemetrySample / AssetInterfaceSample / AssetHardwareSensorSample / AssetStorageSample / AssetIpsecTunnelSample / AssetPerfSlaSample** — seven append-only sample tables. Each has `*Hourly` and `*Daily` rollup companions populated by `runSampleRollup` (14 rollup tables total). `AssetHardwareSensorSample` (the **Hardware Sensors** stream, which superseded the temperature-only stream) holds one row per device hardware sensor per scrape — `sensorClass` (temperature / fan / voltage / current / optical / poe / power / disk / other — `optical` is transceiver RX/TX power in dBm, `current` its TX bias in base amperes, and `poe` the UNIT-level PSE budget/consumption in watts from `pethMainPseTable` (its own class because `power` is deliberately unit-less, carrying Fortinet's status-shaped PSU rows); the enum is mirrored in `notificationTypes`' `sensorClass` dimension, which is CLOSED, so a class missing there is unselectable in the wizard however many samples carry it) + `value` + `unit` + `alarmStatus` (the device's OWN alarm bit, `"ok"`/`"alarm"`/NULL; alertable via the **`hwSensorAlarm`** boolean asset_metric — see business rule 24 — and rendered as the System tab's STATUS column) — from FortiOS `sensor-info` REST or the SNMP `fgHwSensorTable` / ENTITY-SENSOR-MIB walk; it rides the telemetry cadence via the still-internally-named `temperature` polling stream (`Asset.temperaturePolling` etc. unchanged) + the `hardware` retention entity. The last one is the SD-WAN **SLA-metrics** stream (FortiOS only, gated by `Integration.config.pullSdwan`): `AssetPerfSlaSample` = per (health-check, WAN-member) latency/jitter/packet-loss gauges + SLA thresholds; it rides the system-info cadence like IPsec. (The SD-WAN **rules** stream is no longer a time-series — see `AssetSdwanRule` below.) **These sample/rollup tables (+ `AssetCustomWidgetSample`) carry `assetId` but NO foreign key to Asset** (cascade dropped in migration `20260615000000`): they're TimescaleDB hypertables, and a cascade DELETE matching a compressed chunk decompresses it into un-truncatable bloat (prod incident 2026-06-08). Deleting an Asset orphans its sample rows (queried only by assetId, never surfaced) to age out via `drop_chunks`. Never re-add the relation, and never row-DELETE/UPDATE sample rows that could sit in a compressed chunk — see [TOUCHES.md → tiered-sample-retention](TOUCHES.md). **`AssetInterfaceSample` is PINNED-ONLY** (2026-08): it carries one row per *operator-pinned* interface (`Asset.monitoredInterfaces`) per scrape, not one per interface. Unpinned interfaces previously landed here as `cadence="slow"` and were deleted 24h later — roughly 4–5× the pinned volume, for rows nothing ever read as history: never compressed (deleted at 24h while the selection-aware compression floor is 2 days), never rolled up, and removed by the row-level DELETE behind the compressed-chunk bloat incidents. Every consumer of those rows actually wanted *current state*, which now lives in **`AssetInterface`**. Consequences: an unpinned interface has no chart (the slide-over says so and offers the pin), and the counter-metric automations `ifInBps` / `ifOutBps` / `ifInErrorRate` / `ifOutErrorRate` — which were never pin-scoped, unlike `ifOperStatus`/`ifAdminStatus`/`poeStatus` — now only produce readings for pinned interfaces. Storage and IPsec keep the old fast/slow split.
- **AssetSdwanRule** — CURRENT-STATE SD-WAN service rules (one row per `(asset, ruleName)`, plain table `asset_sdwan_rules`), replaced in full per scrape by `persistSdwanRules` — exactly like `AssetLldpNeighbor` / `AssetWirelessStation`. Carries each rule + its currently-selected member (+ criteria / health-checks / destination / enabled config / zone preference). FortiOS only, gated by `Integration.config.pullSdwan`. NOT a hypertable and NOT a retention entity — no history/timeline (dropped 2026-06; the SD-WAN SLA-metrics stream `AssetPerfSlaSample` remains the only SD-WAN time-series).
- **AssetProcess** — CURRENT-STATE process inventory (one row per `(asset, name)` program, aggregated across PIDs; plain table `asset_processes`, NOT a hypertable), replaced in full per scrape by `persistAssetProcesses` — same delete-replace pattern as `AssetSdwanRule`. Carries `instanceCount` + summed `cpuPct`/`memRssBytes` snapshot + `exePath`/`username`/`startedAt` + `serviceUnit`/`controllable` (Phase 4 control). Drives the merged asset **Services** tab's *Include processes* view (`GET /assets/:id/processes`) — the Processes tab was folded into Services 2026-07. Operator pins live on `Asset.monitoredProcesses` (per-minute CPU/RAM telemetry + log tailing — Feature C) and `Asset.alertWatchedProcesses` (flagged for future alerting; storage-only — no longer surfaced in the tab, alerting moved to Automations). The per-pinned-program time-series + logs are `AssetProcessSample` (hypertable + rollups) / `AssetProcessLogSample` (standalone hypertable); per-program log config is `AssetProcessConfig`; operator-defined log-flag rules (read-time eval over the log viewer) are `LogFlagRule` (CRUD at `/api/v1/log-flag-rules`).
- **AssetService** — CURRENT-STATE service inventory (one row per `(asset, unit)` systemd unit / Windows service; plain table `asset_services`, NOT a hypertable), replaced in full per scrape by `persistAssetServices` (`serviceInventoryService.ts`) — same delete-replace pattern as `AssetProcess`/`AssetSdwanRule`. The **unit-centric** sibling of `AssetProcess` (keyed by unit, not backing program): a service running as a shared runtime (e.g. a Spring Boot app as `java`) is visible as itself, and oneshot/exited units with no live process still appear. Carries `platform` (systemd/windows) + `displayName`/`loadState`/`activeState`/`subState`/`enabledState` + `mainPid`/`mainProcess` (cross-link to Processes) + `memBytes` + `controllable` (derived: systemd loaded/non-masked or any Windows service). Agent-only (`serviceInventory` stream; agentless SSH/WinRM doesn't resolve units). Drives the merged asset **Services** tab (`GET /assets/:id/services`; the tab shows units by default and folds the process inventory in via an *Include processes* checkbox) — read-only (Start/Stop/Restart control was removed in the Satellite-posture change). Operator pins live on `Asset.monitoredServices` (per-unit journalctl tailing → `AssetServiceLogSample` via the agent `serviceLog` stream, Linux-only; surfaced in the Services detail-panel log viewer at `GET /assets/:id/service-logs`) and `Asset.mappedServices` (per-unit connection attribution — the agent stamps `AssetProcessConnection.unit` for the unit's PIDs; surfaced in the Services detail panel's Ports & Connections + filterable on the Application Map). `AssetServiceLogSample` is a standalone detail-only TimescaleDB hypertable (mirrors `AssetProcessLogSample` with `unit` for `name`).
- **VcenterDatastore** — CURRENT-STATE vCenter datastore inventory (one row per `(integration, datastore MoRef)`, plain table `vcenter_datastores`, NOT a hypertable), delete-replaced per discovery run by `syncVcenterDevices`. Carries capacity/free/provisioned (provisioned = capacity − free + uncommitted, SOAP-only), the mounting ESXi hosts' morefs, and `backing`/`backingLabel` (VMFS extent NAA device ids → array vendor via `vendorFromNaa`, e.g. "Pure Storage"; NFS remote host). Rendered on the ESXi-host asset's Virtualization section. `Asset.virtualization Json?` is the per-asset counterpart (fortinetTopology precedent): role-discriminated vm/host blob with VM→host link (`hostAssetId`), cluster, power state, VMware Tools state, vCPU/RAM (+ usage snapshot), per-VM disks (with datastore refs), and Tools-reported guest filesystems — single writer `syncVcenterDevices`, surfaced via `GET /assets/:id/virtualization`.
- **AssetInterface** — CURRENT-STATE interface inventory (one row per `(asset, ifName)`, plain table `asset_interfaces` with a real FK, NOT a hypertable), delete-replaced per FULL system-info scrape by `persistInterfaces` — the `AssetPhysicalEntity` / `AssetMacTableEntry` pattern. Carries the 22 fields the System tab renders (status/speed/IP/MAC/counters/ifType/ifParent/VLAN/alias/description/PoE) plus `firstSeen`/`lastSeen`. Exists because every *all-interface* consumer wants current state rather than history — the System tab reads a single timestamp, and topology inference, the auto-monitor pin picker and FortiAP `lan1`↔`eth0` normalization all want "latest row per (assetId, ifName)", which against the hypertable is a `DISTINCT ON` measured at 13.5 min / 90M rows / 9 GB I/O on prod. **Single writer cadence (load-bearing):** only the full pass and the agent push write it — never `recordFastFilteredResult`, which sees only pinned interfaces (a delete-replace from it would wipe every unpinned row per probe tick) and nulls `ifType`/`ifParent`/`vlanId`. Both callers SKIP an empty interface list rather than wiping, because empty is ambiguous (a FortiOS token without monitor scope answers 200 OK with empty results). Capped at 2000 rows/asset with a loud warn; not a retention entity and never pruned.
- **AssetInterfaceOverride** — operator-typed Interface Comments override. Polaris-local by default; when the originating integration's `syncDescriptions` toggle is on it is description-synced to the device (FortiGate `system/interface` description / FortiSwitch port description, Polaris-primary) and carries per-row sync state (`syncStatus` ∈ synced/failed — `conflict` only on legacy rows from the retired newest-wins engine, `lastSyncAt`, `syncError`, `syncedValue` = last synced value). See business rule 14.
- **AssetMacTableEntry** — the switch's layer-2 forwarding database (CAM table), from Q-BRIDGE-MIB `dot1qTpFdbTable` (RFC 4363, VLAN-aware — preferred) with a BRIDGE-MIB `dot1dTpFdbTable` fallback (RFC 4188, no VLAN dimension, hence `vlanId` NULL rather than a guess). Current-state, delete-replaced per scrape by `persistMacTable` — an FDB entry ages out on the switch in minutes, so history would answer a question the switch itself can't. **Both source tables report a `dot1dBasePort`, NOT an ifIndex**: the join runs through `dot1dBasePortIfIndex` then the scrape's ifIndex→ifName map, and unlike the PoE correlation this join is defined by the MIB and reliable. `basePort` is stored alongside `ifName` so a row whose join failed stays identifiable instead of appearing to belong to no port. `status` keeps the RFC distinction — only `learned` is a real endpoint sighting, `self` is the reporting bridge's OWN address — useful only to exclude it from endpoint counts, NOT a peer signal (a peer switch appears in this table as a `learned` entry on the port facing it) — and `invalid` (an aged-out entry the agent hasn't reaped) is dropped at collection. `matchedAssetId` resolves through the SAME cached MAC index LLDP matching uses, because a per-row lookup would dominate the write at a few thousand rows per switch. Capped at 4000 rows per asset with a **loud** truncation warning — a partial table makes the per-port MAC counts, and any uplink inference drawn from them, quietly wrong. Collected SNMP-only on the system-info (heavy) cadence and gated to `assetType="switch"`; `undefined` preserves stored rows, `[]` wipes. Surfaced at `GET /assets/:id/mac-table` (`assets:read`, returns entries + per-port learned-MAC counts) and the asset-details **MAC Table** tab. Also feeds **MAC-derived topology inference**: `peerInferredLldpService` emits `source:"mac-inferred"` neighbours for ports with exactly ONE learned asset-matched MAC (`inferDirectAttachments`), merged read-time into the Device Map + interface slide-over alongside the existing `peer-inferred` rows — so inference is no longer LLDP-only. **Display-only by design: nothing writes `AssetLldpNeighbor` and nothing writes `AssetDependencyParent`**, because dependency edges drive all-down suppression and a wrong edge silences real alerts; edge-writing waits on bidirectional confirmation validated against a real fleet. A multi-MAC port infers nothing (an uplink's data says "a switch with a network behind it", not which device the port IS).
- **AssetTrunkMember** — FortiSwitch trunk → local physical port, from the vendor OctetString at `1.3.6.1.4.1.12356.106.3.1.1.0` (a SCALAR, hence the trailing `.0`). The trunk name is built from the PEER's serial number, so this is the switch stating its own adjacencies over SNMP rather than leaving them to be inferred — and it covers exactly the FortiLink switch↔switch and switch↔FortiGate links LLDP does not republish in managed mode. Current-state, delete-replaced per scrape by `persistTrunkMembers` (the `AssetLldpNeighbor` / `AssetMclagPeer` pattern; shape deliberately close to MCLAG, both being "local port faces peer device, keyed by serial"). **The name is the peer serial left-truncated to 15 characters**, with `-0` on a switch trunk eating two of them — which is why a switch appears to lose three leading characters and a FortiGate only one. Matching is therefore a SUFFIX test (`matchTrunkPeer` in `utils/fortiswitchTrunkMap.ts`), never a reconstruction: rebuilding the serial would hard-code a cap a firmware release could change. An ambiguous tail (two serials sharing it) resolves to NULL rather than to a guess. Feeds `peerInferredLldpService` as `source:"trunk-mapped"` — named for being device-STATED, not inferred, unlike its `peer-inferred` and `mac-inferred` siblings. Collected SNMP-only on the system-info cadence, gated to `assetType="switch"`; `undefined` preserves stored rows, `[]` wipes.
- **AssetPhysicalEntity** — field-replaceable hardware inventory from ENTITY-MIB (RFC 4133) `entPhysicalTable`: transceivers, PSUs and fan trays with the vendor / model / serial / hardware-rev an operator needs to raise an RMA or find the spare. Current-state, delete-replaced per scrape by `persistPhysicalEntities` (the `AssetLldpNeighbor` / `AssetMclagPeer` pattern), plain table with a real FK to Asset — the no-FK rule is hypertables-only, and this deliberately is not one: inventory changes on a maintenance window, not a cadence. Scoped by `entityPhysicalIsInventory` to rows the device flags `entPhysicalIsFRU`, else module/powerSupply/fan rows carrying a serial or model — a chassis publishes a row per container, port and sensor, hundreds of them naming nothing replaceable. Capped at 500 rows per asset with a **loud** truncation log. `firstSeen` survives a re-scrape for a module still in place (so "this SFP has been in this port since March" holds) and resets when the serial in that slot changes, i.e. on a swap. SNMP heavy cadence only; `undefined` from a transport that can't supply it preserves stored rows, `[]` wipes — the LLDP contract. `ifName` is present on the model but **deliberately never populated**: correlating a module to an interface by entPhysicalIndex == ifIndex is the same equivalence the FortiSwitch sensor annotation was reverted for (97e54fd2), right often enough to look correct and silently wrong the rest of the time. The honest chain is entPhysicalContainedIn → entAliasMappingIdentifier (RFC 4133), which needs a real switch to validate against; the column waits for it.
- **AssetLldpNeighbor / AssetWirelessStation** — current-state tables refreshed per scrape.
- **AssetProcessConnection** — ACCUMULATE + AGE socket facts (listening ports / outbound connections / inbound peers) for MAPPED processes (`Asset.mappedProcesses`, the Processes-tab "Map" toggle — independent of `monitoredProcesses`). Plain table with a real FK to Asset (not a hypertable); rows upsert on the business key via `persistProcessConnections` (batched `INSERT … ON CONFLICT` bumping `lastSeen` behind a 5-minute churn gate, `firstSeen` kept; per-(process,kind) caps 200/500/200) and age out on the flat `appMapConnections` retention window (Server Settings → Retention; `POLARIS_PROCESS_CONN_RETENTION_DAYS` is now only its default seed). Collected per-minute for mapped processes ONLY (never full-host collect-then-filter): agent stream `processConnections` (gopsutil `net.Connections`, direction heuristic on-agent — local port ∈ own listen set ⇒ inbound, ephemeral ports never stored) or the agentless ssh/winrm `processes` cadence. A `ManufacturerCustomWidget` with `widgetType="state"` is a *state probe* — a status-shaped OID (alarm bit, PSU present, fan-tray OK) whose reading is normalized to a boolean at scrape time by the probe's operator-DECLARED `stateMap` (`src/utils/stateProbes.ts`: modes `nonzero`/`zero`/`equals`/`notEquals`/`gte`/`lte` + `trueLabel`/`falseLabel`/`trueIsProblem`). Declared rather than inferred because vendors disagree on polarity — SNMPv2 TruthValue is `true(1)/false(2)`, plenty of enums use 2 for the bad state, some agents answer strings — so a bare `value >= 1` is wrong about as often as it's right; storing the boolean means the automation engine never has to know. - **Alert email** — leads with **what fired, in the builder's own words, with the reading in it** (`{trigger.summary}` → "Response time (median over 5 minutes) is 760 ms"; `utils/triggerSummary.ts` mirrors the wizard's `triggerSentence` phrasing, states a hardware sensor's value in the install's display unit, reads an alarm bit as a STATE rather than "is 1", and falls back to the CONDITION when no reading is available rather than a sentence fragment). It covers every trigger type, not just metrics: a device-state alert reads "**Monitor status is down**" (the builder's `FIELD_META` label, never the column name) and an event alert names the **event that actually happened** rather than the pattern that was configured — "integration.discover.error on FMG-Nashville" — with `{event.action|resource|resourceType|actor|level}` tokens behind matching facts rows, which for an event about an integration or a user are the only identifying facts the email has. "Asset down" points at the response-time chart — the climb before the device stopped answering — and a **packet-loss chart** (`{chart.probeLoss}`, derived by bucketing `AssetMonitorSample` success/failure into 2-minute windows, empty buckets skipped rather than plotted as healthy) carries the alerts where every probe failed and there is no latency left to plot. A hardware-sensor automation (**value or alarm — both**) charts the sensor's VALUE with the device's own alarm periods shaded (`{chart.sensor}`, keyed on `Notification.dimension` = the bare sensor name). A metric that reported nothing in the window is dropped from the body entirely rather than printing "no data". The default outbound body is a shared TEMPLATE (`src/utils/alertEmailTemplate.ts`), not server-side string building: severity header, the alert sentence, a device facts table (IP, connected switch/AP, location, model, automation, raised-at), the **last hour of CPU / memory / response time as inline charts**, and **Acknowledge** + **Open device** buttons. Rendered bodies are pruned (`pruneEmptyRows` / `pruneEmptyDivs` / `pruneEmptyTextLines` / `pruneDeadLinks` at compose time, `pruneEmptyChartSection` at delivery time once `substituteChartTokens` has decided which charts had data) so an under-populated device never mails blank cells, an empty headline, an `<a href="">` button, or a "LAST HOUR" heading over nothing. **`pruneEmptyRows` may never match across a nested `<table>` or a second `<tr>`** — see the alertEmailTemplate.ts entry in ARCHITECTURE.md: a container `<tr><td>` plus the first fact row's empty value cell reads as a label/value pair, and dropping that span took the facts table's opening tag with it and closed the 600px card early, so every alert about Polaris itself mailed a visibly broken box. **An alert about Polaris itself says so**: a system-scoped audit Event (capacity, backups, updates) names no resource, so `utils/alertSubject.ts` supplies `"Polaris server"` as the subject for the `{asset}` token, the stored `Notification.assetHostname` and the event-path cooldown key alike — before it those alerts had a blank headline and a subject line reading "[WARNING]  — Capacity severity escalated". - **NotificationAckToken** — a single-use **one-click acknowledge link**, one row per (notification, user recipient, channel), minted at delivery fan-out and carried inside the alert email / web-push payload; redeemed at the PUBLIC `/ack/:token` page (mounted above session + CSRF; the GET is inert because mail gateways follow links, the POST redeems). Minted **only for recipients who are configured Polaris users holding `alerts:write`** — an address-book contact is an address with no account to attribute the acknowledgement to — and redemption re-checks that permission live. Stored as a base64url **sha256** digest with no prefix column, deliberately unlike `ApiToken`/agent tokens' argon2id + prefix walk: the token is 192 bits Polaris mints itself, so a KDF work factor defends nothing, while ~50ms per recipient would land on the alert fan-out path. Owned by `notificationAckService`; swept hourly by the `deliverNotifications` tick.
- **PushSubscription** — a browser/PWA Web Push subscription owned by a User (`endpoint` unique + `p256dh`/`auth` keys). Stored via `POST /push-subscriptions`; the web_push channel sends to a recipient user's endpoints via `web-push` signed with the channel's VAPID keypair; a 410/404 prunes the row. Carries **`surface`** (`desktop` | `mobile`, default desktop — migration `20260807000000`): which Polaris surface enrolled, recorded at subscribe time because that's the only moment it's knowable (on Android the installed PWA and the browser share one subscription). It rides the delivery row's `meta` and selects the push deep link — mobile → `/mobile.html#more/alerts`, desktop → `/automations.html` (`pushDeepLinkUrl` in `src/utils/notificationTemplate.ts`, which — unlike `notificationsPageUrl` — falls back to a RELATIVE path instead of null when `POLARIS_PUBLIC_URL` is unset, so an unset public URL can't force every push to the desktop page). Endpoint rotation (`pushsubscriptionchange`) posts `oldEndpoint` alongside the new one; the retiring row's surface carries forward and the row is retired, scoped to the caller's own `userId`.
- **AutomationScript** — operator-authored script registry for Automation `script` actions (name unique, interpreter bash|sh|powershell|cmd|python3, body ≤64KB, runTarget server|agent|either, timeoutSec ≤600, sha256 recomputed every save, enabled). **RCE-equivalent surface**: CRUD + attaching script actions gated by the `automationScripts` key (seeded fullwrite only for admin-equivalent roles); creation + body changes stamp warning Events with old/new sha256. Owned by `automationScriptService`; routes at `/automations/scripts` (mounted before `/automations`).
- **AutomationScriptRun** — one execution of a registry script (server- or agent-side): scriptName/sha256 snapshots, notificationId/ruleId/assetId (no FK), runOn, args snapshot, status pending|running|succeeded|failed|timeout, exitCode + stdout/stderr (≤64KB each). Server runs are claimed and executed by the `runAutomationScripts` job (5s) via `automationScriptRunner` (0600 temp file + execFile, args as a single argv, SIGKILL on timeout — never inline in the engine/drain). Two hardening properties of that executor: the interpreter resolves to a known **absolute path** where one exists rather than to whatever the inherited PATH names first (bare name only as a last-resort fallback, so a non-standard layout still runs), and the child environment is `process.env` **stripped of secret-shaped keys** (`buildScriptEnv`: `/SECRET|TOKEN|PASSWORD|PASSWD|DATABASE_URL|SESSION|CREDENTIAL|PRIVATE_KEY|_KEY$/i` — a denylist, so PATH/HOME/proxy/locale stay inherited and existing scripts keep working). The scrub matters because **stdout is STORED on the run row and rendered in the Scripts tab**: before it, a one-line `env` copied `DATABASE_URL` and `POLARIS_SECRET_KEY` into a displayed, backed-up column. Authoring a script is already RCE-equivalent so this crosses no privilege boundary — it removes the accidental copy; agent runs ride the AgentCommand queue (`run_script` payload, sha256-verified by the Go `scriptexec` package, results via `/agents/command-result`); pruned after ~90 days.
- **HostMetricsSample** — Polaris host CPU / memory / load time-series sampled every 30s by `hostMetricsCollector` (web/all role only); `host_metric` rules read the latest row. Plain prunable table (7-day retention).
- **AgentCommand** — the agent command queue. The only queued action is **agent-side script runs** (`action="run_script"`, nullable `payload` Json `{runId, interpreter, body, sha256, args, timeoutSec}` — body inline ≤64KB, sha256 VERIFIED by the agent before executing; queued only for active agents ≥0.13.0 via `requestScriptRun`'s version gate, linked to `AutomationScriptRun.agentCommandId`). Agent polls `GET /agents/commands` (the ≤20s poll is the guaranteed floor; a `commands-pending` WS frame wakes it sooner — see `agentCommandWake`), executes via the `scriptexec` sandbox, reports `POST /agents/command-result` (exitCode/stdout/stderr, ≤64KB each). The agent never self-acts and refuses unknown actions. **Process/service start/stop/restart control was removed** (Satellite-posture change, 2026-07): the `stop`/`start`/`restart` actions, their routes, and the agent-side servicecontrol collectors are gone; the `processControl` RBAC key remains in the catalogue but gates nothing.
- **GroupMapping** — IdP group → role + tags map for OIDC / LDAP / SAML SSO login (`provider` + `groupKey`; nullable `roleId` for tags-only mappings).
- **ManagedAgent** — Polaris Agent install record per Asset (os/arch, agent version, install credential, cert-pin set for dual-pin rotation, `installScriptId` = curated OS-locked install-method variant from the `agentInstallScripts` catalog — null = per-OS default). `privilegeTier` (Linux-only, default `"unprivileged"`) selects the systemd unit: **`unprivileged`** = the hardened `DynamicUser`/`NoNewPrivileges`/`ProtectSystem=strict` unit; **`ptrace`** = that same hardened unit plus `AmbientCapabilities=CAP_SYS_PTRACE CAP_DAC_READ_SEARCH`, the pair that lets the agent read other users' `/proc/<pid>/fd` for Application Map connection→PID attribution WITHOUT full root — both are required: the fd dir's open is a DAC check only DAC_READ_SEARCH passes, the readlink is the ptrace check (SYS_PTRACE alone collects zero rows; prod 2026-07-29). Operator opt-in with a warning — the pair also permits reading any process's memory and any file on the host. Unit text is written only at install/reinstall, so pre-fix ptrace agents need a reinstall; the agent (≥0.17.1, Linux) reports its actual CapEff on heartbeat (`ManagedAgent.reportedCapEff`, decoded by `utils/capEff`) so the Privilege surfaces render the VERIFIED state — a stale SYS_PTRACE-only unit shows red "reinstall" instead of looking healthy. Full **root** was retired with service control (Satellite-posture change); `privilegeTier="root"` survives only as a legacy value on pre-migration rows and is never emitted for new installs — reinstalling such an agent downgrades it to `unprivileged`/`ptrace`. Windows agents always run as LocalSystem, macOS LaunchDaemons as root, so the tier is Linux-only. The tier maps to the `[Service]` block in `src/utils/agentUnit.ts` (pure, `linuxServiceBlock`/`normalizePrivilegeTier`). The privilege change on reinstall rides `POST /assets/:id/agent/reinstall` (`privilegeTier` body field).
- **UserDashboard** — per-user dashboard layout (widget set + positions).
- **UserTableTabs** — per-user list-page TABS (the Assets page tab strip): one row per `(user, scope)` holding `{version, tabs[{id, name, state, savedFilterId?, savedFilterName?}], activeId}`. Each tab carries its own filter+sort `state` (validated by the same `sanitizeFilterState` a preset uses); a tab opened from a preset keeps only a REFERENCE for its label — editing it never writes back, since the preset may be someone else's. Strictly per-caller, no Event audit, CASCADES with the user (the UserDashboard pattern — nothing here is shared, unlike a public SavedTableFilter, which deliberately outlives its author). Absent row = the default single tab, materialized client-side and persisted only once the operator changes something. ≤20 tabs; a stale `activeId` is repaired to the first tab rather than 400-ing the layout away.
- **SavedTableFilter** — a named, optionally SHARED snapshot of one list page's table filter + sort state (Assets page → Filters ▾). `scope` names the table ("assets" today) and maps to the RBAC function key that already gates that page (`SAVED_FILTER_SCOPES` in `savedFilterService`) — no new permission key. `visibility` is `private` (owner only) or `public` (anyone who can read the scope; publishing needs `<key>:write`, deleting someone else's needs `<key>:fullwrite`). `state` is the TableSF `getPrefs` shape `{ sfFilters, sortKey, sortDir }`, re-validated by `sanitizeFilterState` on every write because a public preset is replayed into other operators' browsers; column widths/visibility deliberately stay per-browser in localStorage. `ownerId` is SetNull (a shared preset outlives its author; the users DELETE drops only their private rows), with `ownerName` snapshotted for display. Same `(scope, owner, name)` save updates rather than duplicating.
- **TopologyLayout** — SHARED Device Map topology node positions, one row per (siteId = FortiGate Asset id, view = `"flat"` | `computeFloorViews` building/floor key); `positions` = `{nodeId: {x,y}}` pixel coords. Written full-replace by operator drags in the topology modal (debounced PUT, gated `deviceMap=write`, last-write-wins); embedded for every viewer as `savedLayouts` on `GET /map/sites/:id/topology` — server layout wins over the per-browser localStorage fallback. Cascades with the site Asset. Single writer: `topologyLayoutService`.
- **Event** — audit log, 7-day rolling retention.
- **Conflict** — discovery-vs-existing conflicts (reservation + asset variants; the asset variant also covers the ip-override flavor — `proposedAssetFields.collisionReason="ip-override"`, raised when discovery disagrees with an operator IP pin).
- **DiscoveryRun** — per-integration discovery-run state (status / actor / progress counts / timestamps); one row per integration (`integrationId` unique). `scopeDeviceName` marks a single-FortiGate scoped re-discovery (`POST /assets/:id/rediscover` — full run machinery narrowed to one FMG device; finalize runs `"finalize-scoped"` = Phase 2b per-controller switch/AP decommission only, never the roster-based sweeps).
- **Setting** — key-value config store (`manualMonitorSettings`, `sampleRetention`, `mapRegions`, `agentEventLog`, `branding` (appName / subtitle / logoUrl + **`temperatureUnit`** — the install-wide DISPLAY-ONLY °C/°F choice for hardware sensors, Server Settings → Customization → Display Units. It rides branding because that payload is unauthenticated, cached in localStorage for synchronous reads, and reaches the identity-less Dash wallboard), `appMapAutoMap`, `backupSchedule`, `backup_history`, `assetSourcePriority`, `reservationMacPlaceholder`, etc.). `assetSourcePriority` (`{order[], integrationPrefix}`, Assets → Settings → Sources) orders which discovery source's learned location wins — see business rule 22. `reservationMacPlaceholder` (`{prefix}`, default `02:0F:5E`, Server Settings → Identification) is the OUI every generated placeholder MAC starts with, and the only thing marking such a MAC as synthetic — see business rule 26. `agentEventLog` (`{enabled, minLevel, windowsChannels, linuxMinPriority, maxPerPush, perAssetHourlyCap}`, default disabled) tunes the OS event-log → audit Event ingest (`osEventLogService`); ingested host events become `os_event.<channel>` Events (resourceType=asset) visible in the Events tab.
- **MonitorClassOverride** — tier-2 of the monitor settings hierarchy; manual-scope only post-Phase-2.
- **Tag** / **GeocodeCache** — registry tables. `Tag` carries an optional `criteria` JSON (auto-assignment rule set: manufacturer/model/os/osVersion/hostname/department/location/assetType/status/subnet, plus the relation-backed `integration` (discovered-by integration id) and `fortigate` ("behind FortiGate" via learnedLocation + sighting rows) fields added for the maintenance filter — valid in tag criteria too, though the Tags UI doesn't surface them yet); when set, `tagAssignmentService` keeps the tag synced onto matching assets (managed sync — adds AND removes on drift). **TagAutoAssignment** is the per-(tag,asset) provenance table that lets managed sync strip auto-applied copies without ever touching a hand-applied copy of the same tag name.

## Authentication & RBAC

Sessions are PostgreSQL-backed (`connect-pg-simple`), 8-hour max age, HttpOnly/Secure/SameSite=Lax cookies.

**Dynamic-role model (post-cutover).** RBAC is enforced via `requirePermission(functionKey, level)` from [src/api/middleware/permissions.ts](src/api/middleware/permissions.ts). Each route declares the function key it gates + the required access level; the resolver consults the caller's `Role.permissions` matrix denormalized into `req.session.roleSnapshot` at login. The matrix is `{ [functionKey]: "none" | "read" | "write" | "fullwrite" }` over a 31-key catalogue. The five built-in roles (`admin` / `readonly` / `networkadmin` / `assetsadmin` / `user`) are seeded by `prisma/migrations/20260524000000_roles_table_cutover` so existing accounts keep their pre-cutover access exactly. Admin creates custom roles from the Roles section under Users → Manage Roles.

| Built-in role | Locked? | Pre-cutover behavior preserved |
|---|---|---|
| `admin` | Protected — cannot be edited or deleted; hidden from the editable list | every function = `fullwrite` |
| `readonly` | Protected | every function readable by non-admins = `read`, admin-only functions = `none` |
| `networkadmin` | Editable, cannot delete | IP space / integrations / map-regions / discovery-conflicts write; read elsewhere |
| `assetsadmin` | Editable, cannot delete | assets / quarantine / monitor-settings write + own-subnet/own-reservation write |
| `user` | Editable, cannot delete | own-subnet / own-reservation write; read elsewhere |

**Ownership model for networks, reservations and contacts.** `subnets`, `reservations` and `contacts` carry an ownership dimension: `write` lets the caller edit only rows where `createdBy` matches their username; `fullwrite` bypasses the ownership filter. Built-in `user` and `assetsadmin` are seeded with `write`, `networkadmin` and `admin` with `fullwrite`. Route handlers branch on `req.permissionLevel` (set by `requireOwnership(functionKey)`). **A `dhcp_lease` is not a reservation:** it's observed device presence, so reserving an IP that currently shows a lease is a plain *create* (gated on the caller's `reservations:write`), NOT a release of someone's row — `reservationService.createReservation` supersedes the observed lease server-side via `releaseSupersededDhcpLeaseAt`, which **delegates to `releaseReservation`** (so on push-enabled subnets the FortiGate lease is expired via `releaseDhcpLease`, on read-only subnets it's a pure DB release — identical to the old client `release+create` flow, minus the route ownership gate). This parallels how `createReservation` already supersedes `dns_resolved` via `releaseDnsResolvedAt`. The create's collision check excludes `dhcp_lease`, `dns_resolved`, **and lease-backed `fortiswitch`/`fortinap` rows** (`Reservation.dhcpBinding === "lease"` — see business rule 23); `manual`/`dhcp_reservation`/`vip`/`interface_ip` and infra rows that aren't lease-backed are authoritative and still 409. The takeover set has one definition, `isSupersedableByCreate` in `reservationService.ts`, shared by the 409 check and the supersede-release. Because the take-over is a create, the IP-panel "Reserve" button (desktop `_openLeaseReserveModal` + mobile reserve sheet) no longer issues a separate ownership-gated DELETE. (The `owner` column is display metadata with no role in the ownership gate — on discovered rows it carries the matched asset's `assignedTo`; on manual creates/updates it auto-stamps to the caller's username when not explicitly typed. Gating rides `createdBy` only.)
**Function-key catalogue (31 keys).** Single source of truth in `src/api/middleware/permissions.ts:FUNCTION_KEYS`. (Newest — **`contacts`**, migration `20260810000000_contacts`: the address book, and the third key to carry the **ownership dimension** (`hasOwnershipDimension`) alongside `subnets` / `reservations` — `read` browses, `write` adds and edits/deletes only rows the caller created, `fullwrite` manages anyone's. Seeded admin=fullwrite, readonly=read, networkadmin/assetsadmin/user=write. Before that — the **Automations cutover**, migration `20260721000000_automations_rbac_rename`: `notifications` → **`alerts`** and `notificationManagement` → **`automationManagement`** (levels carried over verbatim), plus new **`automationScripts`** — automation script-registry CRUD + attaching script actions; **RCE-equivalent** (server scripts run as the polaris service user, agent scripts as the agent's user — unprivileged on Linux, LocalSystem on Windows), seeded `fullwrite` only for admin-equivalent roles (users+roles=fullwrite), else `none`. Runtime compat: `LEGACY_KEY_ALIASES` + `permissionOf()` in `permissions.ts` resolve the old key names from pre-deploy session snapshots and `normalizePermissions` folds them on write — never remove that without a session-invalidation plan. Prior additions: `applicationMap` (`20260721000000_application_map` — Application Map page/graph read + shared-layout write, mirrors deviceMap: admin=fullwrite, other built-ins=read), `maintenanceManagement` (`20260715000000`), the notification keys (`20260628000000`), `processControl` (`20260627000000` — now vestigial: process/service control was removed in the Satellite-posture change, so the key remains in the catalogue for matrix compat but gates nothing); removed: vestigial `reservationPush` (`20260703000000`).) Exposed at `GET /api/v1/roles/functions` so the frontend matrix UI renders without hardcoding the list. Adding a new key requires a migration to seed it on every existing Role + a corresponding guard at the route layer; removing one requires a migration to strip it (`normalizePermissions` also drops unknown keys on the next role write).

**Session role snapshot + cache invalidation.** `req.session` carries `roleId` + a denormalized `roleSnapshot` stamped at login. Every `requirePermission` call hits a module-level `Map<roleId, updatedAt>` cache first (O(1)); a Role write bumps the map via `bumpRoleVersion(roleId, updatedAt)` and the next request from any session holding the stale snapshot triggers ONE Prisma fetch + `req.session.save()` to refresh. Changing a user's `roleId` takes effect on next login; changing a role's permissions takes effect on the next request for every session that holds the role.

**Region tags + other tags (storage-only consumer pending).** `Role`, `User`, and `GroupMapping` each carry two operator-typed tag dimensions: `regionTags: String[]` and `otherTags: String[]` (free-form). Empty = unrestricted. Effective scope for a session is `union(role, user, group-derived)` per dimension. Returned by `GET /api/v1/auth/me` as `{ regionTags: { user, role, group, effective }, otherTags: {...} }`. Group-derived tags are re-resolved live from `User.ssoGroups` on each `/auth/me` (never persisted onto the user's own columns, so operator-set tags survive a re-login). Normalization is shared in `src/utils/tagNormalize.ts`. The downstream consumer (list filters, map scoping) still lands in a separate change.

**SSO/LDAP login + IdP group mapping.** Beyond local accounts and Azure SAML, Polaris supports **OIDC** (Authorization-Code + PKCE via `openid-client`; `oidcAuthService.ts`), **LDAP/AD bind** login (`ldapAuthService.ts` over the shared `ldapClient.ts`; LDAP routes through the existing `POST /auth/login` form), and **Entra Application Proxy header-based SSO** (`entraProxyAuthService.ts`; for installs published externally through Entra App Proxy — see below). `authProvider` is now `"local" | "azure" | "oidc" | "ldap" | "entra-proxy"`. At SSO/LDAP login the user's IdP groups are matched against `GroupMapping` rows (`groupMappingService.resolveGroupsToAccess`, scoped by provider — `GROUP_MAPPING_PROVIDERS = oidc/ldap/saml/entra-proxy`) to assign a role + tags: **highest-privilege role wins** (`rankRole` in `permissions.ts`), tags from all matched groups union. No match → keep an existing user's role (new user → `readonly` + `needsRoleReview`). Group-mapping CRUD is gated on `users=fullwrite` (no new function key) and exposed at `/api/v1/group-mappings`; managed in the UI under Users → Group Mappings. **Security caveat:** a mapping to an admin-equivalent role makes IdP group membership a path to Polaris admin (outside the `lastAdminEquivalent` guard) — `groupMappingService` stamps a warning Event when one is created/updated. OIDC requires `POLARIS_PUBLIC_URL` (derives the redirect URI); Azure-AD's `groups` claim emits group object-IDs (GUIDs), so map those IDs unless the IdP is configured to emit names.

**Entra App Proxy header SSO (`entra-proxy`).** For installs published through Microsoft Entra Application Proxy with Entra ID pre-authentication + header-based SSO: App Proxy authenticates the user in the cloud and forwards their claims (UPN, object-ID GUID, group object-ID GUIDs) as operator-named **plain HTTP headers** (configured in the App Proxy SSO blade). Polaris reads them at `GET /auth/entra-proxy/login`, matches on `User.azureOid` (shared with SAML — a user who signs in both ways converges to one account), provisions via `ssoProvisioning`, and stamps a session. **The headers are UNSIGNED — the entire security model is source-IP trust:** Polaris honors the identity headers ONLY from operator-allowlisted App Proxy connector IPs (checked against `req.ip`; empty allowlist = header login disabled, fail closed), and a strip middleware (`api/middleware/entraProxyHeaders.ts`) removes them from every untrusted request as defense in depth. Users arriving from a trusted source are silently auto-logged-in (no login page) via the app.ts protected-page branch; a fallback button shows on the login page only when the request is trusted + carries headers. Config + trusted-IP allowlist + header-name mapping live on Users → Authentication → App Proxy (Setting key `entraProxy`, no secrets). The **Test** button reports the request's source IP as Polaris sees it — the value to put in the allowlist. Note: Entra silently omits the groups header past ~150 groups unless the App Proxy app uses "groups assigned to the application".

**Role-bound bearer tokens.** Each `ApiToken` is bound to a Role at mint time (migration `20260706000000_api_tokens_role_cutover` — replaced the prior fixed scope strings `assets:read` / `dashboard:read` / `assets:quarantine`; legacy tokens were mapped onto seeded `api-*` roles with matching matrices). Token callers pass the same `requirePermission` gates as sessions: the token's role matrix is resolved through an in-process cache invalidated by `bumpRoleVersion`, so a token reaches exactly what its role grants — including filter-don't-403 surfaces like `/search` and `/dashboard/noc-summary`. `requireSessionOrTokenPermission` is retired. `integrationIds` on the token is required when the bound role grants `assetsQuarantine` ≥ write (per-integration quarantine scoping is unchanged). Binding a token to an admin-equivalent role logs an `api_token.admin_equivalent` warning Event (same posture as group mappings). A role bound to any token refuses deletion (friendly 409). **CSRF exemption:** requests carrying `Authorization: Bearer` skip the CSRF token check in `csrf.ts` — cross-site attackers can't attach custom headers, and this is what lets token writes (quarantine push, role-granted mutations) through; authentication is still fully enforced downstream. Write routes reachable by tokens attribute Events via `requestActor(req)` (`api:<token name>`) from `auth.ts`.

**Last-admin invariant.** `roleService.countAdminEquivalentUsers` + `roleService.isAdminEquivalentRole` (in `src/services/roleService.ts`) back the guard that refuses any operation that would leave Polaris with zero users holding `users=fullwrite` AND `roles=fullwrite`. Enforced in `src/api/routes/users.ts` on `PUT /users/:id/role` and `DELETE /users/:id`.

Rate limiting: 10 login attempts / 15 min per IP (limiter in `src/app.ts`). Additional per-surface limiters live in `src/api/middleware/rateLimits.ts`: TOTP confirm/disable (10 / 15 min, mirrors login), OIDC login kick-off (30 / 15 min), Entra App Proxy header login (60 / 5 min — deliberately generous: all App Proxy users share the connector IP, and there's no guessable-credential surface), IdP-driven SSO callbacks + the public `/entra-proxy/config` probe (300 / 5 min — a callback carries a signature-validated assertion rather than a guessable credential, so the limiter bounds flood volume, not guessing; per-IP, and one NAT egress address can carry a whole site's shift-start logins), admin maintenance/backup/logo routes (120 / 5 min), SIEM quarantine verify (300 / 5 min), agent bearer router (1200 / 5 min — per-IP, far above any healthy agent's cadence), agent binary downloads (60 / 5 min). The first-run setup server has its own limiters (whole server 600 / 5 min; DB-touching wizard routes 30 / 15 min) built from the same `makeRateLimiter` factory. Azure SAML SSO is optional; users are auto-provisioned on first login with the `readonly` role.

**FMG auth note:** FortiManager 7.4.7+ / 7.6.2+ removed `access_token` query string support. The service uses the Bearer `Authorization` header exclusively. The standalone FortiGate integration (`fortigateService.ts`) uses the same Bearer pattern. **Never call `/sys/logout`** — Polaris authenticates with a predefined REST API Admin api-key, which per Fortinet's FMG API Best Practices Guide is permanent and shares one session per user; logout/login endpoints are for session-based auth only. A prior hourly `/sys/logout` (commit 3e70476) tore that shared session out from under the split-role monitor/discovery processes and caused RPC `-11` "no valid session" churn — removed. The transport layer (`rpcInner`) retries transient faults only (5xx/network, ≤2 retries, exponential backoff, serialized in the FmgWorker lane) and fails fast on permanent ones (401/403/404/405, `-11`).

**Stale-Secure-cookie gotcha (HTTPS → HTTP downgrade):** A `Set-Cookie` from a non-secure origin is silently rejected by Firefox/Chrome if a same-name `Secure`-flagged cookie already exists, and the rejection extends to `Max-Age=0` deletions. The middleware in `csrf.ts` detects the case (HTTP request, no `polaris_csrf` cookie sent at all) and returns a specific error message instructing the operator to clear cookies for the site. The frontend in `public/js/api.js` does a parallel pre-check before mutating requests. Operator-clears-cookies path is the only reliable recovery on Firefox/Chrome.

## Discovery Workflows

Seven integration types feed discovery: **FortiManager** (multi-FortiGate via FMG; proxy or direct realtime per `useProxy`), **standalone FortiGate** (single device via REST), **Entra ID / Intune** (Microsoft Graph), **on-prem Active Directory** (LDAP/LDAPS), **Windows Server** (WinRM DHCP), **VMware vCenter** (vSphere Automation REST session auth + two narrow SOAP property-collector calls against `/sdk` for what REST can't provide: batched VM quickStats and datastore backing/host-mount info — `vcenterService.ts`), and **Azure Arc** (Arc-enabled servers via Azure Resource Manager — `azureArcService.ts`; the Connected Machine agent runs in the guest, so hostname/OS/serial come from the host itself rather than a directory record. Two opt-in enrichments — `enableVmInstances` (Arc-enabled VMware/SCVMM placement, which also supplies the `instanceUuid` that dedupes against a vCenter integration) and `enableSqlServer` — add one Resource Graph query each and create NO assets; both fold into the owning machine's `observed` blob). All produce assets and (for FMG/FortiGate) subnets / reservations / VIPs. Discovery is triggered manually or by `discoveryScheduler.ts` on each integration's `pollInterval`.

**vCenter** discovers VMs (`assetType="server"` — the dedicated `virtual_machine` type was retired 2026-07; VM identity lives in `Asset.virtualization` + the vcenter-vm AssetSource row), ESXi hosts (`"hypervisor"`), and datastores (current-state `VcenterDatastore` table, delete-replaced per run, with NAA-prefix array-vendor identification — `vendorFromNaa`). VM match cascade: `vcenter-vm` AssetSource by externalId (instanceUuid, `${integrationId}:${moref}` fallback) → vNIC MAC (positive-identity takeover of directory/Fortinet-discovered assets) → hostname collision → Conflict → create. Hosts sync first so each VM's `Asset.virtualization` blob can link `hostAssetId`. VM→host placement feeds `AssetDependencyParent` rows with `source="vcenter"`, vMotion-safe: a VM on a clustered host gets one edge per cluster-member host, so all-down suppression fires only when the entire cluster is dark. Merged assets keep their directory assetType (flip only from `"other"`) and their `discoveredByIntegrationId`; the vcenter-vm source row is how the telemetry collector finds the vCenter integration. Because VMs share the `server` type with directory machines, the VM-class behaviors (dependencyLayer=2 stamp, vmMonitor monitored-sweep) gate on ownership — `discoveredByIntegrationId` — not on the type, so vCenter never fights a directory integration over a MAC-matched server it merely enriches. The vCenter classes reuse the workstation/server-style per-class config blocks as `vmMonitor` (full: agent deploy + interface/storage auto-monitor) and `hostMonitor` (addAsMonitored + streams only); the internal auto-monitor/deploy klass name stays `virtual_machine` even though the assets it selects are servers (queries always pair it with `discoveredByIntegrationId`).

The **AD / Entra / Azure Arc** Monitoring-tab Workstations/Servers subtabs additionally support, per class: **agent auto-deploy** (opt-in, default off — pushes the Polaris Agent to newly-discovered, agent-less devices over SSH/WinRM during discovery, bounded + paced + idempotent; `agentAutoDeployService.ts`) and **interface + storage auto-monitor** (`autoMonitorInterfacesService` reused for the `workstation`/`server` classes + new `autoMonitorStorageService` pinning `Asset.monitoredStorage`). Both run as post-sync passes in `runDiscovery`. Storage auto-monitor is AD/Entra-only (not on the Fortinet classes). Since these devices only report interfaces/mounts via the agent, auto-monitor pins land the cycle after the agent first reports — self-healing. A third post-sync pass, **network-presence verification** (`presenceVerificationService.ts`; integration-level `config.verifyPresence` toggle on the Monitoring tab, default ON), establishes `Asset.lastSeen` for directory-sourced assets — cheapest signal first: already-fresh lastSeen → agent heartbeat → answering monitor probe → single-ICMP fallback against the DNS name. A failed ping writes nothing.

Assets converge via the multi-source model: every discovery pathway upserts `AssetSource` rows keyed on `(sourceKind, externalId)`, then `projectAssetFromSources()` derives the projected Asset row (hostname, serialNumber, manufacturer, model, os, osVersion, learnedLocation, ipAddress, lat/long, snmpLocation, learnedAddress) by priority — `polaris-agent` (host-truth) > `vcenter-vm`/`vcenter-host` (definitive over every other discovery source; guest data relayed by VMware Tools) > `arc`-FQDN > AD-FQDN > Intune > Entra > `arc`-short > FortiGate sources. For the non-hostname fields Azure Arc ranks higher still — directly below `polaris-agent` for `os` / `osVersion` / `serialNumber` / `manufacturer` / `model`, since the Connected Machine agent reads the RUNNING OS and live SMBIOS in-guest on every check-in, whereas AD's `operatingSystem` lags until the computer object re-registers and VMware Tools reports the CONFIGURED guest-OS identifier. Inline writers still update `Asset.macAddress` / `assetType` / operator-owned fields. Three operator pins freeze projected fields against discovery: `coordSource="manual"` (lat/long, checked at the discovery write sites), `Asset.hostnameOverride` (hostname; set by editing Hostname in the asset edit form, cleared by blanking it — enforced centrally by the Prisma extension in `src/db.ts`, which re-asserts the pin over any write staging `hostname` without touching `hostnameOverride`; pinned assets are excluded from the duplicate-hostname ghost merge and from projection-drift logging), and `Asset.ipOverride` (IP; same edit-form set/blank-to-clear pattern and the same central `src/db.ts` guard, but discovery gets a vote — a discovery write staging the SAME IP as the pin releases it in that write (self-disabling, audited `asset.ip_override.released`), while a DIFFERENT staged IP is re-asserted back to the pin and raises one pending ip-override Conflict per asset via `ipOverrideService` — accept adopts the discovered IP + releases the pin, reject keeps it and suppresses re-raise for that same IP; pinned assets skip ipAddress projection-drift logging).

**Address-book directory (GAL) search** is a separate, opt-in read on the same two integrations (`config.enableDirectorySearch`, default off): `directorySearchService` fans a typeahead query to Graph (`/users`, mail-enabled `/groups`, org `/contacts`) and an LDAP user/group/contact search, merging and deduping by address. It is the ONLY people-facing query in either integration — discovery is otherwise devices-only (Entra `/devices` + `/deviceManagement/managedDevices`; AD hard-filtered to `objectClass=computer`) — and it **persists nothing**: results live for one request, and only an address an operator picks becomes a rule recipient or a saved `Contact`. Off by default because it needs directory-read permissions device discovery never required, so without the grant every keystroke would 403. Failures degrade per-integration rather than erroring the typeahead, and query strings are never written to Events.

Hybrid-join detection links AD and Entra/Intune via on-prem SID (`ad.observed.objectSid` ↔ `entra.observed.onPremisesSecurityIdentifier`). Re-discovery key precedence: AssetSource `(sourceKind, externalId)` → SID match → Ethernet MAC match (Entra only) → hostname collision (raises a Conflict).

## Business Rules & Constraints

1. **No overlapping subnets** within the same block. Use `cidrContains()` / `cidrOverlaps()` from `src/utils/cidr.ts` before any subnet creation — and take the per-block advisory lock while you do it: create through `createSubnetRowChecked()` (single row) or `lockBlockForSubnetWrites(tx, blockId)` (batch) in `subnetService.ts`, never a bare `prisma.subnet.create`. A bare create re-opens the race described in rule 20a. Backed by a UNIQUE index on `(blockId, cidr)`.
2. **Subnet must be contained within its parent block** — enforced at service layer.
3. **No duplicate IP reservations** — one `active` reservation per IP per subnet (`@@unique([subnetId, ipAddress, status])`).
4. **Block/subnet deletion protection** — HTTP 409 if any `active` reservations exist.
5. **CIDR normalization** — Host bits zeroed on write (e.g., `10.1.1.5/24` → `10.1.1.0/24`).
6. **sourceType tracking** — All discovered reservations carry a `sourceType`; manual entries default to `manual`.
7. **Conflict detection** — Discovery values differing from an existing manual reservation create a `Conflict` record rather than overwriting.
8. **Event archival** — Events older than 7 days are pruned; syslog (CEF) and SFTP/SCP archival are configurable.
9. **Asset `acquiredAt` ≤ `lastSeen`** — Enforced on every write via `clampAcquiredToLastSeen` in `src/utils/assetInvariants.ts`. If a write would leave `acquiredAt` later than `lastSeen`, `acquiredAt` is clamped down to match. Existing rows are repaired by the `clampAssetAcquiredAt` startup job.
10. **Decommissioned/disabled assets are not monitored** — Enforced on every Asset write via `clampMonitoredForStatus` in the Prisma extension in `src/db.ts`. Whenever a create/update/updateMany/upsert sets `status` to `decommissioned` or `disabled`, `monitored` is forced to `false` and `consecutiveFailures` is reset. One-way: flipping status back to `active` does not auto-resume monitoring — re-enabling is operator-driven. Centralized at the DB layer so every write path benefits.
11. **DNS-resolved reservations** — Any Asset with a primary `ipAddress` falling inside a known (non-deprecated) Subnet that has no existing active reservation gets an auto-created Reservation with `sourceType="dns_resolved"`, `createdBy="system:dns-resolved"`, carrying the asset's hostname (`hostname || dnsName`) and `macAddress` when available. Eligible asset statuses: `active`, `maintenance`, `storage`, `quarantined`. IPv4 only. Never pushes to FortiGates. Never raises Conflict rows — defers silently to authoritative source types. See `src/services/dnsResolvedReservationService.ts`.
12. **`Asset.lastSeen` means verified network presence** — written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts` (no-regress: it only advances, and stamps `Asset.lastSeenSource` provenance alongside). Valid evidence: live DHCP lease (`seenLeased`), FortiGate device-inventory sighting (the FortiGate's own per-client `last_seen` timestamp — never discovery-run time), connected FortiSwitch/FortiAP, firewall answering discovery, agent heartbeat, answering monitor probe, presence-verification ping, operator-resolved conflict. **Polling is authoritative for monitored assets**: when `Asset.monitored === true`, the monitor probe is the sole authority for presence — `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter` — a powered-on VM / connected ESXi host reported at scrape time — and `arc`) so they can't advance `lastSeen` past what polling established. A successful probe stamps `lastSeen = now, lastSeenSource = "probe"` (written through the `probePatchBuffer` bulk-update in `recordProbeResult`, not a Prisma write); a failed probe writes nothing, so a monitored-but-down device's `lastSeen` freezes at its last successful poll even if a FortiGate still reports it `is_online` in device inventory. Active/operator sources (`probe`, `agent`, `ping`, `conflict-*`) are never deferred. (Repointing a managed FortiSwitch/FortiAP's response-time stream to poll "via parent FortiGate" / the controller rather than direct SNMP is the fix when the device is genuinely up but unpollable directly.) **Device inventory outranks the DHCP lease** (unmonitored assets): when a MAC appears in this cycle's device inventory, the lease path skips its bump so the inventory's real `last_seen`/`is_online` wins — a bound-but-idle lease (device leased an IP then went home) must not stamp `now`. Lease-only assets keep the lease bump. **Fortinet-discovery-owned infra never takes client-sighting presence**: firewall/switch/access_point assets carrying a `fortinetTopology` stamp skip BOTH the dhcp-lease and device-inventory bumps — their presence comes only from their own discovery loop (gated on answered-live / connected / `!offline`) and the probe, so an offline-in-FMG gate sighted as a DHCP client of another gate (lingering lease binding, stale cached `is_online`) can't keep freshening its lastSeen; the fortigate-firewall AssetSource row's lastSeen likewise freezes on offline cached-CMDB pulls. Operator-typed non-Fortinet "firewall"/"switch" assets (no topology stamp) keep the endpoint-style bumps. Directory timestamps (Entra `lastSyncDateTime`, AD `lastLogonTimestamp`) deliberately do NOT write it — they stay on the `AssetSource` rows and surface as "Last Directory Activity" in the slide-over; the Entra duplicate-registration tiebreaker compares those directory timestamps, not `lastSeen`. (vCenter and Azure Arc are the exceptions among discovery integrations: vCenter's `power_state`/`connection_state` and Arc's `properties.status === "Connected"` are real-time truth READ AT SCRAPE TIME — categorically different from the stored historical timestamps directory sources carry — so unmonitored VMs/hosts/Arc machines DO get a `"vcenter"` / `"arc"`-sourced bump; both are in the deferred set, so polling stays authoritative once monitoring is on. For Arc the evidence timestamp is always RUN TIME, never `properties.lastStatusChange`, which records when the status last CHANGED and so is 90 days stale on a machine that has been Connected for 90 days.) Presence evidence also gates status resurrection: a remembered-but-offline inventory/switch/AP entry must not flip a `decommissioned` asset back to `active`. `decommissionStaleAssets` consults directory/agent `AssetSource.lastSeen` as a veto so cloud-only laptops don't age out. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path).
13. **SD-WAN monitoring is opt-in, read-only, FortiOS-only** — Gated per-integration by `Integration.config.pullSdwan` (default false), on both the FortiManager and standalone FortiGate integrations. When on, the heavy/system-info pass for FortiGate firewalls also calls `collectSdwanFortinet` (`/api/v2/monitor/virtual-wan/health-check` + `/api/v2/cmdb/system/sdwan`). It writes the `AssetPerfSlaSample` **SLA-metrics time-series** (latency/jitter/loss per WAN member — append-only, rolled up + retained), and refreshes the `AssetSdwanRule` **current-state** table (one row per rule, delete-replaced per scrape via `persistSdwanRules` — no history/timeline). Never writes to the device. The asset modal's **SD-WAN** tab appears only for FortiGate firewalls with data. The runtime "selected route" per rule is **inferred** (first candidate member up in priority order) when FortiOS doesn't expose it over REST — clearly labeled in the UI; verify the exact endpoint/field shapes on a real FortiOS 7.x device. Rules configured for zone-based selection (`priority-zone`) carry no interface members — `parseSdwanRules` resolves their candidates from the preferred zones' member interfaces and records the zones in `priorityZones`, so the UI lists each zone's members (grouped) instead of an empty cell.
14. **Description sync is opt-in and Polaris-primary** — Gated per-integration by `Integration.config.syncDescriptions` (default false), on both the FortiManager and standalone FortiGate integrations (Description Sync tab). **A non-empty Polaris value always wins**: pushed to the device on save and re-asserted by every reconcile, so device-side edits are overwritten (audited with the value they replaced — `asset.description.pushed` `overwroteDeviceValue` detail). **An empty Polaris field adopts** the device value (`asset.description.adopted` / `asset.interface.description.adopted` Events) — clearing the Polaris description is how an operator takes the device's value. No conflict state exists (the earlier newest-edit-wins three-way merge was retired 2026-07; legacy `conflict` sync-state rows resolve on the next reconcile by pushing the Polaris value). `Asset.descriptionSync.value` / `AssetInterfaceOverride.syncedValue` persist the last synced value (bookkeeping for the FMG-mirror device-agrees check + the UI badge, not a merge base). A device-side *clear* never removes a Polaris value (the push re-asserts it). `decideDescriptionSync(polaris, device)` is the pure decision. Surfaces: interface comments (`AssetInterfaceOverride`) ↔ FortiGate `system/interface` description / FortiSwitch port description; `Asset.description` ↔ FortiGate `system/global` alias / FortiSwitch managed-switch description / FortiAP wtp **`location`** (AP Manager's field — wtp `comment` doesn't exist in FMG's copy, so installs strip it; confirmed on a live FMG 7.x). All device I/O rides `reservationPushService`'s Transport (works in FMG proxy AND bypass/direct modes + standalone). Runs at save time (always pushes, best-effort, never blocks the Polaris write) plus a Phase 13.7 discovery reconcile that re-pushes drift / adopts into empty fields and is the retry path — no queue. Clearing a Polaris value is local-only (no device-side delete). Push verifies by read-back; transport errors never mutate sync state. FortiOS field shapes (alias cap, ports child-table PUT) are flagged verify-on-real-device in `descriptionSyncService.ts`; the wtp `location` cap is confirmed at 35 chars. **FMG central management:** each FMG discovery start detects whether the ADOM centrally manages FortiAPs / FortiSwitches (`detectCentralManagement` → stamped on `Integration.config.centralManagement`, rendered on the integration card after the FMG Proxy row); for a centrally-managed class, device-side description pushes are additionally **mirrored into FMG's database** — wtp `location` into the controller FortiGate's device DB (`/pm/config/device/<fgt>/vdom/root/wireless-controller/wtp`, where AP Manager's per-AP rows live), switch descriptions into the ADOM-level `obj/fsp/managed-switch` table — via plain JSON-RPC `update` (never `set`, never an install) so the next install doesn't revert them, and the reconcile batch-heals FMG-side drift for values the device already agrees on. See TOUCHES.md → services/descriptionSyncService.ts.
15. **Location codes ride device descriptions; notes are operator-only** — FortiSwitch/FortiAP admin descriptions (managed-switch CMDB `description` / wtp `location` with `comment` fallback — `location` is the sync surface and the only field present in FMG's copy under central AP management) are captured on every FMG + standalone FortiGate discovery cycle into `fortinetTopology.deviceDescription` (`buildDeviceDescriptionStamp` in `discoveryEngine.ts`), and `a:`(area)/`b:`(building)/`f:`(floor)/`r:`(room)/`jb:`(junction box) codes are parsed from them server-side by `src/utils/locationCodes.ts` (effective codes: the `Asset.description`'s codes when it carries any — EXCLUSIVELY, no per-key fall-through, so removing a code from the description removes the node from that group even while the device copy lags a sync cycle — else the device description's; `Asset.notes` is deliberately NOT a source, notes never inform the topology map) to drive Device Map grouping hulls, row clustering, and floor views. **Discovery never writes `Asset.notes` on an existing asset** (the former description→notes mirror and its `notesSyncedFrom` provenance were removed 2026-07); the only discovery-authored notes content is the one-time `Auto-discovered from FortiGate …` boilerplate stamped at asset creation. Interplay with rule 14: with `syncDescriptions` ON, codes maintained in the Polaris description push to the device (Polaris-primary); device-only codes show through only while the Polaris description carries no codes at all.
16. **Maintenance windows pause everything; status flips are scheduler-managed** — While a `MaintenanceSchedule` window is active for a monitored asset, the `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` (restored when the last window closes; a manually-set "maintenance" is parked verbatim so exit can't loop). `status="maintenance"` stops ALL server-driven polling (`MONITOR_CANDIDATE_WHERE` in `monitoringService` — shared by both the cursor pass and the pg-boss publisher — excludes it; presence-verification pings and `decommissionStaleAssets` skip it too; agent pushes and the operator's explicit Poll Now still work), makes the asset count as DOWN for child dependency suppression (`evaluateSuppression` treats it like an active `dependencyTestUntil` overlay — unless the schedule's `suppressChildren` toggle is off, in which case suppression ignores the maintenance status and the asset evaluates by its frozen `monitorStatus`, so dependents keep monitoring/alerting; OR-ed across an asset's open windows, surfaced as the "Mark dependent devices as down" checkbox on the builder + both ad-hoc paths), and silences notifications for the asset AND for every dependency-suppressed asset (`isSuppressedForNotifications` in `notificationEngine`: readings dropped, `pending` state rows reset so a still-bad condition re-earns its debounce post-window, `firing` rows frozen so exit can't double-fire; escalation sends pause). **Discovery/system writers must never write status over a maintenance asset** (Entra/AD sync, FortiSwitch state sync, lease-presence flip, and the `lastSeen`-aging `decommissionStaleAssets` job are guarded; the reconcile self-heals anything missed by re-flipping and absorbing the clobbered value into `maintenanceReturnStatus`). **Deletion-at-source is the one carve-out:** the discovery decommission sweeps (Phase 2a firewalls + its controller cascade onto their managed FortiSwitches/FortiAPs / Phase 2b FortiSwitches+FortiAPs) DO judge maintenance assets and call `releaseAssetsForDecommission` — window closed `endReason="decommissioned"`, parked status cleared, `status="decommissioned"` written in the same transaction (so the reconcile can't re-enter or self-heal-reflip; the `monitored=false` clamp keeps it out of the target set, and the spent ad-hoc schedule self-deletes). Roster/inventory absence is config truth, not reachability (an offline device stays in the FMG roster; a powered-off switch/AP stays CMDB-protected), so a device deleted mid-window must not sit in maintenance and then be restored to `"active"`. An operator status write moving OFF "maintenance" wins: the assets PUT route calls `operatorReleaseAsset` first (windows closed `endReason="operator"`, which suppresses scheduler re-entry for that occurrence). Open `AssetMaintenanceWindow` rows are the restart-safe source of truth; closed rows feed the labeled chart bands. Dashboard surfaces treat maintenance as its own state, never an outage: the NOC feeds (`nocDashboardService`, mirrored by `/summary` monitorAlerts) exclude `status="maintenance"` from every down/warning/stale list — the frozen `monitorStatus` is not live state — and bucket it as `statusCounts.maintenance`; the Status Map dot and Status Summary "Maint" tile paint it purple (matching the assets-page pill). Events: `maintenance.entered` / `maintenance.exited` / `maintenance_schedule.*`.
17. **ARP presence evidence for stale reservations; the sweep is opt-in** — Every FMG/standalone-FortiGate discovery cycle already reads each gate's ARP table; sync Phase 7.6 stamps `Reservation.lastSeenArp` (and clears `staleNotifiedAt`/`staleSnoozedUntil`, same re-arm semantics as a live lease) whenever the table binds an active dhcp_reservation's IP to its **reserved MAC** on the owning device — minutes-fresh L2 presence that keeps statically-configured / ICMP-silent devices (which never pull a lease) out of the stale list. `effectiveLastSignalMs` in `reservationStaleService` folds it in as a third real signal alongside `lastSeenLeased` and the correlated `Asset.lastSeen`. MAC match is required (a different MAC answering the reserved IP is not presence), matching is scoped per (fortigateDevice, ip) so overlapping RFC1918 subnets behind different gates can't cross-match, and absence of an ARP entry is NEVER negative evidence (reach depends on routing + firewall policy). The **ARP presence sweep** (`Integration.config.arpPresenceSweep`, DHCP Push tab, default off, FMG + standalone parity) additionally primes each gate's ARP cache right before its table read: `arpPrimeService` fires one fire-and-forget UDP datagram per reserved IP — per-gate targets only, paced batches, ~2s settle inside the FortiOS neighbor-cache GC window — so even quiet-but-live devices resolve into the table. Opt-in because the sweep is IDS-visible.
18. **Automation precedence is same-trigger, most-specific-wins** — Two automations "watch the same thing" iff their `triggerSignature` matches (asset_metric metric + dimensionFilter / asset_state field + dimensionFilter; host/event/change/composite are exempt, signature `null`). Among same-signature automations, the more-specific one (higher `scopeRank` on the ladder all assets 0 < device type 1 < OS 2 < manufacturer 3 < model 4 < tag 5 < region 6 < subnet 7 < hostname 8; only positive rules count — negatives/none/notAll broaden; a `region:` tag outranks a plain tag; lifecycle status + assetId are OFF the ladder) **carves out** the assets it covers from every lower-rank one: `evaluateThresholdRule` drops those readings (no fire), clears any active alert (`notification.superseded`, unlike maintenance which freezes), and resets pending debounce. Same-rank + same-signature ties both fire. Index built once per tick (`buildShadowIndex`), per-asset test reuses the pure `scopeMatchesAsset`. Authoring-time preview (`previewRule`) warns both directions: `carveOut.carvesFrom` (this specific draft removes N devices from lower-rank automation X) + `carveOut.carvedOut`/per-match `excludedBy` (this general draft's devices already covered by more-specific Y).
19. **Severity bands escalate one alert by value, each on its own clock** — A numeric automation (asset_metric/host_metric) can stack `severityBands` on the base trigger: tier 0 = `rule.severity` at `trigger.threshold` for `trigger.forDurationSec`, each band a higher `{threshold, severity, operator?, forDurationSec?, actions, escalation}`. **Severities must strictly increase** tier-over-tier (`validateSeverityBands`; UI defaults a new tier one rank up + blocks lowering); tiers **share the base sampling** (aggregation / window / dimensionFilter) but may carry their own ordered `operator` and their own **sustained duration** (both fall back to the trigger's). The value is resolved once and compared to each tier; the **most-severe MET tier wins**, so per-tier thresholds need not be monotonic. **"Sustained for" is per tier, not per rule** — "loss > 5% for 30 min = warning, > 25% for 5 min = critical" is one automation, so a shared `conditionMetSince` can't express it: the engine keeps `NotificationRuleState.bandMetSince` (`{[severity]: epochMs}`, each tier's continuously-satisfied run, rewritten only when a tier enters or leaves) and takes the most-severe tier whose OWN run has outlasted its OWN duration (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure + unit-tested). Consequences that follow from that and are deliberate: a higher tier can fire before the base tier has served its time (each tier earns its own severity); a value climbing between bands never restarts the lower tier's run; a tier that drops out and returns restarts only ITS clock, so flapping into critical never sustains while a steady warning still fires. **De-escalation is immediate** (the lower tier's run is already old) and dropping below tier 0 clears every run. `severityForValue` remains the instantaneous tier-0 membership test; the alert is **one row per asset** whose severity climbs and eases in place. `bandNotify` policy governs delivery: `onIncrease` (default on) runs the entered band's actions; `onDecrease` (default off) runs the destination band's actions; `onResolved` (default on, below tier 0) runs the reuse-the-alert-or-dedicated resolved actions then clears. In the hysteresis dead band (auto reset + `clearThreshold`, value below tier 0 but above the clear line) the alert stays active but **eases to the base severity** — it must not park at a higher band the value no longer satisfies. Each band's own time-escalation is swept band-aware (`escalationChainsForSeverity` in notificationTypes — the band's level chain + its actions' per-action chains, with the empty-band fallback to the base actions mirrored; timers restart from `escalationState.bandSince`, stamped on every crossing). Value-bands (severity) and time-escalation (delivery tiers) are independent axes and coexist.
20. **Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup** — Three operability invariants added by the 2026-08 production-readiness remediation. (a) **Subnet overlap** (rules 1 + 2) is a check-then-insert, so it is only as strong as what serializes the two halves. Every subnet-creating path (`createSubnet`, `allocateNextSubnet`, `bulkAllocate`, the DHCP-discovery create in `discoveryEngine`) now goes through `createSubnetRowChecked` or `lockBlockForSubnetWrites` in `subnetService.ts`, which take a per-block `pg_advisory_xact_lock` BEFORE re-reading siblings; a UNIQUE index on `subnets (blockId, cidr)` is the backstop for the exact-duplicate case. `allocateNextSubnet` retries on a lost race rather than 409-ing, because the caller asked for "any free /N". There is deliberately no exclusion constraint for general overlap — stock PostgreSQL has no GiST-indexable `&&` for `inet`/`cidr`. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret-named string leaves of `Credential.config`, `Integration.config`, `NotificationChannel.config` and `Setting.value` (`utils/secretBox.ts` + `utils/configSecretFields.ts`). The extension is the enforcement seam precisely because several legacy route files still read those models with inline Prisma. **Sealing is per-model; OPENING is all-models**, because Prisma query extensions fire for top-level operations only — a per-model open hook never runs for a relation read like `asset.findUnique({ include: { monitorCredential: true } })`, which is how the monitor hot path loads every credential it polls with, how reservation push loads the FortiGate token, and how description sync loads its integration. So the open pass is its own `$extends` layer (`openNestedSecrets` over `$allModels.$allOperations`) that walks whole results, gated by a zero-allocation `containsSecretField` pre-scan and an `isWalkable` plain-object check so rebuilding a row can't turn its `Date` columns into `{}`. Sealing is a NO-OP without `POLARIS_SECRET_KEY`, and `openValue` never throws — a wrong key degrades to "this credential stopped authenticating", never to an exception on every monitor tick. Raw SQL bypasses the extension; the only raw reader of these columns (`monitorOverrideService`'s `integrations.config #>> '{…,addAsMonitored}'`) touches no secret field. (c) **Backup/restore** lives in `services/backupService.ts`: streamed end to end (never `execSync`/`readFileSync`/`gzipSync`), connection via libpq PG* env vars rather than argv, and the restore wrapped in `timescaledb_pre_restore()` / `timescaledb_post_restore()` in three separate psql sessions with post_restore in a `finally`. A failed pre-update backup ABORTS the update by default (`applyUpdate(password, allowWithoutBackup=false)`) — migrations are irreversible, so a silently-missing backup is the difference between a bad update and an unrecoverable one.

21. **SSH host-key verification is opt-in and fails closed** — Polaris passed no `hostVerifier` to ssh2 until 2026-08, so EVERY SSH connection accepted whatever host key was presented: agent install (which SFTPs a script and runs it as root), agentless process collection, and the SSH monitor probe alike. `SshConfig.verifyHostKey` enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin` — no pin stores and accepts, a match accepts, a CHANGED key **refuses the connection** and stamps a warning `ssh.host_key.mismatch` with both fingerprints. It is **opt-in, default OFF** (default ON only for newly created credentials), mirroring WinRM's `verifyTls`: turning it on globally would break every install whose hosts were never pinned. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites (`withSshClient` + `monitoringService.probeSsh` — the only two) so they can't drift, and it **fails closed** — an internal error refuses the connection rather than silently skipping verification. Pins are per `(host, port)` in their own table, never on `Credential.config`, because one credential spans a fleet of hosts. Deleting a pin (Integrations → Polaris Agent → Windows SSH Deployment) is the documented recovery for a legitimately rebuilt or re-keyed host and is audited at warning level, since it re-opens first-use trust. **TOFU only detects a key CHANGING** — enabling it against a running fleet pins whatever currently answers, so it is strongest on a greenfield rollout where the pin is taken at deploy time.

22. **The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered** — An asset known to several discovery sources at once has several competing answers to "where is it?" (an AD OU path, a controller FortiGate, an Azure Arc onboarding, an Intune enrollment), and which one an operator wants to read is a site convention Polaris can't decide. The assets table's **Sources** column (formerly "Server"; the `data-sf-key` stays `_server` so saved presets keep working) renders the operator's `location` when set, else `Asset.learnedLocation`. The priority behind that second half lives in the `assetSourcePriority` Setting (`{order[], integrationPrefix}`, drag-to-reorder on Assets → Settings → Sources, `assetSourcePriorityService`), and it feeds the **projection** — not just rendering — because the column's filter, its sort, "behind FortiGate X" tag/maintenance criteria and the Device Map's per-site narrowing all read `learnedLocation`. The catalogue of contributors is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string (AD `ouPath`, FortiSwitch/FortiAP `controllerFortigate`, fortigate-endpoint device name, vCenter `clusterName`/`hostName`), **label** contributors have nothing location-shaped to say and contribute their own NAME (`arc` → "Azure Arc", `arc-k8s`, `intune`, `entra`) so the column names who knows the device instead of sitting blank. **Azure Arc is deliberately label-mode:** its only location-ish field is the Azure resource group — a billing container whose name ("updatemanager") tells an operator nothing — which stays on the observed blob and the Sources tab. Never contribute the Azure region (it says where the RECORD lives). `polaris-agent` / `manual` / `fortigate-firewall` never contribute; the `fortigate-endpoint` rule stays suppressed when a fortigate-firewall source exists whatever the order says (invariant, not preference). Propagation is **pull-based** — the projection runs in the discovery process, so `refreshProjectionPriority()` installs the order at boot in every role and at the top of every `runDiscovery`; reordering is **not retroactive**, each integration's assets re-project on its next run. The default order reproduces the pre-feature hardcoded rules for the field contributors, so an install that never opens the card sees one change only: previously-blank columns now name their source.

23. **Who owns an IP and how the gate hands it out are two facts, not one** — `Reservation.sourceType` answers the first; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers the second. Conflating them is what made a FortiLink-addressed FortiAP unreservable: Phase 3a/3b create a `fortiswitch`/`fortinap` row for **every** managed switch/AP, and the address can come from the gate's own DHCP lease table via the `dhcpByHostname` fallback — so Polaris recorded a dynamic lease as an authoritative reservation (plain "Active" pill, no Reserve action) while the FortiGate's DHCP page reported the same address `Not Reserved`. Phase 5 is the only pass that can see the difference, and before this it had **no branch** for those two source types: the entry fell through to a bare `continue`, dropping the fact every cycle and (silently) breaking the "path-* counters sum to entriesTotal" property of its own summary Event. The Phase 5 infra branch now records the binding via the pure `decideInfraDhcpBinding` (`src/utils/infraDhcpBinding.ts`), writing **only on change** because it runs per DHCP entry per cycle. Three deliberate non-writes there: `sourceType` is never flipped (ownership is unchanged and the row's Phase 5b sweep exclusion + decommission semantics depend on it); `expiresAt` is **never** stamped (a lease carries one, and that would hand these rows to `expireReservations` — a live AP's row would expire on the gate's lease clock, be re-created next discovery, and churn); and `macAddress` is fill-only **from the lease entry**, never from `ap.baseMac`, since only the MAC the gate saw requesting the address is the one a future MAC→IP push could bind. A `"lease"` row is takeover-able by an operator Reserve exactly like a `dhcp_lease` (`isSupersedableByCreate`), and releasing it is a pure DB release — neither unpush branch nor the lease-expiry branch fires for it, so claiming an AP's address never bounces its lease. `"reservation"` and `null` stay authoritative: absence of evidence is not evidence the address is free. Phase 3a/3b's conflict-raise is gated on `reservationBelongsToInfraDevice` (MAC, else hostname, else "Polaris pushed it") — without that, the first operator reservation of an AP's IP would raise a conflict card per AP on the next cycle. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets`, called from the Phase 2a controller cascade, the Phase 2b stale-infra sweep, both asset DELETE routes, the operator decommission branch of `PUT /assets/:id`, and `decommissionStaleAssets` — every call site filtered to `switch`/`access_point`, since the same predicate would otherwise match a Polaris-pushed reservation on an ordinary server): it delegates to `releaseReservation`, so the CMDB unpush + lease expiry + audit Events all come for free, and it is bounded per invocation because that call can perform device I/O and a controller cascade can cover hundreds of APs. **"No longer discovered" is deliberately NOT a release trigger** — an offline AP stays in its controller's roster (business rule 16's config-truth-vs-reachability line), so the release hangs off the existing decommission decision rather than a second staleness rule. `reconcileOrphanedInfraReservations` (6h job) is the backstop for a decommission that happened while the gate was unreachable; its pure `classifyOrphanInfraRow` releases on an explicitly decommissioned device, but for "no device found at all" — which is also what a transient discovery state looks like — releases only rows Polaris never pushed, because a false positive on a pushed row would delete a reserved-address entry on a live gate. **Optionally, Polaris writes the binding itself** (`infraReservationPushService`, a post-sync discovery pass): double-gated on `config.pushReservations` (the transport nucleus, re-checked server-side via `integrationPushEnabled`) AND `config.autoReserveFortinetInfra`, both default off, on the DHCP Push tab of BOTH Fortinet integration types. It turns a managed device's dynamic lease into a real `reserved-address` entry on its own gate — **pinning an address the device already holds, so pool occupancy never changes** (this is not a mechanism for claiming free space; the pool-capacity question is deferred because Polaris stores no DHCP range and has no subnet-utilization alerting). This is the only DHCP write in Polaris that happens on a schedule rather than because an operator acted on one IP, so it is bounded per cycle (`RUN_CEILING`), low-concurrency, MAC-from-the-lease-table-only, read-back-verified, and never re-attempts a row carrying push state — a permanent refusal is recorded as `pushStatus="failed_permanent"` + `pushError`, which both drops the row from the candidate set and surfaces the device's own message in the IP panel, instead of being retried every cycle. The push pointers it stamps are exactly what the lifecycle release's pinned-unpush branch needs, so decommissioning the device removes the entry.

24. **Alert on the device's own alarm bit before inventing a threshold for it** — Two boolean asset_metrics exist, and which one to reach for is decided by whether Polaris already collects the fact. **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus` — the per-sensor bit the FortiOS REST `sensor-info` and SNMP `fgHwSensorTable` collectors ALREADY write on the normal hardware-sensor cadence, and which the asset System tab already renders as its STATUS column. It needs no operator configuration, works on every transport that fills the column, and shares `hwSensorValue`'s `sensorClass` / `sensorNamePattern` dimensions (same `hwSensorFilterMatches` predicate), so a rule can target one named sensor or a whole class. Prefer it over a threshold on the reading: the device knows its own per-model limits, and for a fan tray or a PSU the health lives in the bit rather than in any comparable number (a FortiGate PSU reports `1` forever and signals failure only through the alarm). **`customStateValue`** (business rule/`AssetStateSample`, state probes) is the general mechanism for status OIDs Polaris does NOT already collect — any vendor, any table — and is deliberately NOT the answer for Fortinet hardware sensors: pointing a probe at `fgHwSensorEntAlarmStatus` re-walks an OID the collector already walks, into a second table, to alert on a value sitting in the first one, and gives two copies of one truth that can disagree. The shared invariant is the NULL rule: `alarmStatusToFlag` (`src/utils/hardwareSensors.ts`) returns `0 | 1 | null` and the engine excludes `alarmStatus: null` **in SQL**, because a source that publishes no alarm bit (the FortiAP-controller path) must not have its absence mapped to 0 — that would assert health nothing ever checked, clearing live alerts and making every such sensor look verified-healthy. An unrecognized non-empty status maps to 1, not null: it's a claim something is off-nominal, and dropping it would go silent on a real fault. **The ENTITY-SENSOR-MIB walk now DOES publish the bit**, from `entPhySensorOperStatus` via `entityOperStatusToAlarm`: `nonoperational(3)` → `"alarm"`, `ok(1)` → `"ok"` (needed so a cleared fault resolves), and — the load-bearing case — **`unavailable(2)` → NULL, never `"alarm"`**, because an empty SFP cage reports unavailable and a port with no transceiver in it is not a fault; mapping it to alarm would fire on every unused port on the switch. Note the bit means something narrower here than on the Fortinet paths: it reports whether the SENSOR is functioning, not whether the reading is inside its limits. For "this optic is degrading but not yet dead", use a severity-band automation on the dBm `hwSensorValue` instead (business rule 19).

25. **An alert you can't acknowledge from where you read it isn't really acknowledgeable** — `POST /alerts/acknowledge` has existed since the notifications feature shipped, gated `alerts:write`, with **zero frontend call sites**: the asset-details Alerts tab and the mobile Alerts list both rendered alerts read-only, so `escalation.stopOn: "acknowledge"` — offered on every escalation chain the wizard builds — could in practice only ever be stopped by clearing. Acknowledgement now reaches the three places an alert is actually read. **In-app** (the Alerts tab + the mobile list) calls the existing route. **Email and web push** carry a one-click link backed by `NotificationAckToken`, and the rules around that link are what keep it from being a hole: (a) a token is minted **only for a recipient who is a configured Polaris user holding `alerts:write`**, because the token records WHO acknowledged and an address-book contact is an address with no account behind it — contacts and typed addresses get the same mail without a link, never a link that 403s; (b) redemption **re-checks the permission live**, so a role downgrade invalidates links already sitting in mailboxes; (c) the **GET is inert and only the POST redeems** — Outlook Safe Links, Proofpoint and every other mail gateway fetches links before a human sees them, so an acting GET would acknowledge every alert Polaris mails at scan time; (d) the route mounts **above `session()` and `csrfMiddleware`**, not merely CSRF-exempt, because `csrfMiddleware` stamps `req.session.csrfToken` on any request carrying a session and would have every scanner GET mint a `connect-pg-simple` row; (e) the digest is **sha256 with no prefix column**, deliberately unlike the argon2id + prefix-walk pattern `ApiToken` and the agent tokens use — that pattern protects operator-visible secrets of unknown entropy, whereas this is 192 bits Polaris mints, embeds once and consumes, and argon2 at ~50 ms/row would spend seconds of blocked CPU per large alert **on the alert fan-out path**. A composed email (one shared body, several recipients) carries a link only when exactly one To address is user-owned and cc/bcc are empty — otherwise a cc'd contact could acknowledge as the To user. `{ack}` is the one catalogued template token with **no key in `buildTemplateContext`**: its value is per-recipient while the context is built once per fire and snapshotted onto `Notification.templateCtx`, so it is substituted at delivery expansion instead (which works only because unknown tokens survive the render — don't "fix" that).

26. **A generated MAC is a placeholder until the network proves otherwise** — A DHCP reservation is a MAC→IP binding, so reserving an IP for a device that isn't racked yet needs a MAC before there is a device to supply one; the IP panel's **Generate** button synthesizes one. Before this, that MAC was `02:` + 5 bytes of `Math.random()` from two duplicated client-side copies, marked as synthetic nowhere — so the entry sat on the gate matching nothing, the device arrived, DHCP'd with its real MAC, missed the reservation and took a pool address, and the reservation looked correct on both sides while doing nothing forever. **The prefix is the marker, and the only one.** `reservationMacPlaceholder` (Setting, default `02:0F:5E`, Server Settings → Identification) is what makes a stored MAC recognizable as synthetic — there is deliberately no boolean column on Reservation and no Conflict row, because the prefix is visible on the FortiGate's own reserved-address table, so an operator reading the gate can tell which entries are waiting on a device without consulting Polaris. `normalizePlaceholderPrefix` (`utils/mac.ts`) accepts 1–5 hex octets and **rejects any prefix that isn't locally-administered unicast** — that rejection is load-bearing: pointing this at a real vendor OUI (`00:50:56`) would make that vendor's genuine devices look like placeholders and hand discovery permission to overwrite them, whereas a locally-administered prefix cannot be assigned to a vendor, so no factory MAC can fall inside the placeholder space. (`AA:BB:CC` is legal here for the same reason — 0xAA has the LA bit set.) **Adoption** (`placeholderMacAdoptionService`, discovery Phase 7.7, double-gated on `config.pushReservations` + `config.adoptDiscoveredMac`, both default off, FMG + standalone parity) replaces such a MAC with the real one when the gate reports a device at that reserved IP, and re-pushes the corrected binding. Evidence is the **ARP table** and **device inventory** only, keyed `(fortigateDevice, ip)` like Phase 7.6 so overlapping RFC1918 subnets behind different gates can't cross-match; ARP wins over inventory (a live L2 binding beats a cache whose `is_online` lags), an online inventory row beats an offline one, and two ARP rows disagreeing about one address drop it permanently — a duplicate IP on the wire is not something to burn into DHCP config. DHCP lease entries are deliberately NOT evidence (a device whose MAC doesn't match never gets the reserved address, so it can't appear there) and neither is `Asset.ipAddress` (not device-scoped). Five guards make the unattended overwrite defensible: the stored MAC must be a placeholder, the observed MAC must **not** be (never swap one synthetic value for another — that also makes the legacy `02` prefix safe, since a genuine `02:` device presents that same `02:` MAC in ARP and is skipped rather than churned), it must differ, it must not already be held by another active reservation in the same subnet (FortiOS would refuse it *permanently*, parking the row), and the row must not be at `failed_permanent`. The gate write goes through `updatePushedReservation` — **device first, verified by read-back, Polaris second** — so the two views can't diverge; a `pending` row skips device contact and lets the retry tick carry the new MAC. Bounded **per RUN, not per call** (`AdoptionBudget`, 50): in FMG mode `syncDhcpSubnets` runs once per managed gate, so a per-call ceiling would multiply by gate count. Audited per row (`reservation.mac.adopted` / `reservation.mac.adopt_failed`). **Changing the prefix is not retroactive in either direction** and the settings card confirms before saving. Related fix in the same change: Phase 6's DHCP-entry MAC overwrite (a bare `prisma.reservation.update` with no push) is now **skipped for rows carrying push pointers** — it was silently diverging Polaris from the gate for any pushed row, and left unfixed it would have adopted the placeholder away in Polaris while the gate kept it forever.

## Deployment & Updates

The production instance is updated via the **in-app update mechanism** in **Server Settings → Maintenance**. When pushing changes, the user applies the update through that UI rather than manually redeploying. Keep this in mind when giving deployment advice — do not suggest `git pull` or manual restart steps unless asked.

The Application Updates card carries an **update train** selector (`update.train` Setting, default `nightly`): **nightly** tracks the update-branch tip (every commit — the historical behavior), **release** tracks only the highest published release tag (`git tag --sort=-v:refname "v[0-9]*"`, applied via detached-HEAD checkout). The release train stays dormant (reports up-to-date) until the first release is tagged. Logic lives in `checkForUpdates`/`applyUpdate` in [src/services/updateService.ts](src/services/updateService.ts); persisted + surfaced through `GET|PUT /server-settings/updates/settings`.

Every production install runs the split-role systemd layout (`polaris.target` + `polaris-web` + `polaris-monitor@N` + `polaris-discovery` + `polaris-dash` + `polaris-migrate`). The legacy single-process `polaris.service` was removed in Phase 3 — fresh installs land split-role + nginx-fronted out of the box via `deploy/setup-*.sh`, and `restartService()` in [src/services/updateService.ts](src/services/updateService.ts) only handles the split-role + Windows-NSSM paths. Local dev (`npm run dev` with `POLARIS_ROLE` unset = `all`) is still the "everything in one process" runtime behavior — that lives in `src/utils/role.ts`, not in deploy artifacts.

Before kicking `polaris.target`, the transient unit `restartService()` spawns also syncs every shipped `deploy/polaris-*.service` + `polaris.target` into `/etc/systemd/system/` (cmp-only, no-op when unchanged) and runs `systemctl daemon-reload`. The same transient unit ALSO syncs `deploy/nginx/polaris.conf` into `/etc/nginx/conf.d/polaris.conf`, validates with `nginx -t`, and reloads nginx — before the polaris.target restart so any new location blocks are live by the time Polaris comes back up. So unit-file AND nginx-config changes shipped in a Polaris update take effect on the next in-app update with zero operator intervention. **Operator unit customization must live in `<unit>.d/*.conf` drop-ins** — direct edits to the main unit file in `/etc/systemd/system/` (or to `/etc/nginx/conf.d/polaris.conf` itself) get clobbered by the sync (a `journalctl -t polaris-updater` line records each sync).

### Reverse-proxy (nginx) front-end

nginx terminates TLS for every install. `POLARIS_PROXY_CERT_PATH=/etc/polaris-nginx/cert.pem` + `POLARIS_PUBLIC_URL=https://polaris.example.com` are required in `/opt/polaris/.env` (boot fails fast otherwise). Polaris listens HTTP-only on `127.0.0.1:${PORT:-3000}` (web role); `TRUST_PROXY` defaults to `"1"` (first-hop trust) so `req.ip`/`req.secure` honor nginx's `X-Forwarded-*` headers, and Server Settings → Certificates renders the in-app nginx GUI (six operator-settable directives + cert rotation via the dual-pin stage→swap→retire workflow). CA records (`category="ca"`) remain operator-editable because outbound TLS to integrations (LDAP, SMTP) still uses them.

**In-app nginx GUI.** Server Settings → Certificates exposes six directives operators actually need to change day-to-day: HTTPS listen port, HTTP/3 toggle, TLS protocols, HSTS (toggle + max-age + includeSubDomains + preload), Prometheus IP allow-list, plus cert+key rotation. `server_name` is derived from `POLARIS_PUBLIC_URL` and is not user-settable. The GUI persists settings to a `proxyConfig` Setting row and applies via a narrow privileged path: `polaris` user → `sudo /usr/local/sbin/polaris-nginx-apply <subcommand>` → wrapper holds `flock /run/polaris-nginx-apply.lock`, takes the staged file from `/run/polaris-nginx-stage/`, runs `nginx -t`, atomic-renames, reloads nginx. The wrapper is the entire privileged surface — sudoers doesn't restrict args, all validation lives in the shell script ([deploy/scripts/polaris-nginx-apply.sh](deploy/scripts/polaris-nginx-apply.sh)). Setup scripts (setup-rhel/setup-ubuntu and the migrate-to-nginx path) install the wrapper + sudoers + tmpfiles entry + add the polaris user to the nginx group so the existing fingerprint pane reads the `0640 root:nginx` cert file directly. Existing installs picking this up via in-app update get the same wiring through [src/services/updateService.ts](src/services/updateService.ts)'s helper-sync block on every restart. **Adopt-managed-mode gate**: `proxyConfig.managedMode` starts at `false` on every install; the GUI shows a yellow drift banner (with up to five specific drift markers from the parser in [src/services/nginxConfigParser.ts](src/services/nginxConfigParser.ts)) and disables the controls until the operator clicks "Adopt managed mode." This prevents silent clobbering of hand-edits beyond the six controls. In-app updates render `/etc/nginx/conf.d/polaris.conf` from the [polaris.conf.template](deploy/nginx/polaris.conf.template) only when `managedMode=true`; they also check sha256 against `lastAppliedHash` and refuse-to-clobber on drift.

**Cert rotation via the GUI** orchestrates the existing dual-pin endpoints (see the Dual-pin paragraph below): upload cert+key → `/cert/preflight` libcrypto-validates the pair + returns metadata → `POST /agents/cert-pins/bulk-add` stages the new pin on every active agent → `POST /server-settings/proxy/cert/rotate` does the sudo file-swap + nginx reload → `POST /agents/cert-pins/bulk-remove` retires the old canonical fingerprint. The same Maintenance card workflow stays available for operators who prefer it.

The Polaris Agent's leaf-cert pinning: `getServerCertFingerprint()` in [src/services/certInfo.ts](src/services/certInfo.ts) reads `POLARIS_PROXY_CERT_PATH` and computes the same SHA-256 nginx serves. The fingerprint stamps `agent.conf` at install time; the Go agent's `pinned.VerifyPeerCertificate` validates against it on every connection.

**Dual-pin cert rotation** (rotation without fleet-wide agent re-install): each `ManagedAgent` row carries `serverCertFingerprint` (canonical pin) plus `additionalServerCertFingerprints String[]` (staged pins). Enroll cross-check accepts ANY pin in the union; `/agents/config` ships the union to the agent on every poll; the Go agent's `pinned.VerifyPeerCertificate` matches the presented cert against the SET. Operator-driven rotation lives on Server Settings → Maintenance → Polaris Agent → "Cert pin rotation": **stage** a new pin → server pushes to every agent + WS refresh-config → agent saves agent.conf + exits via `os.Exit(0)` so systemd cycles it with the new pin set → rotate the server cert (nginx reload) → wait for every agent to heartbeat post-rotation → **retire** the old pin. The agent.conf format gained a `cert_fingerprints = pin1,pin2,...` line; the legacy `cert_fingerprint = <canonical>` line stays for pre-dual-pin binary downgrade safety. Routes: `GET /server-settings/agents/cert-pins/summary`, `POST /server-settings/agents/cert-pins/bulk-add`, `POST /server-settings/agents/cert-pins/bulk-remove`. Bulk-remove of a pin that would leave any agent with zero pins is skipped for that agent (returns `lastPinSkipped: N`). See cross-cutting/polaris-agent → "Cert pin rotation" in [TOUCHES.md](TOUCHES.md) for the full lockstep checklist.

For pre-nginx installs, cutover is operator-driven via `deploy/migrate-to-nginx.sh --public-url https://polaris.example.com --prometheus-ip 10.0.0.42`. The script: ensures nginx ≥ 1.25 (HTTP/3 stable; falls back to nginx.org mainline repo), extracts the active server cert+key from `Setting.certificates`, stages + validates the nginx config (with HTTP/2 + HTTP/3 listeners both on 443), writes `/etc/polaris-nginx/{cert,key}.pem` with `0640 root:nginx` + SELinux `httpd_sys_content_t`, appends env vars to `.env` (with backup), installs the polaris-web systemd drop-in, opens TCP+UDP/443 in firewalld, restarts polaris.target, smoke-tests Alt-Svc + UDP listener + bearer-gated `/metrics-monitor-1`. Idempotent; transactional (rollback at any gate). See [docs/INSTALL.md](docs/INSTALL.md) for the operator-facing walkthrough.

Fresh installs are documented in `docs/INSTALL.md` with three platform sections (RHEL/Rocky/AlmaLinux 9, Ubuntu/Debian, Windows Server). The disk-sizing table at the top of that file is the single source of truth for DB-volume / app-volume / `/var/log` minimums and recommendations — keep it in sync whenever the runtime workload (sample-table cadences, retention defaults, update-staging cost) changes meaningfully. The setup wizard's preflight check uses `RECOMMENDED_DB_FREE_GB = 50` as the threshold for the warning banner; bump that constant in `src/setup/setupRoutes.ts` if the recommended minimum changes and update the docs table to match.

### Disk-space monitoring (post-install)

Three layers catch a filling DB volume before it crashes Postgres:

1. **Boot-time diagnostic** — `runStartupDiskCheck` in `src/utils/startupDiskCheck.ts` statfs's the app/state/backups dirs plus conventional PostgreSQL data directory candidates per platform. Emits an info/warn/error log line per volume. Non-fatal — never blocks boot.
2. **Periodic capacityWatch job** — every 10 minutes, builds a capacity snapshot and calls `recordCapacityTransition` to write a `capacity.severity_changed` Event when severity flips (ok ↔ watch ↔ amber ↔ red). Events flow out through eventArchiveService → syslog/SFTP archival, so the alert reaches on-call independent of whether the UI is reachable.
3. **Maintenance tab volume bars** — Server Settings → Maintenance → Database card renders one bar per distinct filesystem (deduped by stat.dev) with severity-colored fill and the Polaris-named role(s) each volume serves. Severity tiering: **watch** at 20–30% free (Event-only), **amber** at 10–20%, **red** below 10% (drives the non-dismissible sidebar banner).

### First-run setup lock

The setup wizard is unauthenticated by design (the operator needs to reach it from a browser to provision the host). To stop a network attacker from re-running the wizard against an already-configured host whose `.env` got deleted/corrupted, finalize writes a `.setup-complete` marker at the project root. On every boot:

- `DATABASE_URL` set → app boots normally; marker is back-filled if missing (covers existing installs).
- `DATABASE_URL` missing AND no marker → wizard runs (fresh install).
- `DATABASE_URL` missing AND marker present → process logs a recovery message and exits 1; the wizard never starts.

To intentionally re-provision from scratch, an admin with shell access deletes both `.env` and `.setup-complete`.

## Key Coding Conventions

- All IP math lives in `src/utils/cidr.ts`. **Never** do string manipulation on IPs elsewhere.
- **Resolving a FortiSwitch/FortiAP's parent goes through `src/utils/fortinetParentKey.ts`. Never match `fortinetTopology.controllerFortigate` against `Asset.hostname`.** That field holds FortiManager's *device name*; a firewall's hostname is projected from the gate's own configured hostname, and the two differ on any install where an operator named the FMG device differently — in which case every child resolves to *no parent*, silently, because "no parent" is a legitimate state. That single mismatch broke dependency suppression (a gate in a maintenance window left its switches reading "Down" instead of "Dep. Down"), Device Map site membership, map-region membership + subnet propagation, and FortiLink interface auto-monitor. The util resolves `controllerSerial` → the gate's own `fortinetTopology.deviceName` → hostname → the name-as-serial. Note the *second* class of consumer that must keep using the device name: anything addressing an FMG/FortiOS API (parent-FortiGate polling, decommission sweeps, description-sync transports, the Sources column). See `TOUCHES.md → cross-cutting/fortinet-parent-key-resolution`.
- Services (`src/services/`) contain **all business logic**. Route handlers are thin — validate input, call a service, return a response.
- All Zod schemas live co-located with their route file (top of file).
- Database calls go through service functions only — never raw Prisma in route handlers. **Interim state (2026-06):** several legacy route files still carry inline Prisma (heaviest in `agents.ts`, `assets.ts`, `integrations.ts`, `serverSettings.ts`, `users.ts`). New endpoints MUST use services; when you touch a legacy route, extract opportunistically. Until a handler is extracted, any audit-worthy mutation it makes must still write an `Event` inline (these files already import `logEvent`) — auditability is the part that can't wait for the refactor.
- All errors thrown by services must be instances of `AppError` (`src/utils/errors.ts`) with an `httpStatus` property.
- Use `async/await` throughout; avoid `.then()` chains.
- Write a unit test for every public function in `src/utils/` and `src/services/`. `vitest.config.ts` excludes `**/.claude/**`: those are full scratch checkouts of this repo (one per in-flight branch) and Vitest's default include would otherwise collect every worktree's tests into `npm test` — silently inflating the suite ~3× and failing loudly once a worktree diverges enough to reach a real DB. If the file count jumps between runs, suspect that first.
- All audit-worthy actions (creates, updates, deletes, discovery events) must write an `Event` record.
- **Ask before committing.** After completing each logical change, do not commit automatically — ask the user whether to commit. Each logical change still gets its own commit (don't batch unrelated work), but the user decides when.
- **Before any commit, review CLAUDE.md, `ARCHITECTURE.md`, `TOUCHES.md`, and `TEMPLATES.md` for updates.** When the user approves a commit, re-read all four — CLAUDE.md (always-loaded conventions/rules/overview), ARCHITECTURE.md (full file map / domain model / API catalog / discovery / jobs / frontend / observability — most likely to need updates), the relevant `TOUCHES.md` entries (per-service writers/readers/invariants/checklists or cross-cutting writer/reader lists), AND the relevant `TEMPLATES.md` entries (canonical implementations whose file paths, function names, conventions, or checklists may have shifted; new patterns that have crystallized into a clear canonical and should be added). Anything the change moved, broke, or invalidated gets refreshed in the same commit. The indexes only stay trustworthy if they're reviewed every commit. A pre-commit hook + CI job (`npm run check:docs`, `scripts/check-docs.mjs`) enforce the *structural* half automatically — every Prisma model / service / job / route must be named in ARCHITECTURE.md, no `file:line` refs in the indexes, no dead doc-referenced paths — but they cannot judge whether prose is still accurate, which is what this review is for.
- **Ask before pushing.** Never push without the user's explicit go-ahead.
- **Before any push, audit deployment surfaces.** When the user approves a push, re-read `README.md`, `docs/INSTALL.md`, the installation scripts under `scripts/`, and the Dockerfile / compose files for anything the change invalidated. Stage doc/script fixes as additional commits before pushing.
- **Version is automatic.** The patch is computed by `src/utils/version.ts` (Docker: baked-in `POLARIS_BUILD_COMMIT_COUNT`, otherwise `git rev-list --count HEAD`). Do not touch `package.json` version for patch increments — it stays `<major>.<minor>.0`. Bump the minor (e.g. `0.9.0` → `0.10.0`) only when cutting a named release.
- **FortiManager ↔ standalone FortiGate parity.** Treat the FortiManager and standalone FortiGate integrations as paired surfaces. Whenever you add or change a FortiManager-side feature — new tab, config field, toggle, push pathway, monitoring stream, filter, etc. — evaluate whether the same change applies to the standalone FortiGate path and, if so, ship both in the same change. The two integrations talk to the same FortiOS device fleet via different transports (FMG proxy/direct vs. direct REST), so most user-visible features make sense on both. Only skip parity when the feature is structurally FMG-only (multi-FortiGate device filter, ADOM scoping, FMG-proxy concurrency tuning). UI: the Add/Edit modal tab layouts (`General` / `Filters` / `Monitoring` / `DHCP Push` / `Quarantine Push` / `Description Sync` / `SD-WAN` / `Geographic Location`) should look identical between the two types — diverge only on the tab content where the integrations genuinely differ. Backend: prefer `buildTransportForIntegration()`-style helpers that dispatch on integration type so push/quarantine/lease-release pathways stay generic instead of hardcoding `type === "fortimanager"` checks.
- **Scale-check every change at 100 and 2000 monitored assets.** Before shipping any code that touches background jobs, discovery phases, monitor passes, or per-asset DB queries, explicitly reason through its behaviour at both ends of the fleet-size range. At 100 assets, correctness matters most; at 2000, sequential-await-per-row loops, large IN clauses, repeated findMany calls inside ticking jobs, and DB connection churn become the dominant failure modes. The specific anti-patterns to flag: `for...of rows { await prisma...update() }` (should be `$transaction([...])` or batched `Promise.all`), `for...of items { await someDbCall() }` in a reconciler or job tick (parallelize with `Promise.all` when order doesn't matter), and queries that load all monitored assets without a tight `select` (every extra column at 2000 assets adds memory and serialization cost on the hot 5s/30s ticking loops).

## Observability

`GET /health` (gated by `HEALTH_TOKEN`) and `GET /metrics` (Prometheus, gated by `METRICS_TOKEN`). Tokens are auto-generated by the first-run setup wizard; clearing either surfaces a watch-severity capacity reason. Metrics use the `polaris_` prefix and cover monitor pass duration, per-cadence work duration sliced by asset type + transport, probe RTT, queue depth (cursor + pg-boss), FMG worker dual-lane saturation, DB pool, capacity severity + dead-tuple ratios + steady-state size, discovery duration + per-phase histograms, sample-write + rollup duration, HTTP request latency, per-job duration, per-tick integration-tester outcome (`polaris_integration_test_total{integration_type, outcome}` — `outcome ∈ {success, failure, skipped}`, where `skipped` is the in-discovery branch that preserves prior `lastTestAt`/`lastTestOk`), and process crashes (`polaris_process_crash_total{role, kind}` — stamped by the last-resort `unhandledRejection`/`uncaughtException` handlers in `src/utils/crashHandlers.ts` just before `process.exit`; the counter dies with the process, so the signal is `increase()` over a window, not the instantaneous value).

**Multi-process scrape.** prom-client registries are per-process. In the split-role layout (`polaris-web` + `polaris-monitor@N` + `polaris-discovery`), the web process exposes `/metrics` on the main HTTPS listener, but every metric stamped from inside a monitor worker (`runProbeFor`, `runTelemetryFor`, `recordWorkOutcome`, sample-write timers) or discovery consumer (`recordDiscovery`, `observeDiscoveryPhase`, FMG proxy-lane gauges) lives in that worker's local registry. Each non-HTTP role boots a standalone `/metrics` listener via [src/utils/metricsServer.ts](src/utils/metricsServer.ts) when `POLARIS_METRICS_PORT` is set — systemd units default to 910N per monitor replica and 9110 for discovery. Prometheus must scrape **all** role endpoints; dashboard queries aggregate across instances (`sum` for per-process partitions like db_pool / sample buffers / workers, `max` for fleet-wide gauges that one process broadcasts and the others export as 0 — the metric is registered in every process's local registry by virtue of `src/metrics.ts` being imported everywhere) so panels populate as soon as the scrape job is complete. Single-process (`POLARIS_ROLE` unset / `=all`) is unaffected — one registry, one endpoint.

> Full metric catalogue with label sets and operational signal: [ARCHITECTURE.md → Observability](ARCHITECTURE.md#observability).

## Common Claude Code Tasks

- **Add a field to an entity** — Update `prisma/schema.prisma`, generate migration, update Zod schema in the route file, update the service type.
- **Add a new integration type** — New service in `src/services/`, register in `integrations.ts` route (config schema + test/proxy branches), add the sync dispatch in `src/services/discovery/discoveryEngine.ts`. The scheduler is type-agnostic and needs no change; `TOUCHES.md → cross-cutting/integration-type-onboarding` is the authoritative ~30-callsite checklist.
- **Add a new asset field** — Schema + migration, update `assets.ts` Zod schema, update `assets.js` frontend table/form.
- **Add a new role permission** — Add the function key to `FUNCTION_KEYS` in `src/api/middleware/permissions.ts`, migration to seed it on existing Roles, apply the guard at the route layer.
- **Add bulk reservation import via CSV** — Route `POST /api/v1/reservations/import`, service function handles row validation and upsert.
- **Write integration tests** — Vitest + Supertest against a test database (Docker Compose).
- **Add a new environment variable** — Add to `.env.example` with a comment, document in the CLAUDE.md "Environment Variables" block, update `docs/INSTALL.md` if operator-set, and seed a default in `deploy/setup-*.{sh,ps1}` if the install scripts write `.env`. See `TOUCHES.md → cross-cutting/deployment`.
- **Add, rename, or remove a `polaris_*` metric** — Update `src/metrics.ts` (define + helper), the Observability section of this file, the writers list in `TOUCHES.md → cross-cutting/observability-metrics`, AND add/edit/remove the corresponding panel in `docs/grafana/polaris-monitoring-dashboard.json` (with the bullet in `docs/grafana/README.md`). Prometheus picks up new series automatically — Grafana does not.
- **Add a new Polaris Agent sample stream** — Add a Zod variant to `SamplesBodySchema` in `src/api/routes/agents.ts`, map to the enqueue helper, mirror in the Go agent collector under `agent/internal/collectors/`, and bump `agent/VERSION`. See `TOUCHES.md → cross-cutting/polaris-agent`.
- **Bump a runtime dependency or Go pin** — Update `Dockerfile`, every `deploy/setup-*.{sh,ps1}`, and `docs/INSTALL.md` per-platform notes; for Go, bump `agent/go.mod` in lockstep. See `TOUCHES.md → cross-cutting/deployment`.
