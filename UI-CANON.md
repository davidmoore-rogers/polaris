# UI-CANON.md — the Polaris UI canon

The canonical-implementation index for **UI** patterns: when there are several
ways to build the same thing (chart, modal, slide-over, sortable table, wizard,
row menu), this names the reference implementation new work should match, plus
the surfaces Polaris built on top of the kit that a new app won't have (the
mobile SPA, dashboard widgets, the condition builder, per-stream polling
subtabs). It is the UI counterpart of [TOUCHES.md](TOUCHES.md) → Canonical
backend patterns, and it absorbed the UI half of the retired Primaries index in
2026-08.

**Read [design/POLARIS-UI-GUIDE.md](design/POLARIS-UI-GUIDE.md) first** for the
*shape* — that file is the portable UI contract (tokens, themes, shell, tables,
modals, badges, z-index, the phone SPA, the alert email), written to be handed
to a NEW app unchanged. Read this file for *which file in THIS repo* to copy.

> **This index lives outside `design/` on purpose.** `design/` is a drop-in zone
> for the portable kit: it gets re-synced wholesale when the kit is updated, and
> the kit's own guide has no Polaris canon in it. This index used to be Part II
> of that guide, so a kit copy-in silently deleted all 24 sections of it
> (2026-08-26 — caught only because the diffstat read 232 insertions against
> 631 deletions). Out here, a copy-in cannot reach it. Inside this repo
> `public/` is the LIVING source; `design/js/`, `design/css/` and
> `design/email/` are snapshots, never edited to chase `public/`.

Per-pattern sections carry: **What it is** / **Canonical implementation**
(`path/file.ts → symbolName()` — no line numbers, they drift; grep the symbol) /
**Key conventions** / **When adding a new instance**. Per CLAUDE.md's
commit-review rule, every commit re-reads this file for staleness — if your
change replaced a canonical, moved its file, or invalidated a convention, fix
it in the same commit.

## Shared frontend utils

**What it is:** A handful of small helpers that every page is expected to reuse rather than re-declare. Re-rolling these locally is the most common source of subtle frontend drift (an un-escaped value, a date that formats differently on one page, two color palettes for the same status).

**Canonical helpers:**
- **`escapeHtml(s)`** + **`mobileFormatDate(iso)`** — both live in [public/js/api.js](public/js/api.js), which is loaded first on every page (desktop **and** mobile, via `<script src="/js/api.js">`) and exports them onto `window`. Use these everywhere a dynamic value lands in an HTML string or a timestamp needs the short human form — never hand-roll a local copy. **Exception:** [public/js/setup.js](public/js/setup.js) keeps its own self-contained `escapeHtml` (with a comment marking why) because `setup.html` does **not** load `api.js` — the first-run wizard is a standalone bundle. That's the only sanctioned duplicate.
- **`debounce(fn, ms)`** — the generic debounce lives in [public/js/table-sf.js](public/js/table-sf.js). It's available wherever `table-sf.js` is loaded (the desktop list pages). **Mobile is not covered:** `mobile.html` loads `api.js` but **not** `table-sf.js`, so the mobile SPA has its own local **`debounceSearch`** in [public/js/mobile/tabs.js](public/js/mobile/tabs.js) for the search box. Don't reach for `table-sf.js`'s `debounce` from mobile code — it isn't on the page.
- **`window.PolarisPlaceholderMac`** — the placeholder-MAC generator in [public/js/placeholder-mac.js](public/js/placeholder-mac.js), loaded by `ipam.html`, `subnets.html` and `mobile.html`. Every "Generate" button on a reservation MAC field goes through it. This one exists BECAUSE it was duplicated: `ip-panel.js` and `mobile/subnet-detail.js` each carried a byte-for-byte copy, and the drift showed up as the mobile EDIT sheet having no Generate button at all. It also mirrors `normalizePlaceholderPrefix` from [src/utils/mac.ts](src/utils/mac.ts) — if you change the prefix rules server-side, change them here too.
- **Status / health color palettes** — the monitor-state pill palette is **`MONITOR_STATE_COLORS`** (`up` / `down` / `warning`) in [public/js/assets.js](public/js/assets.js); the topology-node palette is **`HEALTH_NODE_COLORS`** in [public/js/topology-render.js](public/js/topology-render.js). These are intentionally two palettes — the topology palette adds node-specific states (unmonitored, dependency-suppressed/unknown) the flat status pill doesn't model. Reuse the matching one for the surface you're building; don't introduce a third.

**When adding a new instance:**
- Reuse `escapeHtml` / `mobileFormatDate` from `api.js` directly — they're global. Only fork a copy if your page genuinely doesn't load `api.js` (today only the setup wizard), and leave a comment saying why.
- Need a debounce on a desktop list page? Use `table-sf.js`'s `debounce`. On mobile, follow `debounceSearch` in `mobile/tabs.js`.
- Coloring a status surface? Pick the existing palette (`MONITOR_STATE_COLORS` for flat pills, `HEALTH_NODE_COLORS` for graph nodes) instead of minting new hex values.
- Generating a MAC for a reservation? Call `window.PolarisPlaceholderMac.generate(prefix)` and pass the prefix off the IP-panel payload (`subnet.macPlaceholderPrefix`). Never hand-roll one — a MAC outside the configured prefix is invisible to discovery's adoption pass, which is the whole point of generating it.

## Time-series chart (SVG)

**What it is:** A range-selectable SVG line chart driven by an API endpoint that returns `{ since, until, samples, stats }`. Used for response time, CPU+memory, interface throughput/errors, IPsec bytes, storage usage, sensor temperatures.

**Canonical implementation:** Asset Details → System → **Response Time** graph.
- Loader: `_loadMonitorHistoryFor()` in `public/js/assets.js` — fetches history + polling-method transitions, calls renderer, schedules auto-refresh.
- Renderer: `_renderMonitorChart()` in `public/js/assets.js` — builds the SVG; uses `_chartTimeBounds()` to align to `since`/`until` so empty regions stay visible.
- Range buttons: `_chartRangeBtnsHTML()` in `public/js/assets.js` — produces the `1h / 12h / 24h / 7d / 30d / Custom` toolbar.
- Drag-select: `_stashChartGeometry(container, t0, t1, padL, innerW, viewW)` (called by every renderer after writing the SVG) + `_wireChartDragSelect(container, applySelection)` (wired ONCE per panel open, next to the range-button handlers) + `_applyCustomRangeSelection(ui, fromIso, toIso)` — click-drag on the plot area applies the selection as the chart's custom window and pre-fills the Custom From/To panel. Geometry rides the container's dataset so re-renders never re-wire.
- Persistence: `_getChartRangePref(key, fallback)` / `_setChartRangePref(key, range)` in `public/js/assets.js` — per-user `localStorage.polaris-prefs-charts-<username>` JSON map keyed by chart id (`assetMonitor`, `assetSystem`, `assetSensor`, `assetInterface`, `assetIpsec`, `assetStorage`).
- Tooltip: `_wireChartTooltip(container, formatHTML)` in `public/js/assets.js` — single shared hover handler all charts use.
- Resize: `_observeChartResize(container, rerender)` — re-renders on container resize via ResizeObserver.
- Stats line: `_renderChartStats(container, count, parts)` — single helper every chart calls; produces the canonical `<count> samples · <Label>: <value> · …` shape and writes a plaintext fallback to `container.dataset.summary` for screenshots/tooltips.
- Camera button: `_addChartScreenshotButton(container, label, axisOpts)` — per-chart clipboard PNG with a self-identifying header (title / subject / asset / stats + axis labels drawn in canvas margins). Pass `getStats: _statsSummaryFrom("<stats-el-id>")` so the capture includes the same samples/Avg/Min/Max line shown above the chart (storage's per-mount bars use `_storageStatsSummaryFor(container)` instead — no fixed id).
- Polling-method badge: `_streamSourceBadgeHTML(asset, stream)` (sync first paint) + `_updateStreamSourceBadgesFromEffective(assetId, asset, effP?)` (async overwrite from `/effective-monitor-settings`). Renders `<method> (<details>) · every <interval> · <tier>`. The optional `effP` is a caller-supplied in-flight settings promise — `openViewModal` passes its per-open memo so the panel costs one fetch instead of three; the sub-panel refreshes (interface / sensor / IPsec / SD-WAN detail) omit it deliberately so they re-read live after a settings change. Same contract on `_renderIntermittencyBar(assetId, effP?)`.
- Lookback overflow: route helper `extendSinceForLookback(since, bucketSeconds)` in `src/api/routes/assets.ts` + optional `fetchSince` parameter on every `read*History` service in `src/services/sampleHistoryService.ts` + frontend helpers `_chartClipId(prefix)` / `_chartClipDefs(id, padL, padT, innerW, innerH)` / `_chartClipAttr(id)` near the chart-prefs block in `public/js/assets.js`.

**Key conventions:**
- **Lookback overflow + clip-path.** Each history endpoint extends the data query backwards by one bucket of overflow (`fetchSince = since − 5min` on detail tier, `since − 1 bucket` on hourly/daily) via `extendSinceForLookback` in the route handler. The service uses `fetchSince` for the WHERE clause but filters stats to `timestamp >= since` so operator-visible counts and averages match the visible window. The response keeps `since` / `until` at the visible bounds. The frontend chart renderers wrap the data layer (line segments / dots / baseline failure dots / hit targets) in `<g clip-path="url(#chart-clip-…)">` whose `<rect>` matches the inner plot area exactly — `_chartClipId(prefix)` generates a unique id per chart instance, `_chartClipDefs(id, padL, padT, innerW, innerH)` emits the `<defs><clipPath>` block, `_chartClipAttr(id)` returns the matching attribute. Axis ticks / grid lines / legend / stale banner stay OUTSIDE the clipped group so they render normally. The pattern keeps the operator-visible window literal (X-axis still spans `[since, until]`) while letting the polyline enter the chart from the left edge with continuous data instead of starting partway through.
- **Failure-aware line rendering.** Failed polls plot as red dots pinned to the chart baseline (0 on the y-axis) and stay CONNECTED to their neighbors — the transition segments fade from the series color into red via per-segment `userSpaceOnUse` linearGradients, and consecutive failures draw red along the baseline. Helpers: `_failureAwareSeriesSVG(pts, seriesColor, idPrefix)` (returns `{defs, segments}` — emit `defs` inside a `<defs>` block, `segments` inside the clipped group in place of the polyline) + `_failureDotsSVG(pts)` + the shared `_CHART_FAIL_COLOR`. Response Time derives failures from the per-sample `success` flag (fully-failed rollup buckets count too); streams with NO success flag (CPU/Memory telemetry, storage, interface throughput/errors) get theirs from `_outageMarkers(outages, sampleTimesMs)` with a `data-miss="1"` hit rect whose tooltip reads "Missed poll — no data collected". Because red now means *missed poll*, no data series may use red — the interface Errors chart runs amber (in) / purple (out).
  - **A missed poll is EVIDENCE, not a shape.** The flagless streams' failures come from the response-time probe's own record, served as `outages` (`[{from, to}]`) on the telemetry / storage / interface history endpoints by [src/services/probeOutageService.ts](src/services/probeOutageService.ts). The heavy cadences don't RUN while an asset is down (`runsHeavyCadences` gates them on `up`), so a skipped poll leaves no row anywhere — but the probe keeps running in every state and writes a real `success:false` row per interval. This replaced a `_pollGapMarkers` heuristic (a hole wider than 2.5× the series' median cadence) that could not tell an outage from an unmounted disk, a metric the device never reports, or an operator widening the cadence — and painted red dives straight through maintenance windows. Evidence gets all three right for free: polling stops entirely during maintenance, so those windows contain no failed probes. **Never re-derive a missed poll from the size of a gap.**
  - **A miss the upstream EXPLAINS is grey, not red** (business rule 38). A failed probe taken while the asset was dependency-suppressed — its parent dark — is stamped `AssetMonitorSample.dependencyDown`, and `probeOutageService` labels each window with an `OutageKind` (`"outage"` | `"dependency"`). Same dive, `_CHART_DEP_COLOR` (`#9aa0a6`) instead of `_CHART_FAIL_COLOR`: nothing was measured either way, so the shape is identical; only the accusation is dropped. Deliberately NOT a band — that vocabulary is maintenance's. `_outageMarkers` therefore returns `{ t, dep }` objects rather than bare timestamps, and the three things every chart does with them are `_outagePts` / `_outageDotsSVG` / `_outageHitsSVG` — use those, don't re-inline the loop. `_failureAwareSeriesSVG` compares point COLORS, not `ok` flags, so a red run flowing into a grey one still splits and fades. Tooltip: "Dependency down — upstream device was down, not polled". The response-time chart reads its own per-sample flag (`ptIsDependency`), and on a rollup tier a bucket is grey only when EVERY failure in it qualified (`dependencyFailureCount >= failureCount`). The grey is duplicated in four places by design — `public/js/assets.js` (also read by `assets-compare.js`), `public/js/mobile/charts.js`, `src/utils/sparklineSvg.ts` — exactly like the red; change one, change all.
  - **A marker landing on a real sample is DROPPED** (`_outageMarkers`' collision guard, half the series' median cadence). The Polaris Agent pushes on its own schedule and is not gated on `monitorStatus`, so an agent host can keep reporting CPU straight through an outage of the server-side probe transport; diving a line that has data would misreport what's actually held.
  - **Two-series charts feed the guard from the UNION of their timestamps, and share one marker set** (CPU/Memory, interface in/out, storage used/total). Both values ride the same sample row, so an outage is an outage for both, and shared markers keep the lines diving at the same x instead of drawing two offset red notches. A series that simply stops reporting while the other continues has no probe failure behind it and correctly BRIDGES. **Per ASSET, never chart-wide, on any chart that co-plots several devices** — the compare view holds one series per asset, so one device's outage must never pull another's line to the baseline; `_cmpApplyOutageMarkers` folds each series' own `outages` into its own points.
  - **Where the `data-miss` hit rect goes in the paint order depends on the chart's other hit targets.** Charts whose hits are small circles anchored on the line (interface throughput/errors) emit `failDots + missHits + hits`. The CPU/Memory chart's hits are full-height Voronoi *lanes* and a gap sits inside the neighboring sample's lane, so the narrow miss rect has to paint LAST (`hits + missHits`) or it never receives the hover.
  - **Email counterpart:** the charts rasterized into alert emails ([src/utils/sparklineSvg.ts](src/utils/sparklineSvg.ts), fed by [src/services/alertChartService.ts](src/services/alertChartService.ts)) implement the SAME treatment — same `#d32f2f`, same baseline dive, same per-transition fade — because an operator must not have to learn an outage twice. They previously shaded the failed window red and broke the line, which is band vocabulary and therefore wrong. What an email chart may still diverge on: physical size, flat-hex palette (a mail client has no theme to read), no hover targets, and same-state runs collapsed into one polyline rather than a `<line>` per segment (a FortiGate can land thousands of points in an hour). The one band that survives there is `alarmSpans`, the hardware sensor's own alarm bit — a different claim about a reading that is still arriving. `failSpansFrom` delegates to `foldProbeOutages` so the two surfaces cannot disagree about where an outage began and ended.
  - **Mobile counterpart:** the mobile SPA's [public/js/mobile/charts.js](public/js/mobile/charts.js) `lineChart` implements the same treatment with the same `#d32f2f`, fed either by explicit `{ts, v: null, ok: false}` points (response time) or a per-series `gapFade: true` flag plus the chart-level `outages` list, resolved once across every flagged series by `applySharedOutageMarkers` (the union rule above). Two deliberate divergences from desktop, both forced by the surface: runs of same-state points collapse into ONE polyline rather than desktop's per-segment `<line>` elements (a phone holds a day of per-minute samples, which would otherwise be thousands of nodes), and failure dots are near-zero-length round-capped non-scaling strokes rather than `<circle>` — the mobile plot uses `preserveAspectRatio="none"`, which squashes circles into ellipses. Pinned by [tests/unit/mobileChartsFailureFade.test.ts](tests/unit/mobileChartsFailureFade.test.ts). Note `_pollGapMarkers`' single-midpoint branch (`if (b <= a)`) is unreachable in both copies — it needs `gap ≤ 2×median` but is only reached when `gap > 2.5×median`.
- **Drag-select = custom range.** Every renderer calls `_stashChartGeometry(container, t0, t1, padL, innerW, W)` after writing the SVG; every panel-open wires `_wireChartDragSelect(container, applySelection)` once, where `applySelection(fromIso, toIso)` calls `_applyCustomRangeSelection({btnClass, customBtnId?, panelId?, fromId?, toId?}, …)` then the chart's loader with `{from, to}`. Bars without a Custom… button (SD-WAN, process) pass just `{btnClass}` — presets un-highlight.
- API returns `{ range, since, until, samples[], stats }`. Custom ranges return `range: "custom"`.
- Loader writes the active selection onto the SVG container's `dataset.range` (or `dataset.from` + `dataset.to`) so probe-now / silent ticks can refetch the same view.
- "Custom" ranges do **not** auto-refresh; preset ranges do, on the resolved monitor interval (`_refreshIntervalMs`).
- Silent refresh ticks capture/restore `panelBody.scrollTop` around the swap so the slide-over doesn't jump.
- Range selection is persisted; "Custom" from/to inputs intentionally are not.
- **Stats line:** call `_renderChartStats(container, count, [{label, value}, …])`. Leading `<strong>{count}</strong> samples` span, then one `<span><strong>{Label}:</strong> {value}</span>` per metric, joined by flex gap. **No** "current/as-of" prose inside the stats line — current readings go in the Status block above the charts, modeled on `Last Response Time` / `Last Poll`. **Each chart owns its own stats line** (don't share one stats container across two charts — see Interface throughput vs errors).
- **Polling-method badge:** every chart's section header carries one. Sync render uses the per-asset override only as a coarse first guess; the async path overwrites with the authoritative resolved value (covers class / integration / manual tiers). Cadence in the badge comes from the same resolved settings as the polling method, NOT a separate lookup.
- **Stale-data banner:** sections rendering `lastTelemetryAt` / `lastSystemInfoAt` / `lastTemperatureAt`-driven data prepend `_staleBannerHTML(assetId, asset, streamKey, lastAt)` (in `public/js/assets.js`). `streamKey` is `"telemetry"` (CPU / memory / hardware sensors), `"systemInfo"` (interfaces / storage / IPsec / LLDP), or `"responseTime"` (special-cased field names: resolved `intervalSeconds`, per-asset `monitorIntervalSec`). Banner text is `⚠ Last successful update <timeAgo>` (`_staleBannerInnerHTML`; the bare box is `_staleBannerBoxHTML(text)` for one-off wordings) and appears only when `lastAt` is older than 3× the resolved polling interval. Resolution priority: `_effectiveResolvedByAssetId` (full `/effective-monitor-settings` walk — covers per-asset / class override / integration / manual tiers) → per-asset override → manual tier from `_monitorSettingsCache` → hardcoded floor (60s telemetry / 600s systemInfo). Output is a `.asset-stale-banner-slot` wrapper so `_updateStaleBannersFromEffective(assetId, asset)` can re-evaluate after the eff fetch lands — the sync first paint can't see a class override, the async pass picks it up. The two `effectiveMonitorSettings()` callers (`_populateAssetMonitorTierBadges`, `_updateStreamSourceBadgesFromEffective`) plus the response-time chart loader all populate the cache + fire the re-evaluator on success. **Never measure freshness from a rollup-tier chart series.** A rollup sample's `timestamp` is its `bucketStart`, so the newest daily point is up to 24h old the moment it's written (and the daily rollup only runs at 02:30 UTC) — deriving the banner from it made a healthy 1-minute probe read "Last successful update 17h ago" as soon as the operator picked 30d. The response-time banner (`_updateMonitorStaleBanner`) reads the payload's `lastSuccessAt` (server-side `readLastMonitorSuccessAt`, the newest successful DETAIL sample) whenever present and only falls back to scanning the series on the detail tier / when the last success predates detail retention. Every other section's banner is already safe because it reads a live `Asset` column (`lastTelemetryAt` / `lastSystemInfoAt`), not a chart sample.
- **Response Time banner (chart-derived timestamp):** the Response Time section carries a `#asset-monitor-stale` slot that `_updateMonitorStaleBanner(assetId, data, opts)` rewrites on every history load — `lastAt` is the newest SUCCESSFUL sample in the fetched window (not `lastMonitorAt`, which stamps on failed probes too). Cleared on custom from/to windows (fixed historical views say nothing about live freshness); a live window with samples but zero successes renders "No successful update in the last <range>".
- **Hardware Sensors:** the section prepends the standard `_staleBannerHTML(…, "telemetry", si.lastTemperatureAt || si.lastTelemetryAt)` banner like every other section (the table-specific timestamp means it fires when CPU/mem succeeds but the sensor pull fails). The header's `#asset-system-temps-updated` slot (`_updateTemperatureUpdatedStamp`) stays as a neutral tertiary-color "updated …" stamp only — it no longer flips amber; staleness is the banner's job.

**When adding a new instance:**
- Pick a unique chart id and add it to the prefs key list above.
- Reuse `_chartRangeBtnsHTML` for the toolbar — don't roll your own.
- Wire `_wireChartTooltip` and `_observeChartResize` — every existing chart does, and skipping breaks behavior parity.
- Wire `_addChartScreenshotButton` with a `getStats` callback (via `_statsSummaryFrom`) — a camera button without it produces screenshots missing the stats line. The button reads the container's `dataset.from/to` at click time (`_chartCustomRangeLabel`) and stamps a "From … to …" header line into the capture when the chart is on a custom window — another reason the loader must stamp the dataset.
- Attach the loader's persisted range to the container dataset so silent refresh and probe-now refetch the same window.
- Call `_stashChartGeometry(container, t0, t1, padL, innerW, W)` in the renderer and wire `_wireChartDragSelect` once at panel setup so drag-to-select works like every other chart.
- Use `_renderChartStats` for the stats line. If your chart has additional "current" readings worth showing, put them in the Status block (or a sibling section that mirrors Status), not inline in the stats line.
- Stats values must come from `data.stats` server-side or be derived once from the same samples the chart renders — don't duplicate aggregation logic.
- Add a polling-method badge to the section header via `_streamSourceBadgeHTML` whenever the chart's data is delivered by a configurable polling stream (response-time / telemetry / interfaces / lldp).
- If the data is unsupported on some monitor transports (e.g. ICMP/SSH), render an empty-state message — don't show an empty chart.
- Prepend `_staleBannerHTML(assetId, asset, streamKey, lastAt)` whenever the section renders sample data driven by a `last*At` timestamp. Use `streamKey: "telemetry"` for CPU / memory / temperature surfaces and `streamKey: "systemInfo"` for interface / storage / IPsec / LLDP surfaces. The slot wrapper auto-rehydrates when `/effective-monitor-settings` resolves — no manual await needed.
- **Apply lookback overflow + clip-path.** In the route handler, call `extendSinceForLookback(since, pick.bucketSeconds)` and pass the result to the history service as `fetchSince`. In the service, default `fetchSince` to `since`, use it for the WHERE clause, and gate stats accumulation on `r.timestamp.getTime() >= since.getTime()` so overflow rows drive line continuity without inflating counts. In the renderer, allocate one clip id with `_chartClipId("<chartName>")`, emit `_chartClipDefs(id, padL, padT, innerW, innerH)` inside the SVG, and wrap every data-drawing element (line segments + dots + baseline failure dots + hit targets) in `<g ' + _chartClipAttr(id) + '>…</g>`. Leave axis ticks, grid lines, legends, and the stale banner OUTSIDE the clipped group — they need to render in the y-axis label gutter where pre-since samples must be hidden.
- **Maintenance bands.** Emit `_dateChangeMarkers(t0, t1, padL, padT, innerW, innerH) + _maintenanceBandLayer(t0, t1, …same args…)` together, BEFORE the clipped series group, so windows where polling was paused render as labeled translucent purple bands instead of unexplained gaps. The band data comes from the per-panel `_maintWindowsCache` (fetched once in `openViewModal` from `GET /assets/:id/maintenance-windows`) — the renderer call is synchronous and free when the asset has no windows. Each band carries a native `<title>` tooltip (name + entry → exit), so no custom hover wiring is needed.
- **Automation severity shading (opt-in).** A chart whose metric an automation watches can fade its line into the tier colors instead of a flat accent, so a reading's severity is legible without opening Automations. Fetch the ladder ONCE per subject with `_loadMetricSeverityTiers(assetId, metric, dim)` (`GET /assets/:id/metric-thresholds`, computed server-side by `notificationRuleService.getMetricSeverityTiers` off the same `resolveTierLadder` the engine evaluates — never re-derive thresholds client-side), stash it keyed by subject so range changes and silent ticks reuse it, and render with the tiers in the render `opts` (so `_observeChartResize` keeps them). Then `var sev = _severityChartLayer(kind, opts.tiers, minV, maxV, geo)` and place its four pieces: `sev.defs` in the SVG head, `sev.lines` + the polyline/dots inside the clipped group with `stroke="sev.stroke"`, `sev.labels` OUTSIDE the clip. `sev.stroke` is the plain accent color when nothing watches the metric, so the un-shaded path is byte-identical to before. The gradient math is pure and lives in `public/js/chart-severity.js` (`window.PolarisChartSeverity`) — thresholds outside the visible domain CLAMP (a range entirely above critical is entirely critical-colored) rather than widening the axis. Canonical instance: `_renderSensorChart`.

## Modal

**What it is:** A centered, draggable modal dialog with header / body / footer, used for forms, confirmations, and inline detail editors.

**Canonical implementation:** `openModal(title, bodyHTML, footerHTML, options)` in `public/js/app.js`. Companion: `closeModal()` at `public/js/app.js`, `showConfirm(message)` at `public/js/app.js`.

**Key conventions:**
- Single shared `#modal-overlay` element appended to `document.body` on first call; reused across opens.
- DOM shape: `.modal-overlay > .modal > [.modal-header, .modal-body, .modal-footer]`.
- Width variants: `options.wide` adds `.modal-wide` (672px); `options.large` adds `.modal-large` (≤1200px, normal padding — form+table modals like Assets → Maintenance); `options.xl` adds `.modal-xl` (≤1360px, zero body padding — full-bleed). Default is the standard width.
- Sticky inner tab strip: when a modal body uses `.page-tabs` as a direct child (e.g. integration edit), the strip is auto-pinned to the top of the scrolling `.modal-body` via the `.modal-body > .page-tabs` rule in `styles.css`. Don't roll your own sticky positioning. Nested sub-tab strips (deeper than direct child) are intentionally not sticky.
- Header is the drag handle (mousedown anywhere outside `.modal-close`).
- Backdrop click flashes the close button instead of dismissing — explicit close only, to protect in-progress edits.
- Confirms use `showConfirm()`, which returns a Promise — never use `window.confirm()` (won't render in some browser/embed contexts).
- Z-index layering: `.modal-overlay` is 1000 by default; if `openModal` detects an open `.slideover-overlay` (1050), it adds the `.above-slideover` class to bump the modal to 1075. Lets modals opened from inside a slide-in (e.g. Reserve IP from the IP panel) render in front. `closeModal` clears the class.
- Accessibility (built into `openModal`/`closeModal` + `showConfirm`, so every caller gets it): the `.modal` carries `role="dialog"` + `aria-modal="true"` + `aria-labelledby="modal-title"` (the header `<h3 id="modal-title">`); on open, focus moves to the first focusable element and Tab is trapped within the dialog (`_trapFocus` in `app.js`); Escape closes; on close, focus is restored to whatever was focused before open. The close button has `aria-label="Close dialog"`. `showConfirm` mirrors this on its own stacked overlay (Escape = Cancel). The static topology modal in `map.html` carries the same ARIA attributes.

**When adding a new instance:**
- Call `openModal(title, bodyHTML, footerHTML, options)` — do not hand-roll a new overlay element.
- Footer buttons close via explicit `closeModal()` calls bound after open.
- For destructive actions, wrap with `await showConfirm(...)` first.
- For wide forms (multi-column / tabbed), pass `{ wide: true }`; `{ large: true }` when the body carries a real data table; reserve `{ xl: true }` for genuinely dense UIs (allocation preview, etc.).
- Re-bind any DOM listeners after each open — the body HTML is replaced wholesale.

## Stacked modal (a second dialog over an open one)

**What it is:** A dialog opened while another modal is already open — a confirm, a review step, or a whole sub-editor — that must leave the first one's DOM intact underneath.

**Why it can't be `openModal`:** `openModal` creates and then reuses ONE shared `#modal-overlay`, overwriting its `.modal-body` / `.modal-footer` innerHTML on every call. Calling it from inside an open modal therefore **destroys that modal's form DOM**, losing whatever the operator had typed. The wizard entry above flags the same trap from the other direction.

**Canonical implementations:** `showConfirm(message)` in `public/js/app.js` (the smallest complete instance — read this one first); `showPrompt(message, opts)` beside it (the same shape plus a text field — use it instead of `window.prompt`, which is unstyled, absent in the mobile PWA and suppressed outright by some browsers, so an operator can be left unable to complete an action with no visible reason why; it resolves the trimmed string, `""` for a blank optional field, or **`null` on cancel/Escape** — that null-vs-empty distinction is the contract callers branch on, and collapsing it turns “I changed my mind” into “do it, no reason given”; `required` refuses a blank field with a stated reason — `requiredMessage`, else a default — rather than a bare red border, because a button that appears to do nothing reads as broken, and the prompt text belongs in `placeholder`, never `value`, so an untouched field submits as no answer at all); `_showMergeReviewModal(survivor, fieldWinners)` in `public/js/assets.js` (a full review dialog, but it drops the focus trap and focus restore — don't copy that part); `buildOverlay(z, title, body, footer, onClose, wide)` in `public/js/app.js`, beside `showConfirm` (the reusable extraction — the address-book picker and its editor, and the automations code editor, all share it; it was promoted out of `automations-address-book.js` when the code editor needed it, because that file loads on ONE page while the wizard that opens the editor loads on five).

**Key conventions:**
- Build a **standalone** `div.modal-overlay` with an inline `z-index`, append it to `document.body`, and remove it on close. Same inner DOM shape as a normal modal (`.modal > .modal-header/.modal-body/.modal-footer`) so all the shared CSS applies.
- Layer rungs: **1300** for a confirm/picker over a base modal, **1320** when a third layer must sit over the second (the address-book editor over its picker). Equal z-index resolves by DOM order — an overlay appended later paints on top — which is what lets `showConfirm` (1300) work from inside a 1300 picker.
- Close teardown: remove `.open`, delete the node on `transitionend`, and keep a `setTimeout(…, 400)` fallback so reduced-motion (no transition event) can't leak the node.
- **Restore focus and trap Tab** — `_trapFocus(dialog, onEscape)` + stash `document.activeElement` before open and refocus it after. `showConfirm` does both; `_showMergeReviewModal` does neither, which is an omission rather than a variation.
- **Carry the modal lock** — the padlock beside the X is ONE global switch governing every modal, so an overlay that ignores it reads as a bug. app.js's injector (`_injectPanelLockButtons`) only ever watches the shared `#modal-overlay`, so a standalone overlay must call `_ensureLockButton(headerEl, "modal")` itself, and its backdrop handler must check `isPanelLocked("modal")` and call `flashModalCloseBtn(closeBtn)` instead of closing. Give the X `class="btn-icon modal-close"` — `.modal-close` alone sets only color/transition, so the browser's default button chrome shows through as a grey box. `buildOverlay` does all three; `showConfirm` is exempt only because it has no X.
- Resolve a Promise from the close path so the caller can `await` the layer and branch on the result (`null`/`false` = dismissed).

**When adding a new instance:** reuse `buildOverlay` — it is in `app.js`, so it is available on every page. (A DOM test that needs it cannot eval all of `app.js`, and stubbing it would make any assertion about overlay structure or z-index vacuous; `tests/fixtures/appOverlay.ts` brace-slices the real function out of `app.js` and evals just that. Note it ends in `requestAnimationFrame`, which Node does not define — without a stub it throws AFTER appending the dialog but BEFORE the click handlers attach, so every button renders inert.) Never call `openModal` from inside an open modal unless you deliberately want a replace-and-reopen flow — for that, follow `openImportPdfModal._reopen` in `assets.js`.

## Integration modal (one shape for all seven)

**What it is:** Any "connect us to another system" dialog — the Add / Edit form for FortiManager, standalone FortiGate, Active Directory, Entra ID, Windows Server, vCenter and Azure Arc.

**Canonical implementation:** `openIntegrationModal(cfg)` in `public/js/app.js`, driven by `_integrationTabs(ctx)` / `_INTEGRATION_REQUIRED_FIELDS` / `_productForType` / `_wireIntegrationModal` in `public/js/integrations.js`. Both flows go through it: `openCreateModal(type)` and `openEditModal(id)`.

**Why it exists:** Polaris grew seven of these by hand and they drifted — two tab implementations, footers in three orders, and per-type required-field checks copy-pasted with different rules. The dialog is the same dialog every time; only the tab CONTENT differs.

**Key conventions:**
- **Title is `"<Action> <Product> Integration"`** — `Add FortiManager Integration`, never a bare `Add Integration` or `Edit Integration`. The operator picked a product to get here and the title should confirm it. `_productForType` is the one name table.
- **Tab order: General first** (identity + connection), **Monitoring second** where it exists, then feature tabs. A concern with three fields is a section inside General, not a tab of its own.
- **Field ids unique ACROSS tabs** (`f-host`, `f-apiToken`) so one read pass collects the whole form — a per-tab read silently drops whatever the operator never opened.
- **Footer: `Test Connection` · `Cancel` · `Create`/`Save Changes`.** Test is a secondary on the LEFT — it's the rehearsal, not the commitment. Cancel is a wired listener, never an inline `onclick="closeModal()"`.
- **Test is gated on `requires`, and the toast NAMES what is missing.** Never fire a request you know will fail and report the server's error as if it were news. Secret fields are dropped from `requires` on the Edit flow, where a stored secret renders blank ("leave blank to keep current") and demanding it would refuse to test an unchanged credential.
- **Saving is never blocked on a passing test.** An operator configuring ahead of a firewall change has a legitimate reason to save something that cannot connect yet; `onSave` receives `{tested}` if it wants to act on it (the create flow uses it to inherit the result onto the new integration, so Discover isn't gated on a redundant re-test).
- **Both buttons disable and relabel while in flight** (`Testing…`, `Creating…`) — these calls reach a remote system and can take seconds. The shell owns that, plus the try/catch that turns a throw into a toast, so `onTest` / `onSave` are plain async functions.
- **The tab list is built ONCE per type**, by `_integrationTabs(ctx)`, and both flows walk it. Create is just Edit with an empty stored `config`, so every tab reads out of `config` and degrades to its off/default state. Two hand-maintained arrays is how a tab added to one flow silently missed the other.
- **The shell does NOT scrape the form.** Unlike the UI kit's version, `onTest` / `onSave` read it themselves through `_formConfigForType` and the per-class block readers, which handle nested blocks, arrays and keep-current secrets.

**When adding a tab or a type:**
- Add the tab to `_integrationTabs` — once. Both flows pick it up.
- Add the type to `_INTEGRATION_PRODUCTS`, to `_INTEGRATION_REQUIRED_FIELDS` (marking secret fields with a third `true`), and to `_NON_FORTINET_TABBED` if it carries a Monitoring tab.
- Add its per-type wiring to `_wireIntegrationModal`, not to the flows.

## Wizard (stepper modal)

**What it is:** A multi-step builder inside a modal — numbered stepper header, one `.step-panel` per step, per-step validation on Next, free navigation back to visited steps. Use when a creation flow has genuinely ordered parts (identity → scope → conditions → outcome); use plain `.page-tabs` when sections are peers with no ordering.

**Folding a repeated block inside a step:** `wireCollapsibles(root)` + `collapseBtnHtml(key)` in the same file. Mark the container `data-collapse-key="<key>"`, put the toggle in a `.aw-collapse-head` and the foldable content in a `.aw-collapse-body`; state lives in a module map so it survives the panel re-render (a flag on the node does not), and the KEY should be a stable property of the thing — the severity, not its index — so removing one block can not slide another's state onto it. Give a folded block a `.aw-collapse-summary` that says what is inside it, or folding just hides information. `wireCollapsibles` includes the root itself when the root IS the collapsible, since `querySelectorAll` only sees descendants.

**Canonical implementation:** the Automations 6-step builder — `openAutomationWizard(existing)` in `public/js/automations-wizard.js`. It is **standalone**: it owns the builder catalogs (`_ruleSchema` / `_ruleTagList` / `_ruleAssetTypes` / `_ruleChannels` / `_ruleRecipientUsers` / `_ruleScopeRoles`, all lazily fetched on open — the last is lifted off the scope-options payload, the only role source a caller without `users:read` has) and reaches its page's list only through an optional `window._reloadRules` hook, so any page can load the file alone and open the editor — which is how the asset-details Alerts tab edits an automation in place, and why the page module (`public/js/automations.js`) reads those globals rather than declaring them. Its pure sentence factory ships separately on `window.PolarisAutomationSentences` (`triggerSentence(trigger, {severity, severityBands})` — pass the ladder and the summary names every severity tier, not just tier 0), so a surface outside the wizard can describe a rule in the wizard's own words instead of inventing a second phrasing. Second instance: the discovery-rule wizard (Integrations → Polaris Agent) — `openAppMapRuleWizard(existing)` in `public/js/appmap-rules-wizard.js` (inline list module: `public/js/appmap-discovery.js`), a smaller 4-step copy of the same idiom; read it when the automations one is more machinery than you need. (Its list renders INLINE in a settings-card, so Cancel/post-save just `closeModal()` — but if you ever open a wizard FROM a list modal, remember `openModal` reuses ONE overlay, so the wizard REPLACES the list and must reopen it on the way out.) Shared CSS: `.stepper` / `.stepper-step{.active,.done,.clickable}` / `.stepper-num` / `.stepper-line` / `.step-panel{.visible}` (the strip **wraps** rather than clipping: six steps fill a `.modal-wide` row almost exactly, so a SEVENTH overflows at any label length — and the sticky header's negative margins hid the overflow instead of making it scrollable, which is how the 7-step Discovery wizard shipped with its last step cut off. Keep labels ≤ 8 characters if you go past six, so the second row reads) + the sticky `.modal-body > .stepper` rule in `public/css/styles.css` (promoted from setup.html's inline copy — the pre-auth setup wizard keeps its own, deliberately self-contained). Companions: `.aw-sentence` (live plain-English summary callout) and `.review-grid` (final summary card).

**Key conventions:**
- Shell is a normal `openModal(..., { wide: true })` — the stepper must be a **direct first child** of `.modal-body` so it pins sticky like `.page-tabs` does (the `.modal-body:has(> .stepper:first-child)` rule zeroes the body's top padding). Both canonical wizards pass `wide`; reserve `large` for the list-plus-table modals.
- **Every step leads with the question, then one line of explanation, then the controls** — an `<h3 style="margin:0 0 0.25rem">` followed by a tertiary-coloured `<p>`. Both canonical wizards do this and the Discovery wizard shipped without it, putting its explanation *under* the form; the step then read as a different product from the one next to it. A one-line `stepHead(question, explain)` helper per wizard is enough, and `tests/unit/assetsDiscoveryDom.test.ts` pins the ordering per step because it is exactly the kind of thing a later edit re-orders without noticing.
- One module-scope draft object holds ALL steps' state; every navigation runs `collect` on the step being left (no hard validation when moving backward), `validate` only on Next. Each step is a `HTML/Wire/Collect/Validate` function quad.
- The footer renders Cancel/Back/Next/Save once; a sync function toggles visibility per step (Save always visible in edit mode — all steps unlocked, `visited = max`).
- Stepper steps ≤ the highest visited step get `.clickable` and jump directly; `updateStepper` stamps `.active`/`.done` on steps and `.done` on the connecting `.stepper-line`s (adapted from `setup.js` `goToStep`/`updateStepper`).
- Save runs validate-all and jumps to the first failing step with a toast rather than silently blocking.
- Live previews inside steps follow the maintenance-builder debounce pattern (`_maintRefreshPreview` in `assets-maintenance.js`): 400–600 ms debounce, cancel the timer on step exit. **Give the preview a fixed height and let its content scroll inside** — a debounced preview reloads while the operator is still editing the step above it, so a box that grows and shrinks with what came back moves the controls under their cursor mid-edit. `.aw-preview-box` (flex column, fixed `height`) + `.aw-preview-head` (the count line, which may wrap) + `.aw-preview-body` (`flex:1; min-height:0; overflow:auto`, the result list) in `styles.css` — with **`.aw-preview-compact`** for a preview whose whole answer is a line or two (the scan-target step's count plus any mistyped-row errors): the fixed height exists because the automations Devices preview lists up to 100 matched devices and must not resize the step while the operator is still typing in it, and a box that only ever holds a couple of lines pays that as dead space instead. The `min-height` still pins the common states, since "Checking…" and the result are both one line; render EVERY state through one shell function so "Checking…", the result and the error path can't differ in height, and render the shell at step-render time so the space is reserved before the first run lands. Put any "showing the first N" note in the head — trailing the list it sits below the fold, which is exactly where someone wondering whether the list is complete can't see it. Canonical: `scopePreviewHtml`/`runScopePreview` (Devices step) in `automations-wizard.js`.
- **Value inputs are populated from the draft's own earlier steps, not left as free text.** Once a step has narrowed the devices, any later field naming something those devices report should offer exactly what they report — and say so when they report nothing, because "none of these 48 devices has a temperature sensor" is the answer the operator needed. Two instances: the automations trigger step's dimensionFilter pickers (`dimControlHtml`/`refreshDimOptions` in `automations-wizard.js` over `POST /automations/dimension-values`; strict enums render a `<select>`, substring-matched fields the `.aw-combo`/`.aw-suggest` combobox below — `.aw-combo-dim`, so partials stay typeable — plus a per-input **match cue** (`awDimMatchCue`) saying whether what's typed hits anything, since a pattern field can't be validated closed and a typo would otherwise save cleanly and never fire) and the discovery-rule wizard's scope-driven item step (`appmap-rules-wizard.js` over `POST /application-map/discovery/inventory`). Keep the resolver shared with the one the runtime uses (the automations picker resolves scope through `notificationEngine.loadScopeAssetIds`) so the list can't offer a device the feature wouldn't act on, cache per (field, narrowing, scope), and preserve a stored value the devices no longer report instead of silently dropping it.
- **When a step asks for the OPPOSITE of an earlier one, seed it — don't hand over a blank builder.** The reset step's "custom conditions" tree opens pre-filled with the trigger inverted (`invertedTree` beside `invertedLeaf` in the `PolarisAutomationSentences` factory — De Morgan, so group combinators flip alongside each leaf's comparator and the result stays inside the and/or-only vocabulary), because the honest starting position for "when should this clear?" is what the automatic reset would have done. Three things make a seed safe rather than presumptuous: it is **pure and non-mutating** (unit-testable without the DOM; the source tree is untouched), a **stored value is kept verbatim and never re-seeded** (the seed is a starting position, not a default that reasserts itself on every render), and a stored value the earlier step has since **invalidated** is dropped and re-seeded rather than left for the operator to hand-fix (here: the trigger switching device↔host, which the server would refuse). Also inherit, rather than re-ask, any setting the second builder has no control for — the reset leaves take the trigger's measurement window (`triggerWindowSec` → `tgStampWindows`), since a second minutes field beside "must stay true for" would recreate the window-vs-hold ambiguity the formula block below exists to resolve. **When the opposite is a value the SERVER knows and the browser would have to guess, seed it from a published map, not from client logic** — the event trigger's reset field prefills its counterpart action pattern (`agent.disconnected` → `agent.connected`) out of the schema catalog's `resetEventSuggestions`, so the pairing lives with the code that writes both events; a new draft whose trigger has a known counterpart lands on that mode instead of the timer default, while a stored rule is untouched (`defaultResetFor` is consulted only for a draft that has made no reset choice).
- **A control belongs to the thing it changes, not to the step it was convenient on.** The re-notify cooldown lived on the reset step, where it read as part of how an alert clears — it decides how often a NEW alert may fire and does nothing to one already up. It moved (2026-08) onto the Actions step's mandatory in-app-alert card beside the other two properties of the alert RECORD, `requireAckNote` and repeat-until-handled, which is also where the copy explaining the distinction already was. Two mechanics when relocating a field: the step it LEFT must stop collecting it (a stale `collectStep4` read would null the value the later step set), and any prose pointing at it ("set a cooldown below") has to move with it.
- **When one input means two things, print the formula next to the sentence.** The trigger step's single duration field is a measurement WINDOW under an aggregation and a HOLD clock under `latest`, and no English sentence distinguishes those at a glance. (It is counted in POLLS since 2026-08-28 — the label changes with the job ("Sustained for (polls)" / "Measured over (polls)" / "History (polls)"), the field stores seconds on `data-sec`, and a caption under it names the wall-clock time and the cadence it converted at. A duration an operator counts in readings is the canon for anything a poll loop decides.) `triggerFormula` (beside `triggerSentence` in the pure `PolarisAutomationSentences` factory) renders the same draft as `latest(CPU usage) > 90 %  held 10m  ⇒ warning` versus `avg(CPU usage, 15m) >= 80 %` — window inside the term, hold outside it — into a monospace `.aw-formula` block under the sentence. Both twins come from ONE factory over the `/schema` payload so they can't drift, both return plain text the caller escapes, and the formula's `note` is where a semantic the UI would otherwise overstate gets said out loud (here: the engine's 15-minute sampling floor). A surface that computes no value returns no lines and the block hides, rather than rendering an empty box.

**When adding a new instance:** reuse the shared classes — don't fork the stepper CSS; keep panels lazy (render HTML strings up front, wire listeners once, re-render only the dynamic regions); stash the draft on modal close and offer a "restore draft?" on reopen if losing input would hurt.

## Editable row grid inside a modal (one row per item, fields per row)

**What it is:** A modal that has to collect a few fields for each of N items —
N subnets to carve, N addresses to name — laid out as a header strip plus one
CSS-grid row per item, not as a `<table>` and not as N repeated form groups.

**Canonical implementation:** `.alloc-entries-header` / `.alloc-entry-row` in [public/css/styles.css](public/css/styles.css), built by `_addAllocEntryRow` in [public/js/subnets.js](public/js/subnets.js) (Networks → Auto-Allocate Next Networks). The second instance is `.ipalloc-header` / `.ipalloc-row`, rendered by `_renderAllocRows` in [public/js/ip-panel.js](public/js/ip-panel.js) (the IP panel's Auto-Allocate modal in Multiple-IPs mode) — same shape, one fixed-width leading cell for the immutable value.

**Key conventions:**
- **Grid, not table.** One `grid-template-columns` declared twice — on the header strip and on the row — so the inputs line up with the rest of the form and a row count can change without re-cutting a layout. `<input>`s get `margin: 0`; the surrounding `.form-group` supplies the spacing.
- **The header strip is the only label.** Per-row `<label>`s would triple the height of a 40-row form. Mark a required column in the header (`Hostname *`) and validate per row on submit, naming the ROW in the message ("Hostname is required for 10.0.0.5") — a generic "fill in all fields" is unusable once the body scrolls.
- **Scroll the body, not the modal.** Cap the row container (`max-height` ~320px, `overflow-y: auto`) so whatever sits below it — shared fields, the footer — stays reachable at the maximum row count. Focus + `scrollIntoView({ block: "nearest" })` on the first invalid row.
- **Fields common to every row live BELOW the grid, once.** Owner / project / expiry / notes are one control each, not a column — a column of identical values is a form nobody wants to fill in.
- **Rebuilding the rows must not discard typing.** Both callers re-render the whole grid when the count changes and re-seed each row from what was typed, keyed by POSITION (the only identity the operator can see). Values Polaris generated carry `data-auto="1"` and are cleared or regenerated freely; the moment an operator edits one it flips to `data-auto="0"` and is never overwritten.

## Nested condition tree (AND/OR device filter)

**What it is:** A SolarWinds-style filter builder — a root group with a combinator (AND / OR / NONE / NOT-ALL), rows of `[field][operator][value]`, nested sub-groups, and grip drag-and-drop between them. Use it wherever an operator picks *which devices* something applies to and a flat ANDed list would be a lie about what they meant ("switches in Ashfield OR anything tagged critical").

**Four consumers today:** the automation wizard's Devices step (`automations-wizard.js`, narrow `SCOPE_FIELD_OPS` vocabulary, two-state "All assets" checkbox), the address book's "devices this contact is responsible for" (`automations-address-book.js`, the wider `DEVICE_FILTER_FIELD_OPS` from `GET /contacts/filter-schema`, three radios because a contact may own nothing), the Assets → Settings → **Mass Pinning** section (`assets-masspin.js`, narrow vocabulary from `GET /assets/pin-filter-schema`, "All assets" defaults UNCHECKED so opening the modal never queues a fleet-wide inventory load), and Server Settings → Identification → **Add/Edit Tag** (`server-settings.js`, wide vocabulary from `GET /server-settings/tags/filter-schema`, a single "Auto-assign by device filter" toggle and NO all-devices control at all — see the note below). All four inject their own `meta` + `valueOptions` and share the evaluator server-side — copy that split rather than growing a second builder.

**A surface with no all-devices control must refuse the empty tree, not store it.** The tag filter has only an on/off toggle, so the empty tree is unreachable as an intention and reachable only as a half-built form — and `and([])` is true for every asset, which would tag the whole fleet on save. So the browser posts an explicit `assetCondition: null` when nothing is built and the server collapses an empty tree to null as well (`normalizeTagCondition`). Contacts do the opposite deliberately: they STORE `and([])` as the form of an explicit All-devices checkbox, reachable only through a separate `assetAllDevices` flag. Decide which of the two you are before wiring the toggle — the shapes are identical and the meanings are opposite.

**A surface editing a filter it can't fully render must omit the field, not null it.** A tag or contact whose stored filter uses a field the builder has no row for (today: the legacy flat `integration` rule, reported as `assetFilterUnconvertible`) shows the toggle ON, an empty builder, and a warning saying the filter still applies. Saving without building anything then sends NO filter key at all, so the server leaves both columns untouched. Posting `null` there — the obvious reading of "empty builder" — silently deletes a live filter the operator was only warned about. `_collectTagFilter(builder, stuck)` in `server-settings.js` and `filterBody()` in `automations-address-book.js` are the two implementations.

**Each non-automations surface needs its OWN schema route, not a reuse of `/automations/schema`.** That endpoint and `/scope-options` are gated `automationManagement:read`; browsing an address book or pinning an interface must not require permission to edit automations. The pattern (`GET /contacts/filter-schema`, `GET /assets/pin-filter-schema`) is: gate on the key that already gates the page, build the vocabulary from the SHARED `scopeConditionMeta(<fieldOps>)` so it can't drift, and ride `assetTypes` + `tags` in the same payload for the same reason regions and roles ride `/scope-options` — their own endpoints carry gates the caller may not hold, and the value pickers would silently degrade to free text.

**Resolving a tree to asset ids server-side:** `loadScopeAssetIds({condition})` (exported from [src/services/notificationEngine.ts](src/services/notificationEngine.ts)) for the narrow vocabulary — take the tree in a POST body and resolve there rather than having the client ship thousands of ids. The wide-vocabulary sibling is `resolveDeviceFilterAssetIds` in [src/services/deviceFilterService.ts](src/services/deviceFilterService.ts), shared by contacts and tag auto-assignment (it used to be private to `contactService`; it moved the moment a second surface wanted it, rather than being copied).

**Canonical implementation:** [public/js/condition-builder.js](public/js/condition-builder.js) — `window.PolarisConditionBuilder`. Two entry points, deliberately separate: `create({meta, valueOptions, onChange})` returns a builder instance (`groupHtml` / `ruleRowHtml` / `wire` / `collect` / `validate` / `seedIfEmpty`) for the scope-shaped tree, while `wireDnD(panel, rootSelector, onChange, maxDepth)` is the drag engine alone, for a tree that renders its OWN leaf rows — which is what the automation wizard's composite *trigger* builder does at `maxDepth` 3. Consumers: the wizard's Devices step (`step2Html`/`wireStep2` in `automations-wizard.js`), the address book's contact device filter, Mass Pinning, and the tag registry's auto-assign filter. Server side, the same tree is evaluated by `evaluateScopeCondition` in [src/services/notificationTypes.ts](src/services/notificationTypes.ts) — one shape, one evaluator, every surface.

**Adding a FIELD is a server change; adding its value PICKER is a three-way client change.** The field row comes straight from `meta.fields`, so a field added to `SCOPE_FIELD_OPS` + `SCOPE_FIELD_META` shows up in every consumer with no client edit at all. Its suggestions do not: each consumer has its own `valueOptions(field)` switching on the field's `optionsFrom` — `scValueOptions` (automations-wizard.js), `valueOptionsFor` (automations-address-book.js), `valueOptions` (assets-masspin.js), `_tagValueOptions` (server-settings.js) — and all four end in `default: return []`, so a new `optionsFrom` key with no case degrades that one surface to a free-text box and nothing anywhere throws. Add the case in all four, or deliberately ship the field with `optionsFrom: null`.

**Key conventions:**
- **The module holds no catalog.** `meta` (fields / ops / labels / `maxDepth`) comes from the server's `scopeCondition` vocabulary and `valueOptions(field)` from whatever the caller has loaded. That injection is the whole reason one module can serve two surfaces whose value sources differ — never hard-code a field list inside it.
- **DOM order IS the tree.** `collect()` walks the rendered markup, so a drop needs no model bookkeeping — only a `data-depth` restamp (`fixDepths`). Corollary: never keep a parallel JS model of the tree in a caller; read it back with `collect()` when you need it.
- **Validation is shared, not per-caller.** `validate(tree)` returns the first problem string (empty group, valueless row, non-CIDR subnet) so both surfaces refuse the same shapes with the same words. A caller adds only what is genuinely its own — the wizard's "or check All assets" hint, for instance.
- **An empty tree is not "everything".** Each caller decides what empty means and says so explicitly (the wizard has an All-assets checkbox above the builder; unchecked + empty is a validation error, never a silent match-all).
- **Load order matters.** The module must be in a `<script>` BEFORE any consumer that reads it during modal-body assembly. A missing or late tag doesn't error visibly — the wizard just fails to open, which is the exact bug `tests/unit/automationsWizardDom.test.ts` exists to catch. Every page hosting a consumer needs the tag: `assets.html`, `automations.html`, `appmap.html`, `index.html`, `map.html`, and `server-settings.html`.
- **The vocabulary must be in hand BEFORE the modal body is assembled**, because `groupHtml` renders its field/operator `<select>`s from `meta`. So a consumer inside a modal `await`s its schema route first and bails with a toast on failure, rather than opening a dialog it can't populate.
- **Depth cap is enforced twice** — the render omits `+ Group` at the last allowed level, and the drop path re-checks destination depth plus the dragged subtree's own height before allowing the move.

**When adding a new instance:** call `create()` with your own `meta`/`valueOptions`, render `groupHtml(tree, 0)` into a container, call `wire(panel, rootSelector)` once, and read `collect()` on save; drive any live preview off `onChange` with the usual 400–600 ms debounce. Pin the round-trip in a DOM test (`tests/unit/conditionBuilderDom.test.ts`) — and repair happy-dom's `<option selected>` parsing with `fixSelects` from [tests/fixtures/happyDomSelects.ts](tests/fixtures/happyDomSelects.ts) first, or you are asserting against the DOM engine's bug rather than your code. The automations trigger/reset trees take the PRODUCT-side variant instead: `pinTreeSelects` in `automations-wizard.js` re-assigns every rendered leaf row's selects from the model right after `innerHTML` (a browser no-op — the `renderBandCond` idiom), so stored rows collect correctly with no per-test fixture; prefer that shape when the render site owns a model it can pin from.

## Full-screen blocking overlay

**What it is:** An unavoidable, app-wide "wait" curtain over the entire viewport — used when the app is briefly unusable and the operator must just wait (currently: restarting Polaris from the Capacity Advisor / Maintenance restart buttons). Distinct from a modal: no dismiss, no header chrome, sits above *everything* including toasts.

**Canonical implementation:** the `.blocking-overlay` + `.blocking-overlay-card` classes in `public/css/styles.css`; built inline by `pollUntilServerReachable()` in `public/js/server-settings.js`.

**Key conventions:**
- DOM shape: `<div class="blocking-overlay"><div class="blocking-overlay-card">…</div></div>` appended to `document.body`.
- Z-index `2100` — the documented top of the layering scheme (modal 1000 < slideover 1050 < modal-above-slideover 1075 < sf-multi-popover 1200 < stacked modal 1300 (see "Stacked modal") < address-book editor 1320 < toast 2000 < blocking-overlay 2100). **When adding a new instance:**
- Reuse `.blocking-overlay` / `.blocking-overlay-card`; put a `.spinner` + a `<strong>` title + an optional status `<p>` in the card.
- Only for genuinely app-blocking states (restart, irreversible migration). For a dismissible dialog use the Modal; for a non-blocking status use a toast.

## Slide-over panel

**What it is:** A right-edge resizable detail panel for entity views (asset details, network/IP details, block details, lease lookups). Distinct from a modal: persistent header + scrollable body, can stay open while the user interacts with the underlying page.

**Canonical implementation:** Asset Details panel built by `_ensureAssetPanelDOM()` in `public/js/assets.js`; opened by `openViewModal(id)` at `public/js/assets.js`.

**Key conventions:**
- Single overlay per page, lazily created on first open and reused.
- DOM shape:
  ```
  .slideover-overlay > .slideover >
    .slideover-resize-handle
    .slideover-header > [.slideover-header-top (.slideover-header-lead [optional .slideover-nav pair + h3] + optional .slideover-header-actions + lock + close), .slideover-meta]
    .slideover-body
    .slideover-footer
  ```
- Width persistence: call `initSlideoverResize(panelEl, "polaris.panel.width.<name>")` from `public/js/app.js`. Each surface uses its own localStorage key.
- Backdrop click closes (target equality check on `.slideover-overlay`) — unless the per-user panel lock is on, which a capture-phase handler in app.js blocks generically for every slide-over. Any OTHER affordance that closes the panel to open something else (the asset panel's Edit button) must check `isPanelLocked("slideover")` itself and skip the close: a locked panel is one the operator pinned, and `openModal` already stacks the modal over it via `.above-slideover`. Pair that with re-rendering the panel after the modal's save, or it sits on pre-save values.
- Open animation: append/build, then `requestAnimationFrame(() => overlay.classList.add("open"))` on the next frame to trigger the CSS transition.
- Auto-refresh timers (e.g. monitor chart, system tab) gate on `_isOverlayOpen("<panel-overlay>")` and `_isCurrentAsset(id)` — close cancels pending ticks via `_clearAssetRefreshTimers()` so a closed panel never fires API requests.
- Nested slide-overs (interface / storage / sensor / IPsec drilldowns) layer on top of the asset panel and only the topmost closes on the close button — see the interface slide-over pattern in assets.js for the layering rules.
- **Back/forward when the panel pivots IN PLACE** (asset panel is the reference — `_assetHistoryOpen` / `_assetHistoryTarget` / `_assetHistoryLabel` / `_renderAssetPanelNav` / `_assetPanelGo` in assets.js, `.slideover-nav` in styles.css). A panel whose links re-open ITSELF on a different record (dependency tree, HA peer, LLDP neighbour, Application Map rail) needs a way back, or the record the operator started from is gone. Keep `{entries:[{id,label}], idx}` in a module var, reduce it with a PURE function so the rules are testable, and render a ‹ / › pair into a `.slideover-header-lead` wrapper left of the `<h3>` (not `.btn-icon` — the header's `.btn-icon:hover` is the close button's red flash, which reads as destructive on a nav control). Three rules are easy to get wrong: re-opening the CURRENT record is a REFRESH and must not push (the header's Refresh button and every post-save re-render call the same opener); a walk must not push either, so set a direction flag and consume it SYNCHRONOUSLY at the top of the opener before any await; and "is this a fresh session" has to read the stack, not the overlay's `.open` class, which the open animation only adds on the next frame. Hide the pair until there are two entries, disable each direction when it's spent, and gate the Alt+Left/Right chord the same way Escape is gated (topmost layer only). Reference test: `tests/unit/assetPanelHistoryDom.test.ts`.
- **Per-record action buttons belong in the header, not the footer** (asset panel is the reference — `#asset-panel-actions` / `.slideover-header-actions`, populated per open by `openViewModal`, cleared alongside the footer in the loading reset so a pivot can't strand the previous record's buttons). A full-height panel puts its footer a screen away from the tab the operator is reading, so buttons that act on the content (Copy, Screenshot, Refresh, Open HTTPS/SSH) go top-right; the footer keeps only the dismiss pair (Close / Edit). Two mechanics: give the group `margin-left: auto` and neutralize the lock button's own inline `margin-left:auto` after it (`.slideover-header-actions ~ .panel-lock-btn { margin-left: 0 !important }`) — with two auto margins flex splits the free space and strands the lock mid-header — and drop any `.drop-up` from the group's dropdowns, since the menus now hang below a header at the top of the viewport instead of above a footer at the bottom.
- **Click-through to asset details from a slide-over on a page that doesn't load assets.js:** call `openViewModal(id)` when it's defined (it appends to `<body>`, so the asset panel stacks over yours — every `.slideover-overlay` is `z-index: 1050`, and later-in-DOM wins) and fall back to `window.location.href = "/assets.html#view=asset:" + encodeURIComponent(id)`, the deep link `processSearchHash()` in app.js opens on load. Same shape in `_wireInstalledAgentHostLinks` (agent-build.js, integrations page), the credential-usage panel (server-settings.js), and `PolarisWidgets.openAssetDetail`. Prefer this over adding assets.js + its four deps (jspdf ×2 / html-to-image / table-sf) to another page.
- **Body padding is the content's job, not the container's:** `.slideover-body` is `padding: 0` in `styles.css` (so full-bleed sections like charts/tables can reach the edges). Every body state you render — loading, empty, error, and the populated content — must supply its own gutter, or text sits flush against the panel edge. Match the canonical `padding: 1rem 1.25rem` the asset panel uses (`_ensureAssetPanelDOM`'s loading state + each content block). Wrap the whole populated body in one padded `<div>` rather than padding each row, so spacing stays uniform across states. Same applies to `.slideover-meta` content if you add any.
- Accessibility: the `.slideover` carries `role="dialog"` + `aria-labelledby` (its header `<h3>`) + `tabindex="-1"`; on open focus moves into the panel and `openViewModal` records the trigger element so `closeAssetPanel` restores focus — but only on the FIRST open of a panel session, because a panel that pivots in place has an in-panel control as its `activeElement` on every later open and restoring focus to a hidden button loses it to `<body>`. Escape closes — but guarded so it fires only when the panel is topmost (an open nested drilldown or a stacked modal intercepts first). Deliberately NOT `aria-modal` / no hard focus trap: a slide-over is a resizable panel meant to coexist with the page, unlike the Modal.

**When adding a new instance:**
- Reuse the `slideover-*` CSS classes; do not invent new container styles.
- Wire `initSlideoverResize` with a unique localStorage key.
- All async data loaders gate on the overlay being open (and on the entity being current) before writing into the body — defends against late responses landing after the user navigated away.
- Cancel any timers in the panel's `close*()` function.
- Silent refresh ticks must capture/restore `panelBody.scrollTop` around the swap (see `_loadMonitorHistoryFor` and `_loadSystemTabFor`).
- **One fetch wave, not a chain of `await Promise.all` barriers.** What the operator experiences as "the panel is slow" is round-trip *depth*, not request count — the body shows nothing but its loading state until the last barrier resolves, and over HTTP/2 a wide wave costs about what a narrow one does. Issue every call that needs only the entity id in a single `Promise.all` alongside the entity fetch itself; for calls that need the entity's *shape* to decide (e.g. `openViewModal`'s Custom MIB keys off `manufacturer`, SD-WAN off `assetType` + integration type), chain them off the entity **promise** (`entityP.then(...)`) and put the derived promise in the same wave, so they overlap it instead of forming a second trip behind it. `openViewModal` went 4 barriers → 2 this way (→ 1 for entities that skip the conditional tabs). Corollary: never `await` a cache-warmer (`_ensureCredentials`) in front of first paint — put it in the wave.
- **Prefetch-vs-lazy for conditional tabs.** A tab whose *presence* depends on fetched data (SD-WAN, Custom MIB, SNMP Walk) must be prefetched, or it flashes-then-vanishes as the tab strip re-renders. A tab whose presence is known up front and only its *content* needs loading (Events, Services) is lazy-loaded on first click. Don't prefetch the latter kind; don't lazy-load the former.

## Token/pill filter box (multi-dimension, typeahead-committed)

**What it is:** One text input that accumulates *filter pills*. The operator types a fragment, a suggestion dropdown built from the data currently on screen offers matches labelled by dimension, Enter turns the pick into a pill, and pills combine **OR within a kind, AND across kinds**. Use it when a surface has many filterable dimensions and a row of checkboxes/selects per dimension would crowd the toolbar (or can't be enumerated up front — hostnames, process names, ports). Use `TableSF`'s per-column controls instead when the filters map cleanly onto table columns.

**Canonical implementation:** the Application Map toolbar — `public/js/appmap.js` (`applyGraphFilter` / `buildFilterCatalog` / `rankSuggestions` / `renderPills` / `addPill` / `removePillAt` / `openSuggest` / `commitInput` / `wireFilterBox`), markup in `public/appmap.html`, CSS `.appmap-filter` / `-pills` / `-input` / `.appmap-suggest{.open}` / `-item{.active}` / `-kind` / `-empty` in `public/css/appmap.css`.

**Key conventions:**
- **Pill model is `{ kind, value }`** and nothing else — serializable, so the whole pill list persists in the page's `polaris-prefs-<scope>-<username>` blob for free.
- **Don't use `<datalist>`.** Most browsers won't open it on click. Reuse the `.aw-suggest` recipe from `public/js/automations-wizard.js` (`scOpenSuggest` / `scCloseSuggest`): absolutely-positioned div, `.open` class, `mousedown` + `preventDefault()` on rows so blur-close doesn't race the tap, `blur` close behind a ~150 ms `setTimeout`, ArrowUp/Down moving an `.active` class with `scrollIntoView({block:"nearest"})`, Escape closing with `stopPropagation()` so a surrounding modal doesn't also close.
- **Catalog is rebuilt from the FULL dataset on every render**, never from the filtered view — otherwise adding one pill hides the suggestions needed to add the next.
- **Rank prefix matches above interior matches** so typing `tc` offers `tcp` first rather than some host whose name merely contains "tc". Cap the list (~50).
- **Matching is substring, not equality.** Catalog-sourced values are full labels (so it behaves as equality for them) while a hand-typed fragment still works; a free-text `text` kind is the fallback when nothing matched.
- **Keep the filter predicate PURE and separate from the DOM**, exposed on a `window.Polaris<Page>` namespace, and unit-test it through a `node:vm` sandbox (`tests/unit/appmapFilter.test.ts`, same approach as `topologyColumns.test.ts`). Pill semantics are exactly the kind of logic that silently drifts.
- **Removal has three affordances**: the pill's `×`, Backspace on an empty input, and (implicitly) clearing all pills to restore the unfiltered view. Debounce only the *suggestion* filtering (~200 ms); committing a pill is a discrete action and should re-render immediately.
- Reuse `.tag-chip` / `.tag-chip-delete` for the pill visuals rather than forking chip CSS; add a dimmed `-kind` prefix span so `host:web01` and `service:web01` are distinguishable at a glance.

**When adding a new instance:** define the kind list up front (each kind needs a haystack function over your row/node shape); decide the cross-kind combinator explicitly and write it into the doc comment (AND-across/OR-within is the default operators expect from a filter bar); make sure an active filter genuinely *narrows* — a "keep these always" rule that survives an active scope means the filter appears not to work.

**Variant — token fields that are the VALUE, not a filter (To / Cc / Bcc):** the automation wizard's Notify recipients (`recipBoxHtml` / `wireRecipBoxes` / `pillsToRecipients` / `recipientsToPills` in `public/js/automations-wizard.js`, CSS `.na-recips` / `.na-recip-row` / `.na-recip-box` / `.na-recip-input` in `styles.css`). Same typeahead recipe, six differences worth copying:
- **Pills are the payload**, not a view filter, so the pill↔wire mapping is its own pure pair at module scope (`window.PolarisAutomationRecipients`) and unit-tested (`tests/unit/automationRecipientPills.test.ts`). Suggestions are TWO halves: catalogues the surface already holds (the dynamic “Asset’s …” recipients, roles, map regions) are filtered locally and painted on the first keystroke, then a SERVER endpoint (`GET /contacts/search`) is called debounced ~250 ms with a min length and its hits are APPENDED to that same list — a stale response is dropped by re-checking the input value before rendering, and the local half is what the box still offers when the fetch fails or the caller lacks the permission behind it. Copy the split: a value the page already knows should never wait on a network round trip to be suggested.
- **Anything a companion PICKER offers must also be typeable, and the fold is where that fails.** The dynamic recipients lived only behind the Address book button, so typing `asset's` matched nothing and read as “we don't have it”. The fix is two lines and both generalize: source the entries from the picker's own export (`PolarisAddressBook.dynamicEntries`) rather than re-declaring them, and compare through a normalizer (`recipNeedle`) that folds the typographic apostrophe your labels are written with onto the straight one every keyboard produces. Suggestions a field can't ACCEPT are withheld there (these are To-only, mirroring `pillAllowedInField`) — offering one into Cc would look like it worked and then send to nobody.
- **One control, a narrower vocabulary — not a second control.** The same To box serves email and Web Push; the box carries a `data-mode` and the kind gate reads it (`pillAllowedInField(kind, field, mode)`), so push simply refuses the kinds its transport cannot reach (an address, an address-book contact) instead of growing a parallel account multi-select with its own pickers, collectors and bugs. Copy that shape: when a second consumer accepts MOST of the vocabulary, narrow the list, don't fork the widget. Two obligations come with it — refuse at the box, with a toast that says why (a pill accepted and then ignored at delivery is the failure being avoided), and carry the mode into the companion picker, which shows what the narrowing means (here a “Push devices” column, since push is opt-in per BROWSER and a named user with no enrolled device receives nothing).
- **An unresolvable pill is kept, not dropped** — a `recipientUserIds` entry with no matching account renders as a dashed "(unknown user)" chip. Silently discarding it on the next save would delete a recipient nobody asked to remove.
- **DOM order IS the model** (`pillsOf(box)` walks `:scope > .tag-chip`), so there's no parallel array to keep in sync; the box is `position:relative` to anchor `.aw-suggest`, and `min-height` keeps an empty box the same height as a full one so the rows don't jitter.
- **Dragging a pill between boxes is a CROSS-CONTAINER move**, so it follows the dashboard-canvas pattern, not the reorder-list one: a custom dataTransfer MIME type (`application/x-polaris-recipient`) makes the drag identifiable during `dragover` (where `getData` is unreadable), the element rides a module-scope var, `.aw-drop-into` marks the destination, and the drop is REJECTED unless source and destination share the same wrapper — otherwise a pill could jump into an unrelated action's recipients.

## Sortable + filterable data table

**What it is:** A `<table>` with per-column sort, inline filter, and (optionally) multi-select dropdown filters. Used for the assets, subnets, blocks, reservations, integrations, events, users, MIBs, and credentials lists.

**Canonical implementation:** `TableSF` in `public/js/table-sf.js`. Used by every list page. The subnets / blocks / reservations lists are the reference for **client-side mode** (whole dataset in the browser, `sf.apply()` filters/sorts/paginates in JS). The **assets** and **events** lists run in **server-side mode** (see below) — assets moved off client-side mode because at 12k+ rows shipping the whole table was slow.

**Key conventions:**
- Mark sortable/filterable columns on `<th>` with:
  - `data-sf-key="<dotted.path>"` — supports nested keys (`block.name`, `_count.subnets`).
  - `data-sf-type="string|number|date|ip|array"` — defaults to `string`.
  - `data-sf-options="value1|value2=Label2|value3"` — when present, renders a multi-select checkbox popover instead of a free-text input.
  - `data-sf-nofilter` (bare attribute) — sortable but NOT filterable: renders the header + sort caret only, no filter control. Sorting still works (it hangs off `.sf-header`, independent of the filter block). Use for numeric columns where a filter box adds noise but sort is useful (e.g. the asset Services tab's CPU % / Memory).
- Construct once after rendering the static `<thead>`: `var sf = new TableSF("<tbody-id>", onChange);`.
- Pipe raw rows through `sf.apply(rawData)` before rendering — sort + filters are applied there.
- The `onChange` callback re-runs the row renderer; never mutate `rawData` in place.
- Multi-select filters store an **array** of values matched case-insensitively against the row value via exact equality.
- Every filter popover (`.sf-multi-popover` — multi-select, date, text-operator, and the column chooser) is closed by ONE document-wide wiring installed once per page: `TableSF._wireDocClose()`. It closes on outside click / resize / Escape, and on a scroll that moved it — the scroll listener is capture-phase because the popover is `position:fixed` and would otherwise float away from its button. Two exemptions keep it from closing when it shouldn't: anything that scrolls or is pressed **inside** a popover (the list has its own `overflow-y`, and a scrollbar drag releases outside the popover, so its click lands on a common ancestor), and — mirroring `showRowMenu`'s handler in app.js — a scroll in a container that does **not** contain the popover's button, since that leaves the popover correctly placed. That second one is load-bearing on the dashboard: the NOC auto-scroll creeps every overflowing widget body by a pixel every 80ms, which used to dismiss a filter dropdown in the asset-details slide-over the instant it opened. The button is read back via `TableSF._popoverAnchor(pop)` — stamped as `pop._sfAnchor` by `_positionPopover` and by `openChooser`, defaulting to the popover's parent element. Add new popover kinds by giving them the `.sf-multi-popover` class rather than wiring their own close handlers; if the popover is appended somewhere other than beside its button (the column chooser goes on `document.body`), stamp `_sfAnchor` too or a scroll in the button's own container won't close it.
- Status / type / monitored-state pills used as cells should remain plain DOM (not React/components) so `data-sf-key` reads them via the underlying value, not display HTML.

**When adding a new instance:**
- Use `TableSF` — do not hand-roll sort/filter logic per page.
- For enum-style columns (status, role, type), prefer `data-sf-options` over a free-text input — operators almost always want exact-match.
- For columns whose displayed text differs from the underlying value (badges, formatted dates), pull the raw value from the row and stash it as the display source — never let the `data-sf-key` resolution diverge from what the user sees.
- Pagination, if needed, lives **outside** `TableSF` (apply pagination after `sf.apply()`).
- Always wire `onChange` to the render function so filter/sort updates live-refresh.

**Sorting a table that re-renders itself (and nests).** The asset-details **Interfaces** table (`_buildInterfacesTableDOM` / `_wireInterfacesTable` in [public/js/assets.js](public/js/assets.js)) is the reference for a `TableSF` table whose container is rebuilt by a refresh tick AND whose default view is a parent/child tree. Pinned by [tests/unit/assetInterfacesTableDom.test.ts](tests/unit/assetInterfacesTableDom.test.ts). Six conventions, each of which is a bug the first time it's missed:
- **Build a flat row model beside the tree.** One entry per row carrying the raw record, its tree placement, and the comparable fields `TableSF` reads (`_ifaceEntry` / `_tunnelEntry`). Build it in tree order — that order doubles as the "natural" ordering a filtered-but-unsorted view falls back to.
- **Name each model field for the column's existing `data-col-id`.** `setupColumnLayout` derives a column's persistence id from `data-sf-key` FIRST and `data-col-id` only as a fallback, so adding sort keys to a table that already has saved layouts silently orphans every stored width / hidden column / drag order unless the two match.
- **Two render modes, one tbody rewrite.** No sort and no filter → render the tree with its section headers; either one active → render flat (no section rows, no indentation, no expand toggles — a row's position no longer implies parentage, and a matching child whose parent filtered out would otherwise vanish). Rewrite ONLY the tbody so `TableSF`'s rebuilt header row and `applyTableLayout`'s widths/handles survive; `setupColumnLayout`'s `MutationObserver` re-applies the column order after each render.
- **Delegate every row handler off the tbody, and mutate shared state in place.** Per-row listeners are dropped on the operator's first keystroke. Likewise, a handler that REBINDS its local copy of a checkbox-state Set leaves the row builder — which closes over the original — drawing stale checkboxes on the next re-render; mutate the Set the builder holds.
- **A header select-all acts on the LISTED rows and leaves the rest alone.** With a filter active the operator can't see the others, so folding them into the write silently changes settings they never looked at. Compute `next = current ∪/∖ listed`, not `next = listed`.
- Persist sort/filter state anywhere the table gets rebuilt (`PolarisPrefs` under a per-user, per-device-type key), and DROP restored state that names a column this render doesn't include — a filter on an absent column matches nothing with no visible control to clear it (`applyState` already drops an unknown `sortKey`).

**Server-side mode (for high-volume tables).** When the table is too large to ship to the browser (Events at 235k–350k rows in a 7-day window, and the assets list at 12k+ rows, are the canonical cases; future telemetry/sample admin views would qualify too), keep using `TableSF` for its header UI but route every filter + sort + page operation through the API. The mode is a consumer convention — no changes to `public/js/table-sf.js` are needed. Canonical implementations: [public/js/events.js](public/js/events.js) + [public/events.html](public/events.html) (simplest), and [public/js/assets.js](public/js/assets.js) (`_buildAssetsQuery` / `fetchAssetsPage`) which adds the favorites-first + cross-page-selection wrinkles below.

- Instantiate once: `_sf = new TableSF("<tbody-id>", onChange)`. **Never call `sf.apply()`** — every row that reaches the tbody came from the server already filtered + sorted.
- The `onChange` callback reads `sf._sortKey`, `sf._sortDir`, `sf._filters` directly, resets offset to 0, and re-fetches. Translate state into API params:
  - Multi-select checkbox arrays (`sf._filters.<key> = [val1, val2]`) → CSV (`?<key>=val1,val2`); the backend treats >1 entry as Prisma `{ in: [...] }` and 1 entry as `{ equals }` so single-value back-compat is preserved.
  - Text-column raw forms (`string` → contains; `{ op: "not-contains", q }` / `{ op: "empty" }` / `{ op: "notempty" }`) → `<field>` + `<field>Op` (the backend operator set is `contains | not_contains | empty | is_not_empty`).
  - Date-range filter `{ type: "date", from, to }` → `since` / `until`.
  - Sort state → `sortBy` / `sortDir`. The route must whitelist the column set and 400 on anything outside; Prisma `orderBy` never accepts user-supplied strings unvalidated. When sort semantics differ from string alpha order (e.g. severity), keep a numeric companion column (Event has `levelRank`) and dispatch the user-facing sort key onto it server-side.
- Dynamic multi-select options (operator-extensible enums like resourceType) — call `sf.setColumnOptions("<key>", values)` after each fetch. Pre-this-change checked values are preserved if they're still in the new option set.
  - When the options come from a **registry endpoint** rather than the loaded rows (the assets Type column reads `GET /asset-types` in `_loadAssetTypeOptions`), keep the built-in set in `data-sf-options` as a pre-fetch seed and `await` the registry load **before** restoring saved prefs / hash filters — `setColumnOptions` deletes any stored filter value that has no matching checkbox, so a saved preset naming a custom value is silently dropped if it lands first.
- Persist filter + sort state in the page's `polaris-prefs-<scope>-<username>` localStorage blob alongside the column layout — match the other list pages. Restore via `sf._filters = saved.filters; sf._sortKey = saved.sort.key; sf._sortDir = saved.sort.dir; sf.restoreFilterUI();` before the first fetch.
- Offset-based pagination still lives outside `TableSF` — wire prev/next/page-buttons to bump a module-scope offset and call the same fetch helper.
- Any non-tbody consumer of filter state (PDF/CSV export's "All filtered results" path) must read from `sf._filters`, not the (now-deleted) DOM filter strip. With only one page in memory, "export filtered/all" re-fetches from the server in chunks (assets.js `_fetchAssetsForExport` pages in 10k-row windows up to a ceiling); "export page" just uses the in-memory page array.
- **Favorites-first across pages** (assets.js): when the page has a favorites set (on Assets that's the active view TAB's — see the view-tabs entry below; elsewhere localStorage), send the starred ids as `?favoriteIds=` (CSV) so the server floats them to the top of the *whole* result set, not just the current page. The route resolves this with a two-bucket query — favorites (matching the active filters, sorted) occupy virtual positions `[0, favTotal)`, non-favorites follow; the requested `[offset, offset+limit)` window is split across the boundary. Skip the param (and the second query) when the set is empty.
- **Cross-page bulk selection** (assets.js): the selection `Set` of ids survives page navigation (page changes call the fetch helper directly, *not* the selection-clearing reload). Because only the current page is in memory, keep a parallel `id → {status, assetType}` metadata map (`_assetsSelectedMeta`) captured at check time so the bulk-action bar's button-visibility logic still works for selected rows the operator has paged away from.

**Saved filter presets (named, shareable filter+sort snapshots).** The Assets page's "Filters ▾" header menu — [public/js/assets-filters.js](public/js/assets-filters.js) backed by [src/services/savedFilterService.ts](src/services/savedFilterService.ts) + [src/api/routes/savedFilters.ts](src/api/routes/savedFilters.ts). Distinct from the per-browser `polaris-prefs-<scope>-<username>` blob above, which persists the LIVE state: a preset is *named*, server-side, and can be published to every operator.

- Save = `sf.getPrefs()` (`{ sfFilters, sortKey, sortDir }`); load = `sf.applyState(preset.state)` then the page's programmatic-refresh entry point (`assetsApplyFilterState()` in assets.js — page 1, re-fetch, persist prefs). `applyState` REPLACES wholesale where `setPrefs` merges: a preset must land on exactly what was saved, and it drops a `sortKey` whose header no longer exists (server-side tables 400 on an unknown `sortBy`).
- Presets carry the query only. Column widths / hidden columns stay per-browser in `applyTableLayout` — decide deliberately before folding another operator's screen layout into a shared preset.
- Authorization has no dedicated function key: the request's `scope` maps to the key that already gates the page (`SAVED_FILTER_SCOPES`), checked inline (`ensureRoleSnapshot` + `hasPermission`) since the key isn't known until the payload is read. Read = list + own private presets; `write` = publish public; `fullwrite` = delete someone else's.
- The stored `state` is replayed into OTHER operators' browsers, so `sanitizeFilterState` accepts only the shapes `table-sf.js` emits, bounded in width/length. Widening the table's filter vocabulary means widening that validator in the same change.
- Adding presets to another list page: one line in `SAVED_FILTER_SCOPES` + a copy of the menu module. No migration, no new function key.
- Each row's trailing **★** pins that preset as the active view tab's BASE filter (below) — offered only when the page HAS a tab strip, and feature-tested per method on `window.PolarisAssetTabs` so a cached older strip module can't break the menu.

**Per-user view tabs (a strip of open views over one table).** [public/js/assets-tabs.js](public/js/assets-tabs.js) + [src/services/tableTabsService.ts](src/services/tableTabsService.ts) + [src/api/routes/tableTabs.ts](src/api/routes/tableTabs.ts), CSS `.table-tabs` / `.table-tab*`. Each tab is a name plus the same `{sfFilters, sortKey, sortDir}` state a preset holds; the whole strip persists per user at `/me/table-tabs?scope=…` (whole-blob replace, `/me/dashboard` pattern). Sits alongside presets, not instead of them: a **tab** is scratch space, a **preset** is the durable artifact — and a tab opened from a preset keeps only a reference, so editing it never writes back to something another operator may be using.

- The page module owns ONE "state changed" entry point (`assetsApplyFilterState` in assets.js: page 1 → re-fetch → persist prefs → `PolarisAssetTabs.syncFromTable()`), wired as `TableSF`'s `onChange` AND called after programmatic changes. Everything else hangs off that single seam.
- Applying a tab drives the same entry point, so the module needs an `_applying` re-entrancy guard — without it, switching tabs writes the incoming state back over the tab you just left.
- Load order + one fetch: publish the module on `window` and `await init()` from the page module's `DOMContentLoaded` BEFORE its first fetch (`init` applies the active tab's state but deliberately does NOT fetch). Tabs script tag goes before the page script.
- First visit seeds one tab from whatever the table already shows (the restored localStorage prefs) and writes nothing until the operator actually uses tabs — no server row for people who never touch the feature.
- Writes are debounced (~800ms) with a `beforeunload` flush; a failed save toasts once and keeps the strip working for the session.
- A stale `activeId` is repaired server-side, never rejected — the operator may have closed that tab in another window.
- **Favorites belong to the tab.** The Assets stars live on the tab (`favoriteIds`), not in localStorage, because a favorite is part of a view and a view is server-persisted. The integration is ONE call — `registerFavoritesProvider("assets", …)` from the strip's `init` — after which the page's existing `starCellHTML` / `isFavorite` / `getFavorites` call sites resolve to the active tab and switching tabs repaints the stars via the re-fetch it already does. Copy the rest too: cap at the click (with a toast) rather than letting the server drop a tail; name the scope in the star's tooltip, since the next tab shows a different set; and treat a null list as "predates the feature, seed me once from the old per-user set" so a second browser can't re-seed a curated tab.
- **Base ("default") filter — filtering inside a filter.** A tab may pin one preset as the view it RESETS to (`defaultState` snapshot + id/name labels), which is how an operator narrows within a saved filter and still has a way back. Consequences worth copying: the page-controls row's "Clear Filters" becomes **"Reset Filter"** while a base is set (label read per render from `activeDefault()`, and the strip asks for a repaint via the page's controls-render function when a base change leaves the query alone); pinning a base APPLIES it, since a click that changed nothing visible reads as a click that didn't take; unpinning leaves the view on screen alone; the snapshot is CLONED on the way in (`applyState` hands filter objects straight to the widgets, so a shared reference would let the next keystroke edit the thing you reset TO); and a preset that has gone leaves the snapshot alone rather than orphaning the tab. Markers: `.table-tab-base` (★) on the tab, `.sfl-star` / `.sfl-row-base` in the presets menu.

## Expand/collapse tree inside a data table

**What it is:** A `data-table` whose rows form a parent → child (→ grandchild) tree: a caret on the parent row hides and shows its descendants, and the collapsed set persists per user per asset.

**Canonical implementation:** the System tab's **interface tree** in `public/js/assets.js` (`_renderInterfacesCard` and the `iface-expand-toggle` handler) — an aggregate/trunk row with its member ports and VLANs nested under it. The Wireless tab's **radio → SSID → client tree** (`_renderWirelessTree`) is the second implementation and follows it exactly; copy from either, but do not invent a third set of mechanics.

**Key conventions:**
- The parent row carries `<button class="<scope>-expand-toggle" data-parent="<key>">` rendering `▼` when expanded and `▶` when collapsed, with a matching `title`.
- Every descendant row carries `class="<scope>-child" data-parent="<the same key>"` — **the key is the whole subtree's, not the immediate parent's**, so one toggle hides every level below it without walking the tree.
- Indent with `padding-left` on the name cell (1.4rem per level) plus the shared connector, `_treeElbow(isLast)` in `public/js/assets.js` — `├─` while more rows follow at that level, `└─` on the last. Depth is a style, never a separate column. Two glyphs, not one: the bare elbow at half opacity read as a stray character at the head of the name rather than as a line drawn INTO the row, and the tee is what identifies the last member of a group without counting. The MAC Table and ARP Table tabs' grouped rows use the same helper, so there is ONE nesting glyph in the app.
- **A per-row control that answers a question about the GROUP does not repeat on the children.** The System tab's Interfaces table is the reference: the Poll 1m pin checkbox renders on the aggregate and is omitted on its member ports, whose empty cell carries a `title` saying which aggregate to pin instead — an empty cell with no explanation reads as a rendering fault. The one exception is a child that ALREADY carries the state (a member with a live pin): hiding that control would leave the state set with nothing in the UI saying so and no way to clear it, so the control stays on exactly those rows.
- Collapsed state persists through `_getCollapsedIfaces(assetId, scope)` / `_setCollapsedIfaces(assetId, set, scope)`. **Pass a `scope`** for anything that is not the interface tree — the default key is the interface tree's, and a radio and a port that happen to share a name would otherwise collapse each other.
- Re-render reads the persisted set first, so an expand/collapse survives the tab's next refresh.
- A count shown on a parent row is **counted from the rows rendered below it**, never taken from a source's own tally: a number next to a list that disagrees with the list reads as a bug in the list.

## Table column layout (resize + hover-gear chooser + reorder)

**What it is:** Drag-to-resize column widths plus a show/hide/reorder column chooser, opened by a gear icon that floats at the top-right corner of the table's scroll wrapper and surfaces on table hover. Replaces the older "Columns ▾" toolbar button — the gear is the only canonical affordance going forward. Pairs naturally with `TableSF` (same `data-sf-key` ids double as column ids) but works standalone on any `<table>` with a `<thead>`.

**Canonical implementations:**
- `setupColumnLayout(tableEl, options)` in [public/js/table-sf.js](public/js/table-sf.js) — the underlying widget. Floats a gear at the top-right corner of the table's scroll wrapper (see the anchor bullet below). Used directly for the long-lived list-page tables (Assets, Blocks, Subnets, Events, IP panel, Users, Roles). Pass `options.onScreenshot(tableEl)` to add a per-table camera button into the same `.sf-col-gear-wrap`, to the **left** of the gear — opt-in, so tables that don't pass it get the gear alone.
- `applyTableLayout(tableEl, typeKey, options?)` in the same file — wrapper for tables that get **re-rendered on every refresh** (asset-detail System tab: Interfaces / Storage / Temperatures / LLDP / Wireless Stations; SD-WAN members/rules; Events; same shape works for any dynamic table). Persists widths + hidden columns + column order under `polaris-table-layout-<typeKey>-<username>` so column widths persist by table type and survive each rebuild (asset-detail tables suffix the asset type onto `<typeKey>` — see below — so a firewall and a switch keep independent layouts). Safe to call after every `innerHTML` replacement. Forwards `options.onScreenshot` through to `setupColumnLayout`; the asset-detail tables pass `onScreenshot: (t) => _screenshotTableEl(t, "<Label>")` (assets.js) which renders only that table — visible columns + headers, titled with the asset name, with a footer note counting any rows hidden by a collapsed parent. It is a **canvas re-draw, not a DOM rasterization**, so anything a cell conveys other than its text has to be carried across deliberately. The two readers are top-level in assets.js (`_shotCellText` / `_shotCellColor`, unit-tested in [tests/unit/sdwanMembersShotDom.test.ts](tests/unit/sdwanMembersShotDom.test.ts)): `_shotCellText` walks the cell inserting a space at every element boundary (inline badges are spaced by CSS margin, with no whitespace text node, so `innerText` would run them together), and `_shotCellColor` resolves the color to draw with — the cell's OWN computed color first, else the first text-bearing descendant whose color differs from the table's base (status pills, type badges, links), skipping descendants whose text is purely decorative glyphs (`▼`, `└`, `·`) since those are muted and sit first. Before that second part existed every cell painted in `--color-text-primary`, which flattened a red PoE "Fault" to near-white in dark theme — exactly the thing the screenshot was taken to show.
- **A cell whose meaning is a COLOR with no text in it needs `data-shot-text` / `data-shot-color`.** The flattened text IS the image, so a text-free element contributes nothing and the column reads blank — the SD-WAN Members up/down dot and its whole green/red Health Check Status strip disappeared from every screenshot of that table while looking correct on screen. `data-shot-text="<glyph or summary>"` is drawn in that element's place (its subtree is skipped, so a 48-segment strip states `▼ 46/48 up` instead of nothing), and `data-shot-color="<color>"` declares the cell's color outright since `_shotCellColor`'s walk deliberately ignores text-free elements. Use a **glyph**, not just a color — a screenshot gets printed and pasted into tickets (`▲`/`▼`, matching the Link column) — and pass a **resolved** color, never a raw `var(--x)`: canvas `fillStyle` ignores an unparseable value and keeps painting in the PREVIOUS cell's color, so an unresolved var leaks one row's state onto the next (`_shotCellColor` rejects `var(` for that reason). Only declare `data-shot-color` when one color can speak for the whole cell — the per-health-check chips deliberately don't, since an up chip and a down chip share one cell.

**Key conventions:**
- **Call `setupColumnLayout` AFTER `new TableSF` on the same table — never before.** `TableSF._setup` rewrites each `th[data-sf-key]`'s `innerHTML` to inject the sort/filter UI, which **wipes the `.sf-resize-handle` spans** `setupColumnLayout` appends. Construct in this order (the `_assetsSF` then `_assetsLayout` setup in `public/js/assets.js` is the canonical reference):
  ```js
  _sf = new TableSF("<tbody-id>", onChange);              // 1. builds header sort/filter UI
  _layout = setupColumnLayout(table, { onChange: save }); // 2. appends resize handles on top
  ```
  Symptom of getting it backwards: sort/filter work but **columns can't be resized** (handles silently gone). This has bitten more than one page.
- Mark every `<th>` with a stable `data-col-id="<name>"`. Falls back to `data-sf-key`, then `__col<index>` if neither is present — but explicit ids survive column reordering, so always set them on dynamic-rendered tables.
- Mark "anchor" columns (the ones a sensible table must always show — usually the leftmost identity column plus any actions column) with `data-col-required="true"` — operators can't hide a required column via the chooser, and it also can't be **reordered**: required columns hold their authored index while the other columns are dragged around them, so a leading checkbox / avatar column and a trailing Actions column stay where the table's design put them.
- **Drag-to-reorder lives in the chooser, not the header.** Each chooser row carries a `.sf-col-grip` (`draggable="true"`, same idiom as the automations condition builder's `.aw-grip` and the Assets → Settings → Sources priority list's `.monset-src-row` — copy the last one for a **flat** reorderable list: grip + rank number + label/description, `dragover` picking before/after off the row's vertical midpoint, DOM order as the source of truth read back only on Save, with `_monsetRenumberSources()` re-stamping the ranks after each drop; it's ~60 lines because there's no nesting or drop-into to handle, unlike the shared condition builder's `PolarisConditionBuilder.wireDnD`; with `.sf-drop-before` / `.sf-drop-after` edge cues); dropping rewrites the order and a "Reset column order" button appears while it differs from the authored one. Reordering **physically moves** the `<th>`, its `<col>`, and every body row's cells — there is no CSS way to permute table columns — which is why:
  - Everything position-derived recomputes from **display** order, not authored order: the `nth-child` hide rules (`rewriteHideStyle`), the auto-fill column (`lastVisibleResizableIdx`), and the resize handle's right-neighbor search. Add a position-derived behaviour and it must go through `displayIds()`.
  - **Pages that rebuild their tbody need no changes.** A `MutationObserver` on the table's own `<tbody>` elements re-applies the order after each render — installed lazily, so a table left in authored order pays nothing. Rows whose cell count doesn't match the column set (colspan empty states, the interfaces table's section headers) are skipped.
  - A `WeakMap` records the order each row's cells are **currently** in, so a second drag (or a reset) reads back from where the cells actually are. Mapping an already-moved row as though it were authored-order scrambles it — that was a real bug, and `tests/unit/tableColumnOrder.test.ts` pins it.
  - The persisted `order` is a permutation of the **movable subset only**, never absolute indexes. That's what lets a saved order survive a Polaris update that adds a column: `normalizeOrder` splices the newcomer in next to its authored neighbour and drops ids that no longer exist.
- Mark secondary columns that should ship **off by default** with `data-col-default-hidden="true"` — they appear unchecked in the chooser until an operator enables them. `getPrefs` persists an explicit `shown` snapshot (alongside `hidden`) so an operator's "turn it on" choice survives reloads, and `setPrefs` applies `shown` (un-hide) before `hidden` (hide). This is backward-compatible: older prefs blobs lacking `shown` leave default-hidden columns hidden and still honor previously-hidden columns. Used by the Assets table's inventory columns (Asset Tag, Manufacturer, Model, OS / Firmware, MAC Address, Assigned To, Purchase Order, DNS Name).
- For list pages using `setupColumnLayout` directly: persist via the page's own `polaris-prefs-<scope>-<username>` blob (call `layout.getPrefs()` in `_save…Prefs` and `layout.setPrefs(p.layout)` in `_restore…Prefs`). `getPrefs` returns `{ widths, hidden, shown, order }` — a page already threading the blob through picks up column order for free, no page-level change. The standalone "Columns ▾" button is gone — the gear replaces it.
- For dynamic-rendered tables: use `applyTableLayout(table, typeKey)` instead. Persistence is by-table-type, NOT by individual asset (never key on an asset id). The asset-detail tables (Interfaces, Storage, Hardware Sensors, LLDP, Wireless Stations, SD-WAN members/rules) additionally suffix the **asset type** onto the key via `_assetTableTypeKey(base, asset)` in assets.js (e.g. `asset-interfaces-firewall` vs `asset-interfaces-switch`) — a FortiGate's interface list looks nothing like a switch's, so operators get independent widths/visibility per device class (null/empty type → `"other"`). The Events tab is the deliberate exception: its columns are type-invariant, so it stays on a single shared `asset-events` key.
- The gear (+ optional screenshot button) **floats at the top-right corner of the table's scroll wrapper**, not inside a header cell: `setupColumnLayout` inserts a zero-height `position:relative` anchor `<div class="sf-col-gear-anchor">` immediately before the wrapper (falls back to before the table when the direct parent isn't a scroll container) and absolutely positions the gear in it. Living outside the overflow container means neither horizontal scrolling nor the sticky wrapper's internal vertical scrolling ever moves it — it's always visible without scrolling right, even when the table overflows. Reveal is JS-driven (wrapper/gear `mouseenter`/`mouseleave` toggling `.sf-gear-visible`, 120ms hide delay so the pointer can cross onto the gear) since it's no longer a `thead` descendant reachable by CSS `:hover`; the right inset is recomputed on each reveal to clear the wrapper's vertical scrollbar. The anchor is stamped `data-sf-for=<tableId>` so re-setups on the same DOM reuse it (no duplicates) while a replaced table render reclaims the stale anchor.
- **Sticky headers survive.** The resize handles need a positioning context on their `<th>`, but `setupColumnLayout` only forces inline `position:relative` when the computed position is `static` — a stylesheet `position:sticky` (e.g. `.ip-table thead th` in the IP panel) is left alone, since sticky is itself a containing block for the absolute handles. Never set inline `position` on header cells from new table code; it silently kills stylesheet sticky.
- **Frozen header on a list page** (Assets / Events / IPAM Blocks + Networks, incl. the legacy blocks/subnets pages): add `.table-wrapper-sticky` to the `.table-wrapper` (turns it into the vertical scroll container + pins `thead th` with `position:sticky`; a box-shadow stands in for the th bottom border, which doesn't travel with sticky cells under `border-collapse`). The shared `sizeStickyTableWrappers()` in app.js bounds every such wrapper to the viewport (`max-height = innerHeight − document-space top − reserve for the bottom pagination row`); it's hooked into `renderPageControls` / `clearPageControls` (re-measuring after every list render, since the empty top pagination row grows when controls first render) and window resize — so for a page using `renderPageControls`, adding the class is the ONLY step. Pages with their own pagination renderer (Events) call it at the end of that renderer. Scrolling then happens *inside* the wrapper, so bulk bars + top pagination freeze in place for free. Filter popovers are `position:fixed`, so they're unaffected by the inner scroll — but see the transformed-ancestor caveat under the slide-over variant below. Not loaded on /dash (no app.js) — don't add the class to dash-rendered tables. **Slide-over variant:** inside a slide-over use `.table-wrapper-panel-sticky` instead — same sticky-thead CSS, but the wrapper is height-bounded by its OWN sizer in assets.js, and which sizer to copy depends on where the table sits in its tab. A table that IS its tab bounds to the slide-over body's visible bottom (`_sizeAssetSvcTableWrapper`, the Services tab — re-run on every tab activation + after each data load + window resize). A table that sits MID-tab with sections below it takes a fraction of the body's height instead (`_sizeAssetIfaceTableWrapper`, the System tab's Interfaces table): a distance-to-bottom measurement would yield a different bound every time the operator scrolls the panel, and a fraction of the body also works while the tab is still `display:none` — which matters when the table is built on panel open while a different tab is showing and there's no per-tab hook to re-size from. **Popovers need a containing-block correction here, and it is not optional:** `.slideover` carries a `transform` for its slide animation and `.modal` a `translateY`, and a transform establishes a containing block for `position:fixed` descendants *even at its identity value* — so a fixed popover inside either is laid out from the panel's own padding box, not the viewport, and lands offset by the panel's left edge (vertically correct in a slide-over, since its `top` is 0). `TableSF._positionPopover` handles this for every filter popover by subtracting `TableSF._fixedHost(pop)`'s rect + border; the column-chooser gear sidesteps it by appending itself to `<body>`. Anything else you position `fixed` from a `getBoundingClientRect()` inside a slide-over or modal must do one or the other. Never put `.table-wrapper-sticky` in a slide-over: `sizeStickyTableWrappers()`'s triggers (list re-renders) fire while the panel tab is `display:none`, where rects are garbage, and would stamp bogus heights. **Self-bounding variant:** `.table-wrapper-modal-sticky` (the Application Map → Discovery picker is the reference; the asset-details Alerts tab's active list is the slide-over instance) — same sticky-thead CSS, but the CALLER sets its own `max-height` (e.g. `42vh`) and there is deliberately no sizer, because a modal or panel body already scrolls and its height isn't a function of the viewport top. Despite the name it is the right choice in a slide-over too whenever a fixed bound is acceptable — it needs no per-table sizer and no tab-activation hook, which is the whole cost of the panel variant.
- Drag-to-resize is **divider-style**: a handle sits on a column's right edge and a drag only affects the **two columns it sits between** — the dragged column grows and its immediate right neighbor shrinks 1:1 (or vice versa), 5px floor on both (`MIN_COL_W` — see the sliver note below); every other column stays put. The exception is when the right neighbor IS the **rightmost visible, resizable column** (`lastVisibleResizableIdx`), which is left auto-width so it absorbs the slack and keeps the table's right edge pinned to the border — in that case the dragged column + the auto-fill column are the two that change. The auto-fill column's own handle is hidden/inert (nothing to its right). When fixed columns sum wider than the container the table overflows past `width:100%` and the wrapper's `overflow-x:auto` shows a horizontal scrollbar. `applyWidths` recomputes the auto-fill column on every resize and whenever the chooser hides/shows a column.
- **Every visible column is explicitly pinned, never `width:auto`, and the leftover is SPREAD rather than dumped:** `fitColumnsToContainer` (scheduled after every `applyWidths`, re-run by a self-disconnecting `ResizeObserver` watching the table AND its parent — the parent because a container shrink doesn't change a fully-pinned table's own size) sizes the visible columns to sum to exactly `container content width` (writes only on change, so the observer doesn't re-fire). When the base widths sum NARROWER than the container, the slack is distributed across every resizable column **in proportion to its base width**, the rightmost visible resizable column taking the rounding residual so the right edge lands on the border. It used to hand the whole remainder to that one column, which is what left a narrow table (Users, Roles, Group Mappings) with cramped columns and one enormous last column holding all the blank space. Columns pinned to a declared width — utility `cb-col`/`fav-col` and static-width `data-col-no-resize` — are the "honor the declared width" tier: they're subtracted from the budget first and never stretch, which is why an icon-sized column (the Users table's 24px online-dot) must be marked `data-col-no-resize="true"` or it grows with everything else. Arithmetic, not measure-based, for three reasons. (1) **Scroll-clamp ratchet:** transiently clearing a column's width to "measure the auto-fill result" shrinks the table for one layout pass; when the table overflows horizontally that clamps the wrapper's `scrollLeft` and yanks the view left on every drag frame. Never transiently un-size a column (`applyWidths` doesn't touch the last one at all). (2) **Colspan first `<tbody>` row** (interfaces table's section header): an auto-width column has no per-column width basis, so fixed layout strands the leftover as a trailing gap instead of growing the column. (3) **Distribution circularity:** fixed layout spreads any un-specified remainder across *every* column, so rendered widths can't be trusted as inputs — `baseWidthOf` reads the stored/declared width first and only falls back to a rect, otherwise each pass would treat the previous stretch as the new base. The **crushed** case (base widths already sum past the container → no slack, leftover < `MIN_COL_W`) keeps every column at its base and falls back to the last column's saved/measured width so it stays visible and the wrapper's scrollbar reaches it — never a ~0px collapse whose header content paints into unreachable overflow. (`UNMEASURED_COL_W` = 40px is a different thing and not a floor: the width handed to a column that never measured at all, so it lands somewhere readable rather than at a sliver nobody chose.) `tests/unit/tableColumnFit.test.ts` pins the arithmetic (proportional spread, declared widths untouched, exact sum, re-fit after a hide, no shrink when over-committed).
- **The floor is a 5px sliver, and the padding comes off with it.** `MIN_COL_W = 5` is the one minimum under every width `setupColumnLayout` writes — the drag clamp (both the dragged column and the neighbor it trades with), the fit pass, and `setPrefs` (so a stale or hand-edited saved width can't seed a sub-floor base for the fit pass to scale from). It's deliberately far below anything readable: the point is that a column an operator parks out of the way still *exists* and still has a grabbable handle to pull it back out, rather than reading as gone. That only renders honestly because of the companion rule — a table cell's border box can't be narrower than its own padding (`0.6rem 1rem` ≈ 33px with borders), so a column under `NARROW_COL_W` (36px) gets `padding: 1px` + `overflow: hidden` from the same generated per-table stylesheet the hidden-column rules use (`rewriteHideStyle`, keyed on DISPLAY position, rewritten only when the text actually changes because it runs on every drag frame). Without it a drag to 5px stops dead around 33px and the floor looks broken; without the `overflow: hidden` a sliver's filter control or button group paints over the neighboring column instead of being clipped by it.
- **A drag commits the stretch first, so it tracks the pointer 1:1.** `commitStretchedWidths` (called on `mousedown`, right after `ensureAllWidthsMeasured`) folds the fit pass's rendered widths back into `widths`. Without it the delta would apply to a base that sums narrower than the container, so the divider would move by `dx × scale`. A committed base sums to the container width, so a drag creates no new slack — narrowing a column widens its neighbour, never the whole table. Only *stale* (seeded / restored) narrow widths get stretched; an operator's own layout is left alone.
- **Fixed utility columns** (`cb-col` checkbox / `fav-col` favorite-star) are non-resizable: they get no drag handle, are skipped by `lastVisibleResizableIdx` (never the auto-fill column), and are pinned to a fixed **34px** (`FIXED_COL_W`) so they never take a share of the leftover the fit pass spreads — a page opts one out with an inline `style="width:…"` on its `th`. They're also always `required` (non-hideable). **Set the width in `table-sf.js`, never in CSS**: under `table-layout: fixed` the `<col>` beats a stylesheet rule and the pin loop overwrites `widths[]` anyway, so a CSS width on `.cb-col` is inert. The **auto-fill (last resizable) column is floored** at `max(AUTOFILL_MIN_W = 36, its declared width)` — starved below its label's min-content it wraps one letter per line and stretches the whole `thead` to ~124px, so overflow goes to the wrapper's horizontal scroll instead (recoverable; a broken header is not). Apply that floor AFTER the crushed-table saved-width fallback, not before, or the fallback becomes unreachable and an over-committed table hands the last column 36px instead of its saved width.
- **Static-width columns** (`data-col-no-resize="true"` on the `<th>`) are the tier between utility and resizable: no drag handle, skipped by `lastVisibleResizableIdx`, but they keep their own width rather than the 20px utility pin. That width comes from the **inline `style="width:…px"` on the `<th>`, which is the single source of truth** — always declare one, and never rely on a measured render: `thead th` sets `overflow-wrap: anywhere`, so a header's min-content is one character, and an over-committed table's auto-layout pass can crush a declared 120px column to ~40px. With no handle to drag, such a measurement used to lock in permanently (and persist via `getPrefs`), so `setupColumnLayout` now pins these columns from the declared width up front and `setPrefs` ignores saved widths for them exactly as it does for cb/fav. They're also the tier the fit pass leaves alone — declaring one is how a column says "this width is my max, don't spend leftover on me". To resize one, edit the inline width in the HTML. Use it for columns whose content is a fixed-size token — enum badges, MACs, timestamps (Assets Type / State / Status / Monitored Via / MAC Address; Events Timestamp / Level; IPAM CIDR / Version / Networks / Created / VLAN / Status / Reservations; Automations Severity / Enabled).
- **Cell content truncates** with an ellipsis rather than wrapping. This only renders in `table-layout:fixed`, so `setupColumnLayout` **seeds fixed layout on first visible render** (`seedFixedLayout`): it measures each visible column's natural width and locks it in (utility + static-width columns are already pinned, so the seed only fills in the resizable ones). It bails when any column measures 0 (table rendered off-screen in an inactive SPA section), leaving auto-layout intact until a later visible re-render or a `setPrefs` width restore. The truncation CSS is scoped to `table[data-sf-table-id]` and exempts `.actions` (button groups keep wrapping), the cb/fav columns, and `td.cell-wrap` — the opt-in class for long-prose cells that should word-wrap inside their column width instead of ellipsizing (the Events page Message column uses it); the `.sf-label` header text ellipsizes too. Consequence: these tables no longer reflow to fill the container on window resize the way auto-layout did.

**When adding a new instance:**
- Long-lived static table on a list page → call `setupColumnLayout(tableEl, { onChange: _saveYourPagePrefs })` once after the `<thead>` is in the DOM; thread its `getPrefs/setPrefs` into the existing per-page prefs JSON.
- Dynamic table inside a modal or panel rebuilt on every refresh → call `applyTableLayout(container.querySelector("table"), "<stable-type-key>")` immediately after the `innerHTML` assignment. Choose a global, type-level key (e.g. `"server-mibs"`) — **never the asset id or page id**. For asset-detail tables that vary by device class, build the key with `_assetTableTypeKey("asset-<thing>", asset)` (assets.js) so it carries the asset-type suffix rather than hardcoding the bare key.
- Do NOT add a standalone "Columns" button to the toolbar — the gear is the only column-chooser entry point going forward.

## Paginated list controls row

**What it is:** The standard one-row layout sitting above a list table: page
navigation **centered** across the full width, with action buttons + the
page-size ("Show N") selector **right-aligned**. There is **no separate
top-of-page "Show" filter-bar** — the selector lives in the controls row.

**Canonical implementation:** `renderPageControls(containerId, total, pageSize, currentPage, onPageChange, onSizeChange, opts)` in [public/js/app.js](public/js/app.js). It renders into `#<containerId>` and `#<containerId>-top` as a **CSS grid** `1fr auto 1fr` — empty left cell, centered pagination in the middle, and a right cell (`.pg-right`) holding `opts.actionButtons` (e.g. Refresh / Clear Filters) followed by the page-size selector. Used by [public/js/assets.js](public/js/assets.js), [public/js/blocks.js](public/js/blocks.js), [public/js/subnets.js](public/js/subnets.js).

**Key conventions:**
- **Pass `onSizeChange(size)`** (the 6th arg) to get the "Show N" selector — it renders into the right cell and calls back with the new size. The selector renders **only in the `-top` row** (not duplicated in the bottom pagination). Optional `opts.pageSizes` overrides `[15,25,50,100]`.
- The page (not the helper) owns the size: `onSizeChange` sets the page's `_<scope>PageSize`, resets to page 1, re-fetches/re-renders, and saves prefs. Mirror the `onPageChange` callback shape.
- **Render the row on ZERO rows too — don't `clearPageControls` a filtered-empty list.** The row carries the page-size selector and `opts.actionButtons`, so clearing it takes **Clear Filters** away in exactly the state that needs it: an operator whose filter matched nothing gets an empty table and no way back but a browser reload. The Assets page routes BOTH branches of its render through one `_renderAssetsPageControls()` ([public/js/assets.js](public/js/assets.js)) instead of calling the helper from the populated branch only. `renderPageControls` handles `total = 0` (one disabled page button, "0 items"); reset the page number to 1 first, since a page-past-the-end clamp that only fires on a non-zero total would otherwise leave "Prev" enabled over an empty result set. `clearPageControls` is for tearing the row down when the table itself goes away, not for an empty result.
- **Do NOT add a standalone `<div class="filter-bar"><label>Show</label><select id="filter-pagesize">` above the table** — that's the old pattern, now removed. If prefs-restore still references `#filter-pagesize`, guard it (`var el = ...; if (el) ...`) since the static element no longer exists.
- **Bespoke (non-`renderPageControls`) pagination** (offset-based: [public/js/events.js](public/js/events.js), [public/js/automations.js](public/js/automations.js)) gets the same look with an HTML grid wrapper instead: `<div style="display:grid;grid-template-columns:1fr auto 1fr;align-items:center"><span></span><div id="…-top"></div><div class="filter-bar" style="justify-self:end">…Show + buttons…</div></div>`. The middle cell is the JS-filled pagination container; the right cell holds the static selector. Only valid when that pagination renderer does **not** absolutely-position its own right-side buttons (those need the full-width container, which is why `renderPageControls` owns the grid itself).

## Row context menu (per-row verbs behind the row name)

**What it is:** A list row’s actions (Open / Edit / Clone / Delete) reached by clicking the row’s **name**, instead of a trailing Actions column of buttons. One affordance per row, no column competing with the data for width, and a verb can be added without re-cutting the table layout. The same helper backs the page-header **account menu**, which is the pattern applied off a table: one identity affordance carrying the actions that belong to it.

**Canonical implementation:** `showRowMenu(anchor, items, opts)` / `closeRowMenu()` in [public/js/app.js](public/js/app.js), styled by `.row-context-menu` + `.row-menu-trigger` in [public/css/styles.css](public/css/styles.css). Used by the account menu (`openUserMenu` in app.js — push / two-factor enrollment / logout, trigger `.user-menu-trigger`; the theme toggle sits in the sidebar instead), the Automations list ([public/js/automations.js](public/js/automations.js) — Edit / Clone / Delete), IPAM’s Blocks + Networks lists ([public/js/blocks.js](public/js/blocks.js), [public/js/subnets.js](public/js/subnets.js) — Open / Edit / Delete), the Assets list ([public/js/assets.js](public/js/assets.js) — Open / Edit / Quarantine|Release / Delete off the hostname) and all three Users-page tables ([public/js/users.js](public/js/users.js) — Users, Roles, Group Mappings).

**Key conventions:**
- The trigger is a real `<button class="row-menu-trigger">` carrying `aria-haspopup="menu"` + `aria-expanded`, NOT an `<a href="#">` — it opens a menu rather than navigating.
- `items` is `[{ label, onSelect, danger?, disabled?, title?, icon? } | { separator: true } | { heading }]`; `opts` is `{ label?, align? }`. `icon` is SVG markup rendered before the label (developer constants only — it goes in via `innerHTML`, while the label stays `textContent`), and `align: "end"` right-aligns the menu under its anchor, which is what a trigger at the right edge of the page header wants. Build the items **per row, from that row’s own permission**: `subnets.js` calls `canEditSubnet(s)` because the ownership dimension makes Edit row-specific, while `blocks.js` can use the page-wide `canManageNetworks()`.
- **The menu is `position: fixed` and mounted on `<body>`.** List tables scroll inside `.table-wrapper-sticky`, which clips an absolutely-positioned menu — the existing `.btn-dropdown-menu` pattern (absolute inside `.btn-dropdown-wrap`) is for toolbar buttons, not table rows. The cost of `fixed` is that the menu cannot track its anchor, so `showRowMenu` closes on resize and on any scroll **that moved the anchor** — the scroll handler closes only when the scrolled element `contains(anchor)` (a document-level scroll always does). A blanket close-on-any-scroll is wrong on the dashboard, where the NOC auto-scroll creeps every overflowing `.dashboard-widget-body` by a pixel every 80 ms: the page-header account menu flashed open and vanished, though its anchor never moved. (`setHeaderExport`'s menu in `widgets/index.js` solves the same problem by naming `.dashboard-widget-body` explicitly — the containment test is the general form of that exemption.)
- **Close before running the handler.** Most verbs open a modal or slide-over, and a lingering fixed menu would float above it.
- **Outside-dismissal tests `anchor.contains(e.target)`, not `e.target === anchor`.** A trigger built out of child elements (the account badge’s avatar, name and caret) would otherwise close on the pointerdown and re-open on the click that follows, so a second click on it could never dismiss the menu. A text-only trigger behaves identically either way, which is why the identity check survived until the first composite trigger.
- **A body-mounted fixed menu outlives a re-rendered anchor.** `renderUserBadge` closes the menu when it drops the badge it is anchored to — scoped by comparing `_rowMenuTeardown.anchor`, so a re-render can’t shut a row menu elsewhere on the page.
- Keep the row’s existing open-the-panel behaviour as the **first** item rather than dropping it — clicking the name used to open the panel directly, and `Open` is what preserves that muscle memory (`openBlockFromRow` / `openSubnetFromRow` also carry the `tr.row-panel-active` highlight that the old click handler owned).
- When the operator can do nothing to a row, render the name as **plain text**, not a trigger that opens an empty menu (automations.js does this below `automationManagement:fullwrite`).
- **Build the items from the row RECORD, not from the trigger’s `data-*` attributes**, whenever which verbs exist is conditional. `users.js` extracts `_userMenuItems(u)` / `_roleMenuItems(r)` as pure builders for exactly this reason — an IdP-managed account has no password to reset, an Azure account’s 2FA belongs to the IdP, and “reset someone else’s 2FA” must not appear on your own row. Pure builders are also what makes that logic testable (`tests/unit/usersRowMenu.test.ts`).
- **Each group of verbs is gated by the key its own routes check, not by one page-level permission.** The Assets menu gates Edit/Delete on `assets:write` but Quarantine/Release on `assetsQuarantine:write`, because those are separate function keys and a role can hold either without the other — gating them together offers an operator a verb whose click can only 403, and (the direction that actually bit) hides quarantine entirely from a SOC-shaped role that may contain a device but not edit inventory. When you add a gate for a verb, check which key its ROUTES use: the asset-details Quarantine tab and the bulk-bar quarantine buttons both shipped gated on `canManageAssets()` against `assetsQuarantine`-gated routes. `canQuarantineAssets()` in app.js plus the `data-quarantine-assets` attribute applier are the correct pair; `tests/unit/assetRowMenu.test.ts` pins all four call sites statically, since they are one-line gates buried in an 18k-line render path. Push separators only immediately before a group that has items, so a divider can never render with nothing after it (`_assetMenuItems` builds this way and it is unit-tested across every permission × row-shape combination).
- **A verb that reaches the DEVICE is gated by what the device permits, not by a Polaris key.** The Assets menu's **Open HTTPS / Open SSH** (`_managementAccessMenuItems` in [public/js/assets.js](public/js/assets.js)) read `Asset.managementAccess` — the `allowaccess` list captured during FortiGate discovery — and offer only the protocols that device actually accepts; a device whose access list couldn't be read (`protocols == null`, the best-effort FortiSwitch path) gets both optimistically, since unknown is not denied. **Where no device can be asked, the ASSET TYPE answers instead, not a guess dressed as a reading**: a `server` offers Open RDP + Open SSH because nothing reads a Windows or Linux host's management surface — same gate, same "unverified" note in the options menu, and no HTTPS (a server's :443 is the application, not a management UI). They ride no permission of their own because opening a management UI is not editing inventory, and a row with no captured access list and no inferable type (every endpoint, everything from a non-Fortinet discovery) contributes nothing rather than dead verbs. Where the same verbs exist as a **split button** on a slide-over header, the row-menu copy performs the operator's stored default rather than growing a submenu — a row menu is a flat list, so the sub-choices stay on the surface that has room for them.
- **A menu whose ROWS use different keys needs a multi-key gate on the trigger too.** The single-key `data-*` attributes (`data-manage-assets`, `data-quarantine-assets`, …) each name one capability and can't express "either of two", so a button fronting two separately-gated things gets **`data-perm-any="assets:write,networkScan:read"`** — the element-level twin of the sidebar's `anyPerm`, applied by `hideAdminOnlyElements` in `app.js` alongside the others. Canonical: the Assets page's **+ Add Asset(s)** button, whose rows are an asset form (`assets`) and a network Discovery (`networkScan`). Two things to know when using it: `hideAdminOnlyElements` only ever HIDES, and it runs once off the cached role and again after the live fetch — so a control it left visible can outlive the grant, which is why the click handler must also refuse to open a menu whose builder returned nothing. And **omit a row the role can never reach rather than disabling it**: the disabled-with-a-reason rule below is for a verb that can't apply *right now*, while a missing grant is not a transient state and a permanently greyed row only advertises something the operator cannot be given.
- A verb that can’t apply right now stays **present but `disabled` with the reason as its `title`** rather than being dropped (the Roles table’s Delete on a built-in role, or one that still has users). Don’t also set `danger` on it — red on an inert control reads as “this will do damage” when it does nothing.
- Dropping an Actions column means updating **three** things in lockstep: the `<th>` in *every* page that mounts the table (blocks/subnets have legacy standalone pages **and** the IPAM tab page — all three share the same JS), the static placeholder `<td colspan>` in the HTML, and every `colspan` in the JS empty/error states. A stale `data-col-id` in a saved column-order pref is harmless — `normalizeOrder` in table-sf.js filters unknown ids.

**Tests:** [tests/unit/rowContextMenu.test.ts](tests/unit/rowContextMenu.test.ts) (the helper), [tests/unit/userAccountMenu.test.ts](tests/unit/userAccountMenu.test.ts) (the account menu’s item set — losing a row there removes the only way to log out from every page at once; it also pins that the theme row is NOT in the menu, since it lives in the sidebar, covered by [tests/unit/sidebarThemeToggleDom.test.ts](tests/unit/sidebarThemeToggleDom.test.ts)), [tests/unit/accountMenuTotpRow.test.ts](tests/unit/accountMenuTotpRow.test.ts) + [tests/unit/totpSelfModule.test.ts](tests/unit/totpSelfModule.test.ts) (the two-factor row’s local-accounts-only gate and state labels, and the shared modal module it opens), [tests/unit/usersRowMenu.test.ts](tests/unit/usersRowMenu.test.ts) + [tests/unit/assetRowMenu.test.ts](tests/unit/assetRowMenu.test.ts) (the conditional item builders — the latter pins the quarantine permission key and the never-quarantine-infrastructure rule), [tests/unit/listTableColspan.test.ts](tests/unit/listTableColspan.test.ts) (header-count ↔ placeholder colspan across every list page, plus “no Actions column” on the converted ones). Positioning is deliberately unasserted — happy-dom reports zero-size rects, so `getBoundingClientRect` placement only means anything in a real browser. [tests/unit/automationsTableContract.test.ts](tests/unit/automationsTableContract.test.ts) pins the header-count ↔ colspan match for the automations table.

## Utilization bar (a percentage drawn as a bar, not just a number)

**What it is:** A 0–100% reading rendered as a slim filled track with the figure
beside it, so a row of volumes/subnets reads as a shape at a glance instead of a
column of numbers to compare by eye.

**Canonical implementation:** `.util-row` / `.util-bar-track` / `.util-bar-fill` in [public/css/styles.css](public/css/styles.css) — a flex row, a `flex: 1` track and a width-percentage fill with a `0.4s` width transition. Consumers: the shared top-N widget renderer (`rowHTML` in [public/js/widgets/_topnBar.js](public/js/widgets/_topnBar.js)), the subnet-utilization line in [public/js/ip-panel.js](public/js/ip-panel.js), and the asset-details Storage table's Used % cell (`_storagePctCell` in [public/js/assets.js](public/js/assets.js)).

**Key conventions:**
- **The track flexes, the label is a fixed-width right-aligned cell.** Inside a resizable table column the fill percentage is a style attribute, never a CSS rule — under `table-layout: fixed` the column width is the `<col>`'s and the bar simply takes what is left after the label. Put the cell in the **last (auto-fill) column** where you can, so the column floor keeps the track from collapsing.
- **Color thresholds must agree with whatever widget shows the same metric.** The Storage table's Used % cell copies the Highest Disk Usage bands verbatim (`#4fc3f7` base, `#ffd600` ≥ 75%, `#ff1744` ≥ 90% — [public/js/widgets/diskUsage.js](public/js/widgets/diskUsage.js)): a volume that reads amber on the dashboard and blue in the slide-over reads as a bug in one of the two. Change one, change both.
- **Round the label, keep the precision in a `title`.** A bar plus `87%` fits a narrow column where `87.4%` does not; the exact figure rides a native tooltip on the row so nothing is lost. No data is a muted em dash — never a 0%-wide bar, which is a positive claim that the volume is empty.
- Where the row carries an active alert, its **severity color wins over the value bands** (`PolarisWidgets.alertSeverityBarColor`) — see the widget-surface section below.

## Operator-customizable widget surface

**What it is:** A page where the operator enters an explicit EDIT MODE, chooses which widgets appear via a full picker (Group-By + search + favorites), arranges them into resizable COLUMNS, and configures per-widget options via a gear popover. Layout persists server-side per user. Read-only by default with a "Customize Page" affordance; empty state prompts the operator to customize. The Dashboard home page is the first instance; future operator-customizable surfaces should match this shape.

**Canonical implementation:** Dashboard home page — entry point is `public/js/dashboard.js` (orchestrator), backed by:
- HTML: `public/index.html` — `#dashboard-empty-state`, `#dashboard-canvas`, the `#dashboard-customize` / `#dashboard-add-widgets` / `#dashboard-done` header buttons, and the `#widget-library-overlay` picker (`#widget-picker-groups`, `#widget-picker-search`, `#widget-picker-sort`, `#widget-library-body`).
- CSS: `public/css/styles.css` — `.dashboard-canvas` (12-col CSS grid of columns), `.dashboard-column*`, `.dashboard-widget*`, `.dashboard-drop-placeholder` (green "+"), `.dashboard-newcol-target`, `.widget-picker*`, `.widget-library-card`, `.widget-config-popover`. **Chrome paints tokens, never literals** — accent states go through `var(--color-accent)` (the retired cyan `#4fc3f7` is not an accent anywhere), pointer feedback on transparent chrome through `var(--color-hover-tint)`, and static faint fills (count badges, chips) through `var(--color-fill-subtle)`. Both tints are defined white-ish on the dark base and black-ish on the daylight base, because a white overlay is invisible on a light surface and morning/noon had no hover feedback at all until they existed. The `.widget-pill-{ok,watch,amber,red}` literals are the one sanctioned exception and carry a comment saying why.
- Widget modules: `public/js/widgets/*.js` — each self-registers via `PolarisWidgets.register({...})` (registry in `public/js/widgets/index.js`).
- Picker: `public/js/widget-library.js` — `WidgetLibrary.open(onAdd)` / `close()` / `isOpen()`.
- Favorites: `public/js/favorites.js` — `getFavorites`/`isFavorite`/`toggleFavorite` (localStorage entity `"widgetlib"`); MUST be `<script>`-included before `widget-library.js`. (A page whose stars belong to something OTHER than the browser calls `registerFavoritesProvider(entity, {get, toggle, titleFor?})` instead of adding a second store — the Assets page does, so its stars follow the view tab; `getStoredFavorites` is the localStorage read that bypasses providers, which is what a provider seeds itself from.)
- Persistence: `UserDashboard` Prisma model + `src/services/userDashboardService.ts` + `src/api/routes/userDashboard.ts` (GET/PUT `/me/dashboard`); client at `api.me.dashboard.{get,put}`. The SHARED (per-resource, not per-user) variant of this pattern is `TopologyLayout` + `src/services/topologyLayoutService.ts` (Device Map topology drag layouts, one row per (site, view); writes RBAC-gated `deviceMap=write`, reads embedded in the topology GET) — copy that when a layout should be one map every operator sees rather than a personal preference.
- Wallboard variant: `public/dash.html` is the unauthenticated read-only mirror (Dash wallboard, served by `src/dash/dashServer.ts`) — same markup/widget list, `dash-mode.js` flags + `dash-boot.js` instead of `app.js`, layout in localStorage (`polaris-dash-layout`) via the `POLARIS_DASH_LOCAL` branch in `dashboard.js`.

**Key conventions:**
- **Tabbed multi-dashboard model (v3).** Layout = `{version:3, dashboards:[{id, name, columns:[{id, width, widgets:[{id,type,height,config}]}]}], activeId}` (max 24 dashboards). Each dashboard is a named tab; `activeDash()` selects the live one. Within a dashboard, columns are CSS-grid items spanning their `width ∈ {3,4,6,12}` (12-col canvas; columns past 12 wrap); widgets stack vertically and carry `height ∈ {1,2,3}` set as a **fixed pixel height** on the article (280/576/872px) so chart/Leaflet bodies get a sized container. Array order IS the layout — no free-grid reflow.
- **Explicit edit mode + tabs.** `state.editing` gates all chrome; "Customize Page" → `enterEditMode()`, "Done Editing" → `exitEditMode()` (forces the debounced save). A "Create New Dashboard" button adds a tab; the active tab's name is click-to-rename inline; tabs remove via their × in edit mode. Toggling edit mode re-renders the canvas (re-runs widget `onUnmount`/mount).
- **v1/v2→v3 migration.** Legacy v1 (`{widgets:[{col,row,...}]}`) and v2 (`{version:2, columns:[...]}`) layouts migrate on load into a single "Dashboard 1" tab; empty fallback on error. GET is server-unvalidated so stored older rows still load; the next save persists v3.
- **Drag = geometry → target.** `dropTargetFromCursor(x,y)` returns `{columnIndex, insertionIndex}` or `{newColumn}` from column rects + card midpoints. A single `.dashboard-drop-placeholder` (green "+") is moved into the target stack; the source widget gets `.lifted`. A trailing `.dashboard-newcol-target` accepts drops into a fresh column. Both dataTransfer mime types (`application/x-polaris-widget` add, `…-move` reorder) + the module-level dragstart stash are kept from v1.
- **Module shape.** `{ type, label, description, category?, defaultSize, minSize?, defaultConfig?, requiredPermission?, fetchData?, renderInstance(el, config, data, ctx), renderPreview(el), renderConfig?(el, config, onChange), onMount?, onUnmount? }`. `category` (default "Other") buckets the picker Group-By. `ctx.onUnmount(fn)` registers cleanup; the orchestrator runs it on remove/re-render.
- **Mini-previews are real renders, not screenshots.** Each widget's `renderPreview(el)` calls the same DOM-emitting code as `renderInstance` with mock data.
- **Per-feed data fetch.** Every widget fetches only the data it renders: the NOC set via `PolarisWidgets.getNocSummary(opts, feeds)` (`/dashboard/noc-summary?feeds=…`), the IP-space set via `PolarisWidgets.getSummary({sections,...})` (`/dashboard/summary?sections=…`) — both 15s-memoized **per (feeds/sections, filter, limit)** with in-flight dedupe, so same-key widgets share one fetch while each widget renders as soon as its own feed returns. The server adds a 10s per-feed TTL cache on top, so distinct widgets/tabs hitting the same feed stay cheap. There is no orchestrator-prefetched `summary` arg on `fetchData` anymore — `fetchData(config)` owns its fetch.
- **Refresh cadence is one of three named tiers.** `PolarisWidgets.REFRESH = { fast: 10000, normal: 30000, slow: 60000 }` in `widgets/index.js` — pick by how fast the underlying thing actually moves: `fast` for in-flight progress (a running discovery), `normal` for outage state (down assets/interfaces, active alerts), `slow` for ranked metrics, forecasts, maps and history. Never write the millisecond literal. **Every widget with a live feed gets a timer**, re-fetching through the same function `fetchData` calls (extract it to a module-local `fetch…()` rather than duplicating the expression, or the two drift) and clearing it in `ctx.onUnmount`. A widget with no timer renders once and is frozen forever on the Dash wallboard, which is where dashboards actually live — six of them were, until 2026-08. Note `NOC_TTL_MS` is 15000, so a `fast` widget gets cached data two ticks out of three; that is fine for a progress readout and must not be copied to anything needing fresh data.
- **Per-widget filters + dynamic title.** `PolarisWidgets.renderNocFilterConfig(el, config, onChange, includeAssetTypes)` appends a shared **Regions** scope (All / My regions → caller's effective `regionTags` / Selected regions… → per-widget checkbox pick of created regions, list from `PolarisWidgets.getRegionOptions()`; "My regions" is hidden on the /dash wallboard) + optional **Asset types** toggle grid to a gear popover; `nocFilterOpts(config)` extracts `{assetTypes, regionScope, regions}` to pass to `getNocSummary`. When the asset-type filter is a strict subset, the chosen types appear in the widget's header title in parens (`widgetTitleFor` in dashboard.js, refreshed on gear change).
- **Header pill + severity-tier CSV export.** `PolarisWidgets.setHeaderCount(el, count[, severity])` stamps the overall-total pill on the widget header — pass `PolarisWidgets.maxAlertSeverity(rows)` and the pill colors to the set's most severe active alert off the same `alertSeverityPill` palette (serious → orange, critical → red), so it can't disagree with the row pills below it; per-group count pills get the same treatment via `PolarisWidgets.countPillClass(rows)` (returns the full `class` string). Both fall back to red when no row carries an alert — there's no severity to honor and red is the generic "these are down" count. Down Assets is the reference; a count pill over rows that aren't severity-tiered (Sites With Issues, the threshold-colored Stale Polls / Conflict Queue counts) stays on its own color rule. **When the operator wants the split rather than the worst**, call `PolarisWidgets.setHeaderSeverityCounts(el, rows[, {unalerted, severityOf}])` instead — it renders one pill per active-alert severity in the set (`alertSeverityCounts(rows[, severityOf])`, most severe first, each in its own severity color) so the title reads "2 critical, 12 serious" rather than one number colored to the worst. `unalerted:"neutral"` (default) appends a grey pill counting the non-alerting rows so the pills still sum to the row total, and a set with NO alerting row keeps the plain red total pill; `unalerted:"omit"` drops them, which is what a ranked top-N list wants (its row count is the operator's Row limit, not a fleet total). **Down Interfaces** is the reference for the first mode, `_topnBar`'s `renderRows` for the second (every top-N widget gets it with no opt-in since 2026-08). **Pass the rows you are about to render**, not the fetched set: the convention is that the pills count what's on screen, so stamp AFTER the row limit / horizon / red-guarantee pass and BEFORE the empty-state return (an empty array clears the pills, which is what makes them track the data). The ⤓ export provider is the deliberate exception and stays on the full matched set. Widgets carrying a severity vocabulary of their OWN — Capacity health's ok/watch/amber/red — use `setHeaderTierCounts(el, rows, {keyOf, order, classOf, noun})` instead; never extend `ALERT_SEVERITY_RANK` with a second ladder, or the two start ranking against each other in the min-severity filter and the export tiers. Both modes go through `setHeaderPills(el, [{text, className, title?}])`, the one place that owns the `.widget-header-count` container — which seats the pills at the **head** of the title (`[2][12] Down Assets`, not `Down Assets [2][12]`), and re-seats them there on every call so a host left behind by an in-place title rewrite can't keep trailing. The title is a single `white-space: nowrap` ellipsized line, so a count appended after the name is the first thing a narrow column drops, and the count is the half an operator scans a wall for. `PolarisWidgets.setHeaderExport(el, {columns, rows, filename?, severityOf?})` stamps a ⌄-menu ⤓ export button whose tiers (All rows / Critical only / Serious and up / Warning and up, live counts) filter the widget's FULL pre-clip listing on each row's active-alert severity (`ALERT_SEVERITY_RANK`, the client mirror of nocDashboardService's ladder — event levels fold in at error=critical / info=informational) and download a CSV with an auto-appended Severity column (filename defaults from the widget `data-type`; local CSV fallback on the Dash wallboard, which lacks app.js `downloadCsv`). Both are re-call-every-render-tick helpers that no-op outside a dashboard shell (library previews) and remove themselves at zero rows/count. Export is wired on Active Alerts, Down Assets, Down Interfaces, Storage Forecast, and all six top-N widgets (once, inside `_topnBar.renderRows`) — a new severity-bearing listing widget should call it with its own column spec.
- **Minimum-severity display filter (gear).** The same ladder drives a per-widget display filter: `PolarisWidgets.renderMinSeverityConfig(el, config, onChange, hint?)` appends the **Minimum severity** select (options from `SEVERITY_TIERS`, the ONE list the export tiers also read — never hardcode tiers), and `PolarisWidgets.filterByMinSeverity(rows, config[, severityOf])` narrows the fetched rows to those carrying an active alert at/above `config.minSeverity`. Call the filter FIRST in the widget's render — before the row limit, the red guarantee, `setHeaderCount` and `setHeaderExport` — so every number the widget shows agrees with what's on screen; client-side filtering is safe because these feeds are `severityFirst`-sorted server-side. Fall back to `PolarisWidgets.minSeverityEmptyText(config) || <your empty text>` so a filtered-empty widget says "No rows at or above serious severity" rather than "No nodes down". Order in the popover: widget-specific controls → `renderMinSeverityConfig` → `renderNocFilterConfig`. A widget that stored severity some other way seeds the control through `severityTierForRank(rank)` (Active Alerts folds its pre-control `severities` checkbox array that way, keeping saved configs behaving as before).
- **In-place asset slide-in.** `PolarisWidgets.openAssetDetail(id)` opens the canonical asset slide-over via the global `openViewModal` when present (the dashboard loads `assets.js` + its deps — jspdf/html-to-image/table-sf/integrations — mirroring `map.html`; both `assets.js`/`integrations.js` guard their page-init), else navigates to `/assets.html#view=asset:`. Down Assets wires it on row click (ctrl/meta/middle-click keep the href).
- **Role gating.** `requiredPermission: { key, level }` checked client-side via `permAtLeast`; the picker hides disallowed widgets (convenience, not security). **Every widget declares one**, and the key MIRRORS the gate the server already applies to the data it reads — `/dashboard/summary` gates its sections on `assets` / `ipBlocks` / `reservations` read, so those are the keys, not whichever picker category the widget sits in (`assetTypes` is filed under IP Space but reads asset counts, so its key is `assets`). Because both `/summary` and `/noc-summary` filter rather than 403, an ungated widget doesn't leak — it renders "No blocks yet" to a role that simply can't see blocks, which is a false statement about the fleet rather than an empty one. That is the reason to declare the key, and the reason the level is always `read`.
- **Favorites are localStorage, layout is server-side.** Per-widget ★ favorites are a pure client preference (`favorites.js`, entity `"widgetlib"`). The layout itself persists in `UserDashboard` (per-user JSON); PUT debounced 800ms; Zod `LayoutSchema` (v3) validates on the route. Don't pivot the layout to localStorage — cross-device is the explicit expectation. (Sole sanctioned exception: the anonymous Dash wallboard, which has no user to persist against — `POLARIS_DASH_LOCAL` in dashboard.js.)

**When adding a new operator-customizable surface (or a new widget to the existing Dashboard):**
- **New widget on the existing Dashboard:** add `public/js/widgets/<type>.js`; self-register via `PolarisWidgets.register`; include a `renderPreview` with mock data; add the `<script src>` line to `public/index.html` **AND `public/dash.html`** (the Dash wallboard mirrors the widget script list — both files carry a lockstep comment). Wire `requiredPermission` to whatever key gates that data server-side — always, not only when it feels sensitive (on dash it resolves against the readonly role). Give it a `PolarisWidgets.REFRESH.<tier>` timer torn down in `ctx.onUnmount` unless the data genuinely cannot change, in which case say so in a comment. If the widget calls an endpoint outside `/dashboard/*`, also add the path to `API_PATH_ALLOWLIST` in `src/dash/dashServer.ts` or it 404s on the wallboard. No backend or registry changes needed when it reads an existing endpoint.
- **New NOC top-N widget (reference: `diskUsage.js`).** The cleanest recent end-to-end example of adding a fleet-ranking widget. Steps: (1) add a feed `getHighest<X>` to `nocDashboardService.ts` returning `TopNRow[]` (windowed DISTINCT-ON / aggregate over the relevant hypertable, hydrate names in ONE `findMany`, take the trailing `assetIds: string[]|null` filter arg); (2) register it in the `NOC_FEEDS` registry (name in `NOC_FEED_NAMES`, gate `assets`/`events`, empty value, runner; optional `flatten` only if the response key differs from the feed name) — the route needs no change; (3) add `public/js/widgets/<type>.js` as a `_topnBar` wrapper passing its feed name to `getNocSummary(opts, ["<feed>"])`, `fillTo:20` + color thresholds (+ `detail` on rows if per-sub-entity like volumes); (4) `<script>` it in `index.html`; (5) the gear gets the shared `renderNocFilterConfig(...)`; (6) add a unit test for the feed; (7) refresh ARCHITECTURE (widget catalog + endpoint shape + service line) and the `nocDashboardService` TOUCHES entry.
- **Shared multi-widget fetch (NOC pattern).** When several widgets read the SAME endpoint on their own refresh timers, don't let each one fetch independently — add a memoized accessor on the registry (`PolarisWidgets.getNocSummary(opts, feeds)` in `public/js/widgets/index.js`: ~15s TTL + in-flight dedupe, keyed per (feeds, filter, limit, samples)) and have every widget call it with only the feed(s) it renders. The backend endpoint (`/dashboard/noc-summary?feeds=`) computes just the requested subset via a feed registry in a dedicated service (`nocDashboardService.getNocSummaryPayload`), per-section permission-filtered like `/summary`, with every (feed, filter, cap[, samples]) result served through a 10s `createTtlCache` (`src/utils/ttlCache.ts`) — the model for caching any read-mostly aggregate endpoint hit by many concurrent viewers.
- **Shared row renderer for near-identical widgets.** The five top-N metric widgets (CPU / Memory / Slowest Response / Packet Loss / Disk Usage) are structurally identical, so the row+bar render lives once in `public/js/widgets/_topnBar.js` (`window.PolarisTopN.renderRows/renderConfig`, reusing the `.util-bar-track`/`.util-bar-fill` bar from blockUtilization). Each widget is a ~40-line wrapper supplying unit / color thresholds / empty text. `renderRows` opts: `fillTo` = red-guarantee mode (on CPU/Memory/Response/Disk): the operator's Row limit (default 20) caps the top-N shown, but every **red** row — at/above the top color threshold — always shows even past the limit; `fillTo` itself is only the fallback count when the config lacks a usable rowLimit. Omit on Packet Loss so the threshold stays a hard filter + rowLimit a plain cap. Rows may carry an optional `detail` string rendered muted beside the hostname (Disk Usage uses it for the mount path); the ellipsizing name cell gets a native `title` tooltip with the full name (+ detail). **An alerting row's bar color comes from its severity, not the widget's thresholds** — `PolarisWidgets.alertSeverityBarColor(sev)` (in `widgets/index.js`, one-for-one with the `alertSeverityPill` palette) wins over `pickColor` whenever the row carries an `alertSeverity`, since the operator's automation threshold is rarely the widget's color band and a yellow bar beside a red `critical` pill reads as a bug. Storage Forecast applies the same override over its days-to-full color. Un-alerted rows keep the value-threshold color. Underscore-prefixed filename = shared helper that registers no widget; include its `<script>` BEFORE its consumers.
- **Embedding Leaflet in a widget (siteMap.js).** The widget body has no intrinsic height in the flex column, and Leaflet throws "Map container is already initialized" if a container is reused. Pattern: set `el.style.position="relative"` + append an inner `position:absolute;inset:0` div as the map container (deterministic box inside the fixed grid-row height); keep `map`/`markerCluster` in the **per-instance render closure** (NOT a module-level singleton like the full map page — a widget can be instanced multiple times); set `L.Icon.Default.imagePath` once behind a module flag; read the basemap theme once from `data-theme` (no MutationObserver); a `ResizeObserver` on `el` calls rAF-debounced `map.invalidateSize()`; and `ctx.onUnmount` MUST `ro.disconnect()` + `map.remove()`. Refresh updates markers in place (`cluster.clearLayers()` + re-add), never recreates the map. Marker/cluster CSS (`.fg-marker`/`.fg-cluster`/`.monitor-*`) lives in both `map.css` and (lifted) `styles.css` since the dashboard page loads only the latter — keep them in sync. Reuses the existing `/map/sites` endpoint; needs the Leaflet `<link>`/`<script>` tags in `index.html`.
- **New customizable surface elsewhere:** model the canvas + picker + per-user storage after this Dashboard. Use a sibling `UserSurfacePreference`-style table keyed on `(userId, surfaceKey)` rather than overloading `UserDashboard`. Reuse `PolarisWidgets.register` for that surface's widgets — the registry is global by design so cross-surface widget reuse is one-line.
- **Don't bake widget positions into seeded defaults** unless you genuinely want every user to see the same starting view — the precedent here is "empty = invitation to customize." Operators have explicitly told us they prefer a clean slate.
- **Auto-save, not a Save button.** Every edit-mode mutation still debounce-saves (800ms); "Done Editing" only exits edit mode and forces a final flush — it is NOT a save-confirm gate. Don't add a confirm step around individual edits; it kills the drag/resize feel.

## Polling methods section (per-stream subtab strip)

**What it is:** A configuration surface that exposes per-stream monitoring settings — polling method (dropdown), credential picker, MIB picker (when polling resolves to SNMP), interval, timeout, and failure threshold (Response Time only). Used inside the integration edit modal (per-class × per-stream), the Assets-page Monitoring Settings modal (Manual Monitoring section), and the asset edit modal's Monitoring tab. Without one canonical layout, three near-identical surfaces drift on label text, sub-row visibility rules, "Inherit" labelling, and DOM id conventions — making the resolver hierarchy harder to read at the UI.

**Canonical implementation:** `_classStreamSubtabHTML(idPrefix, sourceKind, klass, stream, settings, credentials, isPrimary, opts)` in [public/js/integrations.js](public/js/integrations.js). Companion helpers (all in `integrations.js`):
- `_polarisPollingDropdownHTML(id, source, stream, currentValue, opts)` — emits the polling-method `<select>`. Honors `opts.showInherit` (default `true`; pass `false` at the bottom of the resolver hierarchy where there's nothing to inherit from) and `opts.fmgDirectMode` (drives the "FortiGate Direct" vs "FortiManager Proxy" label for FMG sources).
- `_polarisSourceDefaultPolling(source, stream)` — mirrors `defaultPollingForSource()` in `monitoringService.ts`; returns the per-source-kind per-stream default Polaris would resolve to. Used to label the "Inherit" option.
- `_polarisSourceLabel(source, opts)` — the per-source-kind name table: FortiGate Direct / FortiManager Proxy / Active Directory / Entra ID / Windows Server / vCenter / Azure Arc / Manual. A missing entry silently falls through to "Manual", mislabelling every `Inherit (Source …)` option for that type.
- `_streamsForClass(klass)` — returns the per-class stream list. FortiAP omits Storage (APs have no mountable storage); every other class gets all six streams.
- `tabbedBodyHTML(prefix, tabs)` + `wireModalTabs(prefix)` — the tab-strip + body-swap helpers reused for stream subtabs. **Shared globals in `app.js`**: `assets.js` and `integrations.js` each grew a byte-identical private copy (`_renderTabbedBody`/`_wireModalTabs` and `_intRenderTabbedBody`/`_intWireModalTabs`), which is exactly the drift the one pair exists to prevent — both are gone.

**Consumers (parallel surfaces):**
- **Integration edit modal** — class-subtab strip (FortiGates / FortiSwitches / FortiAPs for FMG+FGT; Workstations / Servers for AD/Entra/WinSrv) → stream-subtab strip per class. Uses `_classStreamSubtabHTML(..., isPrimary=true)` for the primary class (FortiGate / Workstations — legacy DOM ids `f-mon-tier-<pollField>`) and `isPrimary=false` with namespaced `f-mon-classecho-<klass>-` prefix for the other class subtabs. **Phase 2 save handler**: each class subtab's stream values serialize independently into `Integration.config.<klass>Monitor.streams.<stream>` via `_readClassStreamSubtabs(klass, isPrimary, includeStorage)` — secondary subtabs no longer echo the primary; each class's own input values are persisted. **Phase 2 load handler**: `_classStreamsBlockFor(klass, opts)` picks the matching `<klass>Monitor.streams` block; `_classSettingsOverlay(flatSettings, classStreams)` overlays the per-stream values onto the flat baseline before passing to each stream subtab so each class renders its own saved settings. `showInherit: true`, `showMib: true` (defaults).
- **Assets page → Monitoring Settings modal → Manual Monitoring section** — no class strip (Manual is class-agnostic). DOM id prefix `f-manual-mon-`. Passes `showInherit: false` (bottom of resolver — nothing to inherit) and `showMib: false` (Manual tier doesn't expose per-stream MIB in this iteration). Renderer at `_monsetManualSectionHTML()` in [public/js/assets.js](public/js/assets.js).
- **Assets page → Monitoring Settings modal → Class Overrides editor (Add / Edit)** — no class strip (manual-scope only, per the Phase 1 narrowing). DOM id prefix `monset-ov-`. Passes `showInherit: true` (class overrides legitimately defer to the integration / manual tier below) and `showMib: true` (per-stream MIB pickers are meaningful here). Renderer at `_monsetOpenOverrideEditor()` in [public/js/assets.js](public/js/assets.js). Sub-row visibility is wired locally — `_refreshOvStreamSubRows()` toggles the per-credtype credential rows (`<pollId>-credrow-snmp` / `-ssh` / `-winrm` / `-http`) and the MIB row (`<prefix>tier-<mibStreamKey>-mib-wrap`) based on each stream's polling-method pick. Per-stream credential save: the helper renders one select per (stream × credtype); the override save handler picks the select matching the chosen polling method and stores it in the per-stream column (`responseTimeCredentialId` / `cpuMemoryCredentialId` / …) the backend expects. Source kind is hardcoded to `"manual"` for the Inherit-option label.
- **Asset edit modal → Monitoring tab** — no class strip (single asset's overrides). DOES NOT use `_classStreamSubtabHTML` because its DOM id conventions diverge from the asset modal's legacy `f-responseTimePolling` / `f-cpuMemoryPolling` / `f-monitorInterval` / etc. ids that `extractAssetEditData()` reads on save. Instead the renderer in `assetMonitoringFormHTML()` ([public/js/assets.js](public/js/assets.js)) builds per-stream subtab bodies inline using the same visual shape (polling-method `<select>` → cred sub-row → MIB sub-row → cadence + timeout → failure threshold on Response Time only) and wraps them with `tabbedBodyHTML("asset-mon-streams", streamTabs)`. `showInherit: true` (the Inherit option here legitimately defers to the class / integration / manual tier above the asset). MIB pickers visible per stream. LLDP + Storage subtabs share the system-info cadence with Interfaces (Asset row carries only 4 cadence columns: `monitorIntervalSec`, `cpuMemoryIntervalSec`, `temperatureIntervalSec`, `systemInfoIntervalSec`) — those two subtabs render a "shared with Interfaces" hint instead of duplicating the inputs.

**Key conventions:**
- **Stream list and order:** Response Time → CPU/Memory → Temperature → Interfaces → LLDP → Storage. FortiAP omits Storage (handled by `_streamsForClass("fortiap")`).
- **Per-stream subtab body shape:** polling-method dropdown → credential sub-row (visible when polling needs auth — `snmp`/`winrm`/`ssh`/`rest_api`/`http`) → MIB sub-row (visible when polling = `snmp` AND `showMib !== false`) → interval input → timeout input (+ failure threshold on Response Time only). A method may add ONE row of its own: the asset edit modal's Response Time subtab renders `f-httpCheckPath-wrap` (the per-asset HTTP-check path override) between the credential row and the interval, shown only while that stream resolves to `http`. Keep such a row inside `refreshStreamCred`'s show/hide pass and HIDDEN rather than removed, so a typed-then-reconsidered value survives a method flip-flop before save — and send it even when hidden, which is how switching away from the method clears a stale override.
- **Inherit-option visibility:** `showInherit: true` is the default everywhere EXCEPT the bottom of the resolver hierarchy (Manual Monitoring section). When false, the `<select>` simply lacks the empty-value option; the first concrete method becomes the default. Routes still accept `null` / empty body fields as "no override"; the UI just doesn't offer it.
- **Inherit-option label format:** `Inherit (Source <SourceLabel>: <ResolvedMethod>)` or `Inherit (Source <SourceLabel>: not delivered)` when the source doesn't deliver that stream by default. The asset edit modal's `_populateAssetMonitorTierBadges` overwrites this with the actual resolved value from `/effective-monitor-settings` (e.g. `Inherit (class override: SNMP)`) once the response lands.
- **ICMP filtering:** `_polarisPollingDropdownHTML` filters ICMP out of every stream except `responseTime` — telemetry / interfaces / LLDP / storage all need a real protocol. The backend `validateStreamPollingMethod()` applies the same filter on writes.
- **Stream-scoped methods live in `_streamAllowedMethods`, not the dropdown helper.** Two methods are restricted by STREAM rather than by source, mirroring the method-level guards in `isMethodValidForStream` (`pollingCompatibility.ts`): `vcenter` is cpuMemory-only, and `http` is responseTime-only (a GET returns a status code and a body — no CPU figure, interface list, sensor reading or mount table). Both are filtered there, AFTER the source intersection, so a new stream-scoped method needs an entry in that function as well as in `_POLLING_COMPAT` — and the backend rejects the pair at write time in `assertPollingCompatible` (tiers) and `validateAssetUpdate` (per asset), so a UI that forgets the filter shows an option that 400s.
- **Source-kind defaults:** `_polarisSourceDefaultPolling` returns `rest_api` for fortimanager/fortigate on CPU/mem/interfaces/temperature, `icmp` for responseTime, `disabled` for LLDP + Storage. AD/Entra/Win/Manual default `icmp` on responseTime, `null` (= "not delivered") elsewhere.
- **DOM id discipline:** stream-subtab inputs use the prefix the consumer's save reader expects. The integration modal's primary subtab uses legacy `f-mon-tier-<pollField>` so `_polarisReadPollingFourStream("f-mon-tier-")` finds them; secondary class subtabs use namespaced `f-mon-classecho-<klass>-` ids that are rendered but never read on save. Manual Monitoring uses `f-manual-mon-tier-` (read by `_polarisReadPollingFourStream("f-manual-mon-tier-")`). Asset edit modal uses bare `f-<pollField>` (read by `_polarisReadPollingFourStream("f-")`).
- **Storage stream MIB:** Storage has no per-stream MIB column on Asset or MonitorClassOverride — `HOST-RESOURCES-MIB` + the vendor disk fallback in `pickVendorProfileMerged` covers it without operator input. The helper skips the MIB sub-row for the storage stream regardless of `showMib`.
- **LLDP + Storage cadence at the asset tier (Phase 2):** the Asset row gains its own `lldpIntervalSec` / `storageIntervalSec` cadence columns and `lastLldpAt` / `lastStorageAt` last-touched stamps alongside `lldpPolling` / `storagePolling`. Each rides its own pg-boss queue (`polaris-monitor-lldp` / `polaris-monitor-storage`) on independent cadences resolved from the per-class streams blocks; the publisher in `monitorAssets.ts` checks `last*At + *IntervalSeconds` to decide when to fire. The legacy `collectSystemInfo` still walks both as session-coalesced side effects on a shared SNMP session — `persistLldpNeighbors` (full-replace + 48 h stickiness) and `enqueueStorageSamples` are idempotent against the dedicated queues' double-walks. Cursor mode keeps both on the systemInfo cadence — the dedicated queues are pg-boss-only.

**When introducing a new polling-method surface:**
- **Reuse `_classStreamSubtabHTML`** — don't fork the helper. Pass the right `idPrefix` and `isPrimary` flag so your save reader can find the inputs.
- **Pick the right `showInherit` flag:** `true` everywhere except the very bottom of the resolver hierarchy (where Inherit would be a misleading no-op).
- **Pick the right `showMib` flag:** default `true` works for every tier above Manual today; pass `false` only when the tier deliberately doesn't expose per-stream MIB picking.
- **Pass the correct `source`** so the Inherit label names the actual source ("FortiGate Direct", "FortiManager Proxy", "Active Directory", "Entra ID", "Windows Server", "Manual"). FMG additionally needs `opts.fmgDirectMode` flipped to match the integration's current Direct Polling toggle state.
- **Use `_streamsForClass(klass)`** to enumerate the streams — never hardcode the six names. FortiAP-specific surfaces will automatically drop Storage.
- **Wrap with `tabbedBodyHTML(prefix, streamTabs)`** and call `wireModalTabs(prefix)` after mounting so the tab strip actually swaps bodies on click. Pick a prefix that doesn't collide with other tab strips on the same page.
- **If your surface diverges in DOM id conventions** (the asset edit modal does), build the per-stream body HTML inline using the same visual shape — polling dropdown + cred sub-row + MIB sub-row + interval + timeout — and reuse `_polarisPollingDropdownHTML` for the dropdown itself so the Inherit-label semantics stay consistent.

## Mobile bottom sheet

**What it is:** A modal slide-up panel anchored to the bottom of the viewport on the mobile SPA. Dismissed by tapping the scrim, tapping the X button, or swiping the sheet down. Used for the Device Map site detail, asset interface drilldown, reservation edit + create-by-IP, subnet reserve, topology node detail, and the full asset detail screen.

**Canonical implementation:** `openSiteSheet()` in [public/js/mobile/map-tab.js](public/js/mobile/map-tab.js) + matching `closeSiteSheet()` — use this for the common two-state (open/dismiss) sheet.

**Three-state minimizable variant:** the asset detail sheet (`PolarisAssetDetail.open(id)` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js)) extends the pattern with a **peek** state for content-heavy sheets the operator wants to keep open while using the page behind. Scrim tap → minimize (slides the sheet down to its header band, measured into `--asset-peek-y`, and hides the scrim so the searchbar is reachable); peek-bar tap → expand; close button → dismiss. **Two-stage swipe-down:** the first swipe-down from expanded snaps to peek, the second swipe-down from peek dismisses. **Swipe-up from peek re-expands** (in expanded state baseline is 0, so upward gestures fall through to native scroll). Wired through `attachSwipeToDismiss`'s `onSwipeDown` / `onSwipeUp` opts (override the default translate-100% animation and the default release-for-native-scroll respectively) plus `baselineTranslate` opt (so drags from a peeked position continue from the peek offset instead of jumping back to natural). Minimize never tears down the DOM, so charts/scroll/per-feature state survive. Capped at 80vh (vs. the generic `.sheet`'s 90vh) and anchored at `bottom: var(--navbar-h) + safe-area` so both expanded and peek states stop at the navbar's top edge instead of covering it. The bottom nav (`.m3-navbar`, z-index 950) sits above the asset sheet (901) and its scrim (900) — so the navbar stays visible + tappable while the asset is open — but below the generic `.scrim`/`.sheet` (1000/1001), so deep drilldowns still take the full screen. Model new minimizable sheets on this; keep simple sheets on `openSiteSheet`.

**Key conventions:**
- DOM shape: one `.scrim` and one `.sheet` element, both appended to `document.body` with unique IDs (`<feature>-sheet-scrim` + `<feature>-sheet`). Close = `remove()` both.
- The sheet's first child is `<div class="sheet-handle"></div>` — the small grabber bar that both signals draggability and is the always-on swipe-dismiss start zone.
- Next comes a `display:flex` header row with the title block on the left and an icon `<button class="icon-btn" id="<feature>-sheet-close" aria-label="Close">` carrying `<svg><use href="#i-close"/></svg>` on the right.
- Three close paths, all calling the same close function: `scrim.addEventListener("click", closeXxx)`, the close button click, and `PolarisTabs.attachSwipeToDismiss(sheet, closeXxx)`. The swipe helper lives in [public/js/mobile/tabs.js](public/js/mobile/tabs.js).
- CSS comes from [public/css/mobile.css](public/css/mobile.css) — the `.scrim`, `.sheet`, `.sheet-handle`, `.sheet-title` rules. Don't invent new container classes; reuse these so the swipe helper's transform composes correctly with the `sheet-in` open keyframe.
- Forms inside the sheet keep their native gesture handling — the swipe helper opts out of `input`, `textarea`, `select`, and `[contenteditable=true]` so iOS text-cursor drag and selection handles work.
- **Mobile SD-WAN charts are intentionally simplified.** The asset detail sheet's stacked SD-WAN sheet (`openSdwanSheet` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js)) renders the per-member **Latency / Jitter / Packet-loss** numeric charts (driven by `loadSdwanPerfSla`), but it deliberately omits the desktop SD-WAN tab's **rule member-selection categorical timeline** — the mobile chart helper is numeric-only, so the sheet shows each rule's *current* selected member instead of its failover history (see the "Out of scope for v1" header comment in `asset-detail.js`). When porting a categorical/timeline chart to mobile, expect to fall back to a current-state list rather than reusing the numeric chart helper.

**When adding a new instance:**
- Mirror the DOM shape — `.sheet-handle` first, header row with `icon-btn` close button second.
- Wire all three close paths: scrim click, close-button click, and `PolarisTabs.attachSwipeToDismiss(sheet, closeXxx)`.
- The close function `remove()`s both the scrim and the sheet by ID; idempotent so double-fire from a swipe finishing while the user also taps scrim is safe.
- If the sheet is scrollable, the swipe-dismiss helper handles "scroll first, dismiss only when at top" automatically — no extra wiring needed.

## Mobile pull-to-refresh

**What it is:** Touch-pull-down on a mobile tab or detail page to re-fetch its data. MD3-style: only a small circular puck moves, body content stays put. The puck rotates with pull progress, flips primary-tinted past the trigger threshold, spins while the caller's onRefresh promise is in flight.

**Canonical implementation:** `PolarisTabs.installPullRefresh(scrollEl, onRefresh)` in [public/js/mobile/tabs.js](public/js/mobile/tabs.js). Wired into the route lifecycle by `installPtrForSpec(spec, ctx)` in [public/js/mobile/app.js](public/js/mobile/app.js) — every route change releases the prior handle + installs a fresh one if the new spec has `onPullToRefresh`.

**Key conventions:**
- Tab specs and detail specs opt in by exposing `onPullToRefresh(ctx)` that returns a Promise. The PTR puck spins until the promise settles; sync returns / non-promises get a 600 ms held-puck fallback.
- Optional `enablesPullToRefresh(ctx)` predicate disables install entirely for one route within a multi-page spec (the More tab uses this to skip its static root menu while still PTR-ing the blocks / subnets / events sub-pages).
- Only tracks a gesture that starts with `scrollEl.scrollTop === 0` — pulling from mid-scroll is left to the browser as normal scroll behavior.
- Form controls (`input`, `textarea`, `select`, `[contenteditable=true]`) opt out so iOS text-cursor drag still works inside any forms on the page.
- Click suppression is left to the browser: a touchmove past ~10 px already cancels the underlying button's `click`, so no `preventDefault` is needed — listeners stay `passive: true`.
- `.app-body` carries `overscroll-behavior-y: contain` so iOS rubber-band doesn't compete with the pull gesture.
- CSS (`.ptr-indicator`, `.ptr-circle`, `.ptr-svg`, `.ptr-indicator.ready`, `.ptr-indicator.refreshing`) lives in [public/css/mobile.css](public/css/mobile.css).
- Skipped on routes where it makes no sense or where touch is owned by another library: Map tab (Leaflet captures touch), Topology tab (Cytoscape captures touch), Site detail (delegates to Map), Search tab (results are query-driven), More root menu (static), Block detail (placeholder), Login.

**When adding a new instance:**
- Define `onPullToRefresh(ctx)` on the tab or detail spec. Return the Promise from the same data-load function the topbar Refresh button uses (or equivalent) — don't fork a separate refresh path.
- The spec's render-time DOM must still be present when the promise resolves; loaders that target `getElementById` should be safe because the user can't navigate away during the PTR gesture without releasing first.
- Whenever the refresh action has variant behavior depending on user role / route parts (e.g. subnet detail's gate-side refresh vs. plain re-pull, or More's per-sub-page dispatch), branch inside `onPullToRefresh` rather than inside the install wiring. Use `enablesPullToRefresh` only for "no PTR at all on this route."

## On-screen keyboard fit (login/form screens)

**What it is:** Keeping the focused field and its submit button above the on-screen keyboard on a viewport-height-locked screen. iOS Safari (and the installed PWA) do **not** shrink the layout viewport when the keyboard opens, so `100vh` / `height:100%` still measure the whole screen and a vertically-centered card doesn't move — the password field and Sign in button end up behind the keyboard. Android Chrome shrinks the layout viewport itself and needs no help.

**Canonical implementations:** the IIFE at the `visualViewport` block in [public/js/login.js](public/js/login.js) (desktop login page, pins `.login-wrapper`) and the `installKeyboardFit` block in [public/js/mobile/auth.js](public/js/mobile/auth.js) (mobile SPA login + TOTP, pins `.app`). CSS lives beside each: the `.kb-open` rules inline in [public/login.html](public/login.html) and in [public/css/mobile.css](public/css/mobile.css). Behavior is unit-tested in [tests/unit/mobileLoginKeyboardFit.test.ts](tests/unit/mobileLoginKeyboardFit.test.ts).

**Key conventions:**
- Measure with `window.visualViewport` — the only API that reports the actually-visible rect on both engines. Treat the keyboard as open when `max(window.innerHeight, documentElement.clientHeight) - vv.height > 120`. The threshold is what tells a keyboard from a collapsing URL bar, and it is also what keeps Android out: there the layout viewport shrinks too, the delta stays ~0, and the native behavior is left alone.
- Pin the container to the visible rect through CSS custom properties (`--vv-height` / `--vv-offset-top`), never by writing layout properties from JS. Include `offsetTop` — iOS scrolls the layout viewport under the keyboard even when the page can't scroll.
- **Top-align in `.kb-open`.** This is required, not cosmetic: overflow above a `justify-content:center` flex item is unreachable because `scrollTop` can't go negative. Shortening the container without flipping the alignment trades one hidden control for another.
- Coalesce every handler through one `requestAnimationFrame` (`if (!pending) pending = rAF(apply)`), bound to `resize` + `scroll` on the viewport, `orientationchange`, and `focusin`. `focusin` is what re-measures when a step swaps the form in place (password → TOTP) with the keyboard already up.
- `scrollIntoView({block:"end"})` the focused element's **form**, and only when that target differs from the last one scrolled — re-running it on every viewport event fights the user's own scrolling.
- Where the screen is replaced wholesale with no teardown hook (the mobile SPA's auth screens), re-check on every measurement that the form is still mounted and unpin when it isn't, rather than trusting a lifecycle callback. Clear the class explicitly on the success path too: the next viewport event may be a long way off, and a stale pin sizes the authenticated shell to a dead height.

**When adding a new instance:** reuse the threshold, the rAF coalescing, and the top-align flip verbatim — the failure modes above are all silent. Anything inside a scroll container that already has room to scroll doesn't need this at all; the browser's own scroll-into-view handles it.

## Standalone task page (one card, no app shell)

**Reference:** `public/alert-ack.html` + `public/js/alert-ack.js` (acknowledge one alert, reached from an alert email or a web push) — built on the shell `public/login.html` established. Tests: `tests/unit/alertAckPage.test.ts`.

**What it is:** A page that exists to do ONE thing for someone who arrived from outside the app — a link in an email, a notification action, a bookmark — and who may be on a phone, in a mail client's embedded browser, or not signed in yet. It is a Polaris page with Polaris tokens and the operator's own branding, but it deliberately has no sidebar, no nav and nothing else to tap by mistake.

**Key conventions:**
- **One centred card on `--color-bg-secondary`**, `max-width` around 460px, `min-height: 100dvh` beside `100vh` (older Safari ignores the `dvh` line and takes the `vh` one). Card gets `--color-bg-primary`, `var(--radius-lg)`, `var(--shadow-md)` and a 4px accent top border driven by a CSS custom property the script sets — never a hardcoded colour, so severity/state can tint the card without touching the stylesheet.
- **Load `/js/theme-init.js` FIRST**, before the stylesheet, exactly as login.html does: it stamps `data-theme` before first paint, and without it the page flashes the wrong theme.
- **Gate it server-side, not in the page.** Add it to `protectedPages` in `src/app.ts` (and to `pageRequiredPermission` when it needs a function key), so an unauthenticated arrival is bounced to login and returned by the `polaris_next` cookie (`src/utils/loginRedirect.ts`). A page that renders and then discovers it is logged out has already shown a shell it cannot fill.
- **Gate the PAGE at `read` and the ACTION at `write`.** A reader whose role can see the thing but not act on it must land here and be told so; bouncing them to `/` leaves them wondering where their link went.
- **Requires script, and that is fine** — it is reached through the login page, which requires script too. Render the states from JS rather than shipping a no-JS fallback that will drift.
- **Every state is a state, including the bad ones.** Loading, the action, the already-done case (naming who got there first), the not-permitted case, the gone case, and a failure that offers **Try again** rather than a dead page. Fold "not found" and "forbidden" into ONE sentence where the distinction would leak whether the record exists.
- **Touch targets:** action buttons `min-height: 44px` and `flex: 1 1 auto`, since this page is opened from a phone more often than not.
- **Brand through `PolarisBrandLogo`** with the unauthenticated `/api/v1/server-settings/branding` read (the `serverSettings` API wrapper needs a permission this reader may not hold), and re-paint on `onThemeChange`.
- **Escape everything.** The card renders server data as HTML; use a local `esc()` and pass every value through it.
- Set `window.__polarisOn401` before the first API call so a session that dies mid-page re-stamps the return cookie instead of losing the destination.

**When adding a new one:** copy the shell from `alert-ack.html`, then work through the state list above before writing the happy path — on a page reached by a link, the unhappy states are most of the traffic.

**Reference:** `public/js/brand-logo.js` (`window.PolarisBrandLogo`) + `public/img/brand/` — consumed by `public/js/login.js`, `public/js/mobile/auth.js`, `applyBranding` in `public/js/app.js`, and the Customization tab in `public/js/server-settings.js`. Tests: `tests/unit/brandLogoResolver.test.ts`.

**What it is:** An image (not CSS) that has to change with the theme — artwork whose ink is near-black on light and near-white on dark, so the wrong variant doesn't look off, it disappears. Ship one file per (variant, theme), and put the choice in ONE module that every surface calls.

**Key conventions:**
- **Name files by the BACKGROUND they're for, not their ink** (`-dark` = for the dark FAMILY = light-colored artwork). Every consumer then indexes with the family string it already has, and nobody has to remember the inversion.
- **Index by theme FAMILY, never by theme id.** There are three themes and two sets of art; `morning` and `noon` both take the light files with no third asset, and an id comparison silently misses every daylight theme but the one it names. `PolarisBrandLogo.currentTheme()` answers the family (and defers to app.js's `isLightTheme` where that exists — brand-logo.js loads before app.js and also runs on login, mobile and dash, which never load it at all).
- One `ASSETS` map, one `resolve(payload, surface)` returning everything the surface needs (`{src, custom, showName, …}`). Surfaces set `src` and toggle visibility; they never branch on the payload themselves. A fifth surface is then a call, not a fifth copy of the rule.
- **Listen for `themechange` on `document` AND observe `data-theme` with a MutationObserver**, instead of hooking each theme setter. `_setTheme` fires the event with `{theme, family}`; the observer additionally covers a theme set by other means (theme-init.js's pre-CSS boot, the OS-preference listener, another tab syncing), so together they cover paths that don't know about each other. Compare FAMILIES, not ids, so a morning → noon flip doesn't force a pointless re-fetch. Evaluate the file in a Node `vm` with a stub `document.documentElement.getAttribute` to unit-test it (see `appmapFilter.test.ts` for the harness).
- **Tag the element with a class for the shipped variant** (`.brand-mark`) so CSS can size fixed-aspect artwork differently from an arbitrary operator upload sharing the same `<img>`.
- A **server-rendered** derivative (here: the logo with a symbol composited on) beats a per-surface CSS overlay the moment more than two surfaces show it — one URL, one geometry, and it works in contexts with no stylesheet of yours (a preview box, an email, an icon). Give it `no-cache` + a strong ETag if its path is fixed, and have it **redirect to the plain asset** rather than 404 when the derivative doesn't apply.
- Follow the OS only while the user has **no** stored preference, and don't persist that resolution — unsaved *is* the "follow my system" state. Match on `light` so a browser stating no preference keeps the product's existing default.
